# Go: структуры

## Шпаргалка

1. Struct копируется по значению: присваивание, аргумент функции и элемент `[]T` создают копию полей.
2. Поля вроде slice, map, chan и указателя копируются как дескрипторы или указатели; данные за ними остаются общими.
3. Метод нужен, когда операция принадлежит типу и работает с его состоянием или инвариантом.
4. Pointer receiver нужен для мутации, больших объектов, sync-полей и единого набора методов.
5. Struct можно использовать как ключ map, если все его поля `comparable`.

---

## Что реально проверяют на собесе

Отдельный вопрос «расскажи про struct» встречается редко. Чаще struct появляется в коде или follow-up, где проверяют практические решения:

- что скопируется при передаче struct в функцию, при append в `[]T` и при использовании `[]*T`;
- почему метод с value receiver не меняет исходный объект, а pointer receiver меняет;
- можно ли сделать struct ключом map и что ломает `comparable`;
- почему struct с `sync.Mutex` нельзя копировать после первого использования;
- где поведение лучше оформить методом, а где обычной функцией.

Embedding, struct tags и конструкторы обычно идут как уточнения: их стоит знать, но не превращать в главный рассказ.

## Модель: zero value, layout, копирование

```go
var s T   // zero value всех полей
s := T{}  // то же
```

Struct хранит поля подряд с выравниванием. Порядок полей может влиять на размер из-за padding, но менять порядок ради памяти стоит только после измерений.

Копирование struct — поверхностное: копируются сами поля. Если поле хранит ссылку на данные, например slice или map, обе копии struct будут смотреть на одни данные.

## Передача, мутация и heap

```go
func f(x T)   // копия; изменения полей снаружи не видны
func f(x *T)  // исходный объект; можно менять поля
```

Передавайте struct по значению, если объект маленький, не содержит sync-полей и функция не должна менять исходное состояние. Передавайте указатель, если нужна мутация, объект большой или копирование нарушит смысл типа.

| Контейнер | Что происходит |
|-----------|----------------|
| `[]T` | хранит значения; append и assign копируют элементы |
| `[]*T` | хранит указатели; изменение объекта видно через все указатели |

`return &local` корректен: компилятор перенесёт объект в heap, если указатель выходит за пределы функции. Это не ошибка, но повод не гадать о размещении, а смотреть escape analysis и профиль.

## Метод или функция

Метод уместен, когда операция принадлежит типу:

- читает или меняет внутреннее состояние;
- поддерживает инвариант объекта;
- должна быть частью публичного поведения типа;
- нужна для реализации интерфейса;
- естественно читается как действие над главным объектом: `user.FullName()`, `cache.Get(key)`, `money.Add(x)`.

Обычная функция лучше, когда операция не принадлежит одному типу:

- связывает несколько равноправных значений: `Distance(a, b Point)`;
- является алгоритмом над данными: `SortUsers(users)`;
- не требует доступа к закрытым полям;
- не должна расширять публичный API типа;
- работает с внешним типом, которому нельзя добавить метод.

Правило: если первый аргумент очевидно главный объект операции — чаще подходит метод. Если аргументы равноправны или операция шире одного типа — лучше функция.

## Receiver и method set

Сначала решите, нужен ли метод. Потом выбирайте receiver.

| Receiver | Когда выбирать                                                                |
| -------- | ----------------------------------------------------------------------------- |
| `(t T)`  | Метод не меняет состояние, тип небольшой, нужна семантика значения            |
| `(t *T)` | Метод меняет поля, тип большой, внутри mutex/atomic, нужен один набор методов |

Не смешивайте value и pointer receiver на одном типе без причины. Смешивание усложняет method set и поведение при реализации интерфейсов.

Method set важен для интерфейсов: если метод объявлен с pointer receiver, интерфейс реализует `*T`, но не `T`.

```go
type Reader interface {
    Read([]byte) (int, error)
}

func (b *Buffer) Read(p []byte) (int, error) { return 0, nil }

var _ Reader = (*Buffer)(nil) // ok
// var _ Reader = Buffer{}    // не ok
```

## Инициализация и инварианты

Сводка способов:

| №   | Способ              | Синтаксис                                | Когда использовать                                      | Ограничения                                        |
| --- | ------------------- | ---------------------------------------- | ------------------------------------------------------- | -------------------------------------------------- |
| 1   | Пустой объект       | `p := Person{}` или `var p Person`       | Zero value валиден; поля заполнят позже                 | Все поля получают zero value                       |
| 2   | Позиционный литерал | `Person{"Иван", "ivan@yandex.ru", date}` | Нужны все поля сразу; тип стабилен                      | Порядок значений должен совпадать с порядком полей |
| 3   | Именованный литерал | `Person{Name: "Иван", Email: "..."}`     | Предпочтительный вариант в большинстве случаев          | Неуказанные поля получают zero value               |
| 4   | Конструктор         | `NewPerson(...) (Person, error)`         | Валидация, скрытые поля, зависимости, сложный инвариант | При росте API может меняться сигнатура             |

```go
p := Person{
    Name:  "Иван",
    Email: "ivan@yandex.ru", // запятая после последнего поля — норма
}
```

Конструктор в Go — обычная функция `NewT`. Если есть валидация, возвращайте `(T, error)` или `(*T, error)`. Не пишите `NewT` для каждой struct: если zero value валиден и инвариантов нет, литерала достаточно.

Неэкспортируемый тип и экспортируемый `NewT` помогают скрыть поля и собрать инвариант в одном месте.

## Struct как ключ map

Ключ map должен быть `comparable`. Struct подходит, если сравнимо каждое поле.

| Можно в ключе | Нельзя в ключе |
|---------------|----------------|
| int, string, bool, pointer, array с comparable-элементами | slice, map, func |
| struct из comparable-полей | struct с полем slice/map/func |

`[]byte` напрямую использовать нельзя. Варианты: `string(b)` или `[N]byte`, если размер фиксирован.

Хороший ключ — маленький объект-значение: `{TenantID, UserID}`. Плохой ключ — большой struct, объект с mutex, строка без нормализации регистра или `time.Time` без явной политики сравнения.

## Atomic, mutex и sync-поля внутри struct

`sync.Mutex`, `sync.RWMutex`, `sync.Once`, `sync.Cond` нельзя копировать после первого использования.

```go
type Cache struct {
    mu sync.Mutex
    m  map[string]string
}
```

Правила:

- передавайте и возвращайте такую struct по указателю;
- методы делайте с pointer receiver;
- не кладите рабочий объект в slice/map по значению;
- не копируйте объект после вызова `Lock`, `Unlock`, `Do`, `Wait` и похожих операций.

`atomic.Int64` и `atomic.Uint64` подходят для одного счётчика или флага. Несколько связанных полей (`balance` + `version`) одной atomic-операцией не обновить: нужен mutex или одна горутина, которая владеет состоянием.

Потокобезопасная struct не делает составную операцию атомарной. Если инвариант включает несколько полей, защищайте весь инвариант одним механизмом.

## Embedding и композиция

```go
type Server struct {
    http.Server // наружу поднимаются методы и поля http.Server
    logger      *zap.Logger
}
```

Embedding — поле без имени. Его экспортируемые поля и методы становятся доступными через внешний тип. Это композиция, а не наследование: нет подтипов и переопределения методов как в классических ООП-языках.

Используйте embedding, когда публичные методы встроенного поля действительно должны стать частью API внешнего типа. Для обычных зависимостей чаще лучше именованное поле.

---

## Struct tags и reflection

```go
type User struct {
    ID   int    `json:"id" db:"user_id"`
    Name string `json:"name" validate:"required"`
}
```

Tags — строковые метаданные для библиотек (`json`, `yaml`, `db`, `validate`). Компилятор их почти не проверяет; ошибка в tag часто всплывает только во время выполнения.

Tags читает код через reflection. Reflection может быть дорогим, поэтому библиотеки обычно кэшируют разбор типа.

## Code review: типичные флаги

| Флаг                                             | Проблема                                            |
| ------------------------------------------------ | --------------------------------------------------- |
| `func (c Cache) Get()`                           | Копируется struct с mutex                           |
| `func (u User) SetName()`                        | Метод меняет состояние через value receiver         |
| Метод сделан только ради синтаксиса              | Операция не принадлежит типу, лучше обычная функция |
| `NewFoo()` без error при валидации               | Объект может быть невалидным                        |
| Один struct = DTO + domain + ORM model           | Смешение слоёв                                      |
| Все поля exported                                | Инвариант нельзя защитить внутри типа               |
| Большой struct передаётся по значению в цикле    | Лишние копии                                        |
| Struct key с `strings.ToLower` только при insert | Lookup и insert используют разные правила           |

## Мини-трюки и идиомы

- `struct{}` имеет нулевой размер; его используют как значение в set `map[K]struct{}` или как сигнал в `chan struct{}`.
- Functional options подходят для конфигурации с дефолтами: `NewServer(opts ...Option)`. Для простых объектов это лишняя сложность.
- Проверка интерфейса на этапе компиляции: `var _ io.Reader = (*T)(nil)`.
- Private fields + `NewT` собирают инвариант в одном месте.
- `time.Time` в struct требует аккуратного сравнения и сериализации: учитывайте monotonic component, используйте `t.Equal(u)` или явную нормализацию UTC.
