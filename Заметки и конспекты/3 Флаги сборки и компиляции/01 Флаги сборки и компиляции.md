# Флаги сборки и компиляции

Вы уже знаете, что, помимо прямого назначения, комментарии используются для автоматического генерирования документации с помощью `godoc`. Кроме этого, существуют определённые виды комментариев, которые позволяют управлять процессом компиляции.

В этом уроке рассмотрим дополнительные возможности, которые даёт компилятор Go при использовании специальных команд в исходном коде или в опциях команд `go build`, `go run`, `go install`. Вы научитесь:

- разделять код для разных ОС и платформ;
- устанавливать значения переменных при компиляции;
- автоматически генерировать исходные файлы при компиляции;
- внедрять файлы в приложение.

## Теги build

Так как язык Go может компилировать код для разных операционных систем и архитектур, рано или поздно возникнет задача кроссплатформенной сборки проекта. Если программа использует специфические возможности конкретной ОС, нужно, чтобы код игнорировался при компиляции на других системах.

Прежде всего надо разложить по отдельным файлам уникальный код для каждой ОС. Если у вас простая архитектура и каждый файл соответствует своей системе, достаточно добавить к именам файлов суффиксы. Суффикс может быть равен одному из трёх вариантов:

- `_$GOOS`,
- `_$GOARCH`,
- `_$GOOS_$GOARCH`.

Вместо `$GOOS` и `$GOARCH` можно указать одно из их допустимых значений:

- `app_linux.go` будет скомпилирован только для Linux,
- `myfile_windows.go` будет скомпилирован только для Windows,
- `myfile_windows_386.go` будет скомпилирован только для 32-битной Windows.

Не забывайте указывать имя перед суффиксом. Если имя файла начинается с `_`, компилятор его проигнорирует.

По суффиксам для кроссплатформенной компиляции разработчики могут сразу понять, где находится код для разных ОС. Но что делать, если какие-то фрагменты кода используются одновременно для нескольких платформ? Нужно указать `build`-теги в начале файла.

В версии Go 1.17 добавлена новая форма записи `build`-тегов. Старая форма выглядела так: `// +build tagnames`. Сейчас теги желательно определять следующим образом: `//go:build tagnames`. Это делает использование тегов похожим на другие команды компилятора.

При указании `build`-тегов нужно придерживаться правил:

- Теги указываются в однострочном комментарии после слова `go:build`. Например, `//go:build tagname`.
- Комментарий размещается перед декларацией `package` и отделяется от неё как минимум одной пустой строкой. Вот так:

```go
//go:build prod

package main
```

- Если перед тегом указан `!`, это означает логическое отрицание. Файл будет участвовать в сборке пакета, если условие не выполняется. Например, `//go:build !linux` будет компилироваться для Windows, а для Linux не будет.
- К тегам, которые разделены `||` (пробелами в старом формате), применяется логическая операция ИЛИ.
- К тегам, которые разделены `&&` (запятой в старом формате), применяется логическая операция И.
- Новый формат позволяет использовать круглые скобки для сложных условий. Например:

```
//go:build (linux && 386) || (darwin && !cgo)
```

- Можно указывать несколько комментариев `//go:build`. В этом случае к тегам каждого комментария применяется операция И.

Вот варианты правильного использования `build`-тегов. В примерах указаны новый и аналогичный ему старый вариант:

```go
//go:build !linux
// +build !linux

package main
```

```go
// Copyright 2021 Developer Team. All rights reserved
// Use of this source code is governed by a MIT license
// that can be found in the LICENSE file

//go:build linux || darwin || freebsd
// +build linux darwin freebsd

package main
```

Следующий пример означает, что файл будет скомпилирован только для 64-битной Windows:

```go
//go:build windows && amd64
// +build windows,amd64

package main
```

## Определение своих тегов

Возможна такая ситуация, когда, кроме кода для разных ОС, надо компилировать версии с разным функционалом.

Допустим, у приложения есть две версии: бесплатная и pro-версия. Если вы разложите их код по отдельным файлам, то с помощью тегов сможете компилировать обе программы из одного проекта. Так как есть только две версии, можно использовать один тег — пусть это будет `pro`. Если тег определён, будет компилироваться pro-версия. Если нет, будет компилироваться бесплатная версия.

Чтобы передать теги компилятору, надо указать их через пробел в параметре `-tags`. Например:

- `go build -tags pro`,
- `go install -tags "stage enterprise"`.

Таким образом, в файле с кодом pro-версии нужно указать `//go:build pro` и запускать компиляцию вызовом `go build -tags pro`. В файле бесплатной версии указывается `//go:build !pro`, а сборка запускается без использования тегов — `go build`.

Это был простейший пример. Для более сложных задач может потребоваться несколько тегов. Например, в файлах пакета `crypto` стандартной библиотеки можно встретить такие условия сборки:

```
//go:build !appengine
```

В пакете `crypto` предусмотрена возможность компиляции под облако Google App Engine. Условие `//go:build !appengine` указывает на то, что код будет компилироваться под хост, а не облако, и специфика Google App Engine не важна.

```
//go:build ignore
```

Тег `ignore` означает, что файл будет игнорироваться при компиляции стандартной библиотеки и не войдёт в её состав по умолчанию, а используется только в особых обстоятельствах. В данном случае файл содержит функцию `main()` и предназначен для сборки специального бинарника.

```
//go:build js && wasm
```

Тегами `js` и `wasm` помечены файлы, необходимые для компиляции пакета на платформу WebAssembly, то есть кода, исполняемого в браузере. Инфраструктура Go такую возможность [предоставляет](https://habr.com/ru/post/417563/).

```
//go:build !arm64 || !gc || purego
```

Тег `purego` информирует, что код будет написан на Go, а не на ассемблере (инфраструктура Go предоставляет свой собственный ассемблер, перекочевавший из Plan 9 и несовместимый с MASM, TASM, AT&T).

Тег `!gc` сообщает, что файл предназначен для окружения не с «родным» компилятором, а, например, с `gccgo`, базирующемся на хорошо знакомом пользователям nix-систем компиляторе GCC.

Тег `!arm64` говорит о том, что файл не предназначен для сборки в системах с процессорной архитектурой `arm64`.

## Флаги линковщика

Процесс сборки приложения в компилируемых языках обычно включает две фазы:

1. Компиляцию отдельных участков кода, файлов, библиотек в бинарный код.
2. Окончательную сборку этих юнитов и зависимостей в один исполняемый бинарник.

На второй фазе компиляции система использует линковщик.

Go не исключение. Предкомпилированные для дальнейшего использования библиотеки можно увидеть в папке `$GOPATH/pkg/`, а пакеты стандартной библиотеки — в папке `$GOROOT/pkg/`. Файлы, подготовленные для сборки на nix-системах, имеют расширение `.a` — например, `crypto.a`.

Линковщик запускается автоматически при выполнении команд `go build` и `go install`. Также его можно вызвать командой:

```go
go tool link [flags] main.a
```

По традиции линковщик обозначают аббревиатурой `ld`, а предназначенные ему флаги — `ldflags`. При сборке Go-проекта вы можете указать флаги линковщика с помощью параметра `-ldflags`. Например:

- `go build -ldflags "-H windowsgui"` — скомпилирует GUI-версию для Windows без консольного окна;
- `go build -ldflags "-s -w"` — скомпилирует исполняемый файл меньшего размера, так как в него не будет включена таблица символов и отладочная информация.

Параметр `ldflags` позволяет определить значение строковых переменных в момент сборки проекта. Для этих целей существует флаг `-X 'importpath.name=value'`, где:

- `importpath` — импортируемое имя пакета, которое содержит переменную `name`;
- `value` — присваиваемое значение.

Если значение не содержит пробелов, кавычки можно опустить. Также вы можете последовательно указать несколько флагов `-X`.

Предположим, в программе нужно использовать номер версии, взятой из других источников, и время сборки приложения. Для начала нужно определить две глобальные строковые переменные, в которые будут записываться соответствующие значения.

```go
var (
    Version   string
    BuildTime string
)

func main() {
    fmt.Printf("version=%s, time=%s\n", Version, BuildTime)
}
```

Если скомпилировать и запустить эту программу, она выведет `version=, time=`, так как обе переменные по умолчанию равны пустым строкам. Запустим программу с использованием флага `-X`.

```go
go run -ldflags "-X main.Version=v1.0.1" main.go
```

Получим `version=v1.0.1, time=`, что соответствует ожиданиям.

Значением может быть не только определённая строка, но и результат работы Bash-выражения. В этом случае вызов скрипта нужно заключать в одинарные кавычки и оформлять следующим образом: `$(bash command)`. Воспользуемся этой возможностью для получения текущего времени и добавим ещё один `-X`-флаг.

```go
go run -ldflags "-X main.Version=v1.0.1 -X 'main.BuildTime=$(date +'%Y/%m/%d %H:%M:%S')'" main.go
```

Результатом работы программы будет строка, подобная этой: `version=v1.0.1, time=2021/09/14 08:57:35`.

Таким образом, с помощью флага линковщика `-X` можно определять необходимые значения переменных в момент сборки приложения, что облегчает интеграцию с другими сервисами, используемыми в разработке.

## Автоматическая генерация кода

Ещё один инструмент для автоматизации процесса сборки — команда `go generate`, которая разбиралась в прошлом уроке. Повторим основные моменты, чтобы закрепить знания.

Команда `go generate` позволяет запускать любые приложения. Она сканирует `.go`-файлы и ищет комментарии вида `//go:generate <command> <arguments>`. Если такой комментарий найден, будет запущена соответствующая команда с указанными аргументами.

Как правило, эта возможность используется для автоматической генерации файлов с исходным кодом. Важно помнить, что комментарии `go:generate` игнорируются компилятором. Например, запуск `go build` не приведёт к выполнению указанных там программ.

Чаще всего автоматическая генерация применяется для определения данных, которые используются в программе. Создадим программу, которая будет содержать свой исходный код и печатать его. Команда `go generate` вызовет дополнительную программу `generate.go`, которая будет читать файл `main.go` и создавать `source.go`, содержащий строку с исходным кодом.

Начнём с создания простейшей программы-генератора.

```go
//go:build ignore

package main // generate.go

import (
    "fmt"
    "log"
    "os"
)

func main() {
    src, err := os.ReadFile("main.go")
    if err != nil {
        log.Fatal(err)
    }
    output := `// Code generated by go generate; DO NOT EDIT.
package main

var src = ` + fmt.Sprintf("`%s`\r\n", string(src))

    err = os.WriteFile("source.go", []byte(output), 0666)
    if err != nil {
        log.Fatal(err)
    }
}
```

Код программы не требует комментариев, но важно отметить два момента:

1. В первой строке определён `build`-тег `ignore`. Он сообщает компилятору Go, что данный файл следует пропустить. Здесь он используется для того, чтобы программа `generate.go` не конфликтовала с основным проектом.
2. Принято делать так, чтобы у всех автоматически сгенерированных файлов в первой строке был комментарий, удовлетворяющий регулярному выражению: `^// Code generated .* DO NOT EDIT\.$`.

Создадим файл `main.go`.

```go
package main //main.go

import "fmt"

//go:generate go run generate.go

func main() {
    fmt.Println(src)
}
```

В отличие от `build`-тегов, для размещения комментария `go:generate` жёстких ограничений нет. В данном случае комментарий расположен ниже декларации `import` и даёт сигнал команде `go generate` запустить программу `generate.go`.

Осталось запустить `go generate` и убедиться, что создался файл `source.go`. После этого можно собрать проект и проверить, что программа выводит в консоль содержимое `main.go`.

## Встраивание файлов в приложение

Пакет `embed` и сопутствующий ему комментарий `//go:embed` появились в версии Go 1.16. Этот комментарий позволяет встраивать отдельные файлы и целые директории в исполняемый файл.

Вcтраиваемые файлы и директории перечисляются после `go:embed`, а в следующей строке указывается переменная типа `string`, `[]byte` или `embed.FS`.

Первые два типа используются при встраивании одного файла. Тип `embed.FS` представляет собой коллекцию файлов и директорий, которые доступны только для чтения. Вы можете читать файл и директорию, а также открывать файл для чтения. Если у переменной указан тип `embed.FS`, то все поддиректории и файлы могут перечисляться в нескольких комментариях `//go:embed`.

Предположим, есть веб-сервер с необходимыми для работы HTML-, CSS- и JS-файлами, но хочется распространять его в виде одного бинарного файла. Покажем на примере, как можно сохранять две директории и один файл в исполняемом файле и использовать их в простейшем файл-сервере:

```go
import (
    "embed"
    "io/fs"
    "net/http"
)

//go:embed images/* html/*
//go:embed js/site.js
var content embed.FS

func main() {
    http.Handle("/", http.FileServer(http.FS(content)))
    http.ListenAndServe(":8080", nil)
}
```

Переменная типа `embed.FS` может эмулировать файловую систему и использоваться, например, в веб-сервере `http.Handle("/static/", http.StripPrefix("/static/", http.FileServer(http.FS(content))))` или при загрузке шаблонов `template.ParseFS(content, "*.tpl")`.

Для каждой задачи нужно подбирать оптимальные способы решения. Выше был рассмотрен пример программы, которая содержит свой исходный код и печатает его. Эта версия использовала возможности `go:generate` и автоматической генерации файлов. Теперь создадим версию, которая будет встраивать файл средствами компилятора Go.

Укажем файл `main.go` в комментарии `go:embed` и определим ниже строковую переменную. Так как в примере не используются элементы пакета `embed`, его нужно импортировать как `_ "embed"`.

```go
package main

import (
    _ "embed"
    "fmt"
)

//go:embed main.go
var src string

func main() {
    fmt.Println(src)
}
```

При запуске пример выведет в консоль содержимое файла `main.go`, так как компилятор присвоит его строке `src`.

Таким образом, использование `//go:embed` облегчает создание переносимых программ, которые не требуют дополнительных файлов, а хранят их внутри двоичного кода.
