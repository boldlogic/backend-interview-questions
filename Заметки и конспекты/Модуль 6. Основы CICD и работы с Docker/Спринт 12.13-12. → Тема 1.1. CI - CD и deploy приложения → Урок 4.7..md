# Как настроить пайплайн

В прошлом уроке вы узнали про GitHub Actions. Он позволяет настраивать рабочие процессы, которые запускаются автоматически, при наступлении какого-то события. Теперь пора разобраться, как настроить рабочие процессы.

## Структура workflow

Workflow состоит из заданий (jobs), задания состоят из шагов (steps), шаги выполняют конкретные команды в консоли или заранее подготовленные действия (actions). Workflow настраивается в файле типа YAML, который лежит в каталоге `.github/workflows` проекта.

Действовать нужно поэтапно — сначала разобрать отдельные кусочки из настроек workflow, а в конце собрать их вместе.

#### **Описание рабочего процесса**

Для workflow можно задать название, условия запуска и задания. Это делается с помощью определённых полей в файле типа YAML. Например, это может выглядеть так.

Скопировать код

YAML

```
name: Go

on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ] 
```

Поля могут быть следующие:

**Поле `name`.** Имя рабочего процесса, которое будет отображаться на вкладке Actions репозитория. Если имя не задано, GitHub отобразит путь к файлу workflow. Пример использования:

Скопировать код

YAML

```
name: Go 
```

**Поле `run-name`.** Имя для запуска рабочего процесса. GitHub отображает имя запуска рабочего процесса в списке запусков на вкладке Actions репозитория. Если `run-name` не задано, то в качестве имени запуска используется информация, относящаяся к конкретному событию для запуска рабочего процесса. Например, если рабочий процесс запустился событием заливки кода, то сообщение коммита будет использовано как имя запуска. Пример использования:

Скопировать код

YAML

````
run-name: New commit pushed
```
**Поле `jobs`.** Список заданий рабочего процесса.

**Поле `on`.** Указывает, какие события могут вызывать запуск рабочего процесса. Можно определить одно или несколько событий или установить расписание. Также можно ограничить выполнение рабочего процесса только для определенных файлов, тегов или изменений в ветках. 

Вот так можно указать запуск только для события `push`, которое происходит при заливке новых изменений:

```yaml
on: push 
````

Для события `push` можно указать ветку, тег или путь к файлу, для которых рабочий процесс должен запускаться. Например, чтобы запускать рабочий процесс только для изменений в ветке `main`, нужно использовать такую настройку:

Скопировать код

YAML

```
on:
  # название события
  push:
    # задаёт фильтрацию по веткам
    branches: ["main"] 
```

А вот так можно запускать рабочий процесс, только если есть изменения в файлах `.go`:

Скопировать код

YAML

```
on:
  push:
    paths:
      - '**.go' 
```

Здесь `**` означает любой путь до файла, в имени которого на конце стоит `.go`.

Ещё одно полезное событие — `pull_request`. Оно происходит, когда создаётся пул-реквест или в нём происходят изменения. Это событие поддерживает фильтр по полю `types`, в котором нужно указать тип изменения: новый комментарий, изменения в файлах, закрытие пул-реквеста и другие. Полный список доступных значений для `types` можно [посмотреть здесь](https://docs.github.com/en/actions/using-workflows/events-that-trigger-workflows#pull_request). Если для поля `types` ничего не будет указано, то по умолчанию будут использоваться типы:

- `opened` — пул-реквест открыт.
- `reopened` — пул-реквест переоткрыт.
- `synchronize` → обновление ветки (например, залили изменения).

А вот как можно это событие использовать:

Скопировать код

YAML

```
on:
  pull_request:
    types:
      - opened
    branches:
      - 'feature' 
```

С такой настройкой рабочий процесс запустится, когда кто-то создаст пул-реквест из ветки `feature`.

Полный список событий, которые запускают workflow, можно найти [здесь](https://docs.github.com/en/actions/using-workflows/events-that-trigger-workflows).

#### **Описание задания**

В секции `jobs` нужно описать одно или несколько заданий. Каждое задание должно иметь уникальный идентификатор в рамках рабочего процесса.

Вот какие поля доступны для настройки:

**Поле `name`.** Имя задания, которое будет отображаться в интерфейсе GitHub. Вот так можно описать задание с идентификатором `job1` и именем `Задание 1`:

Скопировать код

YAML

```
jobs:
  job1:
    name: Задание 1 
```

**Поле `needs`.** Здесь можно указать идентификаторы других заданий, от которых будет зависеть данное задание. Это значит, что оно не будет выполняться, пока не завершатся другие задания. Вот так можно указать, что `job3` зависит от `job1` и `job2`:

Скопировать код

YAML

```
jobs:
  job1:
    name: Задание 1
  job2:
    name: Задание 2
  job3:
    name: Задание 3
    needs: [job1, job2] 
```

При такой настройке `job1` и `job2` будут выполняться одновременно, а `job3` после них.

**Поле `if`.** Условие запуска задания. По умолчанию, если задание Б зависит от задания А, и задание А завершается с ошибкой, задание Б выполняться не будет. Это прервёт выполнение рабочего процесса. Чтобы этого избежать, можно указать в настройках `if: always()`. Таким образом, задание будет запускаться независимо от результатов других заданий.

**Поле `runs-on`.** Указывает раннер, на котором нужно запустить задание. Например, можно указать `ubuntu-latest`, тогда задание будет выполнено в ОС Linux Ubuntu.

**Поле `steps`.** Шаги задания.

#### **Описание шагов**

Задание состоит из шагов. Каждый шаг может выполнить команду в терминале или заранее определённое действие. Шаг выполняется в отдельном процессе и имеет доступ к файловой системе. У шага есть следующие поля:

- `name`. Имя шага.
- `run`. Команда для терминала.
- `with`. Здесь можно указать параметры для действий. Список доступных параметров также можно найти в описании действия на маркетплейсе.
- `uses`. Выполняет указанное действие. Действие можно найти на маркетплейсе или использовать своё из текущего репозитория. Действие можно указать вот так:

Скопировать код

YAML

```
uses: actions/setup-go@v4 
```

Это действие устанавливает Go в систему. Здесь `actions` — это [аккаунт разработчика на GitHub](https://github.com/actions), а `@v4` означает версию действия. Последнюю версию вы можете найти на маркетплейсе. Например, для `golangci/golangci-lint-action@v4`:

- `golangci` — это аккаунт разработчика
- `golangci-lint-action` — название действия
- `@v4` — версия

Вот ещё одно полезное действие: `actions/checkout@v4`. Оно извлекает репозиторий, чтобы с ним можно было работать. По умолчанию извлекается коммит, который запустил рабочий процесс. Вот [тут](https://github.com/marketplace/actions/checkout) можно почитать про это действие на маркетплейсе.

Нужные действия вы можете найти на [маркетплейсе](https://github.com/marketplace). В описании будет сказано, для чего используется действие и как его подключить.

**Взгляните на пример:**

Скопировать код

YAML

```
# здесь описывается список шагов
steps:

# шаг с именем "Set up Go"
- name: Set up Go
  # этот шаг использует действие "actions/setup-go@v4", которое установит Go в систему
  uses: actions/setup-go@v4
  # для этого действия можно задать версию Go, которую надо установить, через параметр "go-version"
  with:
    go-version: '1.20'

# шаг с именем "Build"
- name: Build
  # этот шаг просто выполняет команду 'go build -v ./...'
  run: go build -v ./... 
```

#### **Всё вместе**

Взгляните на рабочий процесс, который вы подключили в прошлом уроке. Теперь вам должно быть всё понятно.

Скопировать код

YAML

```
# Название рабочего процесса
name: Go

# Условие запуска
on:
  # Запуск по событию "push" (заливка изменений в ветку)
  push:
    # Указывает, что нужно запускать рабочий процесс, только если событие относится к ветке main
    branches: [ "main" ]
  # Запуск по событию "pull_request". Поле "types" не указано, поэтому учитываются события по открытию, переоткрытию пул-реквеста и изменению в ветке.
  pull_request:
    # Указывает, что нужно запускать рабочий процесс, только если событие относится к ветке main
    branches: [ "main" ]

# Задания
jobs:
  # Задание с идентификатором "build"
  build:
    # Для запуска задания используется раннер "ubuntu-latest", что соответствует последней версии Ubuntu
    runs-on: ubuntu-latest

    # Шаги задания
    steps:
    # Первый шаг использует действие "actions/checkout@v3", которое извлекает репозиторий для дальнейшей работы с ним
    - uses: actions/checkout@v3

    # Шаг с именем "Set up Go"
    - name: Set up Go
      # Этот шаг использует действие "actions/setup-go@v4", которое установит Go в систему
      uses: actions/setup-go@v4
      # Для этого действия можно задать версию Go, которую надо установить
      with:
        go-version: '1.20'

    # Шаг с именем "Build"
    - name: Build
      # Этот шаг просто выполняет команду 'go build -v ./...'
      run: go build -v ./...

    # Шаг с именем "Test"
    - name: Test
      # Этот шаг выполняет команду 'go test -v ./...'
      run: go test -v ./... 
```

## Последовательные действия

Для лучшего понимания посмотрите на ещё один рабочий процесс. В нём будет описано 4 задания:

- `build` компилирует проект
- `test` запускает тесты
- `tests-race` запускает тесты для обнаружения состояния гонки
- `lint` тщательно проверяет код на соответствие стилю и отсутствие логических ошибок

Задания `tests` и `tests-race` зависят от `build`, то есть они выполнятся только после него. В конце выполнится задание `lint`. Взгляните на настройки рабочего процесса:

Скопировать код

YAML

```
name: Go

on:
  push:
    branches: ["main"]

jobs:

  build:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v3
    - uses: actions/setup-go@v4

    - name: Build
      run: go build -v ./...

  tests:
    # Задание "tests" зависит от задания "build" и будет выполнено после него
    needs: build
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v3
    - uses: actions/setup-go@v4

    - name: Test
      run: go test -v ./...

  # Задание проверяет наличие в коде состояния гонки
  tests-race:
    # Задание "tests-race" зависит от задания "build" и будет выполнено после него
    needs: build
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v3
    - uses: actions/setup-go@v4

    - name: Test
      run: go test -race -v ./...
  
  # Задание проверяет код на соответствие стилю и отсутствие логических ошибок
  lint:
    # Задание "lint" зависит от заданий "tests" и "tests-race" и будет выполнено после них
    needs: [tests, tests-race]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: actions/setup-go@v4
      # Используется действие "golangci/golangci-lint-action@v3", которое запускает линтер. Он проверит код на соответствие стилю и отсутствие логических ошибок
      - uses: golangci/golangci-lint-action@v3 
```

Создайте новый проект, добавьте в него файл `main.go` с таким кодом:

Скопировать код

GO

```
package main

func main() {

}

func MaxInt(a, b int) int {
    if a >= b {
        return a
    }

    return b
} 
```

И файл `main_test.go`.

Скопировать код

GO

```
package main

import (
    "testing"
)

func TestMaxInt(t *testing.T) {
    a, b := 2, 7

    res := MaxInt(a, b)

    if res != b {
        t.Errorf("expected %d, got %d", b, res)
    }
}

func TestMain(m *testing.M) {
    main()
} 
```

Создайте новый репозиторий на GitHub, залейте туда эти файлы и добавьте рабочий процесс, описанный выше, в файл `go.yml`. Рабочий процесс должен лежать в каталоге `.github/workflows`. В итоге у вас должна получиться следующая структура:

Скопировать код

```
|-- .github
    |-- workflows
    |   |-- go.yml
|-- go.mod
|-- main.go
`-- main_test.go 
```

На вкладке Actions вы увидите запуск рабочего процесса. Он должен завершиться успешно, то есть на всех заданиях будут стоять зелёные галочки.

Теперь замените код в файле `main.go` на следующий:

Скопировать код

GO

```
package main

import (
    "fmt"
    "sync"
)

func main() {
    var wg sync.WaitGroup
    wg.Add(5)

    for i := 0; i < 5; i++ {
        go func() {
            fmt.Println(i)
            wg.Done()
        }()
    }

    wg.Wait()
}

func MaxInt(a, b int) int {
    if a >= b {
        return a
    }

    return b
} 
```

Код в функции `main` создаёт состояние гонки. Залейте код в репозиторий и взгляните на выполнение рабочего процесса:

## Практическое задание

Сейчас вы попробуете самостоятельно настроить рабочий процесс, который будет запускаться в определённых условиях.

1. Продолжайте работать в проекте из урока. Создайте новую ветку `new_workflow`. Измените в ней файл `main.go`, сохранив следующий код:

Скопировать код

GO

```
package main

func main() {

}

func MaxInt(a, b int) int {
    if a >= b {
        return a
    }

    return b
} 
```

2. Возьмите за основу текущий рабочий процесс. Уберите из него задания `tests-race` и `lint`. Рабочий процесс должен запускаться при событиях `push` (изменения в ветке) относящееся к ветке `new_workflow`. Сохраните новый рабочий процесс в каталоге `.github/workflows` в файле `go2.yml` и залейте изменения.
    
3. После этого на вкладке Actions вы должны увидеть свой новый рабочий процесс, который состоит всего из двух заданий: `build` и `tests`. Они должны выполняться последовательно и завершиться успешно, с зелёными галочками. При этом предыдущий рабочий процесс не должен запуститься, так как он запускается только при изменении в ветке `main`.
    
4. Влейте ветку `new_workflow` в основную ветку `main` с помощью пул-реквеста. Должен запуститься старый рабочий процесс и завершиться без ошибок. Новый запущен не будет. Проверьте это на вкладке Actions.
