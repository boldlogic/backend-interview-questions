# GitHub Actions: обзор интерфейса и основных возможностей

В этом уроке вы познакомитесь с одним из инструментов CI/CD — GitHub Actions. Узнаете какие функции он предлагает, как его использовать, что такое рабочие процессы и из чего они состоят. Научитесь находить и использовать готовые рабочие процессы. Знание этого инструмента необходимо, чтобы использовать концепцию CI/CD в своей работе.

## GitHub Actions

GitHub Actions позволяет автоматизировать различные процессы в рамках вашего репозитория на GitHub. Он умеет создавать рабочие процессы, которые запускаются в ответ на определенные события, такие как заливка кода, создание пул-реквеста и другие.

Вот основные компоненты GitHub Actions:

**Events (события)** — это конкретное действие в репозитории, которое запускает рабочий процесс. Таким действием может быть изменения в ветке, новый комментарий, открытие или изменение пул-реквеста.

**Workflow (рабочий процесс)** — это набор действий, которые выполняются при определенных событиях в репозитории. Workflow имеет название, условия запуска и одно или несколько заданий. Условием запуска может быть определённое событие. Например, изменения в конкретной ветке. Workflow настраивается в файле типа YAML, который лежит в каталоге `.github/workflows` проекта. Workflow может быть несколько, для каждого нужно создать новый файл. Каждый workflow будет запущен согласно его условию запуска.

**Jobs (задачи)** — задания рабочего процесса. Несколько заданий могут выполняться параллельно или по очереди, если одно задание зависит от другого. Задания иногда называют джобами. Задания могут прерывать выполнение рабочего процесса.

**Steps (шаги)**. Каждое задание состоит из одного или нескольких шагов, которые представляют собой конкретные действия, выполняемые в рамках этого задания. Например, выполнить команду в консоли. Шаги выполняются друг за другом.

**Actions (действия)**. Шаги могут быть выполнены с помощью заранее определённых действий — actions. Их можно создать самостоятельно или найти готовые на **marketplace**.

**Marketplace**. Площадка, где разработчики могут найти готовые действия (actions) для использования. Действия создаются как сообществом разработчиков, так и компаниями. Сам маркетплейс находится [здесь](https://github.com/marketplace).

**Runner (раннер)** — это сервер, который выполняет задачу. Он представляет из себя виртуальную машину, на которой запущена ОС. GitHub предоставляет раннеры с Ubuntu, Windows и macOS. Каждый раннер в один момент времени выполняет только одну задачу.

Вот так будет выглядеть схема рабочего процесса для компиляции и тестирования проекта:

Скопировать код

```
Рабочий процесс «Сборка»
    Задание «Компиляция»
        Шаг 1: получить последние изменения из ветки
        Шаг 2: выполнить команду go build -v ./...
    Задание «Тестирование»
        Шаг 1: получить последние изменения из ветки
        Шаг 2: выполнить команду go test -v ./... 
```

Задания выполняются в разных раннерах. Это значит, что результат работы одной задачи не затрагивает другую. Например, в рабочем процессе выше, в задании «Компиляция» извлекаются последние изменения из ветки. И в задании «Тестирование» делается то же самое, потому что это уже новый раннер со своим окружением. У него нет изменений от других раннеров.

В предыдущем уроке вы познакомились с понятием пайплайна. Можно сказать что workflow — это и есть пайплайн. А задания — это шаги пайплайна.

## Интерфейс GitHub Actions

Создайте новый репозиторий на GitHub и залейте туда новый проект на Go. В проекте можете оставить только функцию `main`, которая выводит на консоль `Hello, world!`.

Чтобы использовать GitHub Actions и подключить новый workflow в проект, перейдите в репозитории на вкладку “Actions”.

![](https://code.s3.yandex.net/go/go1F/43.CI_CD_%D0%B8_delpoy_%D0%BF%D1%80%D0%B8%D0%BB%D0%BE%D0%B6%D0%B5%D0%BD%D0%B8%D1%8F.GitHub_Actions_%D0%9E%D0%B1%D0%B7%D0%BE%D1%80_1.png)

На этой вкладке можно выбрать заранее настроенный workflow из предложенных, самостоятельно найти нужный или пропустить выбор и перейти к настройке workflow с нуля.

![](https://code.s3.yandex.net/go/go1F/43.CI_CD_%D0%B8_delpoy_%D0%BF%D1%80%D0%B8%D0%BB%D0%BE%D0%B6%D0%B5%D0%BD%D0%B8%D1%8F.GitHub_Actions_%D0%9E%D0%B1%D0%B7%D0%BE%D1%80_2.png)

Выберете готовый workflow с названием Go, нажав кнопку “Configure”. Если его нет среди предложенных, воспользуйтесь поиском и найдите его по ключевой фразе “go”. После того, как нажмёте на “Configure”, откроется страница редактирования workflow.

![](https://code.s3.yandex.net/go/go1F/43.CI_CD_%D0%B8_delpoy_%D0%BF%D1%80%D0%B8%D0%BB%D0%BE%D0%B6%D0%B5%D0%BD%D0%B8%D1%8F.GitHub_Actions_%D0%9E%D0%B1%D0%B7%D0%BE%D1%80_3.png)

На этой странице отображается автоматически созданный файл `go.yml`, в котором описана настройка рабочего процесса. Название файла можно изменить вверху рядом с надписью `/.github/workflow`. Согласно настройке, рабочий процесс запустится при изменении в ветке `main` и создании пул-реквеста. В рабочем процессе настроено всего одно задание с названием “build”. Задание запускается на Ubuntu и выполняет 4 шага:

1. Получит последние изменения.
2. Устанавливает go.
3. Выполняет команду `go build -v ./...`.
4. Выполняет команду `go test -v ./...`.

1 и 2 шаги используют готовые действия `checkout` и `setup-go` соответственно. Вы можете найти их в маркетплейсе справа и посмотреть подробнее что делает каждое из действий.

Вот результат поиска по слову `setup-go`:

![](https://code.s3.yandex.net/go/go1F/43.CI_CD_%D0%B8_delpoy_%D0%BF%D1%80%D0%B8%D0%BB%D0%BE%D0%B6%D0%B5%D0%BD%D0%B8%D1%8F.GitHub_Actions_%D0%9E%D0%B1%D0%B7%D0%BE%D1%80_4.png)

Нажмите на результат с названием “Setup Go environment”. Откроется страница с описанием действия и примером как его подключить.

![](https://code.s3.yandex.net/go/go1F/43.CI_CD_%D0%B8_delpoy_%D0%BF%D1%80%D0%B8%D0%BB%D0%BE%D0%B6%D0%B5%D0%BD%D0%B8%D1%8F.GitHub_Actions_%D0%9E%D0%B1%D0%B7%D0%BE%D1%80_5.png)

Попробуйте самостоятельно найти там действие `golangci-lint`, среди результатов будет `Run golangci-lint`. Это официальное действие для линтера [golangci-lint](https://github.com/golangci/golangci-lint). Нажмите на него в результате поиска, и для вас откроется справка как его установить в рабочий процесс.

Подробнее о настройке рабочего процесса вы узнаете в следующем уроке. А сейчас изучите основные компоненты GitHub Actions и взаимодействие с ними.

Чтобы добавить рабочий процесс в репозиторий, на странице редактирования workflow нажмите зелёную кнопку “Commit changes...”. Вам предложат написать сообщение для коммита и выбрать один из двух вариантов: залить изменения напрямую в ветку или создать пул-реквест. Выберете первый вариант и нажмите зелёную кнопку “Commit changes”.

![](https://code.s3.yandex.net/go/go1F/43.CI_CD_%D0%B8_delpoy_%D0%BF%D1%80%D0%B8%D0%BB%D0%BE%D0%B6%D0%B5%D0%BD%D0%B8%D1%8F.GitHub_Actions_%D0%9E%D0%B1%D0%B7%D0%BE%D1%80_6.png)

После этого в репозитории появится новый файл `go.yml` в каталоге `.github /workflows`. Перейдите на вкладку “Actions”. Там можно найти все запуски рабочих процессов и добавить новый кнопкой “New workflow”.

![](https://code.s3.yandex.net/go/go1F/43.CI_CD_%D0%B8_delpoy_%D0%BF%D1%80%D0%B8%D0%BB%D0%BE%D0%B6%D0%B5%D0%BD%D0%B8%D1%8F.GitHub_Actions_%D0%9E%D0%B1%D0%B7%D0%BE%D1%80_7.png)

Название последнего коммита, для которого запустился workflow, будет использовано для названия запуска в списке. В данном случае это “Create go.yml”. Если на него нажать, откроется страница с дополнительной информацией по рабочему процессу.

![](https://code.s3.yandex.net/go/go1F/43.CI_CD_%D0%B8_delpoy_%D0%BF%D1%80%D0%B8%D0%BB%D0%BE%D0%B6%D0%B5%D0%BD%D0%B8%D1%8F.GitHub_Actions_%D0%9E%D0%B1%D0%B7%D0%BE%D1%80_8.png)

Здесь можно увидеть все задания, их порядок запуска, какие из них выполнились успешно и посмотреть файл рабочего процесса (вкладка “Workflow file” слева).

## Практическая работа

Добавьте в проект самостоятельно ещё один workflow. Для того на вкладке Actions нажмите кнопку “New workflow”, откроется страница добавления. Можете добавить тот же самый workflow, но не забудьте поменять имя файла!

Либо можете пропустить выбор, нажав “set up a workflow yourself” вверху страницы, и создать пустой файл. В этом уроке мы не рассматриваем подробно настройку рабочего процесса. Поэтому можете просто скопировать в него содержимое из уже настроенного workflow.

В конце нажмите “Commit changes...”, чтобы влить настроенный workflow в репозиторий. После этого на вкладке Actions вы увидите 2 новых запуска workflow. Их два, потому что в репозитории теперь два настроенных workflow и они оба запускаются при изменении в ветке `main`.

![](https://code.s3.yandex.net/go/go1F/43.CI_CD_%D0%B8_delpoy_%D0%BF%D1%80%D0%B8%D0%BB%D0%BE%D0%B6%D0%B5%D0%BD%D0%B8%D1%8F.GitHub_Actions_%D0%9E%D0%B1%D0%B7%D0%BE%D1%80_9.png)

## Итоги урока

В этом уроке вы познакомились с GitHub Actions, его основными компонентами и маркетплейсом. Запомните: рабочий процесс состоит из заданий, задания из шагов, шаги выполняют определённую команду терминала или запускают заранее созданное действие (action).

Рабочий процесс запускается при наступлении определённого события. Задания могут выполняться параллельно или последовательно, зависеть друг от друга. Задания запускает раннер, у каждого раннера своё изолированное окружение. Готовые действия можно найти на маркетпейсе.
