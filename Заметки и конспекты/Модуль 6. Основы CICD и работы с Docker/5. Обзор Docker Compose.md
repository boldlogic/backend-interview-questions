Предположим, вы хотите добавить в приложение базу данных для хранения задач из туду-листа. Так будет гораздо удобнее: все списки будут под рукой и никуда не пропадут. Для этого вы можете использовать PostgreSQL. Значит, вам нужен образ этой системы управления базами данных, чтобы запустить из него контейнер вместе с контейнером вашего приложения.

Образ PostgreSQL можно взять с Docker Hub, но задача в том, чтобы одновременно запустить и ваше приложение, и базу данных, которую оно использует. Ваше приложение и база данных для него — это два разных контейнера, которые должны одновременно запускаться и взаимодействовать между собой. Для этого придумали **Docker Compose**.

## Знакомство с Docker Compose

**Docker Compose** — это надстройка над Docker, которая позволяет запускать множество контейнеров одновременно и управлять потоками данных между ними.

Каждый контейнер, который запускается с вашим приложением, включая само приложение, будь то http-сервер, база данных, прокси-сервер и так далее, называют **службами**.

**Docker Compose** упрощает управление службами в одном файле конфигурации `compose.yaml`. С помощью одной команды вы можете создать и запустить все службы из своего файла `compose.yaml`.

Для настройки Docker Compose создается файл `compose.yaml` в корне приложения. Он не похож на файл `Dockerfile`, и для его описания используют YAML. Для каждого проекта Docker создает свою изолированную сеть, где контейнеры приложения, которые указаны в файле `compose.yaml`, могут общаться друг с другом.

Использование Docker Compose упрощает разработку, развертывание контейнерных приложений и управление ими.

## Преимущества Docker Compose

- Простое управление приложением. Docker Compose позволяет управлять многоконтейнерными приложениями в одном файле YAML. Это упрощает сложную задачу организации и координации различных служб.
    
- Docker Compose обеспечивает эффективную совместную работу разработчиков и других специалистов.
    
- Быстрая разработка приложений. Docker Compose кэширует конфигурацию создания контейнеров. Это значит, что при перезапуске службы, которая не изменилась, Docker Compose повторно использует существующие контейнеры, а не создаёт новые.
    
- Переносимость в разные среды. Docker Compose поддерживает использование переменных в `compose.yaml`. Эти переменные могут использоваться для настройки приложения для разных сред или разных пользователей.
    
- Обширное сообщество и поддержка обеспечивает пользователей большим количеством ресурсов и руководств.
    

## Распространенные примеры использования Docker Compose

Docker Compose можно использовать по-разному и для разных целей. В этом уроке вы познакомитесь с основными вариантами использования.

- **Среда разработки**. При разработке программного обеспечения важно иметь возможность запускать приложение в изолированной среде. Файл Docker Compose `compose.yaml` предоставляет возможность настройки всех сервисных зависимостей приложения (базы данных, веб-службы и так далее).
    
- **Автоматизированные среды тестирования**. Важная часть процесса развертывания — автоматизированный набор тестов. Docker Compose предоставляет удобный способ создавать и уничтожать изолированные среды тестирования для вашего набора тестов.
    

Теперь, когда стало немного понятнее, зачем нужен Docker Compose, пришло время установить его на свой компьютер и использовать.

## Работа с Docker Compose

Docker Compose целиком полагаетcя на файл конфигурации YAML, который должен находиться в корневом каталоге вашего приложения. Сейчас этот файл принято называть `compose.yaml`.

В старых версиях Docker Compose файлы называли `docker-compose.yml` или `docker-compose.yaml`. Эти имена файлов поддерживаются и сегодня, но только для обратной совместимости. Если в корневом каталоге приложения будут два файла: `docker-compose.yaml` и `compose.yaml`, — то Docker Compose предпочтёт `compose.yaml`.

После создания и настройки файла `compose.yaml`, вы можете взаимодействовать со своим приложением с помощью командной строки.

Для запуска приложения используется команда:

```
docker compose up 
```

А для остановки приложения и удаления контейнеров запустите команду:

```
docker compose down 
```

Чтобы понять правила создания файла Docker Compose, стоит подробнее рассмотреть структуру этих файлов и основные их элементы.

К основным элементам файла Docker Compose относятся **службы (services)**, **тома (volumes)** и **сети (networks)**. Теперь о каждом по порядку.

#### **Службы (services)**

Вычислительные компоненты приложения определяются как `services`(сервис). **Сервис** — это абстрактное определение ресурса приложения, например http-сервера или базы данных. Сервисы определяются образом Docker, из которого могут запускаться контейнеры.

В файле `compose.yaml` должен быть объявлен элемент `services` в виде мапы. Ключ этой мапы представляет собой имя службы и значений, которые определяют службу.

Например, для приложения из прошлого урока вы можете создать файл `compose.yaml` и добавить в него службу. Войдите в корневой каталог приложения TODO-LIST и создайте там файл `compose.yaml`. В новом файле `compose.yaml` введите следующие строки:

```
services:
  server:
    build: .
    ports:
      - "8080:8080" 
```

В самом корне — ключевое слово `services`, которое указывает на то, что будут объявляться службы. Как видите, происходит вложение элементов.

Внутри `services` с отступом в два пробела следует имя службы `server`. Ниже — всё, что идёт с отступом в два пробела, будет относиться к службе `server`. В данном случае это `build` и `ports`.

Всё, что в свою очередь относится к этим параметрам `build` и `ports`, можно записать двумя вариантами. Либо в той же строке. Либо, если это перечисление, строками ниже, отступив два пробела и начав запись с минуса.

Представьте, что у вас две службы, тогда расположение элементов может выглядеть таким образом:

```
services:
  server:
    build: .
    ports:
      - "8080:8080"
  db:
    image: postgres:alpine
    ports:
      - "5432:5432"
    volumes:
      - postgres-db:/var/lib/postgresql/data

volumes:
  postgres-db: 
```

Службы `server` и `db` находятся на одном уровне вложенности, но внутри `services`. Обе являются службами, о чем и говорит элемент `services`.

Элемент `services` указывает на то, что вы будете объявлять службу, которая называется `server`. Далее идет описание службы `server`. Элемент `build` в службе указывает на контекст, из которого будет создан контейнер, то есть текущий каталог. Вспомните, когда вы создавали образ, запускали вот такую команду:

Скопировать код

BASH

```
docker build --tag my-app:v1 . 
```

Команда `build` создавала образ вашего приложения, а точка в конце указывала, откуда нужно начинать добавлять файлы в контейнер, то есть с текущей директории. То же самое происходит и здесь.

Элемент `ports` сопоставляет порты на вашем компьютере с портом в контейнере. Вы выполняли такую команду, когда запускали контейнер из своего образа на стороннем сервисе:

Скопировать код

BASH

```
docker run -d -p 8080:8080 <ваш Docker ID>/todo-app-repo 
```

Опция `-p 8080:8080` как раз делала это сопоставление. Теперь вы сделали то же самое после элемента `ports` в `compose.yaml`.

Теперь можете попробовать запустить ваше приложение. Но сначала удалите из файла `compose.yaml` строки, относящиеся к службе `db`, так как она была добавлена только для демонстрации, но в вашем приложении пока нет базы данных.

Из файла `compose.yaml` нужно удалить вот эти строки:

Скопировать код

YAML

```
  db:
    image: postgres:alpine
    ports:
      - "5432:5432"
    volumes:
      - postgres-db:/var/lib/postgresql/data
volumes:
  postgres-db: 
```

Теперь используйте команду в терминале, чтобы запустить ваше приложение с помощью Docker Compose:

Скопировать код

BASH

```
docker compose up 
```

Перейдите в браузер и в поле адреса введите `localhost:8080/tasks`. Вы должны увидеть JSON с задачами в браузере.

Когда вы добавляли службу `db` в свой файл `compose.yaml`, вы могли заметить несколько непонятных и неизвестных элементов в этой службе, например `image` и `volumes`. О них сейчас и пойдет речь.

#### **Образ (image)**

При контейнеризации своего приложения вы настраиваете среду выполнения, чтобы ваше приложение ни в чем не нуждалось и выполнялось автономно. Всё зависит от того, что делает ваше приложение, как оно настроено и какие службы нужны для его корректной работы. Если приложению нужна база данных, вы её добавляете.

Некоторые образы можете создать вы, а некоторые созданы другими разработчиками и находятся в Docker Hub.

Когда вы определяете службу, для которой уже существует образ, можно указать его после ключевого слова `image`. В примере этого урока для службы `db` вы добавили образ базы данных PostgreSQL, который находится в Docker Hub.

#### **Тома (volumes)**

**Тома (volumes)** — это постоянные хранилища данных. Тома используются для сохранения данных, которые генерируются сервисом.

Возможно, вы также заметили, что здесь добавлен ключ `volumes` с пустым полем `postgres-db` в конце:

Скопировать код

YAML

```
volumes:
  postgres-db: 
```

А затем использован `postgres-db` в конфигурации службы `db`:

Скопировать код

YAML

```
    db:
    image: postgres:alpine
    ports:
      - "5432:5432"
    volumes:
      - postgres-db:/var/lib/postgresql/data 
```

Так объявляются именованные тома (named volumes). Именованные тома сохраняют данные даже после перезапуска или удаления контейнера. Данные по указанному пути будут доступны и для других контейнеров.

Это имеет смысл для базы данных, потому что хотелось бы сохранить данные даже после того, как вы всё отключили и легли спать.

Для настройки базы данных нужны некоторые учётные данные. Поэтому перейдем к учётным данным базы данных и переменным окружения.

#### **Учетные данные базы данных и переменные окружения**

Многие Docker-контейнеры принято параметризировать через переменные окружения. Для сохранения переменных окружения для Docker Compose используется файл с именем `.env`.

Файл `.env` - это текстовый файл, он используется для определения переменных окружения, которые должны быть доступны контейнерам Docker при выполнении команды `docker compose up`. Для установки переменных окружения в ваших контейнерах файл `.env` следует поместить в корневой каталог проекта рядом с `compose.yaml`.

Для службы базы данных в примере выше переменные окружения в файле `.env` могут выглядеть так:

Скопировать код

TEXT

```
DB_USER=postgres
DB_PASSWORD=postgres
DB_NAME=todo_list 
```

А чтобы получить доступ к переменным окружения, в файле `compose.yaml` в службе `server` нужно указать с помощью ключа `env_file`, где они находятся, то есть `.env`:

Скопировать код

YAML

```
services:
  web:
    build: .
    env_file:
      - .env
    ports:
      - "3000:3000"
    volumes:
      - .:/usr/src/app
    ... 
```

В службе `db` с помощью ключа `environment` нужно присвоить значения переменных окружения переменным базы данных PostgreSQL для её инициализации:

Скопировать код

YAML

```
services:
  web:
    ...
    env_file:
      - .env
    ...
  db:
    ...
    environment:
      - POSTGRES_USER=${DB_USER}
      - POSTGRES_PASSWORD=${DB_PASSWORD}
      - POSTGRES_DB=${DB_NAME}
    ... 
```

С помощью ключа `environment` можно добавлять переменные окружения без файла `.env`.

Docker Compose также поддерживает интерполяцию. Простыми словами, **интерполяция** — это подстановка значений в месте, где указана переменная особым образом. Вы только что сделали это, подставив значение `postgres`, записав переменную `${DB_USER}`.

Вот так можно добавить переменные окружения в ваш сервис. Теперь стоит разобрать, что такое сети (networks).

#### **Сети (networks)**

По умолчанию Docker Compose настраивает единую сеть для всего вашего приложения. Каждый контейнер в службе подключается к сети по умолчанию и доступен по имени службы.

Имя сети по умолчанию создается на основе каталога вашего проекта, другими словами, на основе имени вашего проекта.

Посмотрите на пример:

Скопировать код

YAML

```
services:
  server:
    build: .
    ports:
      - "8000:8000"
  db:
    image: postgres
    ports:
      - "8001:5432" 
```

Если ваш проект находится в каталоге `myapp` и в проекте есть такой файл `compose.yaml`, то при запуске `docker compose up` происходит следующее:

1. Создается сеть с именем `myapp_default`.
2. Создается контейнер с использованием конфигурации службы `server`, и он присоединяется к сети `myapp_default` под именем `server`.
3. Создается контейнер с использованием конфигурации службы `db`, и он присоединяется к сети `myapp_default` под именем `db`.

Теперь каждый контейнер получит IP-адрес соответствующего контейнера по названию службы `server` или `db`. Например, код приложения `server` может подключиться к URL-адресу `postgres://db:5432` и использовать базу данных.

Важно понимать разницу между портом хоста и портом контейнера. В примере выше для `db` порт хоста — 8001, а порт контейнера — 5432. Контейнеры связываются между собой по портам контейнера.

Внутри контейнера `server` строка подключения к базе данных будет такая `postgres://db:5432`, а строка подключения к базе данных с вашего компьютера будет выглядеть, например, так `postgres://localhost:8001`, если контейнер запущен локально.

Тема сетей довольно обширная и порой вызывает некоторое непонимание, и это нормально. Сейчас нужно понять лишь основное: в Docker Compose есть возможность создавать несколько сетей, и даже можно указывать пользователей этих сетей. Для текущих задач вам достаточно пока одной сети — той, которая создается по умолчанию.

А теперь допустим: вы создали сервис, который через некоторое время стал очень популярным. Это значит, что количество запросов (трафик) к нему увеличилось в сотни раз. Масштабирование приложений жизненно важно для управления возросшим использованием приложения и поддержания производительности.

К счастью, с Docker Compose возможно масштабирование контейнерных служб.

## Масштабирование контейнерных служб с Docker Compose

Поскольку монолитные приложения масштабировать становится всё сложнее, компании обращаются к микросервисам и контейнерам. Небольшими независимыми сервисами легче управлять, их легче масштабировать и обновлять.

Запуск микросервисов в контейнерах открывает больше возможностей для горизонтального масштабирования. Но чтобы это делать эффективно, нужны правильные инструменты.

Как вы знаете, Docker Compose позволяет определять многоконтейнерные приложения в файле YAML, в котором можно описать сети, тома, зависимости и конфигурации.

После настройки приложения запустить его так же просто:

Скопировать код

BASH

```
docker compose up 
```

Например, у вас есть приложение с тремя службами:

Скопировать код

YAML

```
services:
  frontend:
    build: ./frontend

  api:
    build: /api
    ports:
      - "3000:3000"

  db:
    image: postgres
    ports:
      - "8001:5432"
    volumes:
      - postgres-db:/var/lib/postgresql/data

volumes:
  postgres-db: 
```

Чтобы запустить три экземпляра службы `api`, достаточно ввести такую команду:

Скопировать код

BASH

```
docker compose up --scale api=3 
```

Контейнеры службы `api` совместно используют сеть приложения и тома, поэтому они координируются как кластер, обрабатывающий запросы.

Так же легко масштабировать несколько служб одной командой:

Скопировать код

BASH

```
docker compose up --scale api=3 --scale frontend=2 
```

Количество запускаемых контейнеров для службы в файле `compose.yaml` можно установить и с помощью ключей `deploy` и `replicas`. После ключа реплики (`replicas`) указывается количество контейнеров, которое нужно запустить при запуске приложения.

Скопировать код

YAML

```
services:
  frontend:
    build: ./frontend
    deploy:
      replicas: 3

  api:
    build: /api
    ports:
      - "3000:3000"
    deploy:
      replicas: 2

  db:
    image: postgres
    ports:
      - "8001:5432"
    volumes:
      - postgres-db:/var/lib/postgresql/data
    deploy:
      replicas: 1

volumes:
  postgres-db: 
```

В примере выше служба `frontend` запускает три контейнера, служба `api` — два и служба базы данных — один.

Именно эта простота делает Docker Compose таким мощным для микросервисов.

Но при масштабировании есть несколько важных факторов, которые надо учитывать, — привязка портов и подключение к базам данных. Здесь стоит следовать двум советам, и всё будет хорошо.

По умолчанию Docker Compose использует статические порты, что может вызвать конфликты при масштабировании. Вместо этого используйте динамические порты или диапазоны.

Скопировать код

YAML

```
ports:
  - "3000-3005:3000" 
```

Связывайте все контейнеры с внешней базой данных или хранилищем в памяти.

Масштабирование можно выполнять и динамически — без перезапуска служб:

Скопировать код

BASH

```
docker compose scale api=5 
```

Эта команда расширяет службу `api` до пяти контейнеров.

Давайте рассмотрим небольшой пример масштабирования мультисервисного веб-приложения. Это приложение с интерфейсом, написанным на React, серверной частью на Go и базой данных Postgres. Вот файл compose.yaml этого приложения:

Скопировать код

YAML

```
services:
  frontend:
    build: ./frontend
    deploy:
      replicas: 3
    
  backend:
    build: ./backend
    deploy:
      replicas: 2
    
  db:
    image: postgres:alpine
    volumes:
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql
    deploy:
      replicas: 1 
```

Чтобы масштабировать службу `frontend`, нужно выполнить команду:

Скопировать код

BASH

```
docker compose up --scale frontend=5 
```

Теперь веб-интерфейс может обслуживать больше пользователей.

Docker Compose предоставляет мощный способ масштабирования сервисов с помощью одной команды. Это позволяет приложениям адаптироваться к изменяющимся спросу и трафику.
