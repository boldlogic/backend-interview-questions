# Go: defer

## Шпаргалка

1. `defer` **регистрирует** вызов: аргументы вычисляются сразу, выполнение — при выходе из функции.
2. Несколько defer выполняются в порядке **LIFO**.
3. Defer срабатывает и при **panic** — во время раскрутки stack.
4. **`recover`** работает только внутри deferred-функции **активной goroutine**.
5. Значение `return` вычисляется **до** defer; **именованный** результат можно изменить в deferred-функции.

## Как работает defer

`defer` пишут только внутри функции. Операнд — **выражение вызова** функции. При встрече `defer` аргументы вычисляются, вызов кладётся в стек отложенных вызовов; сам вызов не выполняется.

При выходе из функции — через `return` или panic — отложенные вызовы выполняются **LIFO**. Значение, которое функция возвращает через `return`, вычисляется **до** запуска defer.

Возвращаемое значение deferred-вызова **игнорируется** — некуда его вернуть. Поэтому допустимо:

```go
defer cleanup(a, b, c) // даже если cleanup возвращает (int, error)
```

Анонимная функция в defer задаётся литералом с немедленным вызовом: `defer func() { ... }()`. Ей доступны переменные внешней функции — получается closure.

---

## Аргументы defer vs closure в defer

**Прямой вызов** — аргументы фиксируются при регистрации:

```go
for i := 1; i <= 3; i++ {
    defer fmt.Println(i) // 3, 2, 1
}
```

**Closure без аргументов** — переменные читаются при **выполнении** defer:

```go
for i := 1; i <= 3; i++ {
    defer func() { fmt.Println(i) }()
    // до Go 1.22: 4, 4, 4
    // с Go 1.22 (per-iteration): 3, 2, 1
}
```

Обход для старого кода: передать значение аргументом — `defer func(v int) { fmt.Println(v) }(i)`.

| Ситуация                               | Поведение                                                       |
| -------------------------------------- | --------------------------------------------------------------- |
| Несколько defer                        | LIFO                                                            |
| `defer f(x)`                           | `x` вычисляется при регистрации defer                           |
| `defer func(){ ... }()` без аргументов | Closure читает переменные на момент выполнения defer            |
| Panic в goroutine без recover в ней    | Процесс падает; defer в другой goroutine panic не ловит         |
| `recover()` вне defer                  | Всегда `nil`                                                    |
| Concurrent map write → panic           | `recover` формально возможен, но map уже в невалидном состоянии |

## Именованный результат и defer

Работает только с **именованным** возвращаемым значением в сигнатуре — это переменная в scope функции:

```go
func unintuitive() (value string) {
    defer func() { value = "На самом деле" }()
    return "Казалось бы" // вернёт "На самом деле"
}
```

При `return "Казалось бы"` значение сначала записывается в `value`, затем выполняются defer, затем функция возвращает текущее `value`.

С локальной переменной эффекта нет — defer меняет копию, не результат функции:

```go
func intuitive() string {
    value := "Казалось бы"
    defer func() { value = "На самом деле" }()
    return value // "Казалось бы"
}
```

Редкий приём; в production-коде лучше явный return без сюрпризов.

## Зачем defer на практике

1. **Cleanup без дублирования** перед каждым `return`: `defer f.Close()`, `defer mu.Unlock()` — сразу после захвата ресурса.
2. **Cleanup при panic** — deferred-вызов выполнится при раскрутке stack, даже если до `return` не дошли.
3. **Много точек выхода** — один `defer` вместо копирования unlock/close перед каждым `return`.

---

## Panic и recover

**Panic** немедленно прекращает выполнение текущей функции и передаётся вверх по stack, пока процесс не завершится — если её не перехватят.

Если у функции есть defer, при panic сначала выполняются **все** отложенные вызовы этой функции (LIFO), затем panic идёт дальше по stack. В deferred-функции можно вызвать `recover()` — он вернёт значение panic и остановит дальнейшую раскрутку **в этой goroutine**.

`recover()` вне defer всегда возвращает `nil`. `recover` в `main` **не** перехватит panic из дочерней goroutine — у каждой goroutine свой stack.

OOM, deadlock и concurrent map write `recover` не «лечит» — только предотвращает немедленное падение процесса; состояние программы может остаться испорченным.

---

## Panic vs `error`

Публичный API библиотеки и сервиса возвращает ожидаемые ошибки через `error`. Panic — для нарушенного инварианта или ошибки программиста, не для validation и не для `io.EOF`.

Типичное место для `recover` — граница запроса: HTTP middleware с `defer` + `recover`, чтобы вернуть 500 вместо падения процесса.

---

## Паттерны из корпуса

- `mu.Lock(); defer mu.Unlock()` — unlock при любом выходе.
- `f, err := os.Open(...); defer f.Close()` — закрытие файла.
- Semaphore: `sem <- struct{}{}; defer func() { <-sem }()`.
- Middleware: `func(next http.Handler) http.Handler` с `defer` + `recover` на границе handler.

## Code review: типичные флаги

| Флаг                                         | Проблема                                    |
| -------------------------------------------- | ------------------------------------------- |
| `defer` в hot loop без причины               | Лишние регистрации defer на каждой итерации |
| `recover()` не в defer                       | Panic не перехватывается                    |
| `recover` в main при panic в child goroutine | Ожидание, что процесс не упадёт             |
| Panic для validation error                   | Нарушение идиомы библиотеки                 |
| Named return + defer «для магии»             | Нечитаемый результат функции                |

---

## Идиомы

- Defer сразу после acquire: lock, open, connect — освобождение рядом с захватом, не в конце функции.
- `defer wg.Done()` в goroutine — гарантированный сигнал завершения.
