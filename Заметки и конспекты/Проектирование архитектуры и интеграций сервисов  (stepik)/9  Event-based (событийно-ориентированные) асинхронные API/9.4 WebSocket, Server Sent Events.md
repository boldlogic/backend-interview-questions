# Проектирование API
## WebSocket

## 1. WebSocket handshake (подключение, квитирование)

### А) Клиент отправляет HTTP-запрос на сервер:

**URL:** `ws://example.com/websocket`  
**Метод:** `GET`  
**Заголовки:**
- `Upgrade: websocket`
- `Connection: Upgrade`
- `Sec-WebSocket-Key: <случайное значение в кодировке base64>`
- `Sec-WebSocket-Version: 13` (или другая поддерживаемая версия)

### Б) Сервер отвечает HTTP-ответом:

**Статус:** `101 Switching Protocols`  
**Заголовки:**
- `Upgrade: websocket`
- `Connection: Upgrade`
- `Sec-WebSocket-Accept: <base64-кодированное значение, полученное из Sec-WebSocket-Key>`

## 2. Обмен данными через WebSocket-соединение

### А) Клиент отправляет сообщение чата:

Frontend создает объект JSON. Пример JSON-объекта сообщения:

```json
{
  "type": "chat_message",
  "user_id": "12345",
  "chat_room_id": "67890",
  "content": "Всем привет!"
}
```

Frontend отправляет этот JSON-объект в виде текстового кадра через WebSocket-соединение на сервер.

### Б) Бэкенд Сервер получает сообщение чата:

Сервер анализирует полученный объект JSON.

Сервер создает новый объект JSON:

```json
{
  "type": "incoming_message",
  "user_id": "12345",
  "имя пользователя": "Alice",
  "chat_room_id": "67890",
  "content": "Всем привет!",
  "timestamp": "2023-04-10T12:34:56Z"
}
```

Сервер отправляет сообщение чата получателям, т.е. только что созданный объект JSON в виде текстового кадра всем пользователям в чате через их WebSocket-соединения.

### В) Клиенты получают сообщение чата:

Каждый клиент-получатель получает входящее сообщение, анализирует объект JSON и обновляет свой пользовательский интерфейс для отображения нового сообщения чата.

## 3. Закрытие соединения WebSocket

### А) Клиент (или сервер) посылает кадр Close на сервер (или клиент), чтобы инициировать закрытие.

- **Frame Type:** `Close (0x8)`
- **Status Code:** `1000 (Normal Closure)`
- **Reason:** `"Client is done with the chat."`

### Б) Сервер (или клиент) должен подтвердить кадр Close, отправив обратно клиенту (или серверу) кадр Close с тем же кодом состояния, который был получен от клиента (или сервера).

- **Frame Type:** `Close (0x8)`
- **Status Code:** `1000 (Normal Closure)`
- **Reason:** `"Acknowledged."`

### В) После подтверждения сервер (или клиент) должен закрыть основное TCP-соединение.

**StatusCode** - это числовое значение из реестра кодов состояния WebSocket.

**Распространенные коды состояния следующие:**

- **1000: Нормальное закрытие** - то есть цель, ради которой было установлено соединение, выполнена.
- **1001: Уход** - означает, что сервер (или клиент) завершает работу или пользователь переходит со страницы.
- **1002: Ошибка протокола** - означает, что конечная точка прерывает соединение из-за ошибки протокола.
- **1003: Неподдерживаемые данные** - означает, что конечная точка прерывает соединение, поскольку получила данные неподдерживаемого типа.

**Причина** - это необязательное строковое значение, которое предоставляет дополнительную информацию о причине закрытия соединения.

## Преимущества

### Эффективность

WebSocket разработан для работы через те же порты, что и HTTP и HTTPS (порты 80 и 443).

### Сокращение сетевого трафика

WebSockets минимизирует объем сетевого трафика.

### Упрощенная коммуникация

Связь WebSocket является двунаправленной.

### Масштабируемость

WebSockets может обрабатывать большое количество одновременных соединений.

## Недостатки

### Поддержка браузеров

Старые браузеры могут не поддерживать WebSocket.

### Сложность

Реализация WebSockets может быть сложной.

### Ресурсы сервера

Может потребоваться дополнительная инфраструктура и оптимизации для обработки большого количества WebSocket-соединений.

### Ограниченность веб-приложениями

WebSockets специально разработаны для веб-приложений.

### Безопасность

WebSocket могут обходить некоторые традиционные механизмы безопасности, потенциально подвергая приложения новым векторам атак.

## Про безопасность

Защищенный аналог Secure WebSocket (WSS), реализован на основе протокола Transport Layer Security (TLS), как и HTTPS.

Основное различие между небезопасным соединением WebSocket (WS) и безопасным соединением WebSocket (WSS) заключается в том, что последнее устанавливается по зашифрованному каналу.

В случае WSS URL WebSocket начинается с `"wss://"` вместо `"ws://"`.

**Пример:** URL: `wss://example.com/websocket`
