### Ниже расположен ряд вопросов, отметьте пункт с правильным ответом для каждого вопроса

#### **Вопрос 1: как вы выберете наиболее подходящий метод для сбора информации о бизнес-процессе?**

Компания хочет улучшить процесс обработки заказов, но текущие данные разрозненные и неполные.

- Проведете интервью с ключевыми сотрудниками, чтобы узнать детали процесса.
- Используете анкетирование для быстрого сбора данных от всех участников.
- Проведете наблюдение за реальным выполнением процесса.
- **Скомбинируете интервью, наблюдение и анализ документации для получения полной картины.**

#### **Вопрос 2: как нельзя действовать в эффективном интервью для выявления особенностей бизнес-процесса?**

Вам нужно собрать информацию о процессе обслуживания клиентов.

- Подготовите список открытых вопросов и уточняющих вопросов для интервью.
- **Создадите комфортную атмосферу для собеседника и позволите ему свободно говорить.**
- Зададите наводящие вопросы, чтобы ускорить процесс.
- Запишете интервью для последующего анализа с разрешения собеседника. 

#### **Вопрос 3: как нельзя минимизировать влияние наблюдателя на процесс во время наблюдения?**

Вы наблюдаете за процессом сборки продукции, но сотрудники начинают работать медленнее, зная, что за ними следят.

- Постараетесь быть незаметным и не вмешиваться в процесс.
- Попросите сотрудников действовать так, как будто вас нет.
- **Используете скрытое наблюдение без предупреждения сотрудников.**
- Ограничите время наблюдения, чтобы снизить эффект Хоторна.

- Используете BPMN для детального описания процесса с возможностью автоматизации.
- **Все вышеперечисленные инструменты в зависимости от цели.**

- Уделите внимание процессам, где оптимизация принесет быстрый возврат инвестиций.
- **Все вышеперечисленные критерии.**

- Тактический уровень: управление цепочкой поставок и планирование производства.

- Проведете дополнительные интервью для уточнения деталей.

- Рассчитаете необходимые инвестиции и сроки внедрения.

- **Оцените только финансовую выгоду без учета рисков.**

#### **Вопрос 10: как приоритизировать процессы для автоматизации?**

У компании ограниченный бюджет на внедрение автоматизации.

- Выберите процессы с высокой повторяемостью и низкой сложностью.
- Сосредоточьтесь на процессах, критически важных для выполнения стратегических целей.
- Проанализируйте процессы с высокой стоимостью выполнения, где автоматизация может принести максимальный эффект.
- **Все вышеперечисленные критерии.**

### Нотации для описания процессов

Когда мы хотим **визуально** отобразить, как шаг за шагом выполняется бизнес-процесс, в каком порядке и кто этим занимается, помогают специальные нотации. Две самые популярные — это **BPMN 2.0** и **UML Activity Diagram**. Ниже мы разберём каждую более подробно.

#### Зачем вообще нужна нотация процессов?

1. **Наглядность**: Вместо длинного текстового описания («сначала сотрудник делает то, потом пишет письмо…») мы получаем **диаграмму**. Людям легче воспринимать схему.
2. **Общение**: Бизнес-аналитики, разработчики, заказчики быстрее понимают друг друга, когда видят шаги и ветвления.
3. **Поиск узких мест**: Схема помогает увидеть, где процесс зацикливается, где много ручного труда или дублирования.
4. **Документирование**: Чёткая диаграмма может лечь в основу техзадания, чтобы все видели, **как** будет работать процесс.

#### BPMN 2.0 (Business Process Model and Notation)

**Что это?**

- **Стандарт** для моделирования **бизнес-процессов**. Включает множество элементов: «пулы» (pools), «потоки» (flows), «события» (events), «шлюзы» (gateways), «задачи» (tasks).
- Разработан специально для представления **бизнес-процессов**, включая автоматические шаги, ручные задачи, различные типы событий (стартовые, промежуточные, конечные).

**Ключевые элементы**:

1. **Pool** (или «пул») — это, условно, **организация** или **большой участник**. Внутри можно иметь **swimlane** (сваймлейн) для конкретного отдела или роли (Sales, Warehouse, etc.).
2. **Task** (задача) — один шаг, который кто-то выполняет (сотрудник, система).
3. **Sequence flow** (стрелки) — показывает порядок выполнения.
4. **Gateway (шлюз)** — точка ветвления (например, условный if-else), слияние веток, параллелизм (и т.д.).
5. **Event** — что запускает процесс (Start event), что заканчивает (End event), что происходит в середине (Intermediate event).

**Пример**: «Оформление заказа» в BPMN:

- Start event (покупатель заполнил форму),
- Task «Система проверяет оплату»,
- Gateway «Оплата успешна?» — [Yes → подтверждение; No → отправить уведомление об ошибке],
- End event (Заказ создан).

**Почему BPMN?**

- Он **детально** позволяет показать роли/участников (в swimlanes), события (например, таймер), сообщения между участниками (Message Flow).
- Подходит для **бизнес-процессов**, где важна «хореография» (кто кому что отправляет, что ждет).

#### UML Activity Diagram

**Что это?**

- Diagrams из семейства UML, показывающая **поток работ** (Activities), переходы, ветвления (Decision), слияния (Merge), параллельные ветви (Fork/Join).
- Более **общая** по сравнению с BPMN: часто применяют для описания **логики** (алгоритмов, use case flows), не только бизнес-процессов.

**Ключевые элементы**:

1. **Activity** — блок (прямоугольник со скруглёнными углами), обозначающий действие.
2. **Transition (стрелка)** — показывает последовательность.
3. **Decision** (ромб) — точка ветвления (похож на шлюз BPMN, но меньше типов).
4. **Swimlanes** (по желанию) — если хотим показать, какая роль выполняет действие.
5. **Start Node** (чёрная залитая точка) и **End Node** (чёрная точка с белым ободком).

**Пример**:

- Start → «Пользователь заполняет форму» → Decision («Все поля заполнены?») → [Yes] «Система проверяет оплату» → End, [No] «Показать ошибку».

**Почему UML Activity?**

- Если уже используем UML, Activity Diagram логична.
- Хорошо для **внутренних** алгоритмов или процессов, где не надо показывать сложные события/messages.
- Менее перегружена объектами, чем BPMN.

#### Сравнение BPMN и Activity Diagram

- **BPMN**:
    - Более «бизнес-ориентирована», есть понятия «message flow», «start/end events» разных типов, «pools», «lanes».
    - Детально регламентирует **взаимодействие** между организациями или ролями.
- **Activity Diagram**:
    - Ближе к «блок-схеме» с возможностью ветвлений, параллельности.
    - Не имеет таких расширенных типов событий, зато проще в освоении, если люди знакомы с UML.

> _Если ваш проект **очень** бизнес-процессный (несколько отделов, сообщения, автоматические/ручные шаги), BPMN будет более «официальным» стандартом. Если же нужно **быстро** показать поток логики — Activity Diagram вполне подойдёт._

### Пример

Допустим, нам надо показать процесс «Оформление заказа»:

- **BPMN вариант**:
    
    - **Swimlane** «Покупатель», **Swimlane** «Система», **Swimlane** «Склад».
    - Покупатель заполняет форму (task), система принимает (task), проверяет оплату (automated task), шлюз (оплата успешна?), если «да», система отправляет инфо на склад, склад резервирует товар...
    - Старт event, end event, возможно, промежуточные сообщения.
- **Activity Diagram вариант**:
    
    - Start node → «Покупатель вводит данные» (activity) → Decision «Все поля верны?» [No → вывести ошибку, Yes → «Система проверяет оплату»] → Decision «оплачено?» [Yes → «Система подтверждает заказ» → End, No → «Показать отказ» → End].
    - Всё это в одном потоке, swimlane «Покупатель», swimlane «Система» при желании.

- **BPMN 2.0** и **UML Activity** — два распространённых способа **визуально** изобразить бизнес-процесс или логику.
- **BPMN**: более формально для бизнес-процессов (multiple event types, message flows, gateways).
- **Activity Diagram**: универсальная UML-диаграмма, удобна для описания _потока_ действий/альтернатив (например, use case flow).
- **Что выбрать?** Зависит от корпоративных стандартов, уровня детализации, аудитории. Главное — использовать **какую-то** диаграмму, чтобы **все** понимали, _кто_ делает _что_, _когда_ и _как_ процесс идёт.
