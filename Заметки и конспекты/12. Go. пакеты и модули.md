# Go: пакеты и модули

## Шпаргалка

1. Одна папка — один пакет.
2. Заглавная буква — export.
3. Модуль = `go.mod` + дерево пакетов.
4. `go.mod` и `go.sum` — в git.
5. `internal/` — правило компилятора.

---

## Пакет и экспорт

**Пакет** — единица компиляции, пространства имён и импорта. Весь код Go живёт в пакете; в каждом `.go` в начале — `package имя`.

В одной директории у всех файлов одно имя пакета. Исключение — `*_test.go` (может быть другой пакет для тестов). Имя пакета лучше совпадать с именем папки.

**Именование:**

- строчные буквы, коротко и по смыслу;
- уникально в рамках репозитория, иначе понадобятся алиасы при import;
- не `util`, `common`, `tools`, `lib` — неясный API;
- без множественного числа, кроме устоявшихся исключений (`strings`, `handlers`).

Не повторяйте имя пакета в экспортируемых символах: пакет `md`, функция `HTML`, а не `MarkdownToHTML`.

Видимость задаётся регистром первой буквы имени: тип, константа, переменная или функция с заглавной доступны другим пакетам при import; со строчной — только внутри своего пакета. Внутри одного пакета видны все имена независимо от регистра.

Экспортируемый API держите минимальным. Экспорт переменных — осторожно: лучше функции доступа, иначе внешний код привяжется к полям и усложнит эволюцию пакета.

*На собесе:* обычно ждут понимание, что регистр определяет видимость снаружи, а внутри пакета — нет.

---

## Порядок инициализации

При сборке компилятор начинает с `package main`, рекурсивно собирает все import-зависимости, затем компилирует `main`.

При **запуске** пакеты инициализируются в порядке зависимостей — сначала те, от которых зависят другие. В каждом пакете: переменные уровня пакета, затем функции `init()` (несколько `init` — в порядке объявления в файлах). После всех импортированных пакетов вызывается `main`. Часть логики может отработать до `main`.

*На собесе:* обычно ждут цепочку «зависимости → переменные → `init()` → `main`».

## Модули и зависимости

**Модуль** — коллекция пакетов с общим версионированием. Метаданные — в `go.mod` в корне ([документация модулей](https://golang.org/ref/mod#modules-overview)). Раньше код жил под `GOPATH/src`; сейчас проект можно положить в любую директорию, путь import задаёт module path в `go.mod`.

Команды:

- `go mod init` — создать модуль;
- `go get` — добавить или обновить зависимость ([документация go get](https://golang.org/pkg/cmd/go/internal/get/));
- `go mod tidy` — привести [require](https://golang.org/ref/mod#go-mod-file-require) в соответствие с import в коде.

`go.mod` фиксирует путь модуля, версию Go и нужные версии зависимостей. `go.sum` хранит контрольные суммы содержимого модулей — для воспроизводимой сборки и проверки через `go mod verify`. Оба файла коммитят в git. Скачанные модули кешируются отдельно в `$GOMODCACHE` (или `$GOPATH/pkg/mod`). Подробнее про go.sum: [wiki](https://github.com/golang/go/wiki/Modules#is-gosum-a-lock-file-why-does-gosum-include-information-for-module-versions-i-am-no-longer-using).

**GOPROXY** — откуда качать модули (по умолчанию `proxy.golang.org`; `direct` — минуя прокси). Прокси [ускоряет загрузку](https://twitter.com/sajma/status/1155006281263923201?s=21) и кеширует модули; приватные варианты: [Athens](https://github.com/gomods/athens), [goproxy](https://github.com/goproxy/goproxy).

**GOSUMDB** — публичная база контрольных сумм (по умолчанию `sum.golang.org`); при первом скачивании сверяет хеш. Отключение: `GOSUMDB=off` (осторожно).

**GOPRIVATE** — маска путей приватных модулей (например `*.internal.company.com`): для них не используют публичный прокси и публичную базу сумм, доступ только напрямую к VCS или через корпоративный прокси.

**vendor** — локальная копия исходников зависимостей в `vendor/` (`go mod vendor`). По умолчанию не используется; включение: `-mod=vendor`. Нужен реже при рабочем прокси; минус — раздувание репозитория.

Если репозиторий зависимости удалён — риск для сборки ([пример](https://qz.com/646467/how-one-programmer-broke-the-internet-by-deleting-a-tiny-piece-of-code/)); прокси и зафиксированные суммы снижают, но не убирают полностью.

*На собесе:* обычно ждут различие go.mod и go.sum, знание что sum коммитят, и назначение GOPRIVATE.

## Версии и replace

Go использует [семантическое версионирование](https://semver.org/spec/v2.0.0.html): `vX.Y.Z` — мажор, минор, патч.

- патч — мелкие исправления;
- минор — новая функциональность без лома API;
- мажор — несовместимые изменения; в import path для v2+ добавляют суффикс `/v2`.

В Git версия модуля — тег релиза ([теги в Git](https://git-scm.com/book/ru/v2/%D0%9E%D1%81%D0%BD%D0%BE%D0%B2%D1%8B-Git-%D0%A0%D0%B0%D0%B1%D0%BE%D1%82%D0%B0-%D1%81-%D1%82%D0%B5%D0%B3%D0%B0%D0%BC%D0%B8)).

**replace** — подмена модуля без смены import в коде: форк, локальный путь, срочный фикс до принятия PR. Директива [replace](https://golang.org/ref/mod#go-mod-file-replace):

```
replace (
    golang.org/x/net v1.2.3 => example.com/fork/net v1.4.5
    golang.org/x/net => example.com/fork/net v1.4.5
)
```

*На собесе:* детали semver спрашивают редко; чаще — зачем `/v2` в import path.

## Оценка внешней зависимости

Перед добавлением в `go.mod`:

1. **Зачем** — какую задачу решает; нет ли в [стандартной библиотеке](https://pkg.go.dev/std) (`crypto/*`, `net/http`, `encoding/json`, …).
2. **Живость** — когда последний коммит; проект заброшен или поддерживается.
3. **Доверие** — звёзды и число участников как сигнал, не доказательство; для криптографии и безопасности — особенно осторожно.
4. **Качество** — тесты, документация, читаемый API; при сомнении — смотреть исходники.
5. **Цена** — транзитивные зависимости, лицензия, поддержка обновлений.

Дополнительный ориентир — подборки вроде [awesome-go](https://github.com/avelino/awesome-go), но решение по задаче, а не по звёздам. В зрелых командах обычно держат минимум внешних зависимостей.

*На собесе:* иногда дают repo и просят аргументированно решить — добавлять или нет.

## Layout проекта

```
cmd/
  server/main.go
  client/main.go
internal/
  service/...
  repository/...
pkg/          # редко: код для переиспользования внешними проектами
```

- **`cmd/<имя>/`** — точки входа (`package main`), имя поддиректории = имя бинарника.
- **`internal/`** — пакеты, которые нельзя импортировать извне дерева, содержащего этот `internal` (правило языка). Основной код сервиса обычно здесь.
- **`pkg/`** — публичные библиотеки внутри репо; для открытых проектов чаще отдельный репозиторий.

Папки `api`, `configs`, `deploy`, `docs` — соглашения команды, не часть спецификации Go. Тесты — `*_test.go` рядом с кодом пакета.

Для слоёв handler → service → repository интерфейсы ставят на границах; зависимости собирают в `main`, бизнес-логику держат в `internal`.

*На собесе:* обычно ждут знание назначения `cmd/` и `internal/`.

## Поддержка публичного модуля

Код форматируют [gofmt](https://golang.org/cmd/gofmt/) или [goimports](https://pkg.go.dev/golang.org/x/tools/cmd/goimports). Базовая статическая проверка — [go vet](https://golang.org/cmd/vet/).

Документация экспортируемых сущностей — комментарий **непосредственно перед** объявлением; для пакета — перед `package`. Просмотр — [pkg.go.dev](https://pkg.go.dev/) и утилита [godoc](https://pkg.go.dev/golang.org/x/tools/cmd/godoc).

*На собесе:* gofmt, vet и godoc обычно не отдельный вопрос.
