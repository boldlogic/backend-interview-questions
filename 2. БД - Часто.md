## Что такое индексы БД и зачем они нужны?
**Частота:** 56/105
**Темы:** #database #database/index
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-09

Индекс — дополнительная структура данных, ускоряющая поиск строк без полного сканирования таблицы. Цена: занимает место на диске, замедляет INSERT/UPDATE/DELETE (нужно обновлять индекс).

**B-tree** — основной тип (достаточен для 95% случаев). Сбалансированное дерево: данные в листьях, ключи-навигаторы в промежуточных узлах. Поддерживает равенство, диапазоны (`BETWEEN`, `>`, `<`), сортировку. Поиск O(log n). В листьях — не сами строки, а ссылки (ctid в PostgreSQL: номер страницы + смещение).

**Другие типы:**
- **Hash** — только `=`, быстрее B-tree на больших объёмах, не умеет диапазоны.
- **Composite** — индекс по нескольким колонкам, важен порядок (правило «слева направо»).
- **Partial** — индексирует часть строк по `WHERE`, полезен для hot subset.
- **Covering (INCLUDE)** — key + неключевые колонки в листьях → index-only scan без захода в heap.
- **GIN** — полнотекстовый поиск, массивы, JSONB; быстрый поиск, медленная вставка.
- **GiST/SP-GiST** — геоданные и custom-операторы.
- **BRIN** — для огромных таблиц с физически упорядоченными данными (логи, timeseries).

**Практика:** индекс — под конкретный запрос. Перед добавлением — `EXPLAIN` (Seq Scan → Index Scan / Index Only Scan).

## ACID и транзакции
**Частота:** 41/105
**Темы:** #database #database/transactions

- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-09

Транзакция — набор операций, который переводит БД из одного корректного состояния в другое корректное состояние. Сохраняется либо полностью, либо откатывается полностью.
#### SQL (ACID)
- **Атомарность** (atomicity) — транзакция выполняется целиком или не выполняется вовсе: все операции фиксируются одним commit, иначе rollback. Пример: списание и зачисление на двух счетах — одна неделимая операция. Частичное выполнение невозможно
- **Согласованность** (consistency) — после commit база остаётся в корректном состоянии: ограничения таблицы и бизнес-правила не нарушены (списали с одного счёта — на другом появилась та же сумма). БД переходит из одного согласованного состояния в другое. Все ограничения целостности сохраняются
- **Изоляция** (isolation) — параллельные транзакции должны выполняться независимо и не должны мешать друг другу; насколько сильно они «не видят» чужие незавершённые изменения, задаёт **уровень изоляции**. Промежуточные результаты недоступны другим транзакциям
- **Долговечность** (durability) — после успешного commit результат переживает сбой (запись в журнал, WAL).

## Виды JOIN запросов: INNER vs LEFT
**Частота:** 38/105
**Темы:** #database #database/sql
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-09

**INNER JOIN** — только строки с совпадением в обеих таблицах.
**LEFT JOIN** — все строки левой таблицы + совпавшие из правой; нет совпадения → `NULL` в полях правой.

**Остальные типы:** RIGHT JOIN (все строки правой), FULL JOIN (все строки обеих), CROSS JOIN (декартово произведение), SELF JOIN (таблица с собой через алиасы).

**Важные нюансы:**
- `WHERE` на правую таблицу после `LEFT JOIN` превращает его в `INNER JOIN` — `NULL`-строки отфильтровываются. Условия на правую таблицу кладут в `ON`.
- Дубликаты справа размножают строки слева: 3 строки справа на один ключ → 3 строки в результате.
- `COUNT(*)` после `LEFT JOIN` считает строки слева, `COUNT(right.id)` — только найденные справа.

## Масштабирование БД
**Частота:** 37/105
**Темы:** #database #database/scale
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-09

**Вертикальное** — больше CPU/RAM/дисков на одном сервере. Просто, но упирается в потолок железа, стоимость растёт нелинейно.

**Горизонтальное — чтение:** репликация. Мастер — запись, реплики — чтение. Асинхронная: реплика может отставать (лаг репликации). Синхронная: гарантия консистентности ценой задержки.

**Горизонтальное — запись:** шардирование. Данные распределены по шардам по ключу (диапазон — последовательно, хеш — равномерно). Проблемы: cross-shard-запросы и транзакции, перебалансировка при добавлении шардов, горячая точка при неудачном ключе.

**Партиционирование** — на уровне одной БД: большая таблица режется по диапазону/списку/хешу. Ускоряет запросы (отсечение партиций), упрощает удаление старых данных (отсоединение партиции).

**CAP-теорема:** при разделении сети (Partition) выбираем между Согласованностью (все узлы видят одно) и Доступностью (система отвечает). Большинство БД — CP или AP. Реляционные обычно CP, Cassandra — AP.

## Уровни изоляции транзакций / Default в PostgreSQL?
**Частота:** 33/105
**Темы:** #database #database/transactions
- [x] Скорректировано ✅ 2026-07-04
- [x] последний повтор ✅ 2026-07-09

Уровни от слабой изоляции к сильной:

**Read Uncommitted** — видны чужие незафиксированные изменения (грязное чтение). В PostgreSQL не отличается от Read Committed (грязного чтения нет).

**Read Committed (default PostgreSQL)** — каждый запрос видит снимок зафиксированных данных на момент начала запроса. Между двумя запросами одной транзакции данные могут измениться (неповторяющееся чтение).

**Repeatable Read** — один снимок на всю транзакцию (snapshot). В PostgreSQL предотвращает неповторяющееся чтение, но фантомы возможны. В других СУБД (MySQL/InnoDB) предотвращает и фантомы.

**Serializable** — максимальная изоляция. В PostgreSQL через Serializable Snapshot Isolation (SSI): при конфликте одна из транзакций откатывается с ошибкой сериализации — приложение должно повторить.

Потерянное обновление (lost update) лечится: атомарный `UPDATE` (баланс = баланс - сумма), `SELECT FOR UPDATE` (пессимистичная блокировка), optimistic locking (версия строки), или Serializable.
- **Несогласованное чтение** — в одной транзакции читаете связанные строки, а между чтениями другая транзакция успела зафиксировать изменения; набор данных уже не согласован с вашим первым чтением. На **Read Committed** в PostgreSQL встречается
- **Несогласованная запись** (write skew) — две транзакции читают пересекающиеся данные, каждая меняет **свои** строки, но вместе нарушают правило, которое выполнялось в момент чтения. На **Repeatable Read** в PostgreSQL **возможна**.

#### PostgreSQL
- **READ UNCOMMITTED** в PostgreSQL работает как **Read Committed**: грязное чтение невозможно. Включать Read Uncommitted «для ускорения» — антипаттерн.
- Изоляция построена на **MVCC**: у строки может быть несколько версий; снимок транзакции выбирает видимую версию, читатели не блокируют писателей.

| Уровень         | Потерянные изменения | Грязное чтение | Неповторяющееся | Фантомное | Другие |
| --------------- | :------------------: | :------------: | :-------------: | :-------: | :----: |
| Read Committed  |         да*          |       —        |       да        |    да     |   да   |
| Repeatable Read |          —           |       —        |        —        |     —     |   да   |
| Serializable    |          —           |       —        |        —        |     —     |   —    |
|                 |                      |                |                 |           |        |
`*`На **Read Committed** PostgreSQL защищает от части простых lost update на уровне одного` UPDATE `: если конкурентная транзакция уже изменила строку, PostgreSQL дождётся её завершения и перепроверит условие. Но классический read-modify-write в приложении (`SELECT`, расчёт в коде, потом `UPDATE` с готовым новым значением) всё ещё может потерять изменение без блокировки, версии или атомарного SQL-выражения.
**Отличия от SQL-стандарта:** на **Repeatable Read** в PostgreSQL нет фантомного чтения — транзакция работает с одним snapshot. Если транзакция пытается изменить строку, изменённую после её snapshot, возможна ошибка сериализации. В «других» на **Read Committed** — lost update в read-modify-write паттерне и несогласованное чтение; на **Repeatable Read** — write skew и аномалия read-only транзакции. **Serializable:** SSI (Serializable Snapshot Isolation), predicate/SIREAD locks, обнаружение конфликтов; при конфликте — ошибка сериализации и повтор транзакции.
#### Защита помимо уровня
- Ограничения CHECK, UNIQUE и другие ограничения таблицы.
- Один атомарный SQL-оператор, который меняет колонку выражением от её текущего значения, чтобы между чтением и записью не вклинилась другая транзакция.
- Явная блокировка:`SELECT FOR UPDATE` или блокировка таблицы.
- Оптимистическая блокировка:`UPDATE` с проверкой текущей версии строки; 0 изменённых строк → повтор
- На Serializable — обрабатывать ошибку сериализации и повторять запрос
- на read replica уровень изоляции обычно не меняют; не смешивать разные уровни в одной бизнес-операции приложения.

## Нормализация / Что такое нормальные формы / Когда денормализуют?
**Частота:** 26/105
**Темы:** #database
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-09

Нормализация — проектирование схемы для устранения дублирования и аномалий (вставки, обновления, удаления). Денормализация — сознательное дублирование ради скорости чтения: JOIN заменяются на готовые данные, ценой места и сложности поддержки консистентности.

**1НФ:** атомарность значений (нет списков/массивов в ячейке), уникальность строк (PK), однотипность данных в столбце.

**2НФ:** 1НФ + все неключевые атрибуты зависят от **всего** первичного ключа, а не от его части (нет частичных зависимостей при составном PK).

**3НФ:** 2НФ + нет транзитивных зависимостей — неключевые атрибуты не зависят от других неключевых (зависят только от PK). Пример: `город → страна` — вынести в отдельную таблицу.

Выше 3НФ (Бойса-Кодда, 4НФ, 5НФ) — редко. Денормализуют для аналитики (витрины), hot-запросов с тяжёлыми JOIN, предрасчёта агрегатов.
	- не ключевые атрибуты не должны зависеть от других не ключевых атрибутов (должны зависеть только от первичного ключа).
	- Денормализация: counters, materialized views, cached aggregates, JSON snapshot, search document. Когда нужно уменьшить количество джойнов между таблицами, чтобы упростить запросы.

---
	- Денормализация: counters, materialized views, cached aggregates, JSON snapshot, search document. Когда нужно уменьшить количество джойнов между таблицами, чтобы упростить запросы.
	- Риск денормализации — рассинхронизация данных; нужны транзакции, triggers, background jobs или rebuild. Может привести к увеличению размера базы данных и усложнению её обслуживания.

Первая нормальная форма гласит, что таблица базы данных – это представление **сущности** вашей системы, которую вы создаете. Примеры сущностей: заказы, клиенты, заказ билетов, отель, товар и т.д. Каждая запись в базе данных представляет один экземпляр сущности. Например, в таблице клиентов каждая запись представляет одного клиента.

_Правило: каждая таблица имеет первичный ключ, состоящий из наименьшего возможного количества полей._

**Атомарность.** _Правило: поля не имеют дубликатов в каждой записи и каждое поле содержит только одно значение._
**Порядок записей не должен иметь значение.** _Правило: порядок записей таблицы не должен иметь значения._
Для того, чтобы база данных была нормализована согласно второй нормальной форме, она должна быть нормализована согласно первой нормальной форме. Вторая нормальная форма связана с избыточностью данных.

**Избыточность данных.** _Правило: поля с не первичным ключом не должны быть зависимы от первичного ключа._
Может звучать немного заумно. А означает это то, что вы должны хранить в таблице только данные, которые напрямую связаны с ней и не имеют отношения к другой сущности. Следование второй нормальной форме – это вопрос нахождения данных, которые часто дублируются в записях таблицы и которые могут принадлежать другой сущности.

Третья нормальная форма связана с **транзитивными зависимостями**. Транзитивные зависимости между полями базы данных существует тогда, когда значения не ключевых полей зависят от значений других не ключевых полей. Чтобы база данных была в третьей нормальной форме, она должна быть во второй нормальной форме.

Правило: не может быть транзитивных зависимостей между полями в таблице.
Третья нормальная форма гласит, что вы не должны хранить данные в таблице, которые могут быть получены из других (не ключевых) полей таблицы

Третья нормальная форма не всегда используется при проектировании баз данных. Когда разрабатываете базу данных вы всегда должны сравнивать преимущества от более высокой нормальной формы в сравнении с объемом работ, которые требуются для применения третьей нормальной формы и поддержания данных в таком состоянии.

То есть первая НФ имеет дело, со структурой значений записей.
Вторая (и третья) НФ имеет дело уже с ключами и зависимостями в схеме.

1. Главной целью приведения ко второй нормальной форме есть желание избавиться от избыточности хранения данных и как следствие избежать аномалий модификации этих данных (аномалий изменения, вставки и удаления)
2. Второй по порядку, но не по значению, целью нормализации в 2NF есть максимально разбить модель данных на отдельные отношения, чтобы их можно было комбинировать и использовать в выражениях новыми, не предусмотренными изначально способами.
3. Минимизировать усилия по изменению схемы в случае необходимости. Чем меньше зависимостей внутри схемы, тем меньше изменений в ней потребуется при изменении модели данных.
4. Понятность схемы для пользователя. Чем держать все данные в одной большой таблице, проще представить данные как несколько связанных и логически разделенных отношений. Это проще читать, воспринимать, проектировать и поддерживать. В конце концов, любая модель данных начинается на доске или бумаге в виде кружочков, блоков и линий, которые так любят рисовать дети и программисты.

## Почему B-tree быстрее полного перебора?
**Частота:** 23/105
**Темы:** #database #database/index
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-09

Полный перебор (Seq Scan) читает все страницы таблицы подряд — O(N). B-tree даёт поиск за O(log N): сбалансированное дерево, на каждом уровне отсекается большая часть ключей, глубина ограничена.

В одном узле B-tree много ключей — меньше обращений к диску по сравнению с бинарным деревом в памяти. Листья содержат ссылки на строки (ctid), а не сами данные — компактнее таблицы. Для диапазонных запросов листья связаны в список — не нужно возвращаться к корню.

## SQL vs NoSQL — Чем реляционные БД отличаются от NoSQL?
**Частота:** 21/105
**Темы:** #database #database/sql
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-09

**Реляционные (SQL):** фиксированная схема, таблицы, JOIN, ACID-транзакции, SQL. Сильные стороны: целостность данных, сложные связи, отчёты. Примеры: PostgreSQL, MySQL.

**NoSQL:** гибкая или отсутствующая схема, eventual consistency, заточены под конкретный паттерн доступа.
- Документные (MongoDB) — JSON-документы, каталоги, пользовательские профили.
- Ключ-значение (Redis) — in-memory кеш, счётчики, сессии.
- Wide-column (Cassandra) — timeseries, логи, IoT, большие объёмы.
- Графовые (Neo4j) — соцсети, рекомендации, связи между сущностями.

**Когда NoSQL:** гибкая схема, высокий объём простых операций, горизонтальное масштабирование важнее транзакций. **Когда SQL:** сложные связи и запросы, ACID-транзакции, отчётность.

## EXPLAIN и EXPLAIN ANALYZE / Как понять, почему запрос медленный?
**Частота:** 19/105
**Темы:** #database #database/index
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-09

`EXPLAIN` — предполагаемый план без выполнения: тип сканирования/соединения, стоимость, оценка строк. `EXPLAIN ANALYZE` — реально выполняет и показывает actual time/rows/loops.

**Что смотреть в плане:**
- `cost` — внутренняя оценка планировщика, не миллисекунды. Сравнивайте relative cost между вариантами.
- `rows` (оценка) vs `actual rows` (реальность) — большой разрыв → устаревшая статистика или корреляция колонок.
- `loops` — операция внутри вложенного цикла может выполниться тысячи раз.
- Seq Scan не всегда плох, но сигнал проверить селективность и индекс.
- `EXPLAIN (ANALYZE, BUFFERS)` — сколько страниц из кеша/диска.
- Для `UPDATE/DELETE` — в транзакции с rollback, иначе реально выполнится.

 функции, такие как суммирование, подсчет и вычисление среднего, на основе групп
 строк в окне. так и получение "скользящих" или "накопительных" результатов для каждой
 строки в окне.

 SUM(order_price) OVER ([PARTITION BY client] [ORDER BY product]);

-`ROW_NUMBER`,`RANK`,`LAG/LEAD`, накопительная сумма.
- Отличие от `GROUP BY`— строки сохраняются и выводятся.
-`ROW_NUMBER()` даёт уникальный номер строки внутри partition.
-`RANK()` оставляет дырки при равенстве,`DENSE_RANK()` не оставляет.
-`LAG/LEAD` смотрят на предыдущую/следующую строку в окне.
-`ORDER BY` внутри `OVER` важен для ранжирования и накопительной суммы.
- Window frame (`ROWS BETWEEN ...`) важен для точного поведения агрегатов по окну.

**Оконная функция vs JOIN:** если нужен **агрегат по группе без потери строк** (ранг, running total, prev/next row) — **window**. Если нужно **соединить две сущности** по ключу и фильтровать набор — **JOIN**. Иногда оба: JOIN для связи + `ROW_NUMBER() OVER (PARTITION BY ...)` для «последней записи на заказ».

## Чем отличается WHERE от HAVING?
**Частота:** 14/105
**Темы:** #database #database/sql
- [x] Скорректировано ✅ 2026-06-28
- [x] последний повтор ✅ 2026-06-28

`WHERE` фильтрует строки **до** группировки и агрегатов, по колонкам исходных строк. 

`HAVING` фильтрует группы **после**`GROUP BY` и агрегатных функций (`COUNT`,`SUM`, …) — по результатам агрегации. Условие на агрегат нельзя записать в `WHERE`— для этого `HAVING`.

## Агрегатные функции SQL, для чего они нужны?
**Частота:** 12/105
**Темы:** #database #database/sql
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-09

Агрегатные функции сводят набор строк к одному значению: `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`. Применяются с `GROUP BY` — группировка строк по указанным колонкам, агрегат считается внутри каждой группы.

`WHERE` фильтрует строки **до** агрегации, `HAVING` — **после** (по результату агрегата). Пример: `HAVING COUNT(*) > 5` — только группы с >5 строк.

`COUNT(*)` считает все строки, `COUNT(column)` — только не NULL. `SUM`/`AVG` игнорируют NULL.

Оконные функции (`OVER`, `PARTITION BY`) — агрегация без схлопывания строк (результат добавляется к каждой строке), но это отдельная тема.

## Репликация и read replica
**Частота:** 10/105
**Темы:** #database #database/scale
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

В PostgreSQL репликация обычно строится через WAL: мастер записывает изменения в WAL, реплика получает WAL и воспроизводит его. Read replica разгружает чтения, но чтения с неё eventual consistent: replica может отставать от мастера, поэтому сразу после записи пользователь может не увидеть свои изменения.

- Primary пишет WAL; replica получает его через streaming replication и применяет.
- Асинхронная репликация быстрее для primary, но допускает lag и потерю последних транзакций при аварии primary до доставки WAL.
- Синхронная репликация сильнее по durability, но увеличивает latency commit.
- Read replica нельзя использовать для read-your-writes без routing: после записи читать с primary или ждать, пока replica догонит нужный LSN.
- Репликация копирует те же данные на другой сервер; sharding делит данные по узлам.
- На replica обычно нельзя выполнять обычные write-запросы; она для чтения, бэкапов и аналитических read-only нагрузок.

## CTE vs подзапрос (+ recursive)
**Частота:** 6/105
**Темы:** #database #database/sql
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-22

**Эталон на собесе:**
CTE (`WITH`) — именованный подзапрос внутри одного SQL-запроса. Его используют для читаемости, повторного использования промежуточного результата и рекурсии. Подзапрос и CTE часто эквивалентны по смыслу, но план может отличаться.
**Подробности:**
- Смотреть EXPLAIN: CTE Scan vs inline.
-`WITH RECURSIVE`: обычная часть + рекурсивная, обычно через `UNION ALL`.
- Для простых фильтров JOIN и подзапрос часто дают тот же план.
- Можно явно подсказать planner:`MATERIALIZED` или `NOT MATERIALIZED`.
- Рекурсивный CTE используют для деревьев, графов, цепочек parent-child, обхода зависимостей.
```sql
WITH RECURSIVE sub AS (
SELECT
id
FROM
org.departments
WHERE
id = ?::integer
UNION ALL
SELECT
d.id
FROM
org.departments d
INNER JOIN sub ON d.parent_id = sub.id
)
SELECT
CASE
WHEN EXISTS (
SELECT 1
FROM sub
WHERE id = ?
) THEN 'cycle'
ELSE 'ok'
END AS reason
```

## Selectivity и cardinality индекса
**Частота:** 6/105
**Темы:** #database #database/index
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-22
Что такое селективность индекса
**Что ожидают на собесе:**

**Эталон на собесе:**
Селективность - показатель того на сколько групп разбивается данное поле. Отношение количества уникальных значений в колонке на количество строк.
Как используем когда выбираем на какое поле повесить индекс. Более селективные поля мы должны ставить первее
Cardinality — число уникальных значений в колонке или наборе колонок. Selectivity — насколько условие сужает выборку: какая доля строк останется после фильтра. Чем меньше доля выбранных строк, тем выгоднее индекс. Если условие возвращает большую часть таблицы, sequential scan может быть дешевле index scan.
**Подробности:**
- Высокая cardinality обычно делает индекс полезнее:`user_id`,`email`,`order_id`.
- Низкая cardinality сама по себе не всегда бесполезна: partial index по редкому значению может быть отличным решением.
- Selectivity зависит не только от колонки, но и от конкретного предиката: фильтр по архивному статусу может быть селективным, если archived мало.
- Planner опирается на статистику:`ANALYZE`, histograms, most common values.

## MVCC в PostgreSQL
**Частота:** 5/105
**Темы:** #database #database/transactions #database/sql
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

**Эталон на собесе:**
MVCC в PostgreSQL — механизм многоверсионности строк.`UPDATE` не перезаписывает строку на месте, а создаёт новую версию; старая остаётся, пока может быть видна старым транзакциям. Снимок транзакции решает, какие версии строк видимы. Поэтому читатели обычно не блокируют писателей, а писатели не блокируют читателей.`VACUUM` потом убирает мёртвые версии.
**Подробности:**
- Видимость версий определяется transaction ID (`xmin`/`xmax`) и snapshot.
- Долгие транзакции удерживают старые версии видимыми и мешают vacuum чистить мусор.
- Bloat — рост таблиц/индексов из-за накопления мёртвых версий.
- Autovacuum обычно чистит автоматически;`VACUUM FULL` физически переписывает таблицу и берёт тяжёлую блокировку.
- MVCC хорошо решает конкурирующие чтения/записи, но write skew и сложные инварианты требуют уровня изоляции, constraints или явных блокировок.

## Что такое hash index? 
**Частота:** 4/105
**Темы:** #database #database/index
- [ ] Не AI-generated
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26

Hash index в PostgreSQL поддерживает только поиск по равенству. Он не помогает для range-запросов, сортировки,`ORDER BY`, prefix search.
B-tree обычно универсальнее: equality, range, сортировка,`MIN/MAX`, composite indexes. Поэтому в PostgreSQL hash index используют редко и только когда есть понятный equality-only кейс.
**Подробности:**
- Hash не покрывает сортировку и не поддерживает range.
- Для low-cardinality условий чаще нужен partial B-tree index, а не hash index.
- B-tree по умолчанию хорошо работает и для поиска по равенству, поэтому сначала проверяют его.
- Решение принимать по `EXPLAIN (ANALYZE, BUFFERS)`, а не по названию индекса.

## Что такое триггер
**Частота:** 3/105
**Темы:** #database
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26
Триггер - это вид хранимой процедуры, который автоматически запускается при возникновении определенных событий. Предназначена для проверки сложных ограничений целостности, автоматизации обработки данных, аудита действий пользователя, установки.
Триггер состоит из
* Время срабатывания (before или after)
* Событие, вызывающее срабатывание (insert/update/delete)
* Имя таблицы
* Тело триггера (блок SQL)

**Срабатывают ли триггеры на SELECT?**

**Эталон на собесе:**
Нет. В PostgreSQL (и типично в SQL) триггеры вешают на DML:`INSERT`,`UPDATE`,`DELETE`, иногда `TRUNCATE`. На `SELECT` триггер не срабатывает — чтение не меняет данные. Для аудита чтения нужны другие механизмы (логирование на уровне приложения,`pg_audit` и т.п.).

## B-tree и физическое хранение на диске
**Частота:** 2/105
**Темы:** #database #database/index
- [ ] Скорректировано
- [ ] последний повтор

**Эталон на собесе:**
Индексные страницы B-tree упорядочены; при range-scan читаются соседние страницы последовательно — меньше random I/O, лучше prefetch. Данные в индексе компактны относительно широкой heap-строки. Heap-таблица при вставках/обновлениях может фрагментироваться; индекс помогает не сканировать весь heap.
**Подробности:**
- Sequential read с диска дешевле множества random seek.
- Index-only scan ещё сильнее снижает обращения к heap .

## ClickHouse и колоночные СУБД
**Частота:** 2/105
**Темы:** #database
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26
**Как формулируют на собесе:**
> Зачем ClickHouse? Чем от row-store отличается?

**Эталон на собесе:**
ClickHouse — колоночная OLAP-СУБД: хорошо читает много строк по немногим колонкам, сжимает данные и быстро считает агрегации. Для OLTP с частыми point update, транзакциями и сложными join-heavy сценариями обычно оставляют PostgreSQL. На практике поэтому ClickHouse чаще используют как аналитическое хранилище или витрину рядом с основной БД.
**Типичные ошибки:**
- Предлагать ClickHouse как primary OLTP базу для транзакционных записей.

**Подробности:**
- MergeTree хранит данные по партициям и сортировочному ключу; правильный `ORDER BY` критичен для pruning.
- Сильная сторона — scan/aggregate по большим объёмам; слабая — частые маленькие UPDATE/удаление.
- Данные часто грузят батчами или из Kafka/CDC; consistency обычно проектируют отдельно от OLTP.
