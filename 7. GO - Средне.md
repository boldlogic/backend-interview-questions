## defer, panic, recover / exceptions в Go
**Частота:** 22/84
**Темы:** #go/errors #go/defer
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-08

Классической модели exceptions в Go нет. Ожидаемые ошибки возвращают через `error`. 

Для невосстановимых ситуаций —`panic` и `recover`. 

`defer`— отложенный вызов при выходе из функции. Откладывает вызов функции до выхода из окружающей функции (return или panic). Несколько `defer` выполняются в порядке **LIFO**.

Аргументы выражения в `defer` считаются в момент **регистрации**`defer`, не при выполнении.
Останавливает обычное исполнение текущей горутины, **раскручивает стек**, выполняет отложенные `defer` в обратном порядке, печатает stack trace и завершает процесс — если panic не погашен.

Выполняется **после** вычисления return values, но **до** выхода из функции. Записи defer — на куче (defer chain), не на стеке вызывающего.

`panic(v)`—значение любого типа; `recover()` возвращает этот аргумент.

`recover` ловит panic только в той же горутине, где `defer recover`. Panic в одной горутине не ловится `recover` в другой.

defer с recover — типичный паттерн в HTTP middleware. Handler без recover — одна паника роняет весь процесс.

Не всё recoverable: OOM, concurrent map write, deadlock. 

Runtime сам вызывает panic: nil pointer deref, index out of range, send on closed канал, failed type assertion без `ok`.
```go
defer func() {
if r := recover(); r != nil {
log.Printf("panic: %v\n%s", r, debug.Stack())
}
}()
```

|              | `return error`                        | `panic`                         |
| ------------ | ------------------------------------- | ------------------------------- |
| Когда        | сеть, файлы, validation, «нет данных» | невозможно продолжать безопасно |
| Стоимость    | обычный return                        | раскрутка стека                 |
| В библиотеке | основной путь                         | только документированные случаи |


Типично:`close`,`Unlock`,`cancel()`, recover в middleware.

## Что такое generics?
**Частота:** 10/84
**Темы:** #go/generics
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-04

Дженерики — это механизм параметрического полиморфизма, позволяющий писать универсальные функции и типы, работающие с разными типами данных без дублирования кода. Типы задаются через параметры (`T`), которые при необходимости ограничиваются constraints, например `any` или `comparable`. 
Дженерики сохраняют статическую типизацию и позволяют избежать использования `interface{}` там, где нужен типобезопасный универсальный код.
Не заменяют интерфейсы для поведения.


Generics — **Go 1.18+**. Компилятор мономорфизирует (stenciling) или GC shape — не ручная кодогенерация как `go generate`, но похожий эффект «отдельный код на тип».

## Mutex / RWMutex / Когда Mutex, а когда RWMutex?
**Частота:** 7/84
**Темы:** #go/sync
- [x] Скорректировано ✅ 2026-06-29
- [x] последний повтор ✅ 2026-06-30

**Mutex** — эксклюзивная блокировка: 
- в один момент времени **только одна** горутина выполняет защищённый код. 
- Это убирает гонку при read-modify-write и составных инвариантах на нескольких полях.

**RWMutex** — много параллельных **читателей** **или** один **писатель**. 
- Писатель блокирует всех читателей (приоритет writer);  
- новые читатели не проходят, пока ждёт писатель. 
- при частых записях — читатели могут **голодать**, писатели тоже при постоянном потоке readers.
- Ожидающие горутины ставятся в **FIFO**-очередь семафора; при длинных критических секциях возможен **starvation** — нужны короткие секции и иногда fair lock / отдельная архитектура.
- При частых записях overhead RWMutex не окупается; 

RWMutex имеет те же методы `Lock()` и `Unlock()`, но использовать их нужно только для критической секции, изменяющей данные. Для кода, который читает данные, нужно использовать методы `RLock()` и `RUnlock()`.`RLock()` не даст выполниться `Lock()` и начать изменение данных, пока не будут завершены все операции чтения.

| Состояние                                                             | Метод `RLock()`                                                                                           | Метод `Lock()`                                                                         |
| --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Мьютекс свободен                                                      | Возьмёт мьютекс в режиме чтения                                                                           | Возьмёт мьютекс в режиме записи                                                        |
| Одна горутина уже взяла мьютекс через `RLock()`                       | Возьмёт мьютекс в режиме чтения. Блокировки не будет                                                      | Будет блокировать горутину до тех пор, пока другие горутины не отпустят мьютекс        |
| Одна горутина уже взяла мьютекс через `RLock()`. Вторая ждёт `Lock()` | Будет блокировать горутину до тех пор, пока другая горутина не дождётся метода `Lock()` и не отпустит его | Будет блокировать горутину до тех пор, пока не будут отпущены все остальные блокировки |
| Одна горутина взяла мьютекс через `Lock()`                            | Будет блокировать горутину до тех пор, пока не будут отпущены все блокировки на запись                    | Будет блокировать горутину до тех пор, пока не будут отпущены все остальные блокировки |
При использовании мьютексов нужно обязательно придерживаться трёх основных правил
1. После блокировки мьютекса его всегда нужно разблокировать. Если этого не сделать, другие горутины так и будут ожидать своей очереди на выполнение критической секции.
2. Если вы применяете мьютексы для синхронизации доступа к общим данным, следите за тем, чтобы не было горутин, работающих с этими данными без мьютекса. Например, если значение общей переменной меняется горутинами в двух местах, а мьютекс применяется только в одном, то смысла в этом нет, так как ошибки всё равно будут.
3. В общем случае нужно стремиться сокращать продолжительность выполняемого кода внутри критической секции.

## pprof: CPU, heap, goroutine
**Частота:** 7/84
**Темы:** #go/tooling #go/goroutine
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

**Профайлинг** — измерение, где программа тратит CPU, память и время ожидания. В Go: **`go tool pprof`**,`runtime/pprof`,`net/http/pprof`.

| Профиль                        | Что показывает                | Когда смотреть               |
| ------------------------------ | ----------------------------- | ---------------------------- |
| **CPU**                        | горячие функции, % времени    | «медленно считает»           |
| **heap** (inuse / alloc_space) | живые объекты / все аллокации | утечки, churn GC             |
| **goroutine**                  | стеки, блокировки             | leak, deadlock на chan/mutex |
| **block / mutex**              | где ждут lock/I/O             | contention                   |
Сбор:` go test -cpuprofile cpu.prof -bench .`; в сервисе —` import _ "net/http/pprof"`и` curl localhost:6060/debug/pprof/profile?seconds=30 `.
Разбор:`go tool pprof -http=:8080 cpu.prof`— flame graph, top, graph. Ищем **широкие** полоски в flame graph и функции с большим **flat** + **cum** %.
**Подробности:**
- go tool pprof -http=:8080 cpu.prof — flame graph.
- heap: inuse_objects, alloc_space — утечки и churn.
- горутина: блокировки на канал/mutex.
- Типичный win: убрали лишний `append` в цикле, заменили `fmt.Sprintf` в hot path, шардировали mutex — CPU −30…70% после heap/cpu profile.
- В prod: `import _ "net/http/pprof"` → `/debug/pprof/`; sampling overhead обычно ~2–5% CPU при типичных интервалах.

## Как устроено ООП в Go?
**Частота:** 15/84
**Темы:** #go/oop #go/interfaces
- [x] Скорректировано ✅ 2026-06-29
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Go — не классический ООП-язык (нет классов, нет наследования), но реализует ООП-принципы другими средствами:

- **Инкапсуляция:** exported (заглавная буква) / unexported (строчная) — на уровне пакета, не класса. Пакет = единица инкапсуляции.
- **Наследование:** заменено **композицией**. Embedding struct — встраивание одной структуры в другую: поля и методы встроенного типа «промоутятся», но это не subclass (нет виртуальных методов, нет переопределения).
- **Полиморфизм:** через **интерфейсы**. Реализуются неявно (satisfies implicitly) — тип реализует интерфейс самим фактом наличия методов, без `implements`. Зависимость можно держать на стороне потребителя.
- **Абстракция:** struct + methods. Роль «класса» играет struct с привязанными методами.

**Подробности:**
- Embedding vs наследование: нет доступа к приватным полям встроенного типа (инкапсуляция пакета работает), нет dynamic dispatch по «базовому классу», нет цепочек super(). Вызов «метода родителя» — явно: `e.Type.Method()`.
- Интерфейсы — ключевой механизм: `io.Reader` принимает файл, сокет, буфер — без единой строчки `implements`. Позволяет mocking без фреймворков.
- Переиспользование кода: embedding для состояния + интерфейсы для поведения + функции как first-class values.

## Что такое map / хэш-таблица / Как устроена map под капотом? / Сложность доступа по ключу в map / коллизии / эвакуация
**Частота:** 38/84
**Темы:** #go/map #go/hash #go/runtime #go/complexity
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Map — хэш-таблица: ключ → хэш-функция → бакет. Доступ в среднем O(1), деградирует до O(n) при коллизиях.

Под капотом — массив бакетов по 8 пар ключ/значение. Хэш делится на две части: **low-order bits** определяют номер бакета, **top bits** (tophash) хранятся в бакете для быстрой отбраковки несовпадающих ключей без полного сравнения.

Коллизия — разные ключи дают одинаковый хэш. **Старая map (до 1.24):** метод цепочек — overflow bucket (связный список дополнительных бакетов). **Swiss map (1.24+):** открытая адресация — если слот занят, ищется следующий свободный в группе (triangular probing с SIMD-ускорением).

**Swiss map (1.24+):** принципиально иная реализация. Вместо бакетов с overflow-цепочками — **таблицы из групп** по 8 слотов. Рядом с каждой группой лежит массив **control bytes** (1 байт на слот: старшие 7 бит хэша + флаг empty/deleted). Поиск: SIMD-инструкция сравнивает 16 control bytes за один такт и возвращает битовую маску совпадений — ни одного pointer chase. При заполненной группе probing переходит к группам H1+1, H1+3, H1+6… (треугольные числа). Рост — не удвоение бакетов, а split таблицы с распределением слотов по большему числу групп.

Эвакуация — рост map. Срабатывает при среднем заполнении **6.5** элементов на бакет (load factor). Выделяется новый массив бакетов в **2 раза** больше; старые остаются в `oldbuckets`. Перенос **постепенный** (incremental) — по мере операций insert/delete, а не весь сразу. Именно поэтому **нельзя взять указатель** на элемент map (`&m[k]`) — адрес изменится при эвакуации.

Не потокобезопасна. Конкурентный доступ без синхронизации → `fatal error: concurrent map writes`.

**Подробности:**
- **Ключи:** только **comparable**-типы (`int`, `string`, указатели, каналы, интерфейсы, struct без slice/map/func). Slice, map, func — нельзя.
- **nil map:** чтение `m[k]` → zero value, запись `m[k] = v` → panic. Инициализация: `make(map[K]V)` или `make(map[K]V, hint)`.
- **Capacity hint:** `make(map[K]V, n)` — это ожидаемое число элементов (не бакетов), снижает вероятность эвакуации. От коллизий не защищает.
- **Итерация:** порядок случайный — Go намеренно рандомизирует, чтобы не полагались на insertion order.
- **Потокобезопасность:** `sync.Map` (lock-free, выигрывает при read-heavy и многоядерных нагрузках, но не атомарен для multi-op) vs `map+Mutex` (типобезопаснее, проще для инвариантов).
- **Swiss map (Go 1.24+):** замена старой реализации на основе Swiss Tables (Google, `absl::flat_hash_map`). Конкретно:
  - **Группа** = 8 слотов (ключ + значение) + 8 control bytes. Хэш делится на H1 (номер группы) и H2 (control byte — старшие 7 бит + флаг empty/deleted).
  - **SIMD-поиск:** SSE2 (x86) / NEON (ARM) — одна векторная инструкция сравнивает сразу 16 control bytes с искомым H2 и выдаёт битовую маску совпадений. Ключевое ускорение относительно старого побайтового перебора tophash.
  - **Triangular probing:** если группа заполнена — переход к H1+1, H1+3, H1+6… (треугольные числа). Равномернее линейного probing, не образует плотных кластеров.
  - **Почему быстрее:** control bytes в одной cache line — один cache miss на группу. В старой map каждый overflow bucket = отдельная аллокация + pointer chase в связном списке.
  - **Рост:** при load factor ~0.875 таблица разделяется (split) — каждая группа распределяет слоты по большему числу групп. Эвакуация тоже incremental. Максимальная fill rate выше (87.5% vs 81% = 6.5/8), меньше wasted space.
- **Сравнение:** `==` на двух map не работает — `maps.Equal` (Go 1.21+). Копия — `maps.Clone`. Очистка — `clear(m)` (Go 1.21+).

## Процесс vs поток / Процессы и потоки могут друг с другом как-то общаться?
**Частота:** 12/84
**Темы:** #go/goroutine #go/scheduler
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Процесс — контейнер с изолированным адресным пространством, памятью и ресурсами (файловые дескрипторы, сокеты). Поток — единица выполнения внутри процесса; все потоки одного процесса делят общую память, но имеют собственные стек и регистры. ОС планирует потоки на ядрах.

Общение: процессы изолированы — нужен **IPC** (сокеты, pipes, shared memory, message queues). Потоки общаются через **общую память** (нужна синхронизация — mutex, atomic). Горутины — ещё легче: один процесс, координация через каналы, mutex, WaitGroup внутри Go runtime.

**Подробности:**
- Создание процесса — дорого (копирование адресного пространства, fork). Потока — дешевле (только стек + регистры). Горутины — ~2 КБ стека, user-space, без участия ядра.
- Типовые IPC в Go: `net` (TCP/Unix sockets), `os/exec` + stdin/stdout, gRPC/HTTP между сервисами, Unix domain sockets для локального IPC.

## `sync.WaitGroup` под капотом
**Частота:** 14/84
**Темы:** #go/sync
- [x] Скорректировано ✅ 2026-06-30
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
`sync.WaitGroup` — примитив ожидания группы горутин. Счётчик: `Add(n)` увеличивает, `Done()` уменьшает, `Wait()` блокируется пока счётчик не 0. Типовой паттерн: `wg.Add(1)` перед запуском, `defer wg.Done()` внутри горутины, `wg.Wait()` в ожидающем коде.

**Под капотом:** основа — `atomic.Int64` (счётчик) + `sema` (внутренний семафор runtime). `Add` атомарно меняет счётчик, `Wait` проверяет счётчик и при ненулевом значении вызывает `runtime_Semacquire` (блокировка). `Done` = `Add(-1)` — когда счётчик доходит до 0, `Add` вызывает `runtime_Semrelease` для всех ожидающих. Не `sync.Mutex`/`sync.Cond` — собственный лёгкий механизм на atomic+sema.

**Самописный аналог:** `atomic.Int64` + `sync.Cond` или `atomic.Int64` + `chan struct{}` (закрытие канала будит всех читателей). Без `sync`-пакета — только atomic + канал.

## Сборщик мусора: что, зачем, как работает, отключение
**Частота:** 6/84
**Темы:** #go/gc
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

Garbage Collection - это процесс освобождения места в памяти, которое больше не используется.

GC освобождает **недостижимый** heap даже если память «ещё используется» другими объектами — циклы без ссылок снаружи тоже собираются. Tri-color, concurrent.`GOGC`,`GOMEMLIMIT`; полное off —`GOGC=off`(редко, риск OOM). Упростить жизнь GC: меньше аллокаций,`sync.Pool`, избегать лишних указателей.

- фase mark обходит граф от roots (stack, globals, registers).
- Concurrent GC снижает STW, но write barrier добавляет overhead на указатель writes.
- GOGC влияет на частоту циклов

GC выполняется конкурентно, одновременно с потоками мутатора, в точном соответствии с типом (этот принцип также известен как чувствительность к типу), допускается параллельная выполнение нескольких потоков GC. Это конкурентная пометка и очистка (mark-sweep), при которой используется барьер записи (write barrier). При этом в процессе ничего не генерируется и не сжимается. Освобождение памяти выполняется на основе размера, выделенного для каждой программы Р, чтобы в общем случае минимизировать фрагментацию и избежать блокировок.

В основе работы GC Go лежит "трехцветный алгоритм". Использует барьер памяти. Главный принцип алгоритма трехцветной пометки и очистки состоит в разделении объектов, находящихся куче, на три набора, в соответствии с "цветом".  Условно разделяются на 3 цвета:
- черные объекты - гарантированно не имеют указателей на белые объекты;
- серые объекты - могут иметь указатели на белые объекты;
- белые объекты - на них могут ссылаться некоторые серые объекты и сами некоторые белые объекты могут ссылаться на некоторые черные.
Краткий алгоритм:
1. Все объекты сначала белые;
2. Идет перебор "корневых" объектов, помечаются как серые. Корневые - это объекты к которым можно обращаться напрямую, например глобальные переменные, элементы в стеке и т.д.
3. Идет перебор серых объектов, проверяются ссылки на другие объекты и помечаются на черные объекты. Если есть ссылка на белый объект, то белый становится серым.
4. Продолжается до тех пор, пока не будут перебраны все серые объекты.
5. Оставшиеся после перебора белые объекты считаются недостижимыми и занимаемая ими область памяти может быть освобождена.
Есть еще Мутатор - это приложение, работающее во время сборки мусора. Вызывает функцию барьера записи. Выполняется каждый раз, когда меняется указатель в куче. После изменения указателя объект считается достижимым и помечается как серый.

Настройка GOGC задаёт целевой рост heap относительно live objects после GC (100 = heap ~2× live). Выше GOGC — реже GC, больше память; ниже — чаще GC, меньше RSS. Настраивают через env GODEBUG/gogc или runtime debug.SetGCPercent.

- по умолчанию GOGC=100.
- GOMEMLIMIT (Go 1.19+) — soft limit памяти, взаимодействует с GC pacing.
- Смотреть GODEBUG=gctrace=1 для диагностики пауз.

## Чем конкурентность отличается от параллелизма?
**Частота:** 5/84
**Темы:** #go/concurrency #go/scheduler
- [x] Скорректировано ✅ 2026-06-22
- [x] последний повтор ✅ 2026-07-03

Конкурентность — много задач конкурируют за один общий ресурс. Прогресс за счёт чередования (на одном или нескольких ядрах).

Параллелизм — много задач выполняются на многих ресурсах. Одновременное исполнение на CPU на нескольких ядрах; требует `GOMAXPROCS > 1` и независимую работу.

Будет или нет конкурентный код выполняться параллельно зависит от железа (несколько ядер). На одном ядре возможна конкурентность без параллелизма.

- При `GOMAXPROCS = 1` конкурентность есть, параллелизма на CPU — нет.
- I/O-нагрузка: много G ждут сеть/диск — высокая конкурентность при низкой загрузке CPU.
- CPU-нагрузка: параллелизм требует несколько P и достаточно независимых задач.
- Асинхронность (не блокировать вызывающий код) ≠ параллелизм (несколько ядер одновременно).

## Cooperative vs preemptive scheduling в Go?
**Частота:** 10/84
**Темы:** #go/scheduler
- [x] Скорректировано ✅ 2026-06-22
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Кооперативная — горутина сама добровольно отдаёт управление (канал, mutex, syscall, вызов функции). Вытесняющая — планировщик принудительно останавливает горутину.

Go использует **оба механизма**:
- **До 1.14:** чисто кооперативный — yield только на вызовах функций и blocking-операциях. Tight loop без вызовов мог бесконечно держать P.
- **С 1.14+:** добавлено асинхронное вытеснение — sysmon обнаруживает горутину, работающую >10 мс на P, и посылает ОС-сигнал (SIGURG на Linux). Горутина доходит до safepoint и переключается.
- Это **не** OS-style preemption на каждой инструкции (как у pthread) — вытеснение происходит только в safepoint'ах (prologue/epilogue функций, loop back-edges).

`runtime.Gosched()` — добровольная уступка: G уходит в runq, другая G берёт тот же P.

## Work stealing и global queue
**Частота:** 8/84
**Темы:** #go/scheduler
- [x] Скорректировано ✅ 2026-06-29
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Work stealing — механизм балансировки планировщика: когда у P заканчиваются горутины в локальной очереди, он **ворует половину** runnable-горутин из локальной очереди другого P (выбранного случайно). Это избегает простоя процессоров без блокировки на общей очереди.

Глобальная очередь нужна как общий резерв для новых горутин (`go f()`), пробуждённых из syscall/netpoller и для балансировки когда кража не удалась.

**Порядок поиска работы:** локальная runq → кража у случайного P (половина) → глобальная runq → netpoller.

P заглядывает в глобальную очередь периодически (~каждые 61 scheduler tick) и при неудачной краже — чтобы глобальные G не застревали навсегда.

**Подробности:**
- Локальная очередь — lock-free (на одном P), до 256 G. Глобальная — под mutex, медленнее, но позволяет G мигрировать между P.
- После возврата из блокирующего syscall горутина попадает в глобальную очередь — не возвращается на исходный P (тот уже занят другой работой).
- sysmon при дисбалансе может перемещать G между очередями.
- Без work stealing GMP вырождается в N изолированных очередей — одни P загружены, другие простаивают.

## Какие ключевые особенности Golang / недостатки
**Частота:** 7/84
**Темы:** #go/general
- [x] Скорректировано ✅ 2026-06-26
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Go — компилируемый, статически типизированный язык со сборщиком мусора. Ключевые особенности:

- **Простота:** минималистичный синтаксис, низкий порог входа, код читается одинаково у разных разработчиков.
- **Конкурентность:** goroutines (легковесные, ~2 КБ стека) + каналы для коммуникации. Модель CSP — «не разделяй память, общайся».
- **Компиляция:** быстрая, кроссплатформенная, в один нативный бинарник без внешних зависимостей. Статические ошибки на этапе компиляции.
- **Композиция вместо наследования:** embedding структур, неявная реализация интерфейсов (satisfies implicitly) — нет классов и иерархий.
- **Производительность:** близко к C, GC с низкими паузами — Green Tea GC (1.26, по умолчанию) снижает overhead на 10–40%.

**Недостатки:**
- Многословная обработка ошибок: `if err != nil` после каждого вызова, нет try/catch, ошибки легко пропустить.
- Ограниченная stdlib: нет тернарного оператора, нет map/filter/reduce, нет enum (iota — компромисс).
- GC — паузы есть (хоть и низкие), latency-sensitive приложения могут страдать.
- Нет классического ООП: нет наследования, нет перегрузки методов, нет классов.
- До 1.18 не было дженериков — legacy-код без них; текущие дженерики ограничены (нет method generics, нет операторного overloading).

**Подробности:**
- **Неявные интерфейсы** — ключевое отличие от Java/C#: тип реализует интерфейс самим фактом наличия методов, без `implements`. Позволяет писать мок-реализации и оборачивать чужие типы без изменения их кода.
- **Goroutines vs потоки ОС:** горутина стартует с ~2 КБ стека (растёт динамически), поток ОС — ~1 МБ фиксированно. Go runtime мультиплексирует M горутин на N потоков ОС (модель GMP). Каналы — типобезопасная альтернатива shared memory + мьютексам.
- **Компиляция в бинарник:** нет JVM/CLR, нет холодного старта JIT. Для контейнеров — образ FROM scratch с одним бинарником. Кросскомпиляция: `GOOS=linux GOARCH=arm64 go build`.
- **Обработка ошибок:** Go 1.13+ — `%w` для wrapping, `errors.Is`/`errors.As` для unwrapping, `errors.Join` (1.20) для нескольких ошибок, `errors.AsType` (1.26) — типобезопасный дженерик-вариант `As`. Базовая модель (возврат error последним значением) — по-прежнему многословна.
- **iota:** генерирует последовательные целые в `const`-блоке. Не полноценный enum — нет типобезопасности (iota — это просто int), нет итерации по значениям, нет строкового представления.

## Передача и возврат: значение vs указатель? / Value vs pointer receiver
**Частота:** 4/84
**Темы:** #go/pointers #go/memory #go/performance #go/methods

- [x] Скорректировано ✅ 2026-06-27
- [x] последний повтор ✅ 2026-06-27

**Передача в функцию:**
**По значению** — копия аргумента. Дешево для `int`,`pointer`, маленьких struct (до ~few cache lines). Функция не может изменить оригинал (кроме полей-указателей внутри struct).

**По указателю** — общий объект: нужна **мутация**, struct **большой**, или тип **нельзя** копировать (`sync.Mutex`).

Go разрешает вызывать `*T `-метод на value и наоборот (авто `&`/ разыменование), но семантика копирования остаётся.

**Возврат из функции:**
- **По значению** — компилятор часто кладёт на stack или регистры; для маленьких struct это снижает аллокации на кучу и нагрузку на GC.
- **По указателю** — когда возвращаем большой объект, shared state, или явно «optional» через `nil`.
Escape analysis решает stack vs heap — не угадывать, а смотреть ` go build -gcflags="-m"`.

## errors.Is / errors.As / %w?
**Частота:** 3/84
**Темы:** #go/errors
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-30

`%w `в` fmt.Errorf ` сохраняет цепочку ошибок для unwrap.
`errors.Is` проверяет, есть ли в цепочке конкретная sentinel error, 
а `errors.As` достаёт ошибку нужного типа. Это позволяет добавлять контекст к ошибке и не ломать машинную проверку причины.

-`errors.Is(err, target)` проходит по цепочке `Unwrap` и учитывает пользовательский метод `Is`.
-`errors.As(err, &target)` требует указатель на переменную нужного типа и достаёт типизированную ошибку.

sentinel-ошибки удобны для стабильных причин; типизированные ошибки нужны, когда вызывающему коду важны поля.

**Подробности:**
- `net.Error`: `Timeout()` / `Temporary()` (deprecated в новых версиях) — **recoverable** vs fatal; в современном Go — typed errors + `errors.Is`/`As`, wrapping через `%w`.

## Generics vs interfaces?
**Частота:** 4/84
**Темы:** #go/generics #go/interfaces
- [x] Скорректировано ✅ 2026-06-29
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Интерфейсы — runtime-полиморфизм: описывают поведение через method set, позволяют подменять реализацию (`io.Reader`). Generics — compile-time-полиморфизм: type parameters + constraints, позволяют писать типобезопасные контейнеры и алгоритмы без boxing в `any`.

Ключевое отличие: интерфейсы решают «что объект умеет делать» (поведение), дженерики — «с какими типами он работает» (типобезопасная универсальность).

Пример: `Sort[T any]` — нужен дженерик, чтобы слайс остался `[]int`, а не `[]any` с приведением типов. `io.Reader` — нужен интерфейс, чтобы подменять файл на сокет без изменения кода.

**Когда что использовать:**
- **Generics:** контейнеры (стек, кеш, tree), алгоритмы над типами (sort, filter), type-safe API без `any` и reflection.
- **Interfaces:** подмена реализации (БД/mock, файл/сеть), dependency inversion, несколько типов с общим поведением.

**Подробности:**
- Компилятор мономорфизирует generics (stenciling/GC-shape) — нет боксинга, нет виртуального вызова. Интерфейсы — itable + allocation на heap для non-pointer типов.
- `any` (бывший `interface{}`) + type switch — не замена дженерикам: теряется типобезопасность, паника при неверном cast, аллокации.
- Generics в Go 1.18+ — ограничены: нет method generics (нельзя `func (s Stack[V])` где V — type param), нет операторного overloading, constraint только через interface.

## Атомарные операции
**Частота:** 3/84
**Темы:** #go/atomic
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27
- **Атомарная операция** — это операция, которая выполняется за один шаг относительно других горутин. Горутина не может прервать своё выполнение во время такой операции, а кроме этого, другие горутины не могут начать эту же самую операцию. Это похоже на транзакции из темы про базы данных, только у атомарной операции не может быть отката.
- sync/atomic - атомарные операции для целочисленных типов:`int32`,`int64`,`uint32`,` uint64`
- Во всех функциях передаются указатели на числовые значения в которых необходима атомарность
- atomic.AddInt64(&addr, 1) // прибавляем 1
- В пакете `sync/atomic` определены типы-обёртки:`atomic.Bool`,`atomic.Int32`,`atomic.Int64` и так далее. Для начала работы с такими «обёртками» достаточно описать переменную нужного типа, например,`var i atomic.Int64`. Эти типы вместо функций имеют соответствующие методы.

## Мапа потокобезопасная? / конкурентность и типичные сценарии / почему нельзя
**Частота:** 5/84
**Темы:** #go/map #go/data-race
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

Обычная `map`**не потокобезопасна**. **Read-only** из нескольких горутин допустим, если **никто не пишет**. Если **хотя бы одна** горутина пишет — нужен **Mutex** / одна горутина - владелец /`sync.Map`.

| Сценарий                              | Можно?                                                  |
| ------------------------------------- | ------------------------------------------------------- |
| Несколько goroutine **только читают** | да                                                      |
| Хотя бы одна **пишет**                | **нет** — data race / `fatal error: concurrent map ...` |
| Read + write одновременно             | **нет**                                                 |
`concurrent map writes` и `concurrent map read and map write` приводят к fatal error runtime.`recover` от этого не спасает потому что мапа может быть испорчена

-`go test -race` ловит гонки до production.

Почему:  Запись — не атомарная операция: рантайм считает хеш, ищет место, меняет служебные структуры, иногда запускает рост или перенос данных. Проблема в том, что одна горутина может менять структуру таблицы, а другая одновременно читать или писать по устаревшему состоянию.

В реализации есть внутренние флаги/проверки, которые помогают runtime обнаруживать часть таких ошибок, но это не замена race detector.
