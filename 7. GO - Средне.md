## `sync.Map`
**Частота:** 15/86
**Темы:** #go/sync #go/map
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
`sync.Map` — потокобезопасная map из стандартной библиотеки. Не заменяет `map+Mutex` универсально — выигрывает в конкретных сценариях:

- **Много чтений, редкие записи:** ключи записаны один раз, потом только читаются (cache, который в основном растёт).
- **Многоядерные системы (>4 ядер):** lock-free-архитектура раскрывается на высококонкурентных нагрузках — на малом числе ядер `map+RWMutex` часто быстрее.
- **Разные горутины работают с разными наборами ключей:** почти независимый доступ.

В остальных случаях `map[K]V + sync.Mutex`/`RWMutex` проще и типобезопаснее (`sync.Map` работает через `any`).

**Подробности:**
- **Под капотом:** две обычные map — `read` (read-only, доступ без блокировок) и `dirty` (под mutex). Новые ключи пишутся в dirty; при накоплении dirty «промоутится» в read (lock-free read path — ключевое преимущество на многих ядрах).
- **Методы:** `Load`, `Store`, `Delete`, `LoadOrStore`, `LoadAndDelete`, `Range`, `Swap`, `CompareAndSwap`, `CompareAndDelete`, `Clear`. `Range` — callback-based (не `for range`), обходит снапшот на момент вызова.
- **Нет `Len()`:** точный размер «здесь и сейчас» не имеет смысла при конкурентном доступе (устареет к моменту использования). Обходной путь — `Range` (O(n), без строгого снапшота) или atomic-счётчик при `Store`/`Delete`.
- **Не атомарна для multi-key:** составная операция на нескольких ключах (например, перевод между счетами) не потокобезопасна сама по себе — нужен внешний mutex.
- **Не `make`:** нулевое значение готово к использованию, вызов `make` не нужен.

## Как устроено ООП в Go?
**Частота:** 15/86
**Темы:** #go/oop #go/interfaces
- [x] Скорректировано ✅ 2026-06-29
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Go — не классический ООП-язык (нет классов, нет наследования), но реализует ООП-принципы другими средствами:

- **Инкапсуляция:** exported (заглавная буква) / unexported (строчная) — на уровне пакета, не класса. Пакет = единица инкапсуляции.
- **Наследование:** заменено **композицией**. Embedding struct — встраивание одной структуры в другую: поля и методы встроенного типа «промоутятся», но это не subclass (нет виртуальных методов, нет переопределения).
- **Полиморфизм:** через **интерфейсы**. Реализуются неявно (satisfies implicitly) — тип реализует интерфейс самим фактом наличия методов, без `implements`. Зависимость можно держать на стороне потребителя.
- **Абстракция:** struct + methods. Роль «класса» играет struct с привязанными методами.

**Подробности:**
- Embedding vs наследование: нет доступа к приватным полям встроенного типа (инкапсуляция пакета работает), нет dynamic dispatch по «базовому классу», нет цепочек super(). Вызов «метода родителя» — явно: `e.Type.Method()`.
- Интерфейсы — ключевой механизм: `io.Reader` принимает файл, сокет, буфер — без единой строчки `implements`. Позволяет mocking без фреймворков.
- Переиспользование кода: embedding для состояния + интерфейсы для поведения + функции как first-class values.

## `sync.WaitGroup` под капотом
**Частота:** 14/86
**Темы:** #go/sync
- [x] Скорректировано ✅ 2026-06-30
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
`sync.WaitGroup` — примитив ожидания группы горутин. Счётчик: `Add(n)` увеличивает, `Done()` уменьшает, `Wait()` блокируется пока счётчик не 0. Типовой паттерн: `wg.Add(1)` перед запуском, `defer wg.Done()` внутри горутины, `wg.Wait()` в ожидающем коде.

**Под капотом:** основа — `atomic.Int64` (счётчик) + `sema` (внутренний семафор runtime). `Add` атомарно меняет счётчик, `Wait` проверяет счётчик и при ненулевом значении вызывает `runtime_Semacquire` (блокировка). `Done` = `Add(-1)` — когда счётчик доходит до 0, `Add` вызывает `runtime_Semrelease` для всех ожидающих. Не `sync.Mutex`/`sync.Cond` — собственный лёгкий механизм на atomic+sema.

**Самописный аналог:** `atomic.Int64` + `sync.Cond` или `atomic.Int64` + `chan struct{}` (закрытие канала будит всех читателей). Без `sync`-пакета — только atomic + канал.

## Рост capacity слайса / Как работает append?
**Частота:** 14/86
**Темы:** #go/slice
- [x] Скорректировано ✅ 2026-06-28
- [x] последний повтор ✅ 2026-07-03

При превышении cap — выделяется новый массив, происходит копирование элементов, новый указатель записывается в заголовок слайса.

Рост cap
- Append без превышения cap — тот же базовый массив.
- до 256 элементов ~×2
- далее плавный переход к ~×1.25 через хитрые формулы с выравниваниями.

Runtime `nextslicecap`(Go 1.18+)
 `oldCap < 256`— **×2**
`oldCap ≥ 256`— плавный рост к **~×1.25** (`newcap += (newcap + 3×256) / 4`)
`newLen > 2×oldCap`—` newcap = newLen`
cap округляется до **size class** аллокатора — реальный cap может быть чуть больше формулы. Выравнивание памяти с округлением до 1 байта вверх, если размер элемента меньше 8 бит

**Сложность:** один `append`— O(1)
при создании нового базового массива О(n)
серия append по одному — O(1) амортизированно.

**Append в func** до realloc меняются **элементы** в общем базовый массив, **`len` caller** — нет; после realloc новый ptr только внутри func.

Comparable — тип, поддерживающий `==` и `!=`.

**Comparable:** числа, `bool`, `string`, указатели, каналы, интерфейсы (если динамический тип comparable и не nil), struct (если все поля comparable), array (если тип элементов comparable).

## context - что такое, как устроен и зачем использовать?
**Частота:** 14/86
**Темы:** #go/context
- [x] Скорректировано ✅ 2026-06-26
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
`context.Context` — инструмент управления временем жизни операций: отмена, дедлайн, таймаут + передача request-scoped значений. Первый аргумент функции — `ctx context.Context`.

Дерево: `Background()` / `TODO()` — корень → `WithCancel` / `WithTimeout` / `WithDeadline` / `WithValue`. Отмена родителя каскадно отменяет всех потомков.

- `ctx.Done()` — канал, закрывающийся при отмене. Слушать в долгих I/O и worker-циклах: `select { case <-ctx.Done(): return ctx.Err() }`.
- `ctx.Err()` — причина: `context.Canceled` или `context.DeadlineExceeded`.
- **Значения:** только request-scoped метаданные (trace ID, auth claims), не бизнес-данные. Ключ — свой тип, не `string`, во избежание коллизий.
- **Graceful shutdown:** ловим SIGINT/SIGTERM → cancel корневого контекста → все горутины через `<-ctx.Done()` завершаются.
- Тип `Context`— интерфейсный, но обычно не требует определять свою структуру и соответствующие методы
- Для создания пустого контекста можно использовать две функции:`context.Background()` и `context.TODO()`. Обе они возвращают пустой контекст, который не может быть отменён и не содержит никаких свойств. Это, так называемый, **корневой**, или родительский контекст самого верхнего уровня. Он необходим для создания дочерних контекстов с условием.
- Дочерние контексты создаются навешиванием новых условий на родительский контекст.
- Вызывайте функцию `cancel()`, чтобы избежать утечек памяти. Для этого лучше использовать `defer cancel()`. В противном случае сборщик мусора не удалит созданный контекст
- Кроме прослушивания канала `ctx.Done()` есть ещё один способ узнать об отмене контекста — вызвать метод `Err()`, который возвратит ошибку, если контекст отменён. При этом возможны следующие значения ошибки
-`context.Canceled`— контекст отменён вызовом функции ` cancel()`
-`context.DeadlineExceeded`— контекст отменён по истечению времени

## Процесс vs поток / Процессы и потоки могут друг с другом как-то общаться?
**Частота:** 12/86
**Темы:** #go/goroutine #go/scheduler
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Процесс — контейнер с изолированным адресным пространством, памятью и ресурсами (файловые дескрипторы, сокеты). Поток — единица выполнения внутри процесса; все потоки одного процесса делят общую память, но имеют собственные стек и регистры. ОС планирует потоки на ядрах.

Общение: процессы изолированы — нужен **IPC** (сокеты, pipes, shared memory, message queues). Потоки общаются через **общую память** (нужна синхронизация — mutex, atomic). Горутины — ещё легче: один процесс, координация через каналы, mutex, WaitGroup внутри Go runtime.

**Подробности:**
- Создание процесса — дорого (копирование адресного пространства, fork). Потока — дешевле (только стек + регистры). Горутины — ~2 КБ стека, user-space, без участия ядра.
- Типовые IPC в Go: `net` (TCP/Unix sockets), `os/exec` + stdin/stdout, gRPC/HTTP между сервисами, Unix domain sockets для локального IPC.

## Cooperative vs preemptive scheduling в Go?
**Частота:** 11/86
**Темы:** #go/scheduler
- [x] Скорректировано ✅ 2026-06-22
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Кооперативная — горутина сама добровольно отдаёт управление (канал, mutex, syscall, вызов функции). Вытесняющая — планировщик принудительно останавливает горутину.

Go использует **оба механизма**:
- **До 1.14:** чисто кооперативный — yield только на вызовах функций и blocking-операциях. Tight loop без вызовов мог бесконечно держать P.
- **С 1.14+:** добавлено асинхронное вытеснение — sysmon обнаруживает горутину, работающую >10 мс на P, и посылает ОС-сигнал (SIGURG на Linux). Горутина доходит до safepoint и переключается.
- Это **не** OS-style preemption на каждой инструкции (как у pthread) — вытеснение происходит только в safepoint'ах (prologue/epilogue функций, loop back-edges).

`runtime.Gosched()` — добровольная уступка: G уходит в runq, другая G берёт тот же P.

## Stack vs heap — зачем и производительность? / утечка памяти
**Частота:** 12/86
**Темы:** #go/memory
- [x] Скорректировано ✅ 2026-07-03
- [x] последний повтор ✅ 2026-07-03

**Эталон на собесе:**
- **Стек** — LIFO кадр функции, рост/освобождение за O(1), быстрый, но **ограничен по размеру** (растёт при необходимости, но не бесконечен).
- **Куча** — когда escape analysis не может доказать, что значение не «убежит» из scope: указатель наружу, return slice/map, замыкание, interface, большой объект.
- На куче аллокации дороже: GC, heap allocator; на практике **профилировать**, не гадать (`go build -gcflags=-m` для escape). - компилятор проверяет, «убегает» ли значение из scope на heap.
- Идея Go: всё, что может жить на стеке, компилятор оставляет на стеке; остальное — на куче автоматически.

**Утечка памяти** — объекты на куче достижимы, но не нужны (горутина leak, global cache). 
Глубокая **рекурсия** → stack overflow. 
Бесконечный **append** без освобождения → OOM. 
Большая struct по значению vs указатель — копирование vs один объект на heap (escape analysis).

## Системные вызовы (syscall) в Go?
**Частота:** 11/86
**Темы:** #go/scheduler #go/runtime
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Системный вызов — переход из user mode в kernel mode: файловый I/O, часть сетевых операций, таймеры. Для Go критично не само определение, а **как runtime обрабатывает блокирующий syscall без остановки всех горутин**.

При блокирующем syscall горутина паркуется (`entersyscall`), её M (поток ОС) остаётся в kernel, а P (логический процессор) **передаётся другому M** (handoff) — остальные горутины продолжают работу. После возврата из syscall (`exitsyscall`) горутина попадает в очередь (обычно global runq) и позже подхватывается планировщиком.

**Ключевое различие:** сетевой I/O vs дисковый I/O:
- **Сеть:** не блокирует поток — горутина регистрируется в **netpoller** (epoll/kqueue), M освобождается для других горутин.
- **Диск/файлы:** блокирует поток ОС — runtime создаёт дополнительный M (если есть свободный или новый), чтобы P не простаивал. Причина: ОС не предоставляет неблокирующий API для файловых операций (в отличие от сокетов).

**Подробности:**
- **entersyscall / exitsyscall:** runtime-функции, обрамляющие syscall. `entersyscall` открепляет P от M; `exitsyscall` пытается вернуть P обратно, а если P уже занят новым M — G уходит в global runq.
- **Handoff:** когда P освобождается от M, уходящего в блокирующий syscall, планировщик ищет свободный M (из idle-пула) или создаёт новый (`newm`). Максимум потоков — 10 000 по умолчанию (`runtime/debug.SetMaxThreads`).
- **Кооперативная точка:** до Go 1.14 syscall был одной из немногих точек переключения контекста. Сейчас добавлена асинхронная preemption (сигналы ОС), но syscall остаётся важным механизмом.
- **CGO:** вызов C-функции через cgo — тоже блокирующий с точки зрения Go runtime. Похожая механика — M блокируется на C-стеке, P передаётся другому M.

## Что такое generics?
**Частота:** 10/86
**Темы:** #go/generics
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-04

Дженерики — это механизм параметрического полиморфизма, позволяющий писать универсальные функции и типы, работающие с разными типами данных без дублирования кода. Типы задаются через параметры (`T`), которые при необходимости ограничиваются constraints, например `any` или `comparable`. 
Дженерики сохраняют статическую типизацию и позволяют избежать использования `interface{}` там, где нужен типобезопасный универсальный код.
Не заменяют интерфейсы для поведения.


Generics — **Go 1.18+**. Компилятор мономорфизирует (stenciling) или GC shape — не ручная кодогенерация как `go generate`, но похожий эффект «отдельный код на тип».

## Что такое string? / строки vs руны
**Частота:** 12/86
**Темы:** #go/string
- [x] Скорректировано ✅ 2026-06-30
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
`string` — **неизменяемая** последовательность байт (UTF-8). Внутренне — структура из двух полей: указатель на данные + длина. В отличие от слайса, **нет capacity** — строка не может расти на месте.

- `len(s)` — длина в **байтах**, не в символах. Для не-ASCII-символов (кириллица, эмодзи) байт >1 на символ.
- `range s` — итерирует по **рунам** (Unicode code points), `s[i]` — возвращает **byte** по индексу.
- `rune` — псевдоним `int32`, представляет один Unicode code point. `byte` — псевдоним `uint8`.
- **Иммутабельность:** `s[i] = 'x'` — ошибка компиляции. Любая модификация создаёт новую строку.
- Конкатенация `+=` в цикле — **O(n²)** аллокаций. Для эффективной сборки — `strings.Builder`.

**Подробности:**
- **range vs s[i]:** на строке `"hêllo"` — `len(s)` = 6 (h=1, ê=2, l=1, l=1, o=1), но `utf8.RuneCountInString(s)` = 5. `range` даст 5 рун, `s[1]` даст первый байт `ê` (не весь символ).
- **Преобразования:** `[]byte(s)` копирует данные (новая аллокация), `string(b)` тоже копирует. Для zero-copy — `unsafe`, но рискованно (иммутабельность string нарушается если изменить []byte).
- **UTF-8:** переменная длина кодирования — ASCII-символы = 1 байт, кириллица = 2 байта, эмодзи = 4 байта. Go-исходники — UTF-8. Пакет `unicode/utf8` для операций над отдельными рунами.

## Work stealing и global queue
**Частота:** 8/86
**Темы:** #go/scheduler
- [x] Скорректировано ✅ 2026-06-29
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Work stealing — механизм балансировки планировщика: когда у P заканчиваются горутины в локальной очереди, он **ворует половину** runnable-горутин из локальной очереди другого P (выбранного случайно). Это избегает простоя процессоров без блокировки на общей очереди.

Глобальная очередь нужна как общий резерв для новых горутин (`go f()`), пробуждённых из syscall/netpoller и для балансировки когда кража не удалась.

**Порядок поиска работы:** локальная runq → кража у случайного P (половина) → глобальная runq → netpoller.

P заглядывает в глобальную очередь периодически (~каждые 61 scheduler tick) и при неудачной краже — чтобы глобальные G не застревали навсегда.

**Подробности:**
- Локальная очередь — lock-free (на одном P), до 256 G. Глобальная — под mutex, медленнее, но позволяет G мигрировать между P.
- После возврата из блокирующего syscall горутина попадает в глобальную очередь — не возвращается на исходный P (тот уже занят другой работой).
- sysmon при дисбалансе может перемещать G между очередями.
- Без work stealing GMP вырождается в N изолированных очередей — одни P загружены, другие простаивают.

## Что такое O нотация, какая сложность бывает
**Частота:** 10/86
**Темы:** #go/complexity
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Big-O нотация — способ оценки алгоритмической сложности: как растёт количество операций (или памяти) при росте объёма входных данных n. Не зависит от железа и языка. Берётся **наихудший случай** (верхняя граница). Константы отбрасываются: O(2n + 5) = O(n).

Основные классы с Go-примерами:
- **O(1)** — константная: доступ по индексу `s[i]`, по ключу `m[k]`, `len(s)`.
- **O(log n)** — логарифмическая: бинарный поиск, поиск в сбалансированном дереве.
- **O(n)** — линейная: обход слайса/мапы в цикле, поиск в неотсортированном массиве.
- **O(n log n)** — лог-линейная: эффективные сортировки (`sort.Ints` — pattern-defeating quicksort).
- **O(n²)** — квадратичная: вложенные циклы по n, пузырьковая сортировка.
- **O(2ⁿ) / O(n!)** — экспоненциальная / факториальная: полный перебор.

**Подробности:**
- **Временная vs пространственная сложность:** часто trade-off — ускоряем ценой памяти (кеш, map для O(1)-поиска) или экономим память ценой O(n) повторов.
- **Амортизированный анализ:** одна операция может быть O(n) (ресайз map, growth слайса), но в среднем по всем операциям — O(1). Применяется для `append` в слайс, вставки в map, эвакуации.
- **Ω (Omega) vs Θ (Theta) vs o (little-o):** Ω — нижняя граница (лучший случай), Θ — точная (верхняя = нижняя), o — верхняя НЕ точная. На собесах спрашивают редко — O покрывает 95% вопросов.
- **Худший vs средний случай:** quicksort в среднем O(n log n), в худшем (плохой pivot) — O(n²). Go `sort` гарантирует O(n log n) всегда (pattern-defeating quicksort).
- **Практика на собесе:** спрашивают не «расскажи теорию», а «какая сложность у твоего решения» или «сложность доступа в map» — умей считать O() на написанном коде.

## Mutex / RWMutex / Когда Mutex, а когда RWMutex?
**Частота:** 10/86
**Темы:** #go/sync
- [x] Скорректировано ✅ 2026-06-29
- [x] последний повтор ✅ 2026-06-30

**Mutex** — эксклюзивная блокировка: 
- в один момент времени **только одна** горутина выполняет защищённый код. 
- Это убирает гонку при read-modify-write и составных инвариантах на нескольких полях.

**RWMutex** — много параллельных **читателей** **или** один **писатель**. 
- Писатель блокирует всех читателей (приоритет writer);  
- новые читатели не проходят, пока ждёт писатель. 
- при частых записях — читатели могут **голодать**, писатели тоже при постоянном потоке readers.
- Ожидающие горутины ставятся в **FIFO**-очередь семафора; при длинных критических секциях возможен **starvation** — нужны короткие секции и иногда fair lock / отдельная архитектура.
- При частых записях overhead RWMutex не окупается; 

RWMutex имеет те же методы `Lock()` и `Unlock()`, но использовать их нужно только для критической секции, изменяющей данные. Для кода, который читает данные, нужно использовать методы `RLock()` и `RUnlock()`.`RLock()` не даст выполниться `Lock()` и начать изменение данных, пока не будут завершены все операции чтения.

| Состояние                                                             | Метод `RLock()`                                                                                           | Метод `Lock()`                                                                         |
| --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Мьютекс свободен                                                      | Возьмёт мьютекс в режиме чтения                                                                           | Возьмёт мьютекс в режиме записи                                                        |
| Одна горутина уже взяла мьютекс через `RLock()`                       | Возьмёт мьютекс в режиме чтения. Блокировки не будет                                                      | Будет блокировать горутину до тех пор, пока другие горутины не отпустят мьютекс        |
| Одна горутина уже взяла мьютекс через `RLock()`. Вторая ждёт `Lock()` | Будет блокировать горутину до тех пор, пока другая горутина не дождётся метода `Lock()` и не отпустит его | Будет блокировать горутину до тех пор, пока не будут отпущены все остальные блокировки |
| Одна горутина взяла мьютекс через `Lock()`                            | Будет блокировать горутину до тех пор, пока не будут отпущены все блокировки на запись                    | Будет блокировать горутину до тех пор, пока не будут отпущены все остальные блокировки |
При использовании мьютексов нужно обязательно придерживаться трёх основных правил
1. После блокировки мьютекса его всегда нужно разблокировать. Если этого не сделать, другие горутины так и будут ожидать своей очереди на выполнение критической секции.
2. Если вы применяете мьютексы для синхронизации доступа к общим данным, следите за тем, чтобы не было горутин, работающих с этими данными без мьютекса. Например, если значение общей переменной меняется горутинами в двух местах, а мьютекс применяется только в одном, то смысла в этом нет, так как ошибки всё равно будут.
3. В общем случае нужно стремиться сокращать продолжительность выполняемого кода внутри критической секции.

## pprof: CPU, heap, goroutine
**Частота:** 7/86
**Темы:** #go/tooling #go/goroutine
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

**Профайлинг** — измерение, где программа тратит CPU, память и время ожидания. В Go: **`go tool pprof`**,`runtime/pprof`,`net/http/pprof`.

| Профиль                        | Что показывает                | Когда смотреть               |
| ------------------------------ | ----------------------------- | ---------------------------- |
| **CPU**                        | горячие функции, % времени    | «медленно считает»           |
| **heap** (inuse / alloc_space) | живые объекты / все аллокации | утечки, churn GC             |
| **goroutine**                  | стеки, блокировки             | leak, deadlock на chan/mutex |
| **block / mutex**              | где ждут lock/I/O             | contention                   |
Сбор:` go test -cpuprofile cpu.prof -bench .`; в сервисе —` import _ "net/http/pprof"`и` curl localhost:6060/debug/pprof/profile?seconds=30 `.
Разбор:`go tool pprof -http=:8080 cpu.prof`— flame graph, top, graph. Ищем **широкие** полоски в flame graph и функции с большим **flat** + **cum** %.
**Подробности:**
- go tool pprof -http=:8080 cpu.prof — flame graph.
- heap: inuse_objects, alloc_space — утечки и churn.
- горутина: блокировки на канал/mutex.
- Типичный win: убрали лишний `append` в цикле, заменили `fmt.Sprintf` в hot path, шардировали mutex — CPU −30…70% после heap/cpu profile.
- В prod: `import _ "net/http/pprof"` → `/debug/pprof/`; sampling overhead обычно ~2–5% CPU при типичных интервалах.
