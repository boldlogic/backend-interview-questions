## Виды требований: бизнес, пользовательские, функциональные, нефункциональные
**Частота:** 17/13
**Темы:** #sa/requirements

**По литературе:**
Классификация по уровням нужна, чтобы не смешивать «зачем организации», «что делает пользователь» и «что должна делать система» (Вигерс; выжимка Вигерса).

**Бизнес-требования (business requirements)** — *почему* организации нужна система: цели, которых она должна достичь с помощью ПО. Фиксируются в vision and scope, уставе проекта, business case, market requirements. Пример: «Увеличить долю рынка на 10% за счёт запуска мобильного приложения».

**Бизнес-правила** — политики, законы, отраслевые стандарты, алгоритмы расчёта; часто служат источником для функциональных, пользовательских требований и атрибутов качества (Вигерс).

**Пользовательские требования (user requirements)** — цели и задачи, которые пользователи должны иметь возможность выполнить с системой. Формы: Use Case, пользовательские истории, CJM. Пример: «Как покупатель, хочу искать товары по категории, чтобы быстрее находить нужное».

**Функциональные требования** — поведение системы в конкретных ситуациях: что сделать разработчикам, чтобы пользователи выполнили свои задачи *в рамках* бизнес-требований. Обычно в SRS/ТЗ: «Система должна…».

**Нефункциональные:**
- **атрибуты качества** — «как хорошо» система работает (производительность, безопасность, удобство и т.д.);
- **внешние интерфейсы** — взаимодействие с внешним миром;
- **ограничения** — обязательные рамки (стандарты, совместимость).

Отдельно: **системные требования** (к продукту из нескольких подсистем и их интерфейсам) и **требования к проекту** (обучение, инфраструктура, документация) — не то же самое, что требования к продукту (Вигерс). **Переходные** — миграция, обучение, cutover при смене системы.

## Диаграмма классов vs ER-диаграмма
**Частота:** 14/13
**Темы:** #sa

**По литературе:**
Обе моделируют структуру, но с разными целями (UML vs моделирование данных; Вигерс — модель данных в SRS).

**ER-диаграмма** — для проектирования данных/БД: сущности, атрибуты, связи, ключи, кардинальность. Нормализация убирает избыточность и аномалии обновления.

**Диаграмма классов (UML)** — для объектной модели ПО: классы, атрибуты, операции, наследование, ассоциация/агрегация/композиция.

**Бизнес-модель данных vs логическая:** бизнес-модель описывает предметную область без привязки к СУБД; логическая — структуру под конкретную систему (в т.ч. технические поля). Они не обязаны совпадать 1:1.

Пример: если у клиента один телефон, повторяющийся в строках «клиент+продукт», в логической модели телефон — атрибут Client (или сущность Contact), а не атрибут связи «клиент–продукт».

## BPMN vs UML
**Частота:** 13/13
**Темы:** #sa

**По литературе:**
**BPMN** (Business Process Model and Notation) — нотация для описания бизнес-процессов: кто что делает, в каком порядке, какие события и ветвления. Понятна бизнесу и пригодна для анализа/автоматизации процессов (Репин; BPM-CBOK).

**UML** (Unified Modeling Language) — язык моделирования ПО: структура и поведение программной системы (классы, sequence, state, use case и др.).

Правило выбора: сквозной бизнес-процесс и роли организации → BPMN; проектирование ПО (API, состояния объекта, структура кода) → UML. Часто используют вместе: BPMN для процесса, UML sequence/class для реализации.

## BPMN: основные элементы нотации
**Частота:** 13/13
**Темы:** #sa/bpmn #sa/modeling

**По литературе:**
BPMN — стандарт моделирования бизнес-процессов (Репин; BPM-CBOK). Перед детализацией фиксируют границы процесса, стартовые и завершающие события.

Основные элементы:
- **События:** стартовое, промежуточное, конечное (таймер, сообщение, ошибка и др.).
- **Задачи:** атомарная работа (пользовательская, сервисная, ручная, бизнес-правило, скрипт).
- **Шлюзы:** Exclusive (XOR) — один путь; Parallel (AND) — все ветки; Inclusive (OR) — один или несколько; Event-based — выбор по событию.
- **Потоки:** sequence flow внутри пула; message flow между пулами.
- **Пул / дорожки:** пул — участник (организация/система); дорожки — роли (не ФИО).
- **Подпроцесс** — сворачивает фрагмент для читаемости и повторного использования.

Практика: не перегружать схему (дробить на подпроцессы); для TO-BE отдельно согласовывать изменения относительно AS-IS.

## UML: основные диаграммы
**Частота:** 12/13
**Темы:** #sa/uml #sa/modeling

**По литературе:**
UML — язык моделирования программных систем. Делятся на структурные и поведенческие.

**Структурные:** классы; компоненты; развёртывание (deployment).

**Поведенческие (часто у СА):**
- **Sequence** — сообщения во времени (API, асинхронные вызовы).
- **Activity** — поток работ внутри системы.
- **State** — жизненный цикл объекта (заказ: Новый → Оплачен → …).
- **Use Case** — акторы и цели на верхнем уровне.

Выбор: взаимодействие во времени → sequence; поток работ → activity; состояния → state; контекст → use case; структура данных/кода → class + ER.

## Способы выявления требований
**Частота:** 11/13
**Темы:** #sa/requirements

**По литературе:**
Цель elicitation — понять потребности заказчика и пользователей, отделяя проблему от готового решения (Вигерс; BABOK: elicitation and collaboration).

Типичные техники:
- **Интервью** — открытые вопросы, «5 почему», уточнение классов пользователей.
- **Воркшопы / фасилитация** — согласование нескольких сторон, снятие противоречий.
- **Наблюдение (job shadowing)** — реальная работа пользователя, скрытые шаги.
- **Анализ документации и существующих систем** — регламенты, логи, схема БД, конкуренты.
- **Прототипирование** — уточнение через макеты.
- **Опросы / анкеты** — массовый сбор при большом числе стейкхолдеров.

После выявления: анализ (группировка, конфликты), спецификация (User Stories / Use Cases / SRS), проверка и согласование. Не заполнять пробелы «молча» без фиксации assumptions (Вигерс).

**Частота:** 9/13
**Темы:** #sa/artifacts

**По литературе:**
Документация даёт единый источник правды для команды и заказчика (Вигерс: SRS; BABOK: требования и модели; профстандарт СА — фиксация и согласование требований).

## Agile: Scrum и Kanban для аналитика
**Частота:** 8/13
**Темы:** #sa/agile

**По литературе:**
В agile требования уточняются итерационно, а не «раз и навсегда в финальной спецификации» (Вигерс об agile; практики Scrum/Kanban).

**Scrum:** спринты; SA грумит бэклог, декомпозирует, пишет AC, проверяет DoR на планировании, снимает блокеры по требованиям, участвует в review/retro.

**Kanban:** непрерывный поток; SA держит ready-очередь, учитывает WIP, смотрит cycle time.

Приоритизация многократная, с обратной связью после демо. Аналитик готовит к реализации ближайший горизонт, а не весь проект вперёд.

## DoD и DoR — Definition of Done / Definition of Ready
**Частота:** 7/13
**Темы:** #sa #agile

**По литературе:**
Соглашения agile-команды о качестве входа и выхода работы (Scrum Guide / командные практики).

- **DoR (Ready):** стори достаточно ясна для взятия в работу — описание, AC, зависимости, нужные макеты/данные.
- **DoD (Done):** единый для команды стандарт готовности — код, тесты, ревью, деплой/документация по договорённости.

DoR ≠ AC: AC — критерии конкретной стори; DoR/DoD — процессные Definition'ы команды.

## Use cases — как пишутся
**Частота:** 7/13
**Темы:** #sa

**По литературе:**
**Use Case** — описание взаимодействия актора с системой для достижения цели; обычно формальнее User Story и включает альтернативы (Вигерс; UML).

Структура:
- **Название и цель**
- **Primary / secondary actors**
- **Предусловия / постусловия**
- **Основной сценарий (happy path)** — пошагово
- **Альтернативы и исключения**
- Связи **include / extend** при декомпозиции

На диаграмме Use Case: актор — человечек, прецедент — овал. UC стыкуется с пользовательскими требованиями; детализация сценариев питает функциональные требования в SRS.

## User Story и критерии приёмки
**Частота:** 7/13
**Темы:** #sa/requirements #sa/agile

**По литературе:**
**User Story** — краткое описание ценности с точки зрения роли: «Как [роль], я хочу [действие], чтобы [ценность]». Это приглашение к обсуждению, а не полная спецификация всех веток (Вигерс; agile-практика).

**Acceptance Criteria** — измеримые условия готовности конкретной стори. Формат Given/When/Then удобен для тестируемости. Не путать с **DoD**: AC — у стори; DoD — общий стандарт команды.

**INVEST:** Independent, Negotiable, Valuable, Estimable, Small, Testable. Желательно сравнимый приоритет относительно других историй.

## Валидация и верификация требований
**Частота:** 7/13
**Темы:** #sa/requirements

**По литературе:**
Два разных вида проверки (инженерия требований / Вигерс):

**Верификация** — «правильно ли мы описали / спроектировали?» Соответствует ли артефакт правилам, стандартам, критериям качества. Инструменты: ревью SRS с разработкой и QA, чек-листы полноты (в т.ч. NFR), трассируемость, проверка ID и форматов.

**Валидация** — «то ли мы делаем?» Решает ли решение реальную проблему стейкхолдеров. Инструменты: демо прототипов, UAT, обратная связь с пользователями.

Можно провалить валидацию при идеальной верификации: SRS безупречен, но не закрывает боль. Верификация — соответствие документированным требованиям; валидация — соответствие нуждам заказчика/пользователя.

## Оценка качества требований
**Частота:** 6/13
**Темы:** #sa/requirements

**По литературе:**
Качественное требование пригодно для реализации и проверки (Вигерс; Guide for Writing Requirements). Базовые свойства:

- **Полнота** — входы/выходы, предусловия, ограничения, NFR; нет дыр.
- **Однозначность** — одна интерпретация; «должна», а не «может»; словарь терминов.
- **Непротиворечивость** — нет конфликтов с другими требованиями.
- **Атомарность** — одно требование = одна проверяемая мысль.
- **Проверяемость** — есть объективный критерий/тест; не «удобный интерфейс».
- **Реализуемость** — в рамках бюджета, сроков, стека.
- **Трассируемость** — связь с бизнес-целью / пользовательской потребностью.
- **Актуальность** — устаревшее помечено или удалено.

Ссылка «как в системе X» допустима только если эталон актуален и прослеживается. Практика: чек-лист при ревью спецификации перед передачей в разработку.

## Переходные требования
**Частота:** 6/13
**Темы:** #sa

**По литературе:**
По Вигерсу рядом с требованиями к продукту идут **требования к проекту** и переходные аспекты: обучение, документация, инфраструктурные изменения. На практике к **переходным (transition)** относят всё для перехода AS-IS → TO-BE без срыва сервиса:

- миграция и конвертация данных;
- параллельная работа со старой системой / dual-run;
- обучение пользователей и инструкции;
- cutover-план, критерии готовности, откат;
- временные интеграции и ручные обходные процедуры.

Пример: замена CRM — выгрузка клиентской базы, двойной ввод на переходный период, инструкции для операторов, план отката.

## Пример нефункционального требования
**Частота:** 6/13
**Темы:** #sa/requirements #sa/nfr

**По литературе:**
Нефункциональные требования описывают *как хорошо* система работает и в каких рамках, а не *что* она делает (Вигерс: атрибуты качества, внешние интерфейсы, ограничения). Их нужно выявлять до проектирования: нагрузка и безопасность закладываются в архитектуру.

Категории с измеримыми формулировками:
- **Производительность:** «Среднее время отклика API ≤ 200 мс при 1000 RPS».
- **Безопасность:** «Пароли — bcrypt, трафик — HTTPS, 2FA для администраторов».
- **Доступность:** «99.9% в месяц (простой ≤ ~43 мин)».
- **Масштабируемость:** «Горизонтальное масштабирование, stateless-сервисы».
- **Юзабилити:** «Целевое действие ≤ 3 шага для нового пользователя».
- **Регуляторные / ограничения:** GDPR, совместимость со стандартами.

Правило: не «быстро», а число + условие нагрузки/контекста. Атрибуты качества часто становятся источником функциональных требований (Вигерс).

## User Story — примеры и отличие от Use Case
**Частота:** 5/13
**Темы:** #sa

**По литературе:**
Оба описывают потребность пользователя, но на разной глубине (Вигерс).

**User Story** — upper-level: роль + желание + ценность; планирование и приоритизация бэклога. Пример: «Как покупатель, хочу оплатить заказ картой, чтобы не вводить реквизиты каждый раз».

**Use Case** — детальный сценарий: актор, предусловия, шаги, альтернативы, постусловия. Пример: UC «Оплата заказа» с веткой «карта отклонена».

Правило: Story — что/зачем для планирования; UC — как/что если для проектирования. Одна Story может развернуться в несколько UC.

## Роль системного аналитика в SDLC
**Частота:** 5/13
**Темы:** #sa/roles

**По литературе:**
По профстандарту «Системный аналитик» цель вида деятельности — разработка, восстановление и сопровождение требований к ПО/системе на протяжении жизненного цикла. SA проходит потребность через цикл до работающего функционала.

- **Требования:** выявление, AS-IS, scope, приоритизация (протоколы, глоссарий, story map, BPMN).
- **Проектирование:** спецификации, UML/BPMN/ER, API-контракты, NFR, трассировка.
- **Разработка:** уточнения, снятие неопределённости, эскалация конфликтов.
- **Тестирование:** опора на AC, разбор «баг или фича», участие в приёмке.
- **Внедрение/сопровождение:** переходные требования, актуализация документации.

## Скрытые и неопределённые требования
**Частота:** 5/13
**Темы:** #sa/requirements

**По литературе:**
**Скрытые** — стейкхолдер считает «очевидным» и не сказал (неявные ожидания, неписаные бизнес-правила). **Неопределённые** — размытые формулировки («удобно», «быстро») без метрик (Вигерс: однозначность и полнота).

Как работать: уточняющие техники elicitation (5 почему, JTBD, наблюдение, прототип); критерии приёмки с числами; явные assumptions в спецификации; риск-лог «не уточнено → решение по умолчанию X». Не закрывать пробелы молча без фиксации.

**Частота:** 5/13
**Темы:** #sa/artifacts

**По литературе:**
Типовые разделы SRS / ТЗ на сервис (Вигерс: шаблон SRS; ISO/IEC 29148 как ориентир):

- цель и **scope** (in/out);
- глоссарий;
- акторы / роли / классы пользователей;
- функциональные требования с ID;
- NFR (SLA, RPS, безопасность, ограничения);
- модель данных / ER;
- API-контракты (OpenAPI);
- интеграции (потоки, ошибки, retry);
- сценарии (US/UC, sequence);
- критерии приёмки;
- assumptions и ограничения;
- переходные требования (миграция, обучение).

ГОСТ 34 — формальная структура для гос/АС-заказчиков (отдельная карточка).

## Этапы SDLC: что знает системный аналитик
**Частота:** 5/13
**Темы:** #sa/roles #sa/sdlc

**По литературе:**
Типичная цепочка жизненного цикла ПО/системы:

**идея → требования (формализация) → проектирование → разработка → тестирование → релиз → сопровождение → вывод из эксплуатации.**

## JWT: Access и Refresh токены
**Частота:** 8/13
**Темы:** #sa #security #api

**По литературе:**
**JWT** — компактный самодостаточный токен (header.payload.signature) с claims (sub, exp, roles/scopes). Сервер проверяет подпись; часто используется как access token в OAuth2/OIDC (проектирование API / практики безопасности).

**Access** — короткий TTL, Authorization: Bearer. **Refresh** — длинный TTL, хранится осторожнее; обмен на новый access без повторного логина; при компромете — revoke/rotate.

JWT ≠ обязательно OAuth2; OAuth2/OIDC часто *выдают* JWT как access token.

## Sequence: асинхронное взаимодействие и зацикленность
**Частота:** 4/13
**Темы:** #sa

**По литературе:**
На sequence-диаграмме UML различают синхронные и асинхронные сообщения.

- **Синхронный вызов** — сплошная стрелка с закрашенным наконечником; lifeline ждёт return.
- **Асинхронный** — открытая стрелка; инициатор не ждёт завершения (очередь, событие, callback).
- **Return** — пунктир назад.

Комбинированные фрагменты: **alt** (взаимоисключающие ветки), **opt**, **loop**, **par**, **break**. Пример: alt «оплата успешна» / «карта отклонена» между фронтом, API и платёжным шлюзом.

«Зацикленность» на схеме снимают явными условиями выхода в loop/break и разнесением async-обработки на отдельные сообщения/участников.

## Границы системы и scope фичи
**Частота:** 4/13
**Темы:** #sa/scope

**По литературе:**
Границы фиксируют до детализации, иначе расползается scope (Вигерс: vision and scope; контекстная диаграмма).

**Системная граница** — что «наша система», что внешний мир (акторы, смежные системы, потоки данных).

**Scope релиза/фичи** — явный список in scope / out of scope.

Зачем: защита от scope creep; учёт ownership и SLA внешних систем; понятный объём оценки. Если внешний сервис недоступен 2 часа, нельзя обещать 99.9% uptime «как будто всё наше».

## Чем отличается бизнес-аналитик от системного аналитика?
**Частота:** 4/13
**Темы:** #sa/roles

**По литературе:**
Обе роли работают с требованиями, но на разных уровнях (BABOK vs фокус профстандарта СА на требованиях к системе).

**BA** — «вширь»: бизнес-цели, стейкхолдеры, pain points, бизнес-кейс. Отвечает на «почему». Артефакты: vision, business case, high-level требования.

**СА** — «вглубь» к системе: функции, интеграции, данные, API, модели. Отвечает на «как именно система должна себя вести». Артефакты: SRS, UML/BPMN/ER, спецификации интерфейсов.

BA: «нужно повысить конверсию до 15%». СА: «форма регистрации валидирует email через внешний сервис за ≤ 500 мс». В небольших командах роли совмещают.

## Методы приоритизации (RICE / ICE / MoSCoW)
**Частота:** 2/13
**Темы:** #sa #prioritization

**По литературе:**
До выбора метода учитывают срочность, зависимости, ценность для пользователя (BABOK; продуктовые практики). Категория «функ/нефунк» сама по себе приоритет не задаёт.

**MoSCoW:** Must / Should / Could / Won't — быстрое согласование со стейкхолдерами.

**RICE:** (Reach × Impact × Confidence) / Effort — количественный скоринг потока гипотез.

**ICE:** Impact × Confidence × Ease — упрощённый RICE.

Запрос одного заказчика: зафиксировать, сопоставить с vision/roadmap/OKR, MoSCoW, зависимостями и рисками; при необходимости эскалация владельцу продукта с вариантами «сейчас / отложить / отказать». Часто: MoSCoW наверху → RICE внутри Must.

## Приоритизация требований и MVP
**Частота:** 2/13
**Темы:** #sa/scope #sa/requirements

**По литературе:**
Ресурсы ограничены — выбирают, что делать сейчас (Вигерс; BABOK: prioritize requirements).

## Управление требованиями и версионирование
**Частота:** 2/13
**Темы:** #sa/requirements

**По литературе:**
Требования живут и меняются; без управления версиями команда работает по устаревшим артефактам (Вигерс: requirements management).

Практика:
- **Единый источник правды** — спецификация/реестр, а не «правда в чатах».
- **Версии и changelog** — что изменилось, почему, кто согласовал.

Инструменты вторичны (Confluence/Jira/Git); первична дисциплина фиксации изменений.

## Чем отличается бизнес-требование от пользовательского?
**Частота:** 2/13
**Темы:** #sa/requirements

**По литературе:**
Разница — в уровне и адресате (Вигерс).

**Бизнес-требования** — верхний уровень, *зачем* организации нужна система (цели, KPI, vision/scope). Адресат: заказчик, топ-менеджмент. Пример: «Увеличить онлайн-продажи на 30% за год».

**Пользовательские требования** — *что* пользователь должен уметь сделать с ПО. Формы: User Story, Use Case. Адресат: команда разработки. Пример: «Как покупатель, хочу видеть историю заказов, чтобы повторить покупку».

Пользовательские требования выводятся из бизнес-целей; если связь с бизнес-требованием не прослеживается, требование под вопросом (трассировка, Вигерс).

## AS-IS и TO-BE: зачем и когда
**Частота:** 1/13
**Темы:** #sa/bpmn #sa/process

**По литературе:**
Ключевой приём процессного анализа (BPM-CBOK; Репин).

**AS-IS** — как есть: реальные шаги, роли, задержки, ручной труд, pain points.

**TO-BE** — как должно быть после изменений; согласовывается с бизнесом до детальной реализации.

**Gap-анализ** — что добавить/убрать/изменить; из gap формируют требования и оценку объёма.

Нужны при изменении процессов, замене legacy, автоматизации. Для greenfield AS-IS может отсутствовать — сразу TO-BE.

## C4-диаграммы — уровни моделирования архитектуры
**Частота:** 1/13
**Темы:** #sa #architecture

**По литературе:**
Модель C4 (Simon Brown) упрощает разговор об архитектуре со стейкхолдерами:

- **C1 Context** — система и внешние акторы;
- **C2 Container** — приложения, БД, брокеры;
- **C3 Component** — компоненты внутри контейнера;
- **C4 Code** — классы (редко рисуют).

Меньше условных обозначений, чем «полный UML». **Функциональная схема архитектуры** в корпоративных тестах — другой артефакт: набор функций по назначению системы, не топология контейнеров.

## Матрица трассировки требований
**Частота:** 1/13
**Темы:** #sa/requirements #sa/traceability

**По литературе:**
**Трассировка** — отслеживание связей между уровнями требований и артефактами реализации (Вигерс; BABOK). Функциональные и NFR выводятся из бизнес-требований и трассируются к задачам, бизнес-правилам, тест-кейсам, вариантам решения.

**Зачем:** происхождение требований; покрытие; **impact analysis** при изменении. Не заменяет приоритизацию и не является главным инструментом оценки стоимости.

Матрица: бизнес → пользовательское → функциональное → тест-кейс / задача. При удалении ненужного бизнес-требования можно снять связанные детальные (Вигерс).

## User Story и Use Case — примеры для кейса банка
**Частота:** 0/13
**Темы:** #sa

**По литературе:**
Кейс: открытие расчётного счёта юрлица (формат как у Вигерса: user level → сценарий).

- **User Story:** «Как директор компании, я хочу заполнить заявку на РКО, чтобы открыть расчётный счёт в банке».
- **Use Case «Открытие РС»:** актор — директор; основной поток — форма → проверки (ФНС, МВД) → скоринг → договор → подписание → открытие счёта; альтернативы — отказ по проверкам, дозапрос документов.

Story задаёт ценность; UC фиксирует проверяемые ветки для разработки и QA.

## Анализ и синтез
**Частота:** 0/13
**Темы:** #sa

**По литературе:**
Парные приёмы системного мышления (системная инженерия / аналитическая практика).

**Анализ** — разложение целого на части («из чего состоит?»): модули, данные, пользователи, интеграции.

**Синтез** — сборка частей с учётом связей («как работает вместе?»): из требований — архитектура и scope релиза.

Ошибка — только дробить или только рисовать схемы без проверки потребностей. Цикл: анализ потребностей → синтез решения → показ стейкхолдерам → уточнение.

## Бизнес-процесс — определение
**Частота:** 0/13
**Темы:** #sa

**По литературе:**
**Бизнес-процесс** — устойчивая последовательность действий, преобразующая входы в результат, ценный для клиента или организации (BPM-CBOK; Репин). Примеры: обработка заказа, открытие счёта, найм.

При описании фиксируют:
- границы (триггер и результат / стартовые и завершающие события);
- участников (роли, системы);
- шаги, ветвления, параллельность;
- входы/выходы (данные, документы);
- метрики (время, стоимость, ошибки).

Моделируют в BPMN. AS-IS — текущее с проблемами; TO-BE — целевое после оптимизации.

## Хеширование и целостность данных
**Частота:** 0/13
**Темы:** #sa #security

**По литературе:**
**Хеширование** — преобразование данных в значение фиксированной длины, однозначно связанное с входом для проверки.

Передача/хранение хеша по доверенному каналу позволяет проверить **целостность** (не изменились ли данные) и факт соответствия ожидаемому содержимому. Для паролей используют медленные KDF (bcrypt/argon2), не «голый» быстрый хеш.
