## Виды требований: бизнес, пользовательские, функциональные, нефункциональные
**Частота:** 30/41
**Темы:** #sa/requirements

Классификация требований разделяет уровни и типы.

**Бизнес-требования** отвечают на вопрос, почему организации нужна система (цели). Их фиксируют в vision and scope, уставе, business case, market requirements.

**Бизнес-правила** — политики, законы, стандарты, алгоритмы; они служат источником для бизнес-, пользовательских и функциональных требований, а также для атрибутов качества.

**Пользовательские требования** описывают цели и задачи пользователей и оформляются как Use Case и пользовательские истории.

**Функциональные требования** задают поведение системы, чтобы пользователи выполнили задачи в рамках бизнес-требований; обычно попадают в SRS.

**Нефункциональные требования** включают атрибуты качества («как хорошо»), внешние интерфейсы и ограничения. Отдельно выделяют **системные требования** — для нескольких подсистем и интерфейсов между ними.

**Требования к проекту** относятся не к продукту, а к обучению, документации, инфраструктуре и т.п. **Переходные требования** (термин BABOK) описывают переход к будущему состоянию.

## Способы выявления требований
**Частота:** 25/41
**Темы:** #sa/requirements

Методы выявления требований включают:

1. **Интервью** — контакт, рамки проекта, активное слушание, заранее подготовленные вопросы и модели; после встречи — summary/протокол; ловить субъектность заказчика.
2. **Семинары** — правила, роли (ведущий/секретарь), повестка, границы, лимит дискуссий; состав до ~5 человек.
3. **Фокус-группы** — представители классов пользователей.
4. **Наблюдение** (активное/пассивное) — ловит детали, которые пользователи считают очевидными; выход в поля показывает скрытые процессы, о которых не скажет топ-менеджмент; риск «игры на камеру».
5. **Опросные листы** — при большом числе пользователей; опрос нужно грамотно составить и протестировать.
6. **Анализ системных интерфейсов** — в т.ч. по контекстным диаграммам / экокартам.
7. **Анализ пользовательского интерфейса** — по существующему ПО, которое меняют/заменяют.
8. **Анализ документов** — руководства, SRS, процессы, стандарты, отчёты о проблемах (риск — устаревание).

Область elicitation and collaboration (BABOK) описывает выбор техник выявления (наблюдение, прототипы и др.). Предположения не закрывать «молча» — фиксировать (валидация).

**Event Storming:** визуализация через доменные события на стикерах, часто 4–6 часов; фокус на событиях («что произошло»), не на командах; много участников → хаос.

## BPMN: основные элементы нотации
**Частота:** 23/41
**Темы:** #sa/bpmn #sa/modeling

BPMN — нотация и модель бизнес-процессов; используется и для описания/анализа, и в BPMS для исполняемых процессов. Сначала — контекст, границы, стартовые и завершающие события.

Основные элементы:
- **Пул и дорожки** — рамка процесса; дорожки в терминах ролей/должностей, *не* по фамилии.
- **События** — стартовые (в т.ч. таймер), завершающие (в т.ч. termination), промежуточные.
- **Шлюзы** — в т.ч. эксклюзивный (исключающее «ИЛИ»); плюс параллельные/другие операторы логики по BPMN.
- **Задачи/операции** на схеме.

Message flow — между участниками (свернутые пулы как «чёрные ящики»). Подпроцессы — для читаемости. Не перегружать одну диаграмму.

**Токен** — маркер текущего шага процесса; на параллельном шлюзе может «клонироваться». «Проигрывайте» токен в голове, ища тупики.

**Happy Path** — идеальный сценарий; **Unhappy** — отказы и исключения (часто большая часть логики). Не оставлять Unhappy только разработчикам.

**Исполняемый BPMN** (Camunda и аналоги): схема в engine реально ведёт процесс. Не перегружать бизнес-схему скриптами — технические детали через делегаты/сервисные задачи.

## UML Sequence Diagram для интеграций
**Частота:** 19/41
**Темы:** #sa/uml #sa/modeling #integration

На sequence слева направо — участники (Front, Back, DB, Kafka…). Синхронный вызов — сплошная линия со сплошной стрелкой (ждём ответ); асинхронный — сплошная с открытой стрелкой (не ждём); ответ — пунктир.

Пример: фронт ждёт API (sync); бэк публикует в Kafka (async). Неверные стрелки вводят в заблуждение про блокировку потоков.

Фреймы: alt (if/else), loop, ref (вынести кусок на другую диаграмму). Если alt занимает полстраницы — в ref.

## UML: основные диаграммы
**Частота:** 18/41
**Темы:** #sa/uml #sa/modeling

UML — унифицированный графический язык моделирования: описание, визуализация, проектирование и документирование объектно-ориентированных систем. Словарь — графические элементы с фиксированной семантикой: модель, нарисованная одним человеком, однозначно читается другим (и инструментом). Отсюда же возможность кодогенерации «заготовки» из модели при наличии CASE-инструмента.

Диаграмма — графическое представление куска модели как связного графа (вершины и рёбра с семантикой). Нотация — набор символов и правил, как ими обозначать понятия и связи (в т.ч. ассоциации, кратности). Метамодель — «схема для схем»: что считается синтаксически правильной UML-моделью.

Структурные: class (классы, атрибуты, операции, связи); object (снимок экземпляров); component; deployment (узлы и артефакты); package; реже composite structure / profile. Поведенческие: use case (акторы и прецеденты — «что делает система» для заказчика); activity (поток работ / параллельность); state machine (жизненный цикл объекта); взаимодействие — sequence (по времени), communication (по связям + номера сообщений); реже timing / interaction overview.

Эвристика для СА: сообщения во времени → sequence; бизнес-процесс с ролями → BPMN (или activity); состояния сущности → state; цели/роли → use case; структура кода/ООП → class; данные/PK-FK → ER (рядом, не вместо UML).

## User Story — примеры и отличие от Use Case
**Частота:** 15/41
**Темы:** #sa

**User Story** — короткий формат для разговора и бэклога; **Use Case** — сценарии взаимодействия (основной поток и альтернативы) без описания «как» реализовывать.

Пользовательские требования оформляют как Use Case и/или пользовательские истории: UC детализирует взаимодействие и ведёт к функциональным требованиям; в Agile истории живут в бэклоге под управлением Product Owner.

Рабочее различие уровней: Story кратко фиксирует что/зачем для планирования; UC раскрывает сценарии, альтернативы и исключения. Одна Story может развернуться в несколько UC. Примеры оплаты картой используют как иллюстрации формата.

## Use cases — как пишутся
**Частота:** 14/41
**Темы:** #sa

**Use Case** описывает взаимодействие акторов с системой. На диаграмме UML Use Case применяют include/extend; в текстовом описании — pre/post-условия, happy path, альтернативы и исключения.

В инженерии требований use cases — способ выразить требования заинтересованных сторон на уровне взаимодействия.

Связка с BDD: UC и стори детализируют сценарии; BDD-сценарии в формате «Дано / Когда / Тогда» дают проверяемые примеры поведения. Внутри UC не размещают UI-дизайн и словарь данных.

## Оценка качества требований
**Частота:** 14/41
**Темы:** #sa/requirements

Качество требований оценивают по набору свойств: завершённость, атомарность, недвусмысленность / однозначность, проверяемость / тестируемость, полнота, корректность, понятность, независимость, необходимость, согласованность, краткость, выполнимость, приоритезируемость. На собесе часто достаточно SMART. Формулировки — «должна», не «может»; полезен словарь терминов. Каждое положение должно быть идентифицируемо; у требований — атрибуты вроде приоритета. Вместо «быстро» — «≤ 2 с при …»; на ревью — чек-лист.

По **INVEST** на собесе часто отдельно: разбить «комбо» на атомарные (не «регистрирует и открывает счёт»); проверяемость («≤ 200 мс», не «быстро»); непротиворечивость — кейс «лягушата» (конфликтующие правила → матрица решений / уточнение стейкхолдера).

## Идентификация, аутентификация и авторизация
**Частота:** 12/41
**Темы:** #sa #security

Идентификация — «кто ты?» (логин, заявление личности). Аутентификация — «докажи» (пароль, OTP, биометрия, сертификат). Авторизация — «что тебе можно?» (роли, права, политики).

Пример: вход по биометрии — аутентификация; доступ к просмотру счёта — авторизация. Можно пройти authn и не иметь прав ни на что.

Для СА: права проверять на бэкенде, не только скрывать кнопки на UI. Не путать 401 (нет/невалидна аутентификация) и 403 (аутентифицирован, но нет прав).

## JWT: Access и Refresh токены
**Частота:** 10/41
**Темы:** #sa #security #api

**OAuth 2.0** и **OpenID Connect** задают доступ к API через токен (заголовок `Authorization: Bearer`). OAuth 2.0 сам по себе не описывает, *как* пользователь аутентифицируется — для этого рядом OIDC.

- **Access** — короткий TTL, в каждом запросе к API;
- **Refresh** — длиннее, обмен на новый access без повторного логина; хранить осторожнее; revoke/rotate при компромете;
- **JWT** — компактный signed token из трёх частей `header.payload.signature` (Base64URL, через `.`):
  - **header** — `alg` (HS256/RS256…), `typ: JWT`;
  - **payload** — claims: стандартные (`iss`, `sub`, `exp`, `aud`…) + custom (roles, tenant);
  - **signature** — HMAC/RSA по `base64(header).base64(payload)` + secret/private key — проверка целостности и подлинности.

OAuth2 ≠ «всегда JWT»; JWT часто проверяют подписью без серверной сессии. Payload JWT читается (Base64), подпись нельзя подделать без ключа — **не класть секреты/пароли** в токен. В требованиях: что в токене, TTL, куда кладём refresh, что при истечении.

## Как оцениваете трудоёмкость задач (SA)
**Частота:** 10/41
**Темы:** #sa #soft-skills

Оценку начинают с декомпозиции, затем согласуют с разработкой (story points или часы) и закладывают буфер на уточнения и риски. Оценивать «в одиночку в вакууме» нельзя; после grooming оценку пересматривают.

Planning poker и экспертная оценка полезны, чтобы мерить **сложность**, а не абстрактные часы: расхождение «1 день vs неделя» обычно значит, что в головах разный объём работы.

Для R&D и неопределённости точный срок на исследование не обещают. Отделяют spike с фиксированным timebox (результат — дока или выбранный вариант) от задачи на реализацию.

## Диаграмма классов vs ER-диаграмма
**Частота:** 9/41
**Темы:** #sa

Предметное моделирование описывает сущности, атрибуты, связи 1:1 / 1:N / M:N — «карту» бизнеса (товар, заказ, покупатель).

**ERD** — та же идея под данные/БД (PK/FK).  
**UML Class** — под ООП (операции, наследование). UML Class — для логики кода (методы); ER — для данных; не смешивать уровни в одну «универсальную» схему.

На уровне аналитика (DDD):
- **Ubiquitous Language** — один словарь в глоссарии, сторях, ERD (не «клиент» vs «buyer» вперемешку);
- **Bounded Context** — «Заказ» в Продажах ≠ «Заказ» в Бухгалтерии; разные модели, связь через id/событие, не одна гигантская ERD на всё.

Бизнес-модель vs логическая под систему не обязаны совпадать 1:1. Телефон клиента — атрибут Client/Contact, не атрибут связи «клиент–товар».

На **физическом** ER обязательны: таблицы, колонки, типы (в т.ч. JSONB), PK/FK, обязательность (**NOT NULL**). Пропуск FK и индексов — частый пробел.

## DoD и DoR — Definition of Done / Definition of Ready
**Частота:** 7/41
**Темы:** #sa #agile

Командные agile-соглашения. DoD проекта и Acceptance Criteria рядом, но это разные вещи:

- **AC** — критерии *конкретной* фичи/стори (соответствует ли ПО SRS/целям).
- **DoD** — общий «что значит готово» для команды/релиза (код, тесты, ревью, выкат, документация — как договорились). Пример: «функционал прошёл проверки / интегрирован в продукт»; или: в master, тесты пройдены, документация обновлена — как договорилась команда.
- **DoR** — стори готова к взятию в спринт: описание, AC, зависимости, макеты/данные. Пример: есть макеты и API-контракт.

Путаница DoD↔AC — частая; держать оба явными. Без DoR разработка уходит в недели уточнений.

## SSO (Single Sign-On)
**Частота:** 7/41
**Темы:** #sa #security

Один вход у IdP → доступ к нескольким приложениям. Рядом по смыслу с OIDC из книги веб-API (аутентификация поверх OAuth 2.0); SAML — типичный enterprise-вариант SSO (в SA-учебниках vault отдельно не разобран).

Плюсы: UX, централизованный revoke. Минусы: IdP как SPOF; нужна политика сессий. Для СА: кто IdP, какой протокол, что в assertion/token, как отзываем доступ.

## Виды документации системного аналитика
**Частота:** 7/41
**Темы:** #sa/artifacts

Системный аналитик ведёт разные виды артефактов.

**Спеки:** SRS; BRD/vision-scope (назначение, глоссарий, FR/MR/UR, DoD+AC); спеки с ID.

**Глоссарий / Ubiquitous Language:** фиксировать термины, чтобы бизнес и разработка говорили одинаково.

**Модели:** C4 L1 / контекст; BPMN; sequence; ER/class **по контекстам**, не «одна ERD на весь банк».

**Интеграции:** OpenAPI, схемы сообщений.  
**Качество:** матрица трассировки; измеримые формулировки.

**Impact Map** — полезный артефакт приоритизации (не замена SRS).

Задачи можно вести в Markdown.

## Конфликт с разработчиком по задаче
**Частота:** 7/41
**Темы:** #sa #soft-skills

Если разработчик считает задачу «глупой» — не переходить на личности. Выяснить: техническое ограничение, риск или несогласие с бизнес-логикой.

Шаги: факты и критерии → показать ценность/риск для бизнеса → предложить альтернативу (упростить scope, вынести в техдолг, spike) → при тупике эскалировать с зафиксированными рисками. Пример: «не хочу 10 валидаций на фронте» → что ломается без них, что можно на бэке, что в MVP.

## Пример нефункционального требования
**Частота:** 7/41
**Темы:** #sa/requirements #sa/nfr

NFR — атрибуты качества, внешние интерфейсы, ограничения. Формулируют измеримо и заранее — иначе дорого «прикручивать» архитектуру.

Категории с примерами (адаптировать под свой SLA):
- **Performance:** «до 500 RPS, среднее время отклика ≤ 2 с» / «P95 ≤ 500 мс при 500 RPS»;
- **Security:** HTTPS; пароли хешированы; 2FA для админов; rate limit неудачных логинов;
- **Availability / SLA:** 99.5–99.9%; RTO/RPO при необходимости;
- **Scalability:** горизонтальное масштабирование;
- **Usability:** «оформление ≤ 3 клика»;
- **Регуляции:** GDPR — право на удаление ПДн.

SMART + связь с бизнесом: зачем бизнесу именно этот порог (Чёрная пятница → нагрузка). **RPS** оценивать по **пику**, не по среднему; закладывать запас (×2–×3). NFR задают архитектуру — поднимать рано, не перед релизом.

## Валидация и верификация требований
**Частота:** 6/41
**Темы:** #sa/requirements

**Верификация** — требования и дизайны определены правильно и пригодны к использованию: внутренняя согласованность и целостность внутри уровня и между уровнями абстракции («согласовано и цельно написано»).

**Валидация** — соответствие бизнес-требованиям и нужной пользе (в том числе переходным требованиям): свидетельства, что формальные требования соответствуют **неформальным нуждам** стейкхолдеров («то, что нужно людям»).

Уровни абстракции прослеживают связи «удовлетворяет / удовлетворяется».

## Скорость или качество? (SA)
**Частота:** 6/41
**Темы:** #sa #soft-skills

Выбор между скоростью и качеством — trade-off по контексту. Для MVP допустима скорость с явным tech debt; для регуляторики и платежей — качество и жёсткий DoD. Нужно заранее согласовать минимальный уровень качества и дату; при конфликте — эскалация с зафиксированными рисками.

В ядре и платежах приоритет у качества и DoD; в промо и проверке гипотез — у скорости MVP. Если постоянно выбирать только MVP, копится техдолг: в долгосроке качество и есть скорость.

## Маскирование и шифрование данных
**Частота:** 5/41
**Темы:** #sa #security

Маскирование — скрытие ПДн в UI/логах/тестах (показ ****1234); 
данные могут храниться иначе. Шифрование — обратимое сокрытие: симметричное (один ключ) / асимметричное (пара ключей); для трафика — TLS.

В требованиях: что маскируем (логи, админки, выгрузки), где шифруем at-rest / in-transit, кто держит ключи. Не путать маскирование с хешированием паролей (хеш — для проверки, не для расшифровки).

## Этапы SDLC: что знает системный аналитик
**Частота:** 5/41
**Темы:** #sa/roles #sa/sdlc

Типичные этапы ЖЦ разработки:

1. **Initiation** — идея, цель, стоит ли инвестировать.
2. **Requirements Analysis** — сбор функ/NFR от заказчиков и пользователей.
3. **Design** — архитектура, технологии, интерфейсы, модели.
4. **Implementation** — код и интеграция компонентов.
5. **Testing** — поиск и исправление дефектов.
6. **Deployment** — выкат в prod.
7. **Maintenance** — поддержка, новые требования, развитие.

Waterfall идёт строго по этапам; Agile те же смыслы повторяет итерациями. СА сильнее на анализе и проектировании; на тесте/внедрении — уточнения, приёмка, переходные требования (BABOK).

**SDLC** — этапы создания (анализ → дизайн → код → тест → релиз). **LCA / ЖЦ ПО** шире: ещё эксплуатация, поддержка и **вывод из эксплуатации**. Вывод критичен: миграция данных, отключение интеграций, очистка ресурсов; иначе «мёртвые» системы едят бюджет и дают уязвимости. Документируйте не только «как включить», но и «как выключить без потерь».

## User Story и критерии приёмки
**Частота:** 4/41
**Темы:** #sa/requirements #sa/agile

User Story — форма пользовательских требований в Agile (под PO). Формат: «Как [роль], хочу…, чтобы…». Критерии приёмки — соответствие SRS/целям.

**BDD / спецификация на примерах:** сценарии на естественном языке → исполняемая спецификация; шаги **Дано… Когда… Тогда…** (Given/When/Then); таблицы примеров для нескольких кейсов в одном сценарии. Сценарий понятен бизнесу и автоматизируется.

**INVEST** — качество истории. **AC ≠ DoD**: AC у стори; DoD — стандарт команды. AC писать так, чтобы QA превратил их в чек-лист. Аналитик — «вратарь» **DoR**: сырые задачи без макетов/контракта/AC в спринт не пускать.

## Чем отличается бизнес-аналитик от системного аналитика?
**Частота:** 4/41
**Темы:** #sa/roles

**BA — «почему?» и ценность.** Проблемы, цели (SMART/OKR), as-is→to-be, бизнес-кейс. Инструменты: Vision, stakeholder map, **Impact Mapping** (цель→акторы→impacts→фичи). Общение «вширь». BA проектирует бизнес-систему и «боли» стейкхолдеров; держит связь фич с целью.

**СА — «как система это сделает?»** Модули, данные, функ/NFR, интеграции, detailed SRS, UML/BPMN/ER. Общение «вглубь» с разработкой/архитектором. SA переводит требования на язык системы (API, данные, взаимодействие компонентов); отвечает за реализуемость и контракты.

Пример: BA — потребность в автоплатежах ЖКХ; SA — как биллинг дергает уведомления и какой контракт/JSON уходит в хранилище.

В малых командах совмещают. Часто SA доделывает сырые бизнес-требования. На собесе позиционируйтесь как «мостик»: ценность (зачем) и реализация (как).

## Границы системы и scope фичи
**Частота:** 3/41
**Темы:** #sa/scope

Границы системы задают через vision and scope: не слишком узкие и не слишком широкие, с явными исключениями «чего не будет» и контекстными диаграммами.

**C4 L1** фиксирует, что за система, кто пользуется и как она связана со средой — рамка системной границы.

**Impact Mapping** оставляет только deliverables, которые ведут к Goal через Actors и Impacts — лишний scope отсекается раньше.

На практике релиза явно фиксируют in / out of scope; SLA внешних систем влияет на обещания uptime.

## Декомпозиция задач / User Stories
**Частота:** 3/41
**Темы:** #sa #requirements

Истории — форма пользовательских требований в Agile. Иерархия: Epic → Story → задачи.

- Story: роль → действие → цель.
- Размер — в спринт; INVEST.
- Не «толстое ТЗ на год»: детали ближе к реализации, на grooming.

Декомпозиция в СА — разбиение сложного на управляемые части до уровня, где компонент можно оценить и реализовать относительно независимо. Пример: «Кредит наличными» → анкета → скоринг → резервирование → выдача. Слишком мелкая нарезка плодит сущности и усложняет архитектуру.

## Роль системного аналитика в SDLC
**Частота:** 3/41
**Темы:** #sa/roles

По профстандарту аналитик разрабатывает, восстанавливает и сопровождает требования к системе на протяжении жизненного цикла. Роль по этапам:

- **Requirements:** интервью, AS-IS, список функций и NFR, приоритизация.
- **Design:** декомпозиция, спецификации, UML / BPMN / ER, API, согласование NFR.
- **Implementation:** уточнения «на лету», эскалация конфликтов.
- **Testing:** опора на AC, разбор «баг или фича», приёмка.
- **Deployment / Maintenance:** переходные требования, актуализация документации.

Артефакты растут от протоколов и story map к SRS, диаграммам и матрице трассировки.

## Структура требований к API-методу

**Темы:** #sa/api #sa/artifacts

API — контракт вызова. В спеке метода обычно фиксируют:

- назначение и связь с US / FR;
- вход (тип, обязательность), выход;
- коды ошибок;
- авторизацию (Bearer / OAuth и т.п.);

- примеры request / response.

В контексте фичи рядом идут scope, FR с ID, NFR, модель данных и сценарии — как в SRS (в т.ч. примеры FR-AUTH / PERF / SEC-AUTH).

## AS-IS и TO-BE: зачем и когда
**Частота:** 2/41
**Темы:** #sa/bpmn #sa/process

Модели **AS-IS** («как есть») и **TO-BE** («как будет») описывают текущий и целевой процесс; без границ и событий схема расползается.

Бизнес-аналитик изучает as-is и проектирует to-be; gap между ними даёт требования и оценку.

Модели нужны при замене legacy и автоматизации. На greenfield часто сразу строят TO-BE.

## Как писал спецификации
**Частота:** 2/41
**Темы:** #sa #documentation

Типовой конвейер: истории/UC → функциональные требования/SRS; отдельно интерфейсы и данные. Для продуктовых задач: цели/макеты → stories+AC → поведение UI и источники данных → API-контракт. Для интеграционных: sequence + схема сообщений + ошибки/SLA. Спеки версионируют и держат в одном источнике правды (baseline, changelog, impact-анализ изменений).

## Как системный аналитик помогает проектировать архитектуру?
**Частота:** 2/41
**Темы:** #sa/roles #sa/architecture

В TOGAF четыре домена: **бизнес-архитектура** (стратегия, оргструктура, ключевые процессы); **данные**; **приложения** (связь с процессами); **техническая** (инфраструктура, сети, стандарты). СА чаще всего наполняет вход для бизнес/данных/приложений: цели, процессы, сущности, интеграции, NFR — не рисует всю tech-архитектуру вместо инфраструктурного архитектора.

СА передаёт архитектору: цели/приоритеты (OKR), Impact Map (зачем фичи), функ/NFR, интеграции, границы (C4 L1), **контексты** и контракты между ними (события/API), не «одну ERD на всё».

СА — «что должна делать система и в каких рамках»; архитектор — «как построить». Вопросы: выдержит ли NFR? где source of truth?

Высокая связанность МС (лезем в чужие БД) → «распределённый монолит». Владение данными + общение через API/брокер. Миграция с монолита: **Strangler Fig** — выносить по кускам, с планом синхронизации данных. Границы — по доменам/Bounded Context; искать «швы» процессов.

## Логические задачи на собесе (SA)
**Частота:** 2/41
**Темы:** #sa #soft-skills

Проверяют ясность мышления и работу с противоречиями, не «угадай ответ».

Классика «лягушата» (непротиворечивость требований): А — «зелёные лягушки плавают»; Б — «грустные сидят на берегу». Что делает зелёная грустная? Требования конфликтуют — нужны приоритет, уточнение у стейкхолдера или матрица решений / таблица истинности.

На собесе: проговорить допущения, разложить условия, предложить, как зафиксировать в ТЗ.

## Методы приоритизации (RICE / ICE / MoSCoW)
**Частота:** 2/41
**Темы:** #sa #prioritization

Приоритизация нужна из-за ограниченных ресурсов и Time-to-Market: отделить базу от «приятно иметь», обеспечить прозрачность «почему так» и **пересматривать** приоритеты.

Сначала задают цели SMART / OKR и/или Impact Map (Goal → Actors → Impacts → Deliverables), затем применяют методы ранжирования.

**MoSCoW** — Must / Should / Could / Won’t; минус — всё тянут в Must.

**Kano** — Basic / Performance / Excitement.

**RICE** — (Reach × Impact × Confidence) / Effort. Пример: (1000 × 3 × 0.8) / 20 = 120.

**ICE** — та же идея без Reach.

Частая схема: MoSCoW наверху → внутри Must порядок через RICE → Kano для «вау».

## Переходные требования
**Частота:** 2/41
**Темы:** #sa

В BABOK отдельно выделяют **переходные требования** (рядом с требованиями заинтересованных сторон и требованиями к решению): они нужны, чтобы перейти к будущему состоянию, и поддерживаются на протяжении изменений.

Близкий пласт — **требования к проекту** (не к продукту): обучение персонала, пользовательская и поддержковая документация, инфраструктурные изменения и т.п.

В переходный пакет обычно входят: миграция данных, dual-run / параллель со старой системой, обучение, cutover и откат, временные обходные процедуры. Пример замены CRM: выгрузка базы, двойной ввод, инструкции операторам, план отката.

## Приоритизация требований и MVP
**Частота:** 2/41
**Темы:** #sa/scope #sa/requirements

Ресурсы конечны — выбирают, что делать сейчас.

Без целей и метрик фичи превращаются в «набор хотелок»:
- **SMART:** Specific, Measurable, Achievable, Relevant, Time-bound.
- **OKR:** вдохновляющий Objective + 2–5 измеримых Key Results.

**Impact Mapping:** Goal → Actors → Impacts → Deliverables — зачем → кто влияет → какое поведение нужно → какие фичи это дают. Фича без связи с целью — кандидат на выкидывание; удобно приоритизировать по критичности impact.

**MVP** — минимальный Must-набор для проверки ценности / Time-to-Market (пример: каталог + корзина + оплата).

Методы: MoSCoW / RICE / Kano. Аналитик фиксирует in / out of scope и цену изменений.

**HADI** (продуктовая рамка экспериментов): Hypothesis → Action → Data → Insight.

## Чем отличается бизнес-требование от пользовательского?
**Частота:** 2/41
**Темы:** #sa/requirements

Разница — в уровне и адресате.

**Бизнес-требования** — верхний уровень: *зачем* организации нужна система (цели, KPI, vision / scope). Адресат — заказчик, топ-менеджмент. Пример: «Увеличить онлайн-продажи на 30% за год».

**Пользовательские требования** — *что* пользователь должен уметь сделать с ПО. Формы: User Story, Use Case. Адресат — команда разработки. Пример: «Как покупатель, хочу видеть историю заказов, чтобы повторить покупку».

Пользовательские требования выводятся из бизнес-целей; если связь с бизнес-требованием не прослеживается, требование под вопросом (трассировка).

## BPMN: события
**Частота:** 1/41
**Темы:** #sa/bpmn #sa/modeling

Без границ и **стартовых / завершающих событий** схема BPMN расползается. События ≠ входы / выходы: они задают условия запуска, продолжения и остановки.

- **Стартовые** — инициируют процесс (в т.ч. неопределённое; таймер «ежедневно 10:00» — абсолютный / относительный).
- **Завершающие** — в т.ч. **termination** (чёрный кружок): обрывает остальные ветки.
- **Промежуточные** — по ходу процесса (message, timer и др.).

На собесе часто ловят ошибки «нет завершающего события» и «сигнал от промежуточных событий-сообщений передан неверно».

---

## BPMN: шлюзы
**Частота:** 1/41
**Темы:** #sa/bpmn #sa/modeling

Шлюзы в BPMN — операторы логики (развилка / маршрутизатор).

- **Исключающее ИЛИ (XOR / exclusive)** — после операции процесс идёт **по одной** из альтернативных веток (ошибки → возврат и т.п.). Пустой маркер внутри = тоже XOR. Шлюз может и **разделять**, и **объединять** потоки; удобно подписывать вопросом и стрелки ответами.
- **И (AND / parallel)** — маркер «плюс»: ветки идут **параллельно**; слияние ждёт **все** входящие.
- **Event-Based Gateway** («исключающее ИЛИ по событиям») — ожидание **первого** из событий (ответ vs таймер).

Типичная ошибка на разборе схем — **перепутаны исключающий и параллельный** шлюзы.

## BRD vs SRS
**Частота:** 1/41
**Темы:** #sa/artifacts #sa/requirements

**BRD** фиксирует бизнес-требования и решение «зачем / для бизнеса» (инициация / идея): цель проекта, бизнес-ценность, scope на уровне бизнеса, стейкхолдеры.

**SRS** — спецификация требований к ПО: FR / NFR, зависимости, модель данных, допущения, ограничения, критерии приёмки (этап планирования / детализации).

Различие уровней: BRD ≈ бизнес / стейкхолдеры; SRS ≈ система / реализация.

## C4-диаграммы — уровни моделирования архитектуры
**Частота:** 1/41
**Темы:** #sa #architecture

C4 (Simon Brown) — иерархия «карт» архитектуры со сменой масштаба.

| Уровень | Что видно | Зачем |
|--------|-----------|--------|
| **L1 System Context** | Система + пользователи + внешние системы | Рамки: что за система, кто пользуется, что снаружи |
| **L2 Containers** | Приложения, БД, файловые хранилища, шины… | Форма архитектуры и ключевые технологии; куда писать код |
| **L3 Components** | Компоненты внутри контейнера | Zoom, если нужно |
| **L4 Code** | Классы | Обычно из IDE; редко рисуют вручную |

Рекомендация: всегда L1–L2; L3 — по необходимости; L4 — редко. Цель нотации — единый язык, слабые ограничения, свои нормы команды. Для аналитика **Context + Container** — базовый минимум: кто кого вызывает. Не начинать с уровня Code.

**Функциональная схема** в корпоративных тестах — про функции системы для бизнеса, не топология C4.

## FR vs NFR: в чём отличие
**Частота:** 1/41
**Темы:** #sa/requirements

- **FR** — особенности/функции, которые нужно реализовать: **что** система делает в определённых условиях (поведение). Чек-лист действий и правил; должны быть проверяемы тест-кейсом; не забывать **негативные** сценарии («СМС не пришло»). Аудитория — разработка.
- **NFR** — свойство/ограничение, которым система должна обладать: **как** работает (качество, внешние интерфейсы, ограничения). Категории: performance, security, usability…; формулируют **измеримо**. «Красиво/удобно» без метрики — плохой NFR. Аудитория — архитектор/DevOps.

## Scrum: мероприятия (ceremonies)
**Частота:** 1/41

В Scrum спринты длятся 1–4 недели, в конце — **демо** инкремента. Аналитик грумит бэклог, пишет AC, проверяет DoR, участвует в **review / retro**.

## Sequence: асинхронное взаимодействие и зацикленность
**Частота:** 1/41
**Темы:** #sa

В UML sequence различают синхронные и асинхронные сообщения (разный вид стрелок); return рисуют пунктиром. Комбинированные фрагменты: **alt**, **opt**, **loop**, **par**, **break**.

Параллельность на sequence — combined fragment с оператором **par**; порядок сообщений на одной lifeline фиксирован (в отличие от «свободного» порядка между разными lifeline в пределах par).

Для «зацикленности»: явные условия выхода в loop / break; async-обработку не рисуют как бесконечное ожидание на той же синхронной стрелке.

## Sequence: фреймы alt / opt / loop
**Частота:** 1/41
**Темы:** #sa/uml #sa/modeling

На UML sequence **combined fragments** задают операторами:

- **alt** — взаимоисключающие операнды (ветки if / else).
- **opt** — один опциональный фрагмент (не путать с alt).
- **loop** — цикл; нужны явные условия выхода.
- Также: **par** (параллельность; порядок на одной lifeline фиксирован), **break**, **ref**.

## Матрица трассировки требований
**Частота:** 1/41
**Темы:** #sa/requirements #sa/traceability

## Опыт работы с XSD
**Частота:** 1/41
**Темы:** #sa #integration

XSD (XML Schema) — язык описания структуры XML: словарь имён, модель содержания, типы данных. Для СА это контракт данных интеграции: что обязательно, типы, ограничения, namespaces.

Vs DTD: XSD сам на XML; умеет типы (не только «строка»); можно подключать несколько схем; лучше документируется. DTD — старый синтаксис, слабее по типам, обычно одна схема на документ.

well-formed — синтаксически корректный XML (один корень, закрытые теги, правильная вложенность). valid — ещё и соответствует схеме (XSD/DTD). Где встречается: SOAP/WSDL, отраслевые XML. Рядом — JSON Schema для REST. Валидация сообщения = проверка против схемы до бизнес-логики.

## Постановка интеграции: что описать
**Частота:** 1/41
**Темы:** #sa/artifacts #integration

В постановку интеграции обычно входят: протокол и endpoint / очередь; направление; формат (JSON / XML + схема / XSD / JSON Schema); маппинг полей; ошибки / ретраи; идемпотентность; SLA; безопасность; версионирование.

## Стейкхолдеры: кто это и зачем
**Частота:** 1/41
**Темы:** #sa #stakeholders

Стейкхолдеры — классы пользователей продукта и **другие заинтересованные лица**; у них есть профили, интересы могут **противоречить**, при согласовании у каждой стороны свои критерии (клиент / разработка / тест / руководство). Планируют вовлечение; ведут список / карту / персоны заинтересованных сторон.

По профстандарту: сбор запросов заинтересованных лиц, согласование, консультирование.

## Управление требованиями и версионирование
**Частота:** 1/41
**Темы:** #sa/requirements

Управление требованиями включает снимок на итерации, изменения с оценкой влияния, связи и статусы.

Управление изменениями: зафиксировать предложение → оценить влияние (связи «вниз» к системным / функциональным требованиям и уже сделанному) → принять / отклонить (комитет) → выбрать момент внедрения (сейчас / следующая версия). Практика: один источник правды; changelog; impact → утверждение → обновление FR / тестов.

## BPMN vs UML
**Частота:** 0/41
**Темы:** #sa

**BPMN** — единый язык бизнес- и техспециалистов; путь к BPMS / автоматизации. Элементы: события, задачи, шлюзы, пулы / дорожки, message flow.

**UML Activity** — поток логики / алгоритма; проще и менее «процессный», чем BPMN; меньше типов шлюзов.

**UML в целом** — структура и поведение ПО (class, sequence, state, use case).

Правило выбора: много отделов, сообщения, ручные и авто шаги → BPMN; быстро показать логику сценария → Activity; для API / состояний объекта → sequence / state.

### CRM и ERP: статус заказа для поддержки
**Частота:** 0/41
**Темы:** #sa #integration

В событийных системах применяют **CQRS** (команды / запись отдельно от запросов / чтения), **поток событий как общий источник истины** и слабую связанность при нескольких потребителях состояния.

Стык CRM ↔ ERP:

- master статуса — ERP / OMS; CRM **не дублирует** master, а читает / проецирует;
- sync API, если нужен свежий ответ; иначе события смены статуса → read-model в CRM;
- anti-corruption / маппинг статусов на стыке bounded contexts;
- в требованиях: кто master, SLA свежести, формат события.

### REST: комментарии к заказам (сквозной кейс)
**Частота:** 0/41
**Темы:** #sa #api #database

Учебный сквозной кейс предметного моделирования:

- сущности: Order, Comment (author, text, created_at), связь 1:N;
- API: `GET/POST /orders/{id}/comments` (+ auth, пагинация);
- индекс `(order_id, created_at)`;
- AC/BDD: Given заказ существует When пользователь добавляет комментарий Then он виден в списке…

План: требования → ER + OpenAPI → UI → back/front → QA.

## UML Class: виды отношений
**Частота:** 0/41
**Темы:** #sa/uml #sa/modeling

На диаграмме классов: Generalization (наследование, is-a) — подтип — частный случай супертипа; любой экземпляр подтипа есть и экземпляр супертипа (пример: «Табурет» является «Мебелью»). Realization — класс/компонент реализует поведение, заданное интерфейсом или абстракцией («Кровать» реализует «Мебель для сна»). Association — объекты связаны так, что можно навигировать от одного к другому; общий случай агрегации/композиции; связь можно именовать («Студент» —учится в→ «Университет»). Aggregation — целое–часть «по ссылке»: часть может жить без целого (студенты без конкретной группы ещё существуют). Composition — жёсткая зависимость жизни: уничтожили целое → уничтожили части (факультет без университета не живёт). Dependency — слабое использование: изменение спецификации поставщика может затронуть клиента, наоборот не обязательно (расписание зависит от списка предметов).

Кратность (мультипликатор) на конце связи: 0..1 — ноль или один; 1 — ровно один; 0..* / * — ноль или больше; 1..* — один или больше. Vs ER: class ближе к ООП (операции, наследование); ER — к данным/PK-FK.

## Use Case-диаграмма: элементы
**Частота:** 0/41
**Темы:** #sa/uml #sa/modeling

Элементы Use Case-диаграммы:

- **Actor** — множество логически связанных ролей при взаимодействии с прецедентами; человек, роль или **внешняя система**.
- **Use Case** — аспект поведения с точки зрения пользователя: **что** выполняется, не **как**.
- **Association** — связь актор ↔ прецедент.
- **Include** — общая функциональность, включаемая в другие UC.
- **Extend** — опциональное дополнение основного направления.
- Граница системы — рамка, отделяющая «нашу» систему от акторов.

По схеме ролей видно, какая роль с какими прецедентами связана.

## Авторизация — проверка прав
**Частота:** 0/41
**Темы:** #sa #security

Различают три уровня:

- **Идентификация** — «кто я» (логин, subject);
- **Аутентификация** — проверка личности (пароль, MFA, токен);
- **Авторизация** — право на действие (RBAC/ABAC, scopes). Доступ к API через OAuth 2.0 / Bearer.

Примеры формулировок: при успехе — `access_token`; при неверной паре — `INVALID_CREDENTIALS`; лимит неудачных попыток → `TOO_MANY_ATTEMPTS`.

Скрытие кнопок на UI ≠ авторизация. Проверка прав — на сервере; иначе прямой вызов API обойдёт UI.

## Анализ и синтез
**Частота:** 0/41
**Темы:** #sa

Пара «разобрать → собрать»:

- **анализ** — разбор: цели, акторы, сущности, контексты, NFR;
- **синтез** — Impact Map, scope, модели по bounded contexts, спецификация.

В DDD не смешивать понятия разных контекстов в одну модель (антипаттерн «большой шар грязи»).

**Анализ компонентов** — свойства и поведение частей по отдельности (после декомпозиции). Риск: упустить эффекты только от взаимодействия.

**Синтез** — сборка частей в целую систему (метафора конструктора): проверить, что контракты стыкуются. Пример: auth + счета + платёжный шлюз → «перевод по телефону».

## Бизнес-процесс — определение
**Частота:** 0/41
**Темы:** #sa

**Бизнес-процесс** — устойчивая, целенаправленная совокупность взаимосвязанных видов деятельности, которая по определенной технологии преобразует входы в выходы, представляющие ценность для потребителя. Входы и выходы — информационные и материальные потоки. До схемы задают контекст и границы; отдельно — инициирующие и завершающие события.

Управление охватывает сквозные процессы и модели «как есть» / «как будет».

При описании фиксируют: границы и события, участников (роли / дорожки, не ФИО), шаги и шлюзы, входы / выходы, метрики.

## Внутренний и внешний продукт
**Частота:** 0/41
**Темы:** #sa #product

Внутренний и внешний продукт различаются аудиторией: сотрудники компании vs клиенты рынка. Практики анализа те же (пользователи, потребности, качество), меняются стейкхолдеры и метрики успеха.

Рядом по смыслу стоит пара **проект vs продукт**: проект ограничен сроком и бюджетом («сделали и отдали»), продукт развивается непрерывно по метрикам. В продукте требования часто меняются «на лету», из‑за чего устаревает документация. В проекте акцент на Scope, в продукте — на Time-to-Market.

## ГОСТ 19 vs ГОСТ 34
**Частота:** 0/41
**Темы:** #sa #artifacts #gost

При структуризации спецификации опираются на стандарты **ГОСТ 34 / 19**, BABOK, ISO/IEC 29148.

- **ГОСТ 34** — комплекс стандартов на **автоматизированные системы** (АС): стадии, ТЗ и комплект проектной документации. В Guide for Writing Requirements (INCOSE, рус.) в списке — ГОСТ 34.003-90, 34.601-90; на практике часто всплывает 34.602 — сверять по актуальному тексту. Типичен для гос- / АС-заказчиков.
- **ГОСТ 19** — **ЕСПД** (единая система программной документации): комплект документов именно на **программное изделие**, не на АС в целом.

В продуктовой разработке чаще внутренний SRS / wiki; различие на собесе — **область применения** (АС vs программная документация).

## Джун vs сеньор системный аналитик
**Частота:** 0/41
**Темы:** #sa #career #soft-skills

Профстандарт «Системный аналитик» задаёт обобщённые трудовые функции по уровням:

- **A** — должности вроде «младший системный аналитик / стажёр»: протоколы, сбор из заданных источников, обработка под контролем старшего, интервью пользователей **под руководством**.

## Конфликт требований от стейкхолдеров
**Частота:** 0/41
**Темы:** #sa

Конфликты требований — нормальная часть анализа: разные и противоречивые потребности стейкхолдеров всплывают при валидации; нужны вовлечение заинтересованных лиц и согласование.

- Зафиксировать варианты письменно: плюсы, минусы, затраты, риски — без выбора «стороны» заранее.
- Сравнить с общими целями продукта и согласованным vision.
- Решение на фактах: коллегиально или эскалация (PO / владелец), не «кто громче».
- Типичный конфликт scope / сроков между бизнесом и разработкой — аналитик формализует trade-off и последствия.

## Постановка: что описать для UI
**Частота:** 0/41
**Темы:** #sa/artifacts #ui

В SRS раздел **пользовательские интерфейсы** — требования к внешнему виду и поведению; пример NFR — адаптивный дизайн на ПК/планшет/смартфон. Анализ пользовательского интерфейса делают в т.ч. по существующему ПО при замене; в UC **не** пихать дизайн и словарь данных — UI отдельно.

Прототипы/wireframes/mockups — способ уточнить требования «пощупав» идею. **Быстрое (выбрасываемое)** прототипирование — проверка гипотезы. **Эволюционное** — макет, который доводят до продукта. Явно маркировать статус: бизнес иначе примет прототип за готовую систему.

В постановке обычно: экраны и состояния, поля и валидации, действия, сообщения об ошибках, права, пустые состояния, ссылка на макет.

## Продукт vs проект
**Частота:** 0/41
**Темы:** #sa #product

Проект — конечные срок/бюджет/цель («сделали и отдали»). Продукт — непрерывное развитие, метрики, смена требований. В продукте важнее Time-to-Market; в проекте — Scope. Риск продукта — устаревание документации «на лету».

## Хеширование и целостность данных
**Частота:** 0/41
**Темы:** #sa #security

В NFR безопасности формулируют конкретно — HTTPS, хеширование паролей, защита от XSS / SQL — не «обеспечить безопасность» одной фразой.

**Хеш** — значение фиксированной длины от данных; при изменении входа хеш другой → проверка **целостности**. Хеш передают / хранят по доверенному каналу для сверки. Для паролей — медленные KDF (bcrypt / argon2) + salt, не «голый» MD5 / SHA как пароль.
