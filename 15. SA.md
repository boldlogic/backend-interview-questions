## Виды требований: бизнес, пользовательские, функциональные, нефункциональные
**Частота:** 17/13
**Темы:** #sa/requirements

**По литературе:**
Классификация по выжимке Вигерса (уровни и типы требований):

**Бизнес-требования** — почему организации нужна система (цели). Фиксируются в vision and scope, уставе, business case, market requirements.

**Бизнес-правила** — политики, законы, стандарты, алгоритмы; источник для бизнес-/пользовательских/функциональных требований и атрибутов качества.

**Пользовательские требования** — цели и задачи пользователей; Use Case и пользовательские истории.

**Функциональные** — поведение системы, чтобы пользователи выполнили задачи в рамках бизнес-требований; обычно в SRS.

**Нефункциональные у Вигерса:** атрибуты качества («как хорошо»); внешние интерфейсы; ограничения. Плюс **системные требования** (несколько подсистем и интерфейсы между ними).

**Требования к проекту** (не к продукту): обучение, документация, инфраструктура и т.п. **Переходные требования** — термин BABOK (переход к будущему состоянию).

## Диаграмма классов vs ER-диаграмма
**Частота:** 14/13
**Темы:** #sa

**По литературе:**
Обе моделируют структуру, но с разными целями. У Вигерса в SRS отдельно идут требования к данным / моделирование данных; UML class — язык моделирования ПО (не глава «ER vs class» в выжимке).

**ER-диаграмма** — сущности, атрибуты, связи, ключи для данных/БД (классика моделирования данных).

**Диаграмма классов (UML)** — классы, атрибуты, операции, связи для объектной модели.

**Бизнес- vs логическая модель данных** — предметная область без СУБД vs структура под конкретную систему; 1:1 совпадать не обязаны (аналитическая практика, не дословная цитата Вигерса).

Пример про телефон клиента vs атрибут связи — учебный разбор нормализации/избыточности, не фрагмент из выжимки.

## BPMN vs UML
**Частота:** 13/13
**Темы:** #sa

**По литературе:**
**BPMN** (Business Process Model and Notation) — нотация для описания бизнес-процессов: кто что делает, в каком порядке, какие события и ветвления. Понятна бизнесу и пригодна для анализа/автоматизации процессов (Репин; BPM-CBOK).

**UML** (Unified Modeling Language) — язык моделирования ПО: структура и поведение программной системы (классы, sequence, state, use case и др.).

Правило выбора: сквозной бизнес-процесс и роли организации → BPMN; проектирование ПО (API, состояния объекта, структура кода) → UML. Часто используют вместе: BPMN для процесса, UML sequence/class для реализации.

---

## BPMN: основные элементы нотации
**Частота:** 13/13
**Темы:** #sa/bpmn #sa/modeling

**По литературе:**
По Репину BPMN — нотация и модель бизнес-процессов; используется и для описания/анализа, и в BPMS для исполняемых процессов. Сначала — контекст, границы, стартовые и завершающие события.

Элементы, которые Репин разбирает практически:
- **Пул и дорожки** — рамка процесса; дорожки в терминах ролей/должностей, *не* по фамилии.
- **События** — стартовые (в т.ч. таймер), завершающие (в т.ч. termination), промежуточные.
- **Шлюзы** — в т.ч. эксклюзивный (исключающее «ИЛИ»); плюс параллельные/другие операторы логики по BPMN.
- **Задачи/операции** на схеме.

Message flow — между участниками (свернутые пулы как «чёрные ящики»). Подпроцессы — для читаемости. Не перегружать одну диаграмму.

## UML: основные диаграммы
**Частота:** 12/13
**Темы:** #sa/uml #sa/modeling

**По литературе:**
UML — язык моделирования программных систем. Делятся на структурные и поведенческие.

**Структурные:** классы; компоненты; развёртывание (deployment).

**Поведенческие (часто у СА):**
- **Sequence** — сообщения во времени (API, асинхронные вызовы).
- **Activity** — поток работ внутри системы.
- **State** — жизненный цикл объекта (заказ: Новый → Оплачен → …).
- **Use Case** — акторы и цели на верхнем уровне.

Выбор: взаимодействие во времени → sequence; поток работ → activity; состояния → state; контекст → use case; структура данных/кода → class + ER.

## Способы выявления требований
**Частота:** 11/13
**Темы:** #sa/requirements

**По литературе:**
Цель elicitation — понять потребности заказчика и пользователей, отделяя проблему от готового решения (Вигерс; BABOK: elicitation and collaboration).

Типичные техники:
- **Интервью** — открытые вопросы, «5 почему», уточнение классов пользователей.
- **Воркшопы / фасилитация** — согласование нескольких сторон, снятие противоречий.
- **Наблюдение (job shadowing)** — реальная работа пользователя, скрытые шаги.
- **Анализ документации и существующих систем** — регламенты, логи, схема БД, конкуренты.
- **Прототипирование** — уточнение через макеты.
- **Опросы / анкеты** — массовый сбор при большом числе стейкхолдеров.

После выявления: анализ (группировка, конфликты), спецификация (User Stories / Use Cases / SRS), проверка и согласование. Не заполнять пробелы «молча»: предположения фиксировать явно (BABOK — выявление предположений при валидации).

**По литературе:**

## Agile: Scrum и Kanban для аналитика
**Частота:** 8/13
**Темы:** #sa/agile

**По литературе:**
В agile требования уточняются итерационно, а не «раз и навсегда в финальной спецификации» (Вигерс об agile; практики Scrum/Kanban).

**Scrum:** спринты; SA грумит бэклог, декомпозирует, пишет AC, проверяет DoR на планировании, снимает блокеры по требованиям, участвует в review/retro.

**Kanban:** непрерывный поток; SA держит ready-очередь, учитывает WIP, смотрит cycle time.

Приоритизация многократная, с обратной связью после демо. Аналитик готовит к реализации ближайший горизонт, а не весь проект вперёд.

## DoD и DoR — Definition of Done / Definition of Ready
**Частота:** 7/13
**Темы:** #sa #agile

**По литературе:**
Это командные agile-соглашения (Scrum/практика команд), а не термин Вигерса/BABOK.

- **DoR (Ready):** стори достаточно ясна для взятия в работу — описание, критерии приёмки, зависимости, нужные макеты/данные.
- **DoD (Done):** единый для команды стандарт готовности — код, тесты, ревью, деплой/документация по договорённости.

Не путать с **критериями приёмки** конкретной стори (Вигерс: критерии приёмки ориентированы на соответствие SRS/бизнес-целям). DoR/DoD — процессные Definition'ы команды; AC — у конкретной истории.

## Use cases — как пишутся
**Частота:** 7/13
**Темы:** #sa

**По литературе:**
**Use Case** — описание взаимодействия актора с системой для достижения цели; обычно формальнее User Story и включает альтернативы (Вигерс; UML).

Структура:
- **Название и цель**
- **Primary / secondary actors**
- **Предусловия / постусловия**
- **Основной сценарий (happy path)** — пошагово
- **Альтернативы и исключения**
- Связи **include / extend** при декомпозиции

На диаграмме Use Case: актор — человечек, прецедент — овал. UC стыкуется с пользовательскими требованиями; детализация сценариев питает функциональные требования в SRS.

## User Story и критерии приёмки
**Частота:** 7/13
**Темы:** #sa/requirements #sa/agile

**По литературе:**
По выжимке Вигерса: в Agile требования часто собирают как пользовательские истории; владелец продукта управляет их порядком. **Критерии приёмки** определяют, соответствует ли ПО требованиям SRS/целям (наличие приоритетной функциональности, обязательные атрибуты качества, допустимые дефекты, нормативные требования, проектные требования вроде обучения).

Формат «Как [роль], хочу…, чтобы…» и Given/When/Then — распространённая agile-практика записи.

**INVEST** (Independent, Negotiable, Valuable, Estimable, Small, Testable) — критерий качества истории из agile-сообщества (не глава Вигерса/BABOK). DoD команды ≠ AC конкретной стори.

## Валидация и верификация требований
**Частота:** 7/13
**Темы:** #sa/requirements

**По литературе:**
По BABOK v3 (задачи 7.2 и 7.3):

**Верификация требований** — убедиться, что спецификации и модели требований и дизайнов соответствуют стандартам качества и пригодны для использования по назначению. То есть требования и дизайны *определены правильно* (структура текста, нотации, чек-листы, термины). Обычно итеративно в ходе анализа; готовит материал к валидации.

**Валидация требований** — удостовериться, что требования заинтересованных сторон, требования к решению и **переходные требования** соответствуют *бизнес-требованиям* и помогают получить нужную пользу; что дизайны выполняют требования. Это про соответствие желаемому будущему состоянию стейкхолдеров, а не только «красиво написанному SRS».

Итог: верификация — качество и корректность артефакта; валидация — нужность и соответствие бизнес-целям. Валидацию нельзя завершить до полной верификации (BABOK).

## Оценка качества требований
**Частота:** 6/13
**Темы:** #sa/requirements

**По литературе:**
Характеристики качественных требований по BABOK (верификация, 7.2): атомарность, полнота, согласованность (не конфликтуют), краткость, выполнимость, однозначность, тестируемость, приоритезируемость, понятность.

Дополнительно из выжимки Вигерса по формулировкам: слова должны быть однозначными — использовать «должна», а не «может»; избегать неоднозначной терминологии (словарь). Guide for Writing Requirements (INCOSE) тоже подчёркивает однозначность и полноту текстовых требований.

Практика ревью: чек-лист перед передачей в разработку. Ссылка «как в системе X» допустима только если эталон актуален и прослеживается.

## Переходные требования
**Частота:** 6/13
**Темы:** #sa

**По литературе:**
В BABOK отдельно выделяют **переходные требования** (рядом с требованиями заинтересованных сторон и требованиями к решению) — они нужны, чтобы перейти к будущему состоянию и поддерживаются на протяжении изменений.

По выжимке Вигерса близкий пласт — **требования к проекту** (не к продукту): обучение персонала, пользовательская/поддержка документация, инфраструктурные изменения и т.п.

На практике в переходный пакет обычно входят: миграция данных, dual-run/параллель со старой системой, обучение, cutover и откат, временные обходные процедуры. Пример: замена CRM — выгрузка базы, двойной ввод, инструкции операторам, план отката.

## Пример нефункционального требования
**Частота:** 6/13
**Темы:** #sa/requirements #sa/nfr

**По литературе:**
Нефункциональные требования описывают *как хорошо* система работает и в каких рамках, а не *что* она делает (Вигерс: атрибуты качества, внешние интерфейсы, ограничения). Их нужно выявлять до проектирования: нагрузка и безопасность закладываются в архитектуру.

Категории с измеримыми формулировками:
- **Производительность:** «Среднее время отклика API ≤ 200 мс при 1000 RPS».
- **Безопасность:** «Пароли — bcrypt, трафик — HTTPS, 2FA для администраторов».
- **Доступность:** «99.9% в месяц (простой ≤ ~43 мин)».
- **Масштабируемость:** «Горизонтальное масштабирование, stateless-сервисы».
- **Юзабилити:** «Целевое действие ≤ 3 шага для нового пользователя».
- **Регуляторные / ограничения:** GDPR, совместимость со стандартами.

Правило: не «быстро», а число + условие нагрузки/контекста. Атрибуты качества часто становятся источником функциональных требований (Вигерс).

## User Story — примеры и отличие от Use Case
**Частота:** 5/13
**Темы:** #sa

**По литературе:**
Оба описывают потребность пользователя, но на разной глубине (Вигерс).

**User Story** — upper-level: роль + желание + ценность; планирование и приоритизация бэклога. Пример: «Как покупатель, хочу оплатить заказ картой, чтобы не вводить реквизиты каждый раз».

**Use Case** — детальный сценарий: актор, предусловия, шаги, альтернативы, постусловия. Пример: UC «Оплата заказа» с веткой «карта отклонена».

Правило: Story — что/зачем для планирования; UC — как/что если для проектирования. Одна Story может развернуться в несколько UC.

## Роль системного аналитика в SDLC
**Частота:** 5/13
**Темы:** #sa/roles

**По литературе:**
По профстандарту «Системный аналитик» основная цель вида деятельности: *разработка, восстановление и сопровождение требований к ПО / системе на протяжении их жизненного цикла*.

Трудовые функции включают выявление, анализ, представление и согласование требований, сопровождение реализации/тестирования (карта функций A–D в профстандарте).

Практически по этапам поставки:
- требования — интервью, AS-IS, scope, приоритизация;
- проектирование — спецификации, модели, API, NFR, трассировка;
- разработка/тест — уточнения, опора на критерии приёмки;
- внедрение — переходные требования, актуализация документации.

## Скрытые и неопределённые требования
**Частота:** 5/13
**Темы:** #sa/requirements

**По литературе:**
**Скрытые** — стейкхолдер считает «очевидным» и не сказал (неявные ожидания, неписаные бизнес-правила). **Неопределённые** — размытые формулировки («удобно», «быстро») без метрик (Вигерс: однозначность и полнота).

Как работать: уточняющие техники elicitation (5 почему, JTBD, наблюдение, прототип); критерии приёмки с числами; явные assumptions в спецификации; риск-лог «не уточнено → решение по умолчанию X». Не закрывать пробелы молча без фиксации.

## Этапы SDLC: что знает системный аналитик
**Частота:** 5/13
**Темы:** #sa/roles #sa/sdlc

**По литературе:**
Профстандарт фиксирует работу СА с требованиями **на протяжении жизненного цикла** системы (разработка, восстановление, сопровождение требований к ПО/системе).

Типичная инженерная цепочка поставки ПО (общая схема SDLC, не дословная цитата профстандарта):

**идея → требования → проектирование → разработка → тестирование → релиз → сопровождение → вывод из эксплуатации.**

Сильнее всего СА на формализации и сопровождении требований; на соседних этапах — согласование, приёмка, переходные требования, актуализация артефактов.

## JWT: Access и Refresh токены
**Частота:** 8/13
**Темы:** #sa #security #api

**По литературе:**
В «Проектирование веб-API» разбираются защита API и **OAuth 2.0 / OpenID Connect**, в примерах — заголовок `Authorization: Bearer …`. Детальная схема JWT (header.payload.signature) и пара access/refresh — распространённая практика IAM/OIDC, не отдельная глава этой книги в выжимке.

Кратко по практике:
- **Access** — короткий TTL, Bearer для API;
- **Refresh** — длиннее, обмен на новый access; при компромете — revoke/rotate;
- JWT часто *носитель* access token в OIDC, но OAuth2 ≠ «всегда JWT».

## Sequence: асинхронное взаимодействие и зацикленность
**Частота:** 4/13
**Темы:** #sa

**По литературе:**
На sequence-диаграмме UML различают синхронные и асинхронные сообщения.

- **Синхронный вызов** — сплошная стрелка с закрашенным наконечником; lifeline ждёт return.
- **Асинхронный** — открытая стрелка; инициатор не ждёт завершения (очередь, событие, callback).
- **Return** — пунктир назад.

Комбинированные фрагменты: **alt** (взаимоисключающие ветки), **opt**, **loop**, **par**, **break**. Пример: alt «оплата успешна» / «карта отклонена» между фронтом, API и платёжным шлюзом.

«Зацикленность» на схеме снимают явными условиями выхода в loop/break и разнесением async-обработки на отдельные сообщения/участников.

## Границы системы и scope фичи
**Частота:** 4/13
**Темы:** #sa/scope

**По литературе:**
Границы фиксируют до детализации, иначе расползается scope (Вигерс: vision and scope; контекстная диаграмма).

**Системная граница** — что «наша система», что внешний мир (акторы, смежные системы, потоки данных).

**Scope релиза/фичи** — явный список in scope / out of scope.

Зачем: защита от scope creep; учёт ownership и SLA внешних систем; понятный объём оценки. Если внешний сервис недоступен 2 часа, нельзя обещать 99.9% uptime «как будто всё наше».

## Чем отличается бизнес-аналитик от системного аналитика?
**Частота:** 4/13
**Темы:** #sa/roles

**По литературе:**
Обе роли работают с требованиями, но на разных уровнях (BABOK vs фокус профстандарта СА на требованиях к системе).

**BA** — «вширь»: бизнес-цели, стейкхолдеры, pain points, бизнес-кейс. Отвечает на «почему». Артефакты: vision, business case, high-level требования.

**СА** — «вглубь» к системе: функции, интеграции, данные, API, модели. Отвечает на «как именно система должна себя вести». Артефакты: SRS, UML/BPMN/ER, спецификации интерфейсов.

BA: «нужно повысить конверсию до 15%». СА: «форма регистрации валидирует email через внешний сервис за ≤ 500 мс». В небольших командах роли совмещают.

## SSO (Single Sign-On)
**Частота:** 3/13
**Темы:** #sa #security

**По литературе:**
Единый вход через IdP к нескольким приложениям — тема IAM. В книге проектирования веб-API рядом лежат OAuth 2.0 и OpenID Connect (аутентификация на базе OAuth). SAML чаще в enterprise SSO; в vault-книгах это не развёрнутый учебник по SAML.

Смысл: пользователь аутентифицируется у IdP; приложения доверяют assertion/token. Плюс — единый UX и централизованный revoke; минус — зависимость от IdP.

## Конфликт требований от стейкхолдеров
**Частота:** 3/13
**Темы:** #sa

**По литературе:**

## Нотации моделирования процессов и систем
**Частота:** 3/13

## Как системный аналитик помогает проектировать архитектуру?
**Частота:** 2/13
**Темы:** #sa/roles #sa/architecture

**По литературе:**
СА не заменяет архитектора, но даёт контекст для решений (профстандарт: требования к системе; Вигерс: NFR и ограничения).

Что передаёт:

## Методы приоритизации (RICE / ICE / MoSCoW)
**Частота:** 2/13
**Темы:** #sa #prioritization

**По литературе:**
**MoSCoW** есть в выжимке Вигерса: Must / Should / Could / Won't; недостаток — всё часто сваливают в Must. Также рекомендует Химонин; в BABOK встречается MoSCoW-приоритизация в agile-контексте.

У Вигерса рядом другие методы: попарное сравнение, важно/срочно, «100 долларов», таблица ценность/стоимость/риск (приоритет ≈ Ценность / (Стоимость + Риски)).

**RICE** (Reach × Impact × Confidence / Effort) и **ICE** — продуктовые скоринги; в vault кратко перечислены в «ТОП 25 вопросов…», это не главы BABOK/Вигерса. Использовать как практику приоритизации гипотез, не выдавая за BABOK.

## Приоритизация требований и MVP
**Частота:** 2/13
**Темы:** #sa/scope #sa/requirements

## Управление требованиями и версионирование
**Частота:** 2/13
**Темы:** #sa/requirements

**По литературе:**
Требования живут и меняются; без управления версиями команда работает по устаревшим артефактам (Вигерс: requirements management).

Практика:
- **Единый источник правды** — спецификация/реестр, а не «правда в чатах».
- **Версии и changelog** — что изменилось, почему, кто согласовал.
- **Процесс изменения** — предложение → impact → утверждение → обновление связанных FR/тестов (трассировка).
- Изменение уже согласованных требований бьёт по срокам, стоимости, иногда архитектуре — это проговаривают до переработки.

Инструменты вторичны (Confluence/Jira/Git); первична дисциплина фиксации изменений.

## Чем отличается бизнес-требование от пользовательского?
**Частота:** 2/13
**Темы:** #sa/requirements

**По литературе:**
Разница — в уровне и адресате (Вигерс).

**Бизнес-требования** — верхний уровень, *зачем* организации нужна система (цели, KPI, vision/scope). Адресат: заказчик, топ-менеджмент. Пример: «Увеличить онлайн-продажи на 30% за год».

**Пользовательские требования** — *что* пользователь должен уметь сделать с ПО. Формы: User Story, Use Case. Адресат: команда разработки. Пример: «Как покупатель, хочу видеть историю заказов, чтобы повторить покупку».

Пользовательские требования выводятся из бизнес-целей; если связь с бизнес-требованием не прослеживается, требование под вопросом (трассировка, Вигерс).

## AS-IS и TO-BE: зачем и когда
**Частота:** 1/13
**Темы:** #sa/bpmn #sa/process

**По литературе:**
В BPM-CBOK используют модели процесса **как есть** и **как будет**: анализ текущего состояния, поиск улучшений, проектирование целевого. Репин подчёркивает: без контекста, границ и событий описание процесса расползается; автоматизация «как есть» без переосмысления часто неэффективна.

**Gap** между как есть и как будет даёт список изменений → требования и оценка объёма. Для greenfield модели «как есть» может не быть.

## C4-диаграммы — уровни моделирования архитектуры
**Частота:** 1/13
**Темы:** #sa #architecture

**По литературе:**
Модель **C4** (Simon Brown): Context → Container → Component → Code. В md-книгах этого vault отдельного разбора C4 нет — это отраслевая схема уровней архитектуры, не цитата из BABOK/Репина.

Смысл уровней:
- **C1 Context** — система и внешние акторы;
- **C2 Container** — приложения, БД, брокеры;
- **C3 Component** — компоненты внутри контейнера;
- **C4 Code** — классы (редко рисуют).

**Функциональная схема архитектуры** в корпоративных тестах — другой артефакт (функции по назначению), не топология C4.

## Матрица трассировки требований
**Частота:** 1/13
**Темы:** #sa/requirements #sa/traceability

**По литературе:**
**Трассировка** — отслеживание связей между уровнями требований и артефактами реализации (Вигерс; BABOK). Функциональные и NFR выводятся из бизнес-требований и трассируются к задачам, бизнес-правилам, тест-кейсам, вариантам решения.

**Зачем:** происхождение требований; покрытие; **impact analysis** при изменении. Не заменяет приоритизацию и не является главным инструментом оценки стоимости.

Матрица: бизнес → пользовательское → функциональное → тест-кейс / задача. При удалении ненужного бизнес-требования можно снять связанные детальные (Вигерс).

**По литературе:**
В системной инженерии анализ и синтез — парные виды деятельности: анализ потребностей/альтернатив и синтез системы (см. «Системная инженерия: принципы и практика» — акцент на анализе и проектировании системы в целом, синтезе систем).

В работе аналитика:
- **анализ** — разбор вводных на части (пользователи, данные, интеграции, правила);
- **синтез** — сборка согласованного решения/scope из частей.

Ошибка — только дробить или только рисовать схемы без проверки потребностей.

## Бизнес-процесс — определение
**Частота:** 0/13
**Темы:** #sa

**По литературе:**
По Репину (BPMN): процесс (бизнес-процесс) — *устойчивая, целенаправленная совокупность взаимосвязанных видов деятельности, которая по определенной технологии преобразует входы в выходы, представляющие ценность для потребителя*. Входы и выходы — информационные и материальные потоки. До схемы важно задать контекст и границы; отдельно — инициирующие и завершающие события.

BPM-CBOK описывает управление такими сквозными процессами и модели «как есть» / «как будет».

При описании фиксируют: границы и события, участников (роли/дорожки, не ФИО), шаги и шлюзы, входы/выходы, метрики.

## Вопросы заказчику при неполных вводных
**Частота:** 0/13
**Темы:** #sa

**По литературе:**
Если заказчик отвечает «не знаю», сужаем неопределённость структурой elicitation (Вигерс; BABOK):

**цель** → **пользователи / классы** → **функции** → **ограничения** → **метрики успеха** → **интеграции**.

Пример (кофейный аппарат / вендинг): для кого (офис/улица), сколько пользователей, виды напитков, оплата/лимиты, обслуживание, безопасность (кипяток, дети), учёт/CRM, NFR (время налива, мощность). Фиксировать assumptions явно.

## Способы документирования требований
**Частота:** 0/13
**Темы:** #sa

**По литературе:**
Форма зависит от этапа жизненного цикла требований (Вигерс; BABOK):

- **Сбор:** протокол встречи, глоссарий, vision/scope, user story mapping, AS-IS BPMN.
- **Проектирование:** sequence/activity, ER, API-спецификация, критерии приёмки, сценарии к макетам, state machine для статусов.
- **Согласование:** утверждённые требования, задачи в трекере с фиксацией решений.
- **Сопровождение разработки:** живые уточнения; артефакт — обновлённая спецификация с версией.

Документ должен поддерживать трассировку и однозначность формулировок.

## Управление дефектами (bug report)
**Частота:** 0/13
**Темы:** #sa #qa

**По литературе:**
В bug report обязательны **шаги воспроизведения** и **окружение/условия**; ожидаемый результат — отдельное поле.

«Не воспроизводится» — дополнить описание (данные, лог, скрин), не закрывать молча. **Priority** — срочность исправления по влиянию на сервис; не путать с **Severity** (техническая тяжесть).

## Хеширование и целостность данных
**Частота:** 0/13
**Темы:** #sa #security

**По литературе:**
**Хеширование** — преобразование данных в значение фиксированной длины, однозначно связанное с входом для проверки.

Передача/хранение хеша по доверенному каналу позволяет проверить **целостность** (не изменились ли данные) и факт соответствия ожидаемому содержимому. Для паролей используют медленные KDF (bcrypt/argon2), не «голый» быстрый хеш.
