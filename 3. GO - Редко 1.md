## `context.WithValue` — антипаттерны
**Частота:** 1/56
**Темы:** #go/context
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
`context.WithValue` не предназначен для optional parameters или конфигурации. При этом, его используют для на время запроса metadata, которое проходит через границы API: трассировка id, auth data, request id. Ключи лучше делать типизированными, чтобы избежать конфликтов.

**Типичные ошибки:**
- Класть в context обязательные параметры бизнес-логики.
- Использовать строковые ключи, которые могут конфликтовать между пакетами.

**Подробности:**
- Основная роль context — cancel/deadline, values вторичны.
- WithValue усложняет явность зависимостей, поэтому данные должны быть небольшими и на время запроса.
- Типизированный private key снижает риск коллизий ключей

## `GOGC` и настройка GC
**Частота:** 1/56
**Темы:** #go/gc
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
GOGC задаёт целевой рост heap относительно live objects после GC (100 = heap ~2× live). При этом, выше GOGC — реже GC, больше память; ниже — чаще GC, меньше RSS. Настраивают через env GODEBUG/gogc или runtime debug.SetGCPercent.

**Типичные ошибки:**
- Думают, что GOGC=off полностью отключает GC без последствий.
- Путают GOGC с лимитом памяти процесса.

**Подробности:**
- по умолчанию GOGC=100.
- GOMEMLIMIT (Go 1.19+) — soft limit памяти, взаимодействует с GC pacing.
- Смотреть GODEBUG=gctrace=1 для диагностики пауз.

## `len(sync.Map)` — почему нет, как считать
**Частота:** 1/56
**Темы:** #go/sync #go/map
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
У `sync.Map` нет метода `Len`. Точный размер нельзя получить дешёвой O(1)-операцией, потому что map может параллельно меняться, а внутри есть несколько представлений данных.

Посчитать можно через `Range`, но это O(n), и при конкурентных изменениях результат не является строгим snapshot. Для метрик обычно держат отдельный счётчик, например atomic counter, и аккуратно обновляют его только когда ключ действительно добавлен или удалён.

**Подробности:**
- `Range` безопасен, но во время обхода другие goroutine могут делать `Store`/`Delete`.
- Для счётчика нужно учитывать семантику операций: `LoadOrStore`, `LoadAndDelete`, `CompareAndDelete` помогают понять, изменилось ли число ключей.
- Если нужен строгий размер как часть бизнес-инварианта, чаще проще использовать обычную `map` под mutex.

**Частота:** 1/56
**Темы:** #go/sync
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**

- На собесе часто путают с WaitGroup/Cond; Once — ровно один init.

## `sync.Pool`
**Частота:** 1/56
**Темы:** #go/sync #go/gc
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
Sync.Pool — кэш временных объектов per-P, снижает аллокации под нагрузкой. При этом, объекты могут быть удалены GC в любой момент между Get/Put — Pool не должен хранить долгоживущее состояние.

**Типичные ошибки:**
- Хранят в Pool объекты с важным lifecycle или ссылками на большие графы.
- Считают Pool гарантированным кэшем как LRU map.

**Подробности:**
- Запись в nil map или конкурентная map без sync — panic или data race; `-race` ловит второе.
- Закрытый channel: чтение отдаёт zero значение + ok=false; запись — panic.

## `sync.WaitGroup`
**Частота:** 3/56
**Темы:** #go/sync
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
содержит счетчик который равен количеству еще не завершенных горутин

**Подробности:**
`wg.Add(n)` перед стартом goroutines; каждая goroutine вызывает `Done`; `Wait` в main ждёт counter=0. При этом, panic при отрицательном счётчике.

- `Add` до `go` или внутри goroutine до `Wait`, но не после `Wait`.
- `defer wg.Done` в каждой goroutine — типичный паттерн.
- Не вызывать `Wait` из goroutine, которая сама делает `Done` — deadlock.

Для работы с `WaitGroup` достаточно запомнить три метода:

- `(*WaitGroup) Add(delta int)` — изменяет значение счётчика на указанную величину. Перед тем как создать горутину, достаточно вызвать `Add(1)`.
- `(*WaitGroup) Done()` — уменьшает значение счётчика на единицу. Этот метод вызывается в конце горутины.
- `(*WaitGroup) Wait()` — ожидает, когда значение счётчика будет равно нулю. Этот метод используется в основной функции, где нужно ожидать завершения горутин.

Увеличивать счётчик необходимо до вызова горутины, а не внутри или после неё. Представьте, что горутины ещё не успели начать работу, а цикл уже завершился. В таком случае `wg.Wait()` ждать просто нечего, так как счётчик не успел увеличиться.

## go.mod — зачем нужен?
**Частота:** 1/56
**Темы:** #go/tooling #go/modules
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
`go.mod` — манифест Go-модуля: путь модуля (`module`), версия Go (`go`), прямые зависимости (`require`), при необходимости `replace` / `exclude` / `retract`.

Фиксирует **какие** модули и **какие версии** нужны проекту. Это не checksum-файл: целостность и воспроизводимость обеспечивает `go.sum`.

**Типичные ошибки:**
- Путают `go.mod` с lock-файлом npm — без `go.sum` checksums не зафиксированы.
- Редактируют `require` вручную вместо `go get` / `go mod tidy`.

**Подробности:**
- `go mod init`, `go mod tidy` синхронизируют зависимости с импортами в коде.
- `replace` — локальная подмена модуля (форк, monorepo).
- Коммитят в git вместе с `go.sum`.

## GOPRIVATE и GOPROXY?
**Частота:** 1/56
**Темы:** #go/tooling #go/modules
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
`GOPROXY` — список URL module proxy (по умолчанию `https://proxy.golang.org,direct`). Proxy кэширует модули; `direct` — загрузка напрямую с VCS при недоступности proxy.

`GOPRIVATE` — шаблоны приватных путей (`github.com/myorg/*`). Для них **не** используют публичный proxy и checksum database (`sum.golang.org`); модули качают напрямую. Часто вместе задают `GONOSUMDB` с теми же паттернами.

**Типичные ошибки:**
- Приватный модуль «утекает» в публичный proxy — не настроен `GOPRIVATE`.
- В CI нет доступа к VCS / `.netrc` / `GOPRIVATE` — `go mod download` падает.

**Подробности:**
- Корпоративный сценарий: свой Athens/Artifactory proxy + `GOPROXY=https://internal-proxy,direct`.
- `go env -w GOPRIVATE=...` для локальной разработки.
- См. [[3. GO - Редко 1#go.sum в git?]] · [[3. GO - Редко 1#go.mod — зачем нужен?]].

## Swiss map (Go 1.24+)
**Частота:** 1/56
**Темы:** #go/map #go/hash #go/runtime
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
С Go 1.24 runtime использует новую реализацию встроенной map на основе идей Swiss Table. Семантика для пользовательского кода та же: `map[K]V`, `range`, `delete`, `clear`, nil map и правила конкурентного доступа не изменились.

Главное отличие — другая внутренняя организация данных, которая улучшает locality и уменьшает накладные расходы старых overflow buckets.

**Подробности:**
Хеш-таблица основана на Swiss Table. Ключ хешируется, по хешу выбирается место, где может лежать ключ.

Данные организованы группами, рядом хранится служебная метадата — короткие отпечатки хеша. Сначала runtime быстро отбирает кандидатов по отпечаткам, затем сравнивает полные ключи.

Старой модели overflow buckets в прежнем виде нет: если место занято или произошла коллизия, поиск продолжается по правилам open addressing/Swiss Table. При росте используется другая логика расширения и разделения таблиц, поэтому старые детали про buckets и эвакуацию нельзя переносить один-в-один.

## Value vs pointer receiver
**Частота:** 1/56
**Темы:** #go/methods
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**
- **Value receiver** — копия; мутации метода **не** видны снаружи (кроме мутаций через pointer fields).
- **Pointer receiver** — меняет оригинал; обязателен для `sync.Mutex` в struct.
- (бонус) **Передача/возврат**: маленькие struct — по значению (меньше pressure на GC); мутировать — по указателю.

**Эталон на собесе:**
**Value receiver** — метод получает копию `T`; изменения полей не меняют оригинал. **Pointer receiver** `*T` — меняет исходный объект. Go разрешает вызывать `*T`-метод на value и наоборот (авто `&` / разыменование), но семантика копирования остаётся.

**Передавать в функцию:**
- **По значению** — копия (дешево для маленьких struct, int, pointer сам по себе).
- **По указателю** — если функция **мутирует** объект, struct **большой**, или тип **нельзя** копировать (`sync.Mutex`, `bytes.Buffer` с lock).

**Возвращать из функции:**
- **По значению** — маленькие immutable struct: меньше аллокаций на heap, проще для GC.
- **По указателю** — большой объект, нужен shared mutable state, или «nullable» через `nil` pointer.

**Подробности:**
- Slice в value receiver копирует **заголовок** — `append` может не виден снаружи без pointer receiver или return нового slice.
- Удовлетворение интерфейса проверяется на **конкретном** типе receiver.
- См. [[2. GO - Средне#Передача и возврат: значение vs указатель?]] · [[1. GO - Часто#Stack vs heap — зачем и производительность?]].

## Атомарные операции
**Частота:** 1/56
**Темы:** #go/atomic
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Атомарная операция** — это операция, которая выполняется за один шаг относительно других горутин. Горутина не может прервать своё выполнение во время такой операции, а кроме этого, другие горутины не могут начать эту же самую операцию. Это похоже на транзакции из темы про базы данных, только у атомарной операции не может быть отката.

sync/atomic - атомарные операции для целочисленных типов: `int32`, `int64`, `uint32`, `uint64`
Во всех функциях передаются указатели на числовые значения в которых необходима атомарность

```
var addr int64 
atomic.AddInt64(&addr, 1) // прибавляем 1
```


В пакете `sync/atomic` определены типы-обёртки: `atomic.Bool`, `atomic.Int32`, `atomic.Int64` и так далее. Для начала работы с такими «обёртками» достаточно описать переменную нужного типа, например, `var i atomic.Int64`. Эти типы вместо функций имеют соответствующие методы.

## Есть ли исключения (exception) в Go?
**Частота:** 1/56
**Темы:** #go/errors
- [ ] Скорректировано
- [ ] последний повтор

**Как формулируют на собесе:**
> Есть ли в Go exceptions, как в Java/C#?

**Эталон на собесе:**
Классической модели checked/unchecked exceptions в Go нет. Ожидаемые ошибки возвращают через `error`. Для невосстановимых ситуаций — `panic` и `recover` (обычно на границе goroutine, например HTTP middleware).

**Типичные ошибки:**
- Считать, что `panic` — это то же самое, что exception в ООП-языках.

## Какие ключевые особенности го
**Частота:** 1/56
**Темы:** #go/types
- [x] Скорректировано ✅ 2026-06-26
- [ ] последний повтор

**Что ожидают на собесе:**


Go — компилируемый, статически типизированный язык.

Основные особенности:
• простота языка;
• высокая производительность;
• горутины и каналы;
• композиция вместо наследования;
• неявная реализация интерфейсов;
• встроенный набор инструментов (fmt, test, mod, pprof);
• кроссплатформенная компиляция;
• богатая стандартная библиотека.

- простота и скорость разработки, минималистичный синтаксис
- нет наследования, нет классической ооп модели
- встроенная конкаренси
- программа компилируется в один бинарник, в котором есть все необходимое для работы
- статическая типизация, типобезопасность на этапе компиляции
- кроссплатформенный - легко создавать бинарники для разных ОС
