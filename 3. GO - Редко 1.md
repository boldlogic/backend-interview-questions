## Можем ли взять указатель на элемент мапы
**Частота:** 3/84
**Темы:** #go/map #go/pointers
- [x] Скорректировано ✅ 2026-06-27
- [x] последний повтор ✅ 2026-06-27

- Нельзя взять адрес элемента map:`&m[k] ` не компилируется. Значение внутри map не addressable потому что такой адрес может потом оказаться недействительным.
- Причина: runtime может перемещать данные map при росте или внутренней перестройке, поэтому стабильный адрес элемента не гарантируется. Go запрещает указатель на значение, которое map может переложить в другое место.
- Адрес самой переменной map взять можно:`&m `. Нельзя именно брать адрес элемента по ключу.
- При этом если поместили структуру в мапу и нужно менять значение в поле, то можно сделать так
```go
type a struct{
b int
}
c:=make(map[key]*a,10)
c[key].b=1

```
- и менять через точку

## Сложность доступа по ключу в map?
**Частота:** 3/84
**Темы:** #go/map #go/hash #go/complexity
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26

Чтение по ключу в среднем O(1) - константная. В худшем случае может деградировать до O(n), если много коллизий.
Запись и удаление тоже O(1) в среднем, но амортизированно: отдельная операция может быть дороже из-за роста таблицы и переноса данных.

Go использует рандомизацию хеширования; у map есть собственный seed, а runtime добавляет случайность на уровне процесса.

Стоимость ключа важна:`int`/`uint`/указатели дешевле,`string` зависит от длины, большие struct/array дороже хешировать и сравнивать.

## Утечка горутин
**Частота:** 3/84
**Темы:** #go/goroutine #go/channel #go/tooling
- [x] Скорректировано ✅ 2026-06-26
- [x] последний повтор ✅ 2026-06-27

Утечка горутин — это ситуация, когда горутина больше не нужна приложению, но не может завершиться и продолжает удерживать ресурсы. Чаще всего причиной являются зависание на канале, отсутствие отмены через context, незакрытые каналы или забытые ticker/timer. Предотвращается корректным управлением жизненным циклом через context и закрытие каналов.


- Переключение G: block (chan/mutex/WaitGroup), syscall, netpoll park,`runtime.Gosched`, preemption.
- Blocking syscall: handoff P, G в waiting; M может block в kernel, P продолжит другие G.
- Netpoller (epoll/kqueue/IOCP): readiness → G runnable → run queue.
- Safepoints нужны для GC stack scan, stack growth check и preemption.
- Long CPU loop: sysmon (~10 ms) может инициировать preemption post-1.14, но не на каждой инструкции.
- Утечка горутина: G заблокированы навсегда — send без recv, забытый ctx, worker без shutdown.
- Диагностика leak:` go tool pprof -http=:8080 'http://localhost/debug/pprof/goroutine?debug=2'`— stack trace покажет, на каком sync-примитиве висит G
- Fix leak: context cancel,`close(ch)`, WaitGroup, корректное завершение worker pool.

## `errgroup`
**Частота:** 2/84
**Темы:** #go/sync #go/context #go/errors
- [x] Скорректировано ✅ 2026-06-30
- [x] последний повтор ✅ 2026-06-30

`errgroup` — это удобная обертка над ожиданием группы горутин. Она позволяет запускать параллельные задачи, дождаться их завершения, получить первую ошибку и, при использовании `WithContext`, отменить остальные задачи через `Context`, если одна из них завершилась с ошибкой.
```go
g, ctx := errgroup.WithContext(ctx)

g.Go(func() error {
    return loadUsers(ctx)
})

g.Go(func() error {
    return loadOrders(ctx)
})

if err := g.Wait(); err != nil {
    return err
}
```

## Append внутри функции по значению — виден ли снаружи?
**Частота:** 2/84
**Темы:** #go/slice
- [x] Скорректировано ✅ 2026-06-18
- [x] последний повтор ✅ 2026-07-03

**Эталон на собесе:**
В функцию передается копия заголовка, базовый массив общий.
Append обновляет локальный заголовок внутри функции.
Функция меняет len у своей копии; у вызывающего len не меняется если не возвращать.
При этом если позволяет cap, то базовый массив обновляется и можно увидеть снаружи через расширение len (взятие слайса)
Аналогично при выделении нового базового массива - обновление указателя на базовый массив снаружи не виден.
существующие элементы могут измениться в общем массиве - мутация существующих элементов `s[i] = v` видна вызывающему
**Подробности:**
Фиксы
- Return `s = append(s, x)` или указатель `*[]T `.
- Всегда переприсваивать результат append.
- Без return/указателя len снаружи не меняется.
- При достаточном cap элементы мутируют общий базовый массив.

## Бинарный поиск vs дерево поиска (оба O(log n))
**Темы:** #go/complexity #go/algorithms
**Частота:** 2/84
- [ ] Скорректировано
- [ ] последний повтор
**Как формулируют на собесе:**
> Бинпоиск и дерево — оба O(log n). Зачем оба? В чём разница по памяти?

**Эталон на собесе:**
Одинаковая **асимптотика**, разная **модель данных**
- **Бинарный поиск** — по **отсортированному массиву** in-place; доп. Память O(1), но вставка/удаление O(n).
- **Дерево поиска (BST/B-tree)** — структура с указателями/узлами; вставка/удаление/поиск O(log n) при балансировке; больше памяти на метаданные узлов, зато динамические обновления.
На собесе VK ждут: бинпоиск — когда массив уже есть и редко меняется; дерево — когда нужны частые вставки или индекс в БД (B-tree).
**Типичные ошибки:**
- «Разницы нет, оба логарифм» — игнорировать стоимость вставки и память.
- Путать бинпоиск в массиве с обходом дерева рекурсией (стек/alloc).

## Канал vs мьютекс
**Частота:** 2/84
**Темы:** #go/channel #go/sync
- [x] Скорректировано ✅ 2026-06-26
- [x] последний повтор ✅ 2026-06-27

**Мьютекс** — примитив синхронизации, который позволяет только одной горути не находиться в части кода, где необходим эксклюзивный доступ.
канал — передача работы/результатов между goroutines.


- Counter/cache — mutex проще.
- Fan-in/fan-out — канал + select.
Когда первый поток входит в критическую секцию, мьютекс блокируется до тех пор, пока поток не поки нет её. Пока мьютекс заблокирован, другие горутины ждут его разблокировки. Как только он разблокирован, одна из ожидающих горутин успевает заблокировать его и получить эксклюзивный доступ к критической секции кода.

## Когда interface == nil?
**Частота:** 2/84
**Темы:** #go/interfaces #go/errors
- [x] Скорректировано ✅ 2026-06-30
- [x] последний повтор ✅ 2026-06-27

Interface равен nil только когда и динамический тип, и данные nil. 
Если в interface лежит типизированный nil указатель, сам interface уже не nil, потому type-компонента заполнена. Это часто ломает `if err != nil`, когда возвращают `(*MyError)(nil) `как` error `.

**Подробности:**
- Модель: interface значение =`(type, data) `.
-`var e *MyErr = nil; var err error = e` даёт `err != nil`.
- Проверять нужно место возврата: возвращать `nil`, а не типизированный nil.

## Конкурентная запись в мапу, почему нельзя?
**Частота:** 2/84
**Темы:** #go/map #go/data-race
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27


Обычная map **не потокобезопасна**. **Read-only** из нескольких горутина допустим, если **никто не пишет**. Если **хотя бы одна** горутина пишет — нужен **Mutex** / владелец /`sync.Map`.

Запись — не атомарная операция: рантайм считает хеш, ищет место, меняет служебные структуры, иногда запускает рост или перенос данных.
**Подробности:**
- `concurrent map writes` и `concurrent map read and map write` приводят к fatal error runtime.`recover` от этого не спасает потому что мапа может быть испорчена
- Несколько параллельных чтений допустимы, если в это время никто не пишет.
- Проблема в том, что одна горутина может менять структуру таблицы, а другая одновременно читать или писать по устаревшему состоянию.
- Одна горутина владеет map — типичный паттерн через канал.
- В реализации есть внутренние флаги/проверки, которые помогают runtime обнаруживать часть таких ошибок, но это не замена race detector.

## Очередь с приоритетом и binary heap
**Темы:** #go/algorithms #go/complexity
**Частота:** 2/84
- [ ] Скорректировано
- [ ] последний повтор
**Как формулируют на собесе:**
> Что такое очередь с приоритетом? На какой структуре реализовать? Что такое heap?

**Эталон на собесе:**
**Priority queue** — элемент с наивысшим (или наименьшим) приоритетом извлекается первым. Наивно — отсортированный список O(n) на вставку; оптимально — **binary heap** (min-heap / max-heap): вставка и извлечение корня O(log n), peek O(1). В памяти heap часто хранится как **массив** с индексной арифметикой (родитель/дети).
**Типичные ошибки:**
- Путать heap (куча приоритетов) с heap памятью в Go.
- Предлагать только linked list без оценки сложности.

**Подробности:**
- В Python —`heapq`; в Go —`container/heap`.
- При коллизии приоритетов — FIFO внутри одного веса (зависит от реализации).

## Параллельные исходящие HTTP-запросы (fan-out)?

**Темы:** #go/concurrency #go/context #go/stdlib

- Типовая задача: один входящий HTTP-запрос → N независимых исходящих REST-вызовов → агрегировать JSON и отдать клиенту

**Эталон на собесе:**

- Нет timeout на весь fan-out — handler висит.
- Забыть передать `ctx` в `http.NewRequestWithContext`.

## Указатель в цикле — один адрес
**Частота:** 2/84
**Темы:** #go/pointers #go/slice
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

В `for range` до Go 1.22 переменная итерации переиспользовалась, поэтому взятие `&v ` давало один и тот же адрес. Правильнее брать адрес элемента через индекс:`&items[i] `, либо создавать копию переменной на итерации. В новых версиях ловушка смягчена для range, но привычка проверять адрес остаётся полезной.

**Подробности:**
```
for i := range items {
ptrs = append(ptrs, &items[i])
}
```
берёт адрес элемента.
- Для map нельзя взять стабильный адрес значение напрямую: значения могут перемещаться.
- Та же идея важна для closures, которые захватывают переменную цикла.

## Что произойдет с читателями/писателями если закрыть канал?

**Темы:** #go/channel
- [x] Скорректировано ✅ 2026-06-26
- [x] последний повтор ✅ 2026-06-27

### Читатель
- Если в канале **еще есть данные**, они будут прочитаны.
- Закрытие не выбрасывает данные
- Когда буфер опустеет, получим нулевое значение типа
```go
for v := range ch {
fmt.Println(v)
}
```
Цикл автоматически завершится после чтения всех данных из закрытого канала.
### Писатель
Любая попытка записи в закрытый канал приводит к панике.
### Если были заблокированные читатели
После закрытия канала читатель **разблокируется**.

## Что такое string? / строки vs руны
**Частота:** 2/84
**Темы:** #go/string
- [x] Скорректировано ✅ 2026-06-30
- [x] последний повтор ✅ 2026-07-03

`string`— **неизменяемая** последовательность байт (обычно UTF-8). 

Строка состоит из двух полей:
pointer -> данные
length

Длина в байтах —`len(s)`; 
количество символов (рун) —`utf8.RuneCountInString` или `range` по строке.

любая модификация приводит к созданию новой строки. 
Если нужно изменить содержимое, строку преобразуют в `[]byte` или `[]rune`, в зависимости от задачи.

Проверка «есть ли кириллица» —`unicode.Is` по рунам. 
Строка immutable; изменение — через `[]rune `или` strings.Builder `.

Например, чтобы избавиться от лишних аллокаций, можно воспользоваться типом strings.Builder и методом WriteString:
```go
 func join(strs ...string) string {
    var sb strings.Builder
    for _, str := range strs {
            sb.WriteString(str)
    }
    return sb.String()
 }
 И никто не мешает пользоваться пакетом strings.
```

## Что такое планировщик
**Частота:** 2/84
**Темы:** #go/scheduler
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27
Планировщик Go — это компонент Go, отвечающий последовательность выполнения горутин, из которых состоит программа Go

планировщик Go оперирует горутинами только одной программы, он намного проще, дешевле и быстрее, чем планировщик ядра операционной системы.

В Go используется модель планировщика GMP.
**G (горутина)** — горутина, выполняемая задача.
**M (machine)** — поток операционной системы.
**P (processor)** — логический процессор runtime, через который горутины назначаются потокам.
У каждого процессора есть локальная очередь горутин. Если у одного процессора задач много, а у другого нет, используется механизм **воровства работы (work stealing)** — свободный процессора забирает часть задач себе.
При блокирующих системных вызовах runtime старается отвязать процессора от заблокированного потока и продолжить выполнение на другом потоке.
Для того чтобы одна горутина не могла бесконечно занимать процессор, используется **вытесняющая многозадачность (preemption)**.
Вытеснение и работа сборщика мусора выполняются через **безопасные точки (safepoints)** — места, где runtime может безопасно остановить горутину.

## `GOGC` и настройка GC
**Частота:** 1/84
**Темы:** #go/gc
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

GOGC задаёт целевой рост heap относительно live objects после GC (100 = heap ~2× live). Выше GOGC — реже GC, больше память; ниже — чаще GC, меньше RSS. Настраивают через env GODEBUG/gogc или runtime debug.SetGCPercent.

- по умолчанию GOGC=100.
- GOMEMLIMIT (Go 1.19+) — soft limit памяти, взаимодействует с GC pacing.
- Смотреть GODEBUG=gctrace=1 для диагностики пауз.

## `len(sync.Map)` — почему нет, как считать
**Частота:** 1/84
**Темы:** #go/sync #go/map
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

У `sync.Map` нет метода `Len`. Точный размер нельзя получить дешёвой O(1)-операцией, потому что map может параллельно меняться, а внутри есть несколько представлений данных.
Посчитать можно через `Range`, но это O(n), и при конкурентных изменениях результат не является строгим snapshot. Для метрик обычно держат отдельный счётчик, например atomic counter, и аккуратно обновляют его только когда ключ действительно добавлен или удалён.
**Подробности:**
-`Range` безопасен, но во время обхода другие горутина могут делать `Store`/`Delete`.
- Для счётчика нужно учитывать семантику операций:`LoadOrStore`,`LoadAndDelete`,`CompareAndDelete` помогают понять, изменилось ли число ключей.
- Если нужен строгий размер как часть бизнес-инварианта, чаще проще использовать обычную `map` под mutex.

## GOPRIVATE и GOPROXY?
**Частота:** 1/84
**Темы:** #go/tooling #go/modules
- [ ] Скорректировано
- [ ] последний повтор

**Эталон на собесе:**
`GOPROXY`— список URL module proxy (по умолчанию `https://proxy.golang.org,direct`). Proxy кэширует модули;`direct`— загрузка напрямую с VCS при недоступности proxy.
`GOPRIVATE`— шаблоны приватных путей (` github.com/myorg/*`). Для них **не** используют публичный proxy и checksum database (`sum.golang.org`); модули качают напрямую. Часто вместе задают `GONOSUMDB` с теми же паттернами.

**Подробности:**
- Корпоративный сценарий: свой Athens/Artifactory proxy +`GOPROXY=https://internal-proxy,direct`.
-` go env -w GOPRIVATE=...` для локальной разработки.
