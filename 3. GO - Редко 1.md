## `len(sync.Map)` — почему нет, как считать
**Частота:** 4/59
**Темы:** #go/sync #go/map
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
У `sync.Map` нет метода `Len`. Точный размер нельзя получить дешёвой O(1)-операцией, потому что map может параллельно меняться, а внутри есть несколько представлений данных.

Посчитать можно через `Range`, но это O(n), и при конкурентных изменениях результат не является строгим snapshot. Для метрик обычно держат отдельный счётчик, например atomic counter, и аккуратно обновляют его только когда ключ действительно добавлен или удалён.

**Подробности:**
- `Range` безопасен, но во время обхода другие goroutine могут делать `Store`/`Delete`.
- Для счётчика нужно учитывать семантику операций: `LoadOrStore`, `LoadAndDelete`, `CompareAndDelete` помогают понять, изменилось ли число ключей.
- Если нужен строгий размер как часть бизнес-инварианта, чаще проще использовать обычную `map` под mutex.

## `sync.WaitGroup`
**Частота:** 3/59
**Темы:** #go/sync
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
содержит счетчик который равен количеству еще не завершенных горутин

**Подробности:**
`wg.Add(n)` перед стартом goroutines; каждая goroutine вызывает `Done`; `Wait` в main ждёт counter=0. При этом, panic при отрицательном счётчике.

- `Add` до `go` или внутри goroutine до `Wait`, но не после `Wait`.
- `defer wg.Done` в каждой goroutine — типичный паттерн.
- Не вызывать `Wait` из goroutine, которая сама делает `Done` — deadlock.

Для работы с `WaitGroup` достаточно запомнить три метода:

- `(*WaitGroup) Add(delta int)` — изменяет значение счётчика на указанную величину. Перед тем как создать горутину, достаточно вызвать `Add(1)`.
- `(*WaitGroup) Done()` — уменьшает значение счётчика на единицу. Этот метод вызывается в конце горутины.
- `(*WaitGroup) Wait()` — ожидает, когда значение счётчика будет равно нулю. Этот метод используется в основной функции, где нужно ожидать завершения горутин.

Увеличивать счётчик необходимо до вызова горутины, а не внутри или после неё. Представьте, что горутины ещё не успели начать работу, а цикл уже завершился. В таком случае `wg.Wait()` ждать просто нечего, так как счётчик не успел увеличиться.

## Safepoints и переключение горутин
**Частота:** 3/59
**Темы:** #go/scheduler #go/gc
- [x] Скорректировано ✅ 2026-06-22
- [x] последний повтор ✅ 2026-06-26

**Что ожидают на собесе:**


**Эталон на собесе:**

Safepoint (безопасная точка) — место в коде, где runtime гарантированно понимает состояние горутины и может безопасно сделать что-то служебное:
- остановить горутину для GC;
- выполнить preemption;
- просканировать стек;
- переместить стек при его росте;
- собрать диагностическую информацию.


Идея:

1. Runtime помечает горутину как кандидата на остановку.
2. Потоку отправляется сигнал.
3. Когда поток достигает безопасного места выполнения, происходит прерывание.


**Подробности:**
```
GMP
  ↓
Work stealing распределяет задачи

Preemption не дает одной G захватить CPU

Safepoints позволяют безопасно выполнить это preemption
и работу GC
```

## Work stealing и global queue
**Частота:** 3/59
**Темы:** #go/scheduler
- [x] Скорректировано ✅ 2026-06-22
- [x] последний повтор ✅ 2026-06-23

**Что ожидают на собесе:**


**Эталон на собесе:**
Воровство работы — балансировка планировщика: P (логический CPU) с пустой локальной очередью пытается забрать часть runnable горутин у другого P. 

При этом, глобальная очередь нужна как общий резерв для новых или пробуждённых горутин и для балансировки, когда локальные очереди не дают работы. Это снижает простой процессора и уменьшает contention на одной общей очереди.

**Подробности:**
- Локальная очередь привязана к P → меньше lock contention, лучше cache locality.
- Work stealing: простаивающий P забирает ~половину не выполняющихся G у другого P (рандомная жертва).
- Global run queue — fallback для новых/woken G и fairness при неудачном steal.
- P периодически (~каждые 61 scheduler tick) проверяет global, чтобы local-heavy P не starvel других.
- Порядок поиска работы: local → steal → global → netpoll.
- Sysmon при дисбалансе может перемещать G в global.
- Stealing снижает idle time P при неравномерной нагрузке (burst HTTP handlers).
- Глобальная очередь участвует при wakeup/syscall return — runnable G не застревают у одного P.

## Системные вызовы (syscall) в Go?
**Частота:** редко
**Темы:** #go/scheduler #go/runtime
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
Системный вызов — переход из user mode в kernel mode: файловый I/O, часть сетевых операций, таймеры и т.д. Для потока ОС это дорогое переключение контекста.

В Go горутина на **блокирующем** syscall паркуется: связанный M может остаться в kernel, а P (логический CPU) передаётся другому M, чтобы другие G продолжали работу. После возврата из syscall G попадает в run queue (часто через global queue).

Сетевой I/O часто идёт через **netpoller** без долгой блокировки M на каждую операцию.

**Типичные ошибки:**
- «Горутина = поток ОС, syscall блокирует всё приложение» — неверно при нормальном GMP.
- Путают syscall с cooperative yield на channel/mutex.

**Подробности:**
- См. [[2. GO - Средне#Что такое модель GMP и GOMAXPROCS?]] · [[3. GO - Редко 1#Work stealing и global queue]].
- После syscall: [[2. GO - Средне#Memory arenas (runtime после syscall)]].
- События парковки G: channel, mutex, syscall, netpoll, GC safepoint, preemption.

## `sync.Map`
**Частота:** 2/59
**Темы:** #go/sync #go/map
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
`sync.Map` — потокобезопасная специализированная map из стандартной библиотеки. 
Она работает не как обычная мапа, а через методы
Она нужна не просто «когда есть несколько goroutine», а когда подходит её модель нагрузки.

Официальные хорошие сценарии:
- ключ один раз записали и потом много раз читают, например cache, который в основном только растёт;
- разные goroutine часто работают с разными, почти независимыми наборами ключей.

В обычном коде часто лучше `map[K]V` + `sync.Mutex`/`sync.RWMutex`: это типобезопаснее и проще для инвариантов.
`sync.Map` не типобезопасна: ключи и значения имеют тип `any`.

**Подробности:**
- Основные методы: `Load`, `Store`, `LoadOrStore`, `LoadAndDelete`, `Delete`, `Range`.
- - `(m *Map) Delete(key any)` — удаляет значение указанного ключа;
- - `(m *Map) Load(key any) (value any, ok bool)` — возвращает значение ключа или `nil`, если оно отсутствует. В первом случае `ok` равно `true`, во втором — `false`;
- - `(m *Map) LoadOrStore(key, value any) (actual any, loaded bool)` — функция возвращает значение ключа, если оно существует. В противном случае, сохраняется и возвращается значение `value`. Возвращаемый параметр `loaded` равен `true`, если значение существует, и `false`, если оно было добавлено;
- - `(m *Map) Range(f func(key, value any) bool)` — перебирает все элементы мапы и для каждого вызывает функцию `f`. Если нужно прекратить перебор, то функция должна возвратить `false`;
- - `(m *Map) Store(key, value any)` — присваивает значение ключу.
- В новых версиях Go есть также `Swap`, `CompareAndSwap`, `CompareAndDelete`, `Clear`.
- Под капотом используется read-only часть и dirty-часть под mutex, но это implementation detail.
- Составная операция на нескольких ключах не становится атомарной: нужен внешний mutex, owner goroutine или транзакция на уровне хранилища.
- что для начала работы достаточно создать переменную типа `sync.Map`, вызов `make()` не нужен

Потокобезопасность типа `sync.Map` относится только к обращению с элементами мапы. Если мапа содержит какие-то объекты, например, слайсы, работа непосредственно с этими объектами требует отдельной синхронизации.

## `sync.Pool`
**Частота:** 2/59
**Темы:** #go/sync #go/gc
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
Sync.Pool — кэш временных объектов per-P, снижает аллокации под нагрузкой. При этом, объекты могут быть удалены GC в любой момент между Get/Put — Pool не должен хранить долгоживущее состояние.

**Типичные ошибки:**
- Хранят в Pool объекты с важным lifecycle или ссылками на большие графы.
- Считают Pool гарантированным кэшем как LRU map.

**Подробности:**
- Запись в nil map или конкурентная map без sync — panic или data race; `-race` ловит второе.
- Закрытый channel: чтение отдаёт zero значение + ok=false; запись — panic.

## Как работает GC (tri-color)?
**Частота:** 2/59
**Темы:** #go/gc
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
GC Go — concurrent tri-color mark-sweep: белые (не достигнуты), серые (в очереди), чёрные (обработаны). При этом, mutator работает параллельно с mark; write barrier сохраняет invariant. На практике, sweep освобождает неиспользуемые объекты.

- GOGC влияет на частоту циклов

## Когда interface == nil?
**Частота:** 2/59
**Темы:** #go/interfaces #go/errors
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
Interface равен nil только когда и динамический тип, и данные nil. Если в interface лежит типизированный nil указатель, сам interface уже не nil, потому type-компонента заполнена. Это часто ломает `if err != nil`, когда возвращают `(*MyError)(nil)` как `error`.

**Типичные ошибки:**
- Считать, что nil указатель внутри interface делает весь interface nil.
- Возвращать типизированный nil как `error` без явного nil.

**Подробности:**
- Модель: interface значение = `(type, data)`.
- `var e *MyErr = nil; var err error = e` даёт `err != nil`.
- Проверять нужно место возврата: возвращать `nil`, а не типизированный nil.

## Параллельные исходящие HTTP-запросы (fan-out)?
**Частота:** редко
**Темы:** #go/concurrency #go/context #go/stdlib
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
Типовая задача: один входящий HTTP-запрос → N независимых исходящих REST-вызовов → агрегировать JSON и отдать клиенту.

Паттерн: `errgroup.WithContext(parentCtx)` + по `g.Go` на каждый upstream; общий `ctx` с deadline/timeout; `g.Wait()` — сигнал «все завершились»; первая ошибка отменяет остальные через context.

Альтернатива: `sync.WaitGroup` + mutex под сбор результата; или одна goroutine-агрегатор и канал, но закрытие канала и «последняя goroutine» — хрупко без счётчика/`WaitGroup`.

**Типичные ошибки:**
- Счётчик/таймер вместо `WaitGroup`/`errgroup` — ненадёжное определение «все ответили».
- Нет timeout на весь fan-out — handler висит.
- Забыть передать `ctx` в `http.NewRequestWithContext`.

**Подробности:**
- См. [[3. GO - Редко 1#`errgroup`]] · [[3. GO - Редко 1#`sync.WaitGroup`]] · [[1. GO - Часто#context - что такое и зачем использовать?]].
- `errgroup.SetLimit(n)` — ограничить параллелизм к upstream.

> Как тестировать handler без поднятия порта?

**Эталон на собесе:**
`httptest` позволяет тестировать HTTP handler как обычную функцию: создать request, передать `ResponseRecorder` как `ResponseWriter`, вызвать `ServeHTTP` и проверить код, headers и body. При этом, внешние зависимости handler лучше вынести за interface и подменить fake/mock.

**Подробности:**
- `httptest.NewRecorder` хранит код ответа, заголовки и тело после вызова handler.
- `httptest.NewRequest(method, path, body)` создаёт request с контекстом без сетевого I/O.
- Для интеграционного теста можно использовать `httptest.Server`, когда нужно проверить client/transport.

**Что ожидают на собесе:**


**Эталон на собесе:**
Sync.Once гарантирует однократный вызов функции init в конкурентной среде — типично для ленивый singleton или тяжёлой конфигурации. При этом, повторные Do ждут завершения первого; внутри используется atomic + mutex.

**Типичные ошибки:**
- Вызывают Do с разными функциями — Once привязан к одному f.

- Повторные `Do` ждут завершения первого вызова; при panic в f поведение зависит от версии Go.
- На собесе часто путают с WaitGroup/Cond; Once — ровно один init.

## Append внутри функции по значению — виден ли снаружи?
**Частота:** 1/59
**Темы:** #go/slice
- [x] Скорректировано ✅ 2026-06-18
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
В функцию передается копия заголовка, базовый массив общий. 

Append обновляет локальный заголовок внутри функции. 
Функция меняет len у своей копии; у вызывающего len не меняется если не возвращать. 
При этом если позволяет cap, то базовый массив обновляется и можно увидеть снаружи через расширение len (взятие слайса)

Аналогично при выделении нового базового массива - обновление указателя на базовый массив снаружи не виден. 

При этом, существующие элементы могут измениться в общем массиве  - мутация существующих элементов `s[i] = v` видна вызывающему

**Подробности:**
Фиксы: 
- Return `s = append(s, x)` или указатель `*[]T`.
- Всегда переприсваивать результат append.
- Без return/указателя len снаружи не меняется.
- При достаточном cap элементы мутируют общий базовый массив.

## errors.Is / errors.As / %w?
**Частота:** 1/59
**Темы:** #go/errors
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
`%w` в `fmt.Errorf` сохраняет цепочку ошибок для unwrap. При этом, `errors.Is` проверяет, есть ли в цепочке конкретная sentinel error, а `errors.As` достаёт ошибку нужного типа. Это позволяет добавлять контекст к ошибке и не ломать машинную проверку причины.

**Типичные ошибки:**
- Сравнивать обёрнутую ошибку через == вместо `errors.Is`.
- Использовать `%v` там, где нужен unwrap через `%w`.

**Подробности:**
- `errors.Is(err, target)` проходит по цепочке `Unwrap` и учитывает пользовательский метод `Is`.
- `errors.As(err, &target)` требует указатель на переменную нужного типа и достаёт типизированную ошибку.
- sentinel-ошибки удобны для стабильных причин; типизированные ошибки нужны, когда вызывающему коду важны поля.

## go.mod — зачем нужен?
**Частота:** редко
**Темы:** #go/tooling #go/modules
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
`go.mod` — манифест Go-модуля: путь модуля (`module`), версия Go (`go`), прямые зависимости (`require`), при необходимости `replace` / `exclude` / `retract`.

Фиксирует **какие** модули и **какие версии** нужны проекту. Это не checksum-файл: целостность и воспроизводимость обеспечивает `go.sum`.

**Типичные ошибки:**
- Путают `go.mod` с lock-файлом npm — без `go.sum` checksums не зафиксированы.
- Редактируют `require` вручную вместо `go get` / `go mod tidy`.

**Подробности:**
- `go mod init`, `go mod tidy` синхронизируют зависимости с импортами в коде.
- `replace` — локальная подмена модуля (форк, monorepo).
- Коммитят в git вместе с `go.sum`.

## GOPRIVATE и GOPROXY?
**Частота:** редко
**Темы:** #go/tooling #go/modules
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
`GOPROXY` — список URL module proxy (по умолчанию `https://proxy.golang.org,direct`). Proxy кэширует модули; `direct` — загрузка напрямую с VCS при недоступности proxy.

`GOPRIVATE` — шаблоны приватных путей (`github.com/myorg/*`). Для них **не** используют публичный proxy и checksum database (`sum.golang.org`); модули качают напрямую. Часто вместе задают `GONOSUMDB` с теми же паттернами.

**Типичные ошибки:**
- Приватный модуль «утекает» в публичный proxy — не настроен `GOPRIVATE`.
- В CI нет доступа к VCS / `.netrc` / `GOPRIVATE` — `go mod download` падает.

**Подробности:**
- Корпоративный сценарий: свой Athens/Artifactory proxy + `GOPROXY=https://internal-proxy,direct`.
- `go env -w GOPRIVATE=...` для локальной разработки.
- См. [[3. GO - Редко 1#go.sum в git?]] · [[3. GO - Редко 1#go.mod — зачем нужен?]].

## Swiss map (Go 1.24+)
**Частота:** 1/59
**Темы:** #go/map #go/hash #go/runtime
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
С Go 1.24 runtime использует новую реализацию встроенной map на основе идей Swiss Table. Семантика для пользовательского кода та же: `map[K]V`, `range`, `delete`, `clear`, nil map и правила конкурентного доступа не изменились.

Главное отличие — другая внутренняя организация данных, которая улучшает locality и уменьшает накладные расходы старых overflow buckets.

**Подробности:**
Хеш-таблица основана на Swiss Table. Ключ хешируется, по хешу выбирается место, где может лежать ключ.

Данные организованы группами, рядом хранится служебная метадата — короткие отпечатки хеша. Сначала runtime быстро отбирает кандидатов по отпечаткам, затем сравнивает полные ключи.

Старой модели overflow buckets в прежнем виде нет: если место занято или произошла коллизия, поиск продолжается по правилам open addressing/Swiss Table. При росте используется другая логика расширения и разделения таблиц, поэтому старые детали про buckets и эвакуацию нельзя переносить один-в-один.
