## REST — принципы и best practices

**Частота:** 30/177
**Темы:** #http #network #architecture
- [ ] Скорректировано
- [ ] последний повтор

REST (Representational State Transfer) — архитектурный стиль для WEB-API: как клиент и сервер взаимодействуют через HTTP. Шесть ограничений (constraints):

1. **Клиент–сервер** — независимое развитие UI и бэкенда.
2. **Stateless** — каждый запрос самодостаточен; сессия клиента не хранится на сервере между запросами.
3. **Кэширование** — ответы явно помечают кешируемость (Cache-Control, ETag); меньше повторных вычислений.
4. **Единообразие интерфейса** — ресурсы + стандартные HTTP-методы; на высоком уровне зрелости — **HATEOAS** (ссылки в ответах).
5. **Слоистая система** — прокси, балансировщики, gateway; клиент не знает, сколько hop'ов за endpoint.
6. **Code on Demand** (опционально) — сервер может отдать исполняемый код клиенту (JS).

**RESTful** — API, которое следует этим принципам (ресурсы, глаголы HTTP, предсказуемые URL). **RESTless** — сознательные отклонения (RPC-стиль поверх HTTP, нестандартные verbs в path). Допустимо в маленьком внутреннем API или legacy, где переделка дороже; для публичного контракта лучше держаться REST/OpenAPI.

**HTTP-методы и семантика:**
- **GET** — чтение; **idempotent**, **safe**; параметры в query; тело обычно не используют.
- **POST** — создание / неидемпотентный action; тело; повтор может создать дубликат без idempotency key.
- **PUT** — полная замена ресурса (idempotent); иногда «создать, если нет» по известному URI.
- **PATCH** — частичное обновление (по стандарту часто не считают идемпотентным — зависит от реализации).
- **DELETE** — удаление (idempotent при корректной реализации).
- **HEAD** / **OPTIONS** — метаданные / список методов.

**GET vs POST (полно):**

| | GET | POST |
| --- | --- | --- |
| Назначение | получить данные | создать / обработать |
| Данные | чаще query/URL | body |
| Идемпотентность | да | нет |
| Кэш | да (по умолчанию) | нет |
| Секреты | не класть в URL (логи, history, Referer) | body + HTTPS |

«Только POST на всё» технически возможно, но ломает REST, кэш и SEO/индексацию. Создавать ресурс через GET — антипаттерн (кэш, prefetch, повторные запросы). Body у GET формально не запрещён, на практике ломается прокси/кэшами — не использовать.

**Версионирование API:** URL `/api/v1/…`, заголовок `Accept`, query `?version=`.

**Дополнительно:** OpenAPI; Richardson Maturity Model (0–3); **REST vs RPC** — REST описывает **существительными** (ресурсы), RPC — **глаголами** (login/logout/actions). Для CRUD данных чаще REST; для «действия» иногда честнее RPC/RPC-over-HTTP.---

## gRPC vs HTTP?
**Частота:** 15/177
**Темы:** #http #network #architecture
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-09

**Эталон на собесе:**

gRPC — RPC-фреймворк от Google на HTTP/2 с protobuf. Отличия от REST/HTTP:

|                    | REST/HTTP                      | gRPC                                                       |
| ------------------ | ------------------------------ | ---------------------------------------------------------- |
| Транспорт          | HTTP/1.1 (обычно)              | HTTP/2                                                     |
| Формат данных      | JSON (текстовый)               | Protobuf (бинарный, сжатый)                                |
| Стриминг           | Нет на уровне протокола        | 4 типа: unary, server stream, client stream, bidirectional |
| Типизация          | Слабая (JSON)                  | Строгая (.proto)                                           |
| Генерация кода     | Вручную или OpenAPI-генераторы | Автоматическая из .proto                                   |
| Производительность | Ниже                           | Выше (бинарный протокол, мультиплексирование)              |

gRPC подходит для internal low-latency RPC (микросервисы), REST — для external API и browser-клиентов.

**Подробности:**

**gRPC:**
- HTTP/2: мультиплексирование потоков, бинарные фреймы, сжатие заголовков
- Protobuf в приоритете — бинарный формат, строгая типизация, компактный
- 4 типа RPC:
  - Унарный — request + response синхронно
  - Серверный стрим — сервер стримит сообщения клиенту
  - Клиентский стрим — клиент стримит сообщения
  - Двунаправленный стрим — оба стримят одновременно
- Поддерживает JSON, но теряется смысл gRPC (скорость, типизация)
- grpc-gateway — REST API поверх gRPC (генерация JSON-эндпоинтов из proto)
- Версионирование proto через optional fields (backward compatibility)
- mTLS для аутентификации клиентов

**Когда выбирать gRPC:**
- Internal микросервисы, низкая latency
- Высоконагруженные системы (экономия трафика)
- Стриминг данных
- Полиглотная среда (генерация клиентов для разных языков)

**Когда выбирать REST/HTTP:**
- External API (третьи стороны, browser)
- Простота, человекочитаемость
- Когда не нужен стриминг
- Когда команда не знает protobuf

## HTTP vs HTTPS?
**Частота:** 12/177
**Темы:** #http #network
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-04

**Эталон на собесе:**
HTTP передаёт данные открытым текстом — любой промежуточный узел может читать и модифицировать трафик. HTTPS = HTTP поверх TLS: шифрование (конфиденциальность), HMAC (целостность), аутентификация сервера сертификатом. Порты: 80 (HTTP) vs 443 (HTTPS).

**Подробности:**
- **TLS handshake:** клиент → ClientHello (версии TLS, cipher suites, SNI) → сервер → ServerHello + сертификат → асимметричный обмен ключами (ECDHE) → сессионный симметричный ключ для данных. TLS 1.3: 1-RTT вместо 2-RTT у 1.2, forward secrecy по умолчанию, убраны устаревшие cipher suites.
- **Что НЕ шифрует HTTPS:** SNI (имя домена — видно до рукопожатия), IP-адреса, размер и тайминги пакетов (traffic analysis), DNS-запросы (если не DoH/DoT).
- **SSL** (1.0–3.0) устарел и небезопасен. В prod — **TLS 1.2** (минимум) / **TLS 1.3** (рекомендован). Разговорно «SSL» часто значит TLS.
- **mTLS:** сервер дополнительно проверяет клиентский сертификат. Применяется в межсервисном взаимодействии (service mesh / Istio / нулевое доверие).
- **HSTS:** заголовок `Strict-Transport-Security` заставляет браузер всегда использовать HTTPS для домена, даже если пользователь ввёл `http://`. Защита от downgrade-атак.

## TCP vs UDP?
**Частота:** 12/177
**Темы:** #http #network
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-04

Оба — **транспортный уровень**. Разница в модели доставки.

**TCP** — протокол **с установлением соединения**. Перед данными — handshake: `SYN` → `SYN-ACK` → `ACK`. Дальше — двусторонний обмен.

- **Надёжность** — ACK, повторная передача, таймауты; потерянный сегмент дожимают, пока не доставят (или соединение не оборвут).
- **Упорядоченность** — сегменты собирают в исходный порядок; out-of-order буферизуют.
- **Поток байт** — границы сообщений приложения TCP сам не сохраняет (фрейминг — на прикладном уровне).
- **Цена** — состояние соединения, 3 пакета на старт, контроль перегрузки; медленнее «голого» UDP.

Где типичен: HTTP/HTTPS, FTP, SMTP/IMAP, SSH, PostgreSQL wire, gRPC.

**UDP** — **без соединения**, сообщения-датаграммы. Отправил — и не знает, дошло ли.

- **Без гарантий** — нет ACK/retransmit на уровне протокола.
- **Без порядка** — два пакета могут прийти в любом порядке.
- **Границы сообщений** сохраняются (прочитал — получил исходную датаграмму).
- **Легковесность** — нет handshake и тяжёлого state; выше риск коллапса перегрузки, если приложение само не ограничивает поток.

Где типичен: DNS, VoIP/видеозвонки, онлайн-игры, SNMP/DHCP; база для QUIC (надёжность уже на прикладном/QUIC-слое).

**Как выбирать на собесе:** нужна доставка и порядок «из коробки» → TCP. Нужна минимальная latency и допустимы потери/дубли → UDP (или чинить надёжность самим / брать QUIC).

В стеке backend: наружный HTTP API и БД-клиент почти всегда TCP; realtime/metrics/DNS-резолв — часто UDP.

## Уровни стека TCP/IP
**Частота:** 3/177
**Темы:** #http #network
- [ ] Скорректировано
- [ ] последний повтор

**TCP/IP** (модель Internet, 4 уровня) — практический стек сети:

1. **Link (канальный)** — Ethernet, Wi‑Fi: кадры, MAC, физическая среда.
2. **Internet (сетевой)** — **IP**: адресация и маршрутизация между сетями, фрагментация; **без** гарантии доставки и порядка. Работает и на хостах, и на роутерах.
   - IPv4 — 32 бит (`192.0.2.34`); IPv6 — 128 бит (`2001:db8::1`).
3. **Transport** — **TCP** / **UDP**: порты, связь конец–конец (см. «TCP vs UDP»).
4. **Application** — HTTP/HTTPS, DNS, FTP/SFTP, SMTP/IMAP/POP3, SSH, WebSocket, MQTT, gRPC…

В заголовках IP+транспорт обычно: IP отправителя/получателя + порт источника/назначения.

**OSI** — учебная 7-уровневая модель (physical → data link → network → transport → session → presentation → application). Маппинг на собесе: TCP/IP application ≈ OSI 5–7; link ≈ OSI 1–2; IP ≈ OSI 3; TCP/UDP ≈ OSI 4. Не смешивать «7 слоёв OSI» и «4 слоя TCP/IP» как одну нумерацию.---

## Передача данных в HTTP: body, path и query
**Частота:** 2/177
**Темы:** #http
- [ ] Скорректировано
- [ ] последний повтор

- **Path** — идентифицирует ресурс (`/users/42`).
- **Query** — фильтры/опции (`?page=1&sort=asc`); попадает в логи, Referer, историю — **не для секретов**.
- **Body** — полезные данные (JSON / form-data) у POST/PUT/PATCH; у GET тело обычно не используют.

**GET vs POST (смысл + практика):**
- **GET** — «получить ресурс»: идемпотентен и safe, хорошо кэшируется; параметры чаще в query/URL. Длина URL ограничена (порядка килобайт — зависит от клиента/сервера).
- **POST** — «отправить на обработку/создание»: данные в body, объём больше (лимит задаёт сервер), повтор без защиты может создать дубликат. Пароль в URL через GET — антипаттерн (светится в истории/прокси).

См. также семантику методов в «REST — принципы…» и path vs query в ярусе 2.

## HTTP cookies: Set-Cookie, хранение и отправка
**Частота:** 1/177
**Темы:** #http #network
- [ ] Скорректировано
- [ ] последний повтор

**Cookie** — небольшой фрагмент данных: сервер отдаёт `Set-Cookie`, браузер сохраняет и при следующих запросах к подходящему домену/пути автоматически шлёт в заголовке `Cookie`.

```
Set-Cookie: session_id=abc123; HttpOnly; Secure; Max-Age=3600; SameSite=Strict
Cookie: session_id=abc123
```

Типичное применение: аутентификация / session id; персональные настройки; корзина; аналитика/трекинг.

| Тип / атрибут | Смысл |
| --- | --- |
| Session | живёт до закрытия браузера |
| Persistent | `Max-Age` / `Expires` |
| HttpOnly | JS не читает (XSS) |
| Secure | только HTTPS |
| SameSite | ограничение cross-site (CSRF) |

**Сессия** — логика/хранилище на сервере (часто по session id из cookie) или JWT без серверного state. Cookie сами по себе — хранилище у клиента.
