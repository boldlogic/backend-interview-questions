

### 5.4 Set через map
**Частота:** 42/59
- [ ] Скорректировано
- [ ] последний повтор
**Эталон на собесе:**
В Go нет встроенного типа set, но его обычно делают через map. В качестве значения часто используют пустую структуру: она не несёт данных и явно показывает, что важен только факт наличия ключа.

**Подробности:**
`map[T]struct{}` для set;
`struct{}` занимает 0 байт.
При этом, проверка: `_, ok := m[k]`;
удаление: `delete(m, k)`.

- `map[T]bool` тоже работает, но `struct{}` явно показывает, что значение не несёт смысла.
- Ключ set должен быть comparable: `int`, `string`, struct/array из comparable полей; slice/map/func нельзя.

### 4.1 Чем слайс отличается от массива?
**Частота:** 36/59
- [ ] Скорректировано
**Эталон на собесе:**
Массив - это структура с фиксированной длиной, размер - часть типа. 
А слайс это надстройка над массивом которая позволяет иметь динамическую длину. Слайс не хранит данные сам, а является ссылкой на часть базового массива = ссылка+метаданные. 

Массив обычно сравнимый, если элементы сравнимые, слайс не сравнимый. 

Массив после объявления заполняется нулевыми значениями, а слайс nil - нужно мейкать.

Массив в функцию обычно копируется целиком - мутации снаружи не видны, а у слайса копируется только заголовок - мутации существующих элементов в общем базовом массиве видны.

### 4.3 Рост capacity слайса / Как работает append?
- [x] Скорректировано ✅ 2026-06-18
**Частота:** 10/59

**Эталон на собесе:**
При `len == cap` — выделяется новый массив, копирование элементов, новый указатель в заголовке слайса.

Рост cap при append: 
- до 256 элементов ~×2, 
- далее плавный переход к ~×1.25 через хитрые формулы с выравниваниями.
- cap округляется до **size class** аллокатора — реальный cap может быть чуть больше формулы

**Подробности:**
Runtime `nextslicecap` (Go 1.18+):
- `oldCap < 256` — **×2**
- `oldCap ≥ 256` — плавный рост к **~×1.25** (`newcap += (newcap + 3×256) / 4`)
- `newLen > 2×oldCap` — `newcap = newLen`
- cap округляется до **size class** аллокатора — реальный cap может быть чуть больше формулы. Выравнивание памяти с округлением до 1 байта вверх, если размер элемента меньше 8 бит

**Сложность:** один `append` — O(1); 
realloc — O(n); 
серия append по одному — O(1) амортизированно.

**Append в func** до realloc меняются **элементы** в общем базовый массив, **`len` caller** — нет; после realloc новый ptr только внутри func.

### 5.2 Как устроена map под капотом?
**Частота:** 23/59
- [ ] Скорректировано
**Эталон на собесе:**
Map — хеш-таблица. Ключ хешируется, по хешу выбирается область таблицы, дальше рантайм ищет конкретный ключ внутри бакета/группы.

До Go 1.24 основа реализации — массив бакетов. В одном бакете до 8 пар ключ/значение + служебные данные. Если в бакете несколько кандидатов, сначала проверяется короткий фрагмент хеша, потом сравнивается полный ключ.
Если в один бакет попало слишком много ключей, появляются **overflow buckets** — дополнительные бакеты-цепочки. Это хуже для производительности, потому что приходится ходить дальше по связанному списку.

При росте создаётся новая область бакетов. Обычно число бакетов увеличивается, но возможен и same-size grow, когда проблема в большом числе overflow buckets. Старые бакеты остаются в `oldbuckets`, данные переносятся не сразу, а постепенно — это называется эвакуацией.

**Подробности:**
При чтении `v := m[key]` считается хеш, выбирается нужная область таблицы, затем runtime проверяет кандидатов и сравнивает ключи.

- Мутация map во время `range` в той же goroutine разрешена с оговорками; конкурентная запись из другой goroutine без синхронизации — fatal error.
- В старой реализации `hmap` хранит, например, `count`, `B` (`log2` числа бакетов), seed хеша и указатели на бакеты. Это детали runtime, не часть спецификации языка.

### 5.6 Порядок итерации map
**Частота:** 24/59
- [ ] Скорректировано
**Эталон на собесе:**
Итерация `for k, v := range m` идёт в неопределённом порядке. Нельзя полагаться ни на порядок вставки, ни на стабильность между разными обходами. Для детерминированного порядка нужно собрать ключи и отсортировать.

**Подробности:**
- Runtime намеренно не даёт стабильного порядка, чтобы код не начинал зависеть от детали реализации.
- Порядок может отличаться между запусками программы и между двумя обходами одной и той же map.
- С Go 1.23 `maps.Keys(m)` возвращает iterator, а не slice. Для сортировки удобно: `keys := slices.Sorted(maps.Keys(m))`.
- Если во время обхода удалить ключ, который ещё не был посещён, он уже не будет выдан. Если добавить новый ключ, он может попасть в текущий обход, а может не попасть.

### 2.2 Какие виды каналов бывают?
**Частота:** 36/59
- [x] Скорректировано ✅ 2026-06-17
**Эталон на собесе:**
Есть буферизированный и не буферизированный. 

**Небуферизированный** канал — синхронный: отправитель встречается с получателем, данные передаются из стека одной горутины в стек другой горутины. Работают по аналогии с эстафетной палочкой: нельзя отправить, пока некому прочитать. 
- Создание без ёмкости:
  ```go
  ch := make(chan [тип данных])
  ```
- Ёмкость и длина равны 0.

**Буферизированный** - канал у которого есть определенный буфер, не блокирует запись, пока len < cap. Буферы помогают избежать лишних простоев. Буфер это кольцевая очередь. По аналогии с почтовым ящиком: пока есть место в ящике, отправитель может положить значение и уйти. 
- Создание с ёмкостью:
  ```go
  ch := make(chan [тип данных], 1)
  ```
- Ёмкость фиксирована (проверяется через `cap()`), текущее количество элементов — через `len()`.
- **Буферизация влияет только на поведение блокировки.**

### 11.9 Map + channel: concurrent send
**Частота:** 40/59
- [ ] Скорректировано
**Эталон на собесе:**
Map не потокобезопасен — нужен `sync.Mutex`/`RWMutex` или `sync.Map`. При этом, channel требует парного читатель/писатель или buffer; иначе блокировка или deadlock.

**Подробности:**
- Паттерн: одна goroutine владеет map, остальные шлют команды в channel.
- close(channel) только когда все senders завершены — иначе panic у поздних send.
- hchan содержит send/recv queues и lock; size>0 — ring buffer в channel struct.

### 11.8 Указатель в цикле — один адрес
**Частота:** 31/59

**Эталон на собесе:**
В `for range` до Go 1.22 переменная итерации переиспользовалась, поэтому взятие `&v` давало один и тот же адрес. При этом, правильнее брать адрес элемента через индекс: `&items[i]`, либо создавать копию переменной на итерации. В новых версиях ловушка смягчена для range, но привычка проверять адрес остаётся полезной.

**Типичные ошибки:**
- Не различать адрес копии значения и адрес элемента в slice.

**Подробности:**
- `for i := range items { ptrs = append(ptrs, &items[i]) }` берёт адрес элемента.
- Для map нельзя взять стабильный адрес значение напрямую: значения могут перемещаться.
- Та же идея важна для closures, которые захватывают переменную цикла.

### 2.5 Select: псевдослучайный выбор case
**Частота:** 13/59
- [ ] Скорректировано
**Эталон на собесе:**
Если несколько ветвей готовы — runtime выбирает случайный. Порядок ветвей игнорируется. Это сделано для предотвращения зависаний и взаимоблокировок. 

При этом, `default` только если ни один не ready.

**Подробности:**
- Не путать с `switch` по порядку.
- Starvation не гарантируется равномерной.
- select с default даёт non-blocking операции; без default goroutine блокируется.

### 5.1 Сложность доступа по ключу в map?
**Частота:** 13/59
- [ ] Скорректировано
**Эталон на собесе:**
Чтение по ключу в среднем O(1). В худшем случае может деградировать до O(n), если много коллизий.
Запись и удаление тоже O(1) в среднем, но амортизированно: отдельная операция может быть дороже из-за роста таблицы и переноса данных.

**Подробности:**
- Go использует рандомизацию хеширования; у map есть собственный seed, а runtime добавляет случайность на уровне процесса.
- Стоимость ключа важна: `int`/`uint`/указатели дешевле, `string` зависит от длины, большие struct/array дороже хешировать и сравнивать.
