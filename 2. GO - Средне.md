## Select: псевдослучайный выбор case
**Частота:** 13/59
**Темы:** #go/select #go/channel
- [x] Скорректировано ✅ 2026-06-21
- [x] последний повтор ✅ 2026-06-26

**Что ожидают на собесе:**


**Эталон на собесе:**
Если несколько ветвей готовы — runtime выбирает случайный. Порядок ветвей игнорируется. 

- Позволяет работать с несколькими каналами одновременно.
- Перебирает условия `case`; выполняется случайный сработавший блок. Это сделано для предотвращения зависаний и взаимоблокировок. 
- нужно учитывать что при закрытии канала может возвращать нулевые значения
- case с чтением nil канала игнорируется

default
- Выполняется, если ни один `case` не может быть выполнен.
- Если отсутствует, `select` будет ожидать выполнения одного из `case`.

**Подробности:**
- Не путать с `switch` по порядку.
- Проверка вариантов идёт в **случайном порядке!**
- Starvation не гарантируется равномерной.
- select с default даёт non-blocking операции; без default goroutine блокируется.

Если нужно постоянно проводить проверки условий `case`, то `select` помещают в цикл. Важно не забыть про `default`, он может привести к росту утилизации ресурсов — может срабатывать на каждой итерации.

 Для прерывания цикла с select
- `return` для выхода из функции.
- Изменение условия цикла.
- `break` с меткой цикла.

## Data race и `-race`
**Частота:** 12/59
**Темы:** #go/data-race #go/sync
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
Data race возникает, когда несколько goroutines обращаются к одной переменной без синхронизации и хотя бы одно обращение — запись.
При этом, исправляют через mutex, channel владение, atomic или неизменяемый data. 

`-race` инструментирует программу и находит реальные гонки на выполненных путях, но не доказывает их отсутствие.

**Подробности:**
- Happens-before задают `Mutex.Unlock` → `Lock`, channel send → receive, `sync.Once`, atomic Load/Store.
- `-race` обычно запускают в CI на тестах и интеграционных сценариях; он замедляет выполнение и увеличивает память.
- Гонка возможна и при `GOMAXPROCS=1`: модель памяти Go требует синхронизацию, а не только отсутствие параллельных ядер.

## Канал vs мьютекс
**Частота:** 11/59
**Темы:** #go/channel #go/sync
- [x] Скорректировано ✅ 2026-06-26
- [x] последний повтор ✅ 2026-06-26

**Что ожидают на собесе:**


**Эталон на собесе:**
**Мьютекс** — примитив синхронизации, который позволяет только одной горутине находиться в части кода, где необходим эксклюзивный доступ. 

При этом, channel — передача работы/результатов между goroutines. 

**Подробности:**
- Counter/cache — mutex проще.
- Fan-in/fan-out — channel + select.
Когда первый поток входит в критическую секцию, мьютекс блокируется до тех пор, пока поток не покинет её. Пока мьютекс заблокирован, другие горутины ждут его разблокировки. Как только он разблокирован, одна из ожидающих горутин успевает заблокировать его и получить эксклюзивный доступ к критической секции кода.

## Что если GOMAXPROCS=1 и goroutine блокируется?
**Частота:** 11/59
**Темы:** #go/scheduler #go/data-race
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26

**Что ожидают на собесе:**


**Эталон на собесе:**
При `GOMAXPROCS=1` все горутины на одном процессоре — параллелизма нет, но конкурентность есть. При этом, блокирующий syscall/network может парковать горутину; netpoller и другие горутины продолжают работу.

**Типичные ошибки:**
- Думать, что GOMAXPROCS=1 убивает все goroutines.

**Подробности:**
- Один P — G исполняются по очереди на одном CPU, но тысячи G могут существовать одновременно.
- Block на channel/mutex: G паркуется, другая runnable G берёт P.
- Netpoller на одном P: сетевые G ждут readiness, CPU-G продолжают крутиться.
- Blocking syscall может отнять M; runtime создаст новый M для P, если нужно.
- `-race` ловит unsynchronized memory access даже при `GOMAXPROCS=1`.
- Логические гонки (lost update без data race) `-race` не найдёт.
- CPU-heavy G после 1.14 вытесняются sysmon, но не мгновенно — возможны короткие «монопольные» участки.

## Что при записи/чтении из закрытого канала?
**Частота:** 11/59
**Темы:** #go/channel
- [x] Скорректировано ✅ 2026-06-21
- [x] последний повтор ✅ 2026-06-26

**Что ожидают на собесе:**


**Эталон на собесе:**
Запись в закрытый channel — panic. При этом, чтение — сначала буфер, потом zero значение, `ok=false`. 
повторное закрытие — panic.

| Состояние                | Запись (`ch <- v`)                                                                                                                  | Чтение (`<-ch`, `v, ok := <-ch`)                                                                             | Закрытие (`close(ch)`)                               |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| **nil**                  | Блокировка навсегда                                                                                                                 | Блокировка навсегда                                                                                          | Паника                                               |
| **Не nil и не закрыт**   | Небуферизованный: без готового получателя — блокировка. Буферизированный: при месте в буфере — без блокировки, иначе блок до чтения | Блокируется до получения значения; в буфере — сразу, если есть данные                                        | Закрывает канал; не влияет на уже находящиеся данные |
| **Закрыт** (`close(ch)`) | **Паника**                                                                                                                          | Возвращает нулевое значение типа канала (например, 0 для `chan int`); `ok = false` при форме `v, ok := <-ch` | **Паника** (повторное закрытие)                      |

**Подробности:**
- `for range ch` завершается после close+вычитывания.

## Как устроен слайс?
**Частота:** 10/59
**Темы:** #go/slice
- [x] Скорректировано ✅ 2026-06-18
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
Слайс — заголовок, который содержит
- Адрес первого элемента (&slice[0]) указывает на фактические данные в массиве.
- len - сколько элементов сейчас
- cap - максимальная емкость, сколько элементов может разместить текущий базовый массив 
- cap ≥ len всегда

Инициализируется через make или литерал. Иначе nil - слайс. 

Адрес слайса (&slice) — это адрес структуры с метаданными (SliceHeader), которая содержит информацию о Data, Len, Cap.

Длина меняется через append.
- Append без превышения cap — тот же базовый массив.
- Рост cap при append: до 256 элементов ~×2, далее плавный переход к ~×1.25 через хитрые формулы с выравниваниями.

Передача slice в функцию копирует заголовок, базовый массив общий но не элементы — мутации существующих элементов видны снаружи.

Сложность append O(1), при создании нового базового массива О(n) 

copy(dst, src) копирует min(len(dst), len(src)) элементов, не cap.

**Nil vs пустой:** `var s []int` — nil (`len=0`, `cap=0`); `s := []int{}` или `make([]int, 0)` — non-nil, тоже `len=0`. Оба принимают `append`.

**Синтаксис среза:** `s[low:high]` — `[low, high)`; опущенный low = 0, high = len. Full slice: `s[low:high:max]` — cap нового view = `max - low`.

```go
var nilSlice []int           // nil
nonNil := make([]int, 0)     // [] non-nil
s := make([]int, 3, 10)
t := []int{1, 2, 3}
```

### Строка и `[]byte`

- Строка **неизменяемая**, UTF-8; `s[i]` — **байт**, не символ.
- `for range` по строке — **руны**.
- Изменить текст: `[]rune`, `strings.Builder` или `[]byte` + копия.

## Рост capacity слайса / Как работает append?
**Частота:** 10/59
**Темы:** #go/slice
- [x] Скорректировано ✅ 2026-06-26
- [x] последний повтор ✅ 2026-06-23

**Что ожидают на собесе:**


**Эталон на собесе:**
При превышении cap — выделяется новый массив, копирование элементов, новый указатель в заголовке слайса.

Рост cap при append: 
- до 256 элементов ~×2, 
- далее плавный переход к ~×1.25 через хитрые формулы с выравниваниями.

**Подробности:**
Runtime `nextslicecap` (Go 1.18+):
- `oldCap < 256` — **×2**
- `oldCap ≥ 256` — плавный рост к **~×1.25** (`newcap += (newcap + 3×256) / 4`)
- `newLen > 2×oldCap` — `newcap = newLen`
- cap округляется до **size class** аллокатора — реальный cap может быть чуть больше формулы. Выравнивание памяти с округлением до 1 байта вверх, если размер элемента меньше 8 бит

**Сложность:** один `append` — O(1); 
realloc — O(n); 
серия append по одному — O(1) амортизированно.

**Append в func** до realloc меняются **элементы** в общем базовый массив, **`len` caller** — нет; после realloc новый ptr только внутри func.

## Что такое модель GMP и GOMAXPROCS?
**Частота:** 10/59
**Темы:** #go/scheduler
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26

**Что ожидают на собесе:**


**Эталон на собесе:**
GMP: 
- **G** (goroutine). Содержит стек горутины, состояние выполнения, информацию для планировщика. 
- **M** (Machine). Реальный поток ОС. На них запускаются горутины
- **P** (Processor) логический CPU (контекст планировщика). связывает горутины и потоки. У каждого P есть локальная очередь горутин, кэш аллокаций и данные для планировщика

**Подробности:**

- M должен быть привязан к P, чтобы выполнять G; без P M idle или в syscall.
- Local run queue (~256 G): новые G от `go` кладутся в local P текущей G (load spreading).
- Пустая локальная очередь → кража половины горутин у случайного P → global run queue → netpoll.
- `GOMAXPROCS(n)` ограничивает число P (на скольких ядрах будет выполняться код), не число G и не число M (M может быть больше при блокирующих syscall).
- Sysmon — фоновый поток (M): следит за long-running G, retake P, будит netpoller.
- Blocking syscall: G отсоединяется, M может остаться в kernel; P передаётся другому M.
- Netpoller пробуждает G, когда файловый дескриптор готов к read/write.

```
M1 -> syscall (заблокирован)

P1 отвязывается от M1

P1 прикрепляется к M2

другие G продолжают работать
```

## Cooperative vs preemptive scheduling в Go?
**Частота:** 9/59
**Темы:** #go/scheduler
- [x] Скорректировано ✅ 2026-06-22
- [x] последний повтор ✅ 2026-06-26

**Что ожидают на собесе:**


**Эталон на собесе:**

кооперативная многозадачность - Горутина сама должна добровольно отдать управление.
вытесняющая многозадачность - Планировщик может принудительно остановить горутину и переключиться на другую.
Современный Go использует GMP-планировщик с поддержкой асинхронного вытеснения, поэтому одна "жадная" горутина обычно не мешает остальным работать.

Runtime вставляет специальные безопасные точки (safe points), где можно выполнить переключение без повреждения состояния программы.

 sysmon вытесняет long CPU loops.

**Подробности:**
- До Go 1.14: yield только на blocking ops — channel, mutex, select, syscall, GC safepoint.
- Tight loop без вызовов функций мог indefinitely держать P до 1.14.
- С 1.14+: cooperative **и** preemptive — sysmon + async preemption (signal) на safepoints.
- Safepoint: prologue/epilogue функций, loop back-edges, runtime checks — не «любая инструкция».
- Не OS-style preemption: нет прерывания на каждой инструкции как у pthread.
- `runtime.Gosched()` — добровольная уступка: G попадает в run queue, другая G берёт тот же P.
- С Go 1.21+ preemption улучшен для части паттернов (async preemption без остановки на каждом safepoint).

## Утечка горутин
**Частота:** 7/59
**Темы:** #go/goroutine #go/channel #go/tooling
- [x] Скорректировано ✅ 2026-06-26
- [x] последний повтор ✅ 2026-06-23

**Что ожидают на собесе:**


**Эталон на собесе:**
Утечка горутин — это ситуация, когда горутина больше не нужна приложению, но не может завершиться и продолжает удерживать ресурсы. Чаще всего причиной являются зависание на канале, отсутствие отмены через context, незакрытые каналы или забытые ticker/timer. Предотвращается корректным управлением жизненным циклом через context и закрытие каналов.

**Подробности:**
- Переключение G: block (chan/mutex/WaitGroup), syscall, netpoll park, `runtime.Gosched`, preemption.
- Blocking syscall: handoff P, G в waiting; M может block в kernel, P продолжит другие G.
- Netpoller (epoll/kqueue/IOCP): readiness → G runnable → run queue.
- Safepoints нужны для GC stack scan, stack growth check и preemption.
- Long CPU loop: sysmon (~10 ms) может инициировать preemption post-1.14, но не на каждой инструкции.
- Утечка goroutine: G заблокированы навсегда — send без recv, забытый ctx, worker без shutdown.
- Диагностика leak: `go tool pprof -http=:8080 'http://localhost/debug/pprof/goroutine?debug=2'` — stack trace покажет, на каком sync-примитиве висит G 
- Fix leak: context cancel, `close(ch)`, WaitGroup, корректное завершение worker pool.

## defer, panic, recover
**Частота:** 5/59
**Темы:** #go/errors
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
`defer` — отложенный вызов при выходе из функции (LIFO). 
Аргументы выражения в `defer` считаются в момент **регистрации** `defer`, не при выполнении.

Останавливает обычное исполнение текущей goroutine, **раскручивает стек**, выполняет отложенные `defer` (LIFO), печатает stack trace и завершает процесс — если panic не погашен.

`panic(v)` — `v` любого типа; `recover()` возвращает этот аргумент.

При этом, `recover` ловит panic только в той же goroutine, где `defer recover`.

**Подробности:**
- defer с recover — типичный паттерн в HTTP middleware. Handler без recover — одна паника роняет весь процесс.
- `recover` только в `defer` **той же goroutine**. Panic в одной goroutine не ловится `recover` в другой.
- Не всё recoverable: OOM, concurrent map write, deadlock.
- `recover()` вне deferred func — no-op, возвращает nil.
- Runtime сам вызывает panic: nil pointer deref, index out of range, send on closed channel, failed type assertion без `ok`.

```go
defer func() {
    if r := recover(); r != nil {
        log.Printf("panic: %v\n%s", r, debug.Stack())
    }
}()
```

|              | `return error`                        | `panic`                         |
| ------------ | ------------------------------------- | ------------------------------- |
| Когда        | сеть, файлы, validation, «нет данных» | невозможно продолжать безопасно |
| Стоимость    | обычный return                        | раскрутка стека                 |
| В библиотеке | основной путь                         | только документированные случаи |

## Можем ли взять указатель на элемент мапы
**Частота:** средне
**Темы:** #go/map #go/pointers
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26

**Что ожидают на собесе:**


Нельзя взять адрес элемента map: `&m[k]` не компилируется. Значение внутри map не addressable потому что такой адрес может потом оказаться недействительным. 

Причина: runtime может перемещать данные map при росте или внутренней перестройке, поэтому стабильный адрес элемента не гарантируется. Go запрещает указатель на значение, которое map может переложить в другое место.

Адрес самой переменной map взять можно: `&m`. Нельзя именно брать адрес элемента по ключу.

При этом если поместили структуру в мапу и нужно менять значение в поле, то можно сделать так:
```go
type a struct{
b int
}
map[k]=*a
//и менять через точку
map[k].b++
```

## Что такое планировщик
**Частота:** средне
**Темы:** #go/scheduler
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26

**Что ожидают на собесе:**


Планировщик Go — это компонент Go, отвечающий последовательность выполнения горутин, из которых состоит программа Go

планировщик Go оперирует горутинами только одной программы, он намного проще, дешевле и быстрее, чем планировщик ядра операционной системы.

**подробности:**
В Go используется модель планировщика GMP.

**G (goroutine)** — горутина, выполняемая задача.

**M (machine)** — поток операционной системы.

**P (processor)** — логический процессор runtime, через который горутины назначаются потокам.

У каждого процессора есть локальная очередь горутин. Если у одного процессора задач много, а у другого нет, используется механизм **воровства работы (work stealing)** — свободный процессора забирает часть задач себе.

При блокирующих системных вызовах runtime старается отвязать процессора от заблокированного потока и продолжить выполнение на другом потоке.

Для того чтобы одна горутина не могла бесконечно занимать процессор, используется **вытесняющая многозадачность (preemption)**.

Вытеснение и работа сборщика мусора выполняются через **безопасные точки (safepoints)** — места, где runtime может безопасно остановить горутину.
