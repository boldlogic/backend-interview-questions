## defer, panic, recover / exceptions в Go
**Частота:** 15/84
**Темы:** #go/errors #go/defer
- [ ] Скорректировано
- [ ] последний повтор

`defer`— отложенный вызов при выходе из функции (LIFO).
`panic(v)`—значение любого типа;`recover()` возвращает этот аргумент.
`recover` ловит panic только в той же горутине, где `defer recover`.
**Подробности:**
- defer с recover — типичный паттерн в HTTP middleware. Handler без recover — одна паника роняет весь процесс.
- `recover` только в `defer`**той же горутина**. Panic в одной горутине не ловится `recover` в другой.
- Не всё recoverable: OOM, concurrent map write, deadlock. 
- `recover()` вне deferred func — no-op, возвращает nil.
- Runtime сам вызывает panic: nil pointer deref, index out of range, send on closed канал, failed type assertion без `ok`.
```go
defer func() {
if r := recover(); r != nil {
log.Printf("panic: %v\n%s", r, debug.Stack())
}
}()
```
| | `return error` | `panic` |
| ------------ | ------------------------------------- | ------------------------------- |
| Когда | сеть, файлы, validation, «нет данных» | невозможно продолжать безопасно |
| Стоимость | обычный return | раскрутка стека |
| В библиотеке | основной путь | только документированные случаи |
`defer` откладывает вызов функции до выхода из окружающей функции (return или panic). Несколько `defer` выполняются в порядке **LIFO**. 
`defer` выполняется **после** вычисления return values, но **до** выхода из функции. Записи defer — на куче (defer chain), не на стеке вызывающего.
Аргументы выражения в `defer` считаются в момент **регистрации**`defer`, не при выполнении.
Останавливает обычное исполнение текущей горутины, **раскручивает стек**, выполняет отложенные `defer` в обратном порядке, печатает stack trace и завершает процесс — если panic не погашен.
Типично:`close`,`Unlock`,`cancel()`, recover в middleware.
**Как формулируют на собесе:**
> Есть ли в Go exceptions, как в Java/C#?
**Эталон на собесе:**
Классической модели checked/unchecked exceptions в Go нет. Ожидаемые ошибки возвращают через `error`. Для невосстановимых ситуаций —`panic` и `recover`(обычно на границе горутина, например HTTP middleware).

## Что такое generics?
**Частота:** 10/84
**Темы:** #go/generics
- [ ] Скорректировано
- [ ] последний повтор

Дженерики — это механизм параметрического полиморфизма, позволяющий писать универсальные функции и типы, работающие с разными типами данных без дублирования кода. Типы задаются через параметры (`T`), которые при необходимости ограничиваются constraints, например `any` или `comparable`. 
Дженерики сохраняют статическую типизацию и позволяют избежать использования `interface{}` там, где нужен типобезопасный универсальный код.
Не заменяют интерфейсы для поведения.
**Эталон на собесе:**
Generics — **Go 1.18+**. Компилятор мономорфизирует (stenciling) или GC shape — не ручная кодогенерация как `go generate`, но похожий эффект «отдельный код на тип».

## Расскажи про каналы / Что это такое каналы, какие бывают, все-все

- Канал - примитив синхронизации который предназначен для обмена данными между горутинами. либо сообщать горутине что нужно завершить работу
- Потокобезопасный за счет мьютекса внутри, 
- обработка в порядке ФИФО. 
- Ссылочный тип. Когда передаете канал в функции, на самом деле передается указатель на канал.
- **какие бывают** есть деление по направлению - на каналы только для чтения или только для записи, делаются через приведение типа.
- есть разделение на буферизированный и небуферизированный
- Небуферизированный сразу блокируется, не может записать или не может прочитать
- Буферизированный позволяет хранить несколько значений и блокировка возникает только когда буфер переполнен.
- буферизированный имеет буфер, очередь на запись, очередь на чтение
- Каждое записанное в канал значение может быть считано только один раз
- Хранится в куче.

## Mutex и RWMutex / Когда Mutex, а когда RWMutex?
**Частота:** 7/84
**Темы:** #go/sync
- [x] Скорректировано ✅ 2026-06-29
- [x] последний повтор ✅ 2026-06-30

**Mutex** — эксклюзивная блокировка: 
- в один момент времени **только одна** горутина выполняет защищённый код. 
- Это убирает гонку при read-modify-write и составных инвариантах на нескольких полях.

**RWMutex** — много параллельных **читателей** **или** один **писатель**. 
- Писатель блокирует всех читателей (приоритет writer);  
- новые читатели не проходят, пока ждёт писатель. 
- при частых записях — читатели могут **голодать**, писатели тоже при постоянном потоке readers.
- Ожидающие горутины ставятся в **FIFO**-очередь семафора; при длинных критических секциях возможен **starvation** — нужны короткие секции и иногда fair lock / отдельная архитектура.
- При частых записях overhead RWMutex не окупается; 

RWMutex имеет те же методы `Lock()` и `Unlock()`, но использовать их нужно только для критической секции, изменяющей данные. Для кода, который читает данные, нужно использовать методы `RLock()` и `RUnlock()`.`RLock()` не даст выполниться `Lock()` и начать изменение данных, пока не будут завершены все операции чтения.

| Состояние                                                             | Метод `RLock()`                                                                                           | Метод `Lock()`                                                                         |
| --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Мьютекс свободен                                                      | Возьмёт мьютекс в режиме чтения                                                                           | Возьмёт мьютекс в режиме записи                                                        |
| Одна горутина уже взяла мьютекс через `RLock()`                       | Возьмёт мьютекс в режиме чтения. Блокировки не будет                                                      | Будет блокировать горутину до тех пор, пока другие горутины не отпустят мьютекс        |
| Одна горутина уже взяла мьютекс через `RLock()`. Вторая ждёт `Lock()` | Будет блокировать горутину до тех пор, пока другая горутина не дождётся метода `Lock()` и не отпустит его | Будет блокировать горутину до тех пор, пока не будут отпущены все остальные блокировки |
| Одна горутина взяла мьютекс через `Lock()`                            | Будет блокировать горутину до тех пор, пока не будут отпущены все блокировки на запись                    | Будет блокировать горутину до тех пор, пока не будут отпущены все остальные блокировки |
При использовании мьютексов нужно обязательно придерживаться трёх основных правил
1. После блокировки мьютекса его всегда нужно разблокировать. Если этого не сделать, другие горутины так и будут ожидать своей очереди на выполнение критической секции.
2. Если вы применяете мьютексы для синхронизации доступа к общим данным, следите за тем, чтобы не было горутин, работающих с этими данными без мьютекса. Например, если значение общей переменной меняется горутинами в двух местах, а мьютекс применяется только в одном, то смысла в этом нет, так как ошибки всё равно будут.
3. В общем случае нужно стремиться сокращать продолжительность выполняемого кода внутри критической секции.

- Назвать **профайлинг** как основной способ найти узкие места.
- Знать `go tool pprof`, уметь читать flame graph / top.
- (бонус) Пример, когда pprof дал кратный выигрыш (лишние аллокации, горячий lock, лишние копии).

**Профайлинг** — измерение, где программа тратит CPU, память и время ожидания. В Go: **`go tool pprof`**,`runtime/pprof`,`net/http/pprof`.

| Профиль                        | Что показывает                | Когда смотреть               |
| ------------------------------ | ----------------------------- | ---------------------------- |
| **CPU**                        | горячие функции, % времени    | «медленно считает»           |
| **heap** (inuse / alloc_space) | живые объекты / все аллокации | утечки, churn GC             |
| **goroutine**                  | стеки, блокировки             | leak, deadlock на chan/mutex |
| **block / mutex**              | где ждут lock/I/O             | contention                   |
Сбор:` go test -cpuprofile cpu.prof -bench .`; в сервисе —` import _ "net/http/pprof"`и` curl localhost:6060/debug/pprof/profile?seconds=30 `.
Разбор:`go tool pprof -http=:8080 cpu.prof`— flame graph, top, graph. Ищем **широкие** полоски в flame graph и функции с большим **flat** + **cum** %.
**Подробности:**
- go tool pprof -http=:8080 cpu.prof — flame graph.
- heap: inuse_objects, alloc_space — утечки и churn.
- горутина: блокировки на канал/mutex.
- Типичный win: убрали лишний `append` в цикле, заменили `fmt.Sprintf` в hot path, шардировали mutex — CPU −30…70% после heap/cpu profile.
- В prod: `import _ "net/http/pprof"` → `/debug/pprof/`; sampling overhead обычно ~2–5% CPU при типичных интервалах.

## Как устроено ООП в Go?
**Частота:** 7/84
**Темы:** #go/oop #go/interfaces
- [x] Скорректировано ✅ 2026-06-29
- [x] последний повтор ✅ 2026-06-30

ООП в Go строится через композицию и интерфейсы.

В Go нет наследования (возможность создания производных от родительского объекта). Есть **Embedding**  - встраивает поле и продвигает его методы, но это не subclass: состояние и инварианты всё равно принадлежат конкретной struct. 

**Полиморфизм** (возможность одному и тому же фрагменту кода работать с разными типами данных) — через **интерфейсы**; 
Интерфейсы реализуются неявно, поэтому зависимость можно держать на стороне потребителя.

**Embedding** позволяет "унаследовать" поля и методы встроенного типа, 
а **интерфейсы** обеспечивают единый контракт для разных реализаций.

**Инкапсуляция** (возможность скрыть реализацию объекта) — экспортируемые/неэкспортируемые имена.

**Подробности:**
- **Accept interfaces, return structs** — интерфейс объявляют в пакете **потребителя**; маленький iface дублировать дешевле, чем тянуть зависимость на пакет реализации (как `io.Reader` в stdlib).

**Абстракция** — возможность описать свойства и методы объекта; в Go роль «класса» играет struct + methods.

## Порядок итерации map
**Частота:** 7/84
**Темы:** #go/map
- [x] Скорректировано ✅ 2026-06-29
- [x] последний повтор ✅ 2026-07-03


Итерация `for k, v := range m` идёт в неопределённом порядке. Нельзя полагаться на стабильность между разными обходами.


- Runtime намеренно не даёт стабильного порядка, чтобы код не начинал зависеть от детали реализации. 
- Неупорядоченность обхода - побочный эффект seed хэша (задается на процесс для защиты от DoS)
- Порядок может отличаться между запусками программы и между двумя обходами одной и той же map.
- Для детерминированного порядка нужно собрать ключи и отсортировать.
- Если во время обхода удалить ключ, который ещё не был посещён, он уже не будет выдан. 
- Если добавить новый ключ, он может попасть в текущий обход, а может не попасть.

## Что такое map? / Как устроена map под капотом?
**Частота:** 7/84
**Темы:** #go/map #go/hash #go/runtime
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-30

Map — хеш-таблица: ключ-значение
Состоит из **массива бакетов** + **hash-функция** по ключу.
- Хеш-функция это функция...
- быстрый доступ по ключу (в среднем O(1)), 
- неупорядоченная итерация. 
- Ссылочный тип;`nil` map нельзя писать без `make`. 
- Не потокобезопасна без синхронизации.

в Go 1.24+ (Swiss map) — **open addressing** внутри групп. Много коллизий = хуже locality и больше сравнений ключей.

До Go 1.24 основа реализации — массив бакетов. В одном бакете до 8 пар ключ/значение + служебные данные. Если в бакете несколько кандидатов, сначала проверяется короткий фрагмент хеша, потом сравнивается полный ключ.

**Коллизии:** несколько ключей попали в один бакет → в старой реализации **overflow buckets** (цепочка дополнительных бакетов);  Это хуже для производительности, потому что приходится ходить дальше по связанному списку.

При росте создаётся новая область бакетов. Обычно число бакетов увеличивается, но возможен и same-size grow, когда проблема в большом числе overflow buckets. Старые бакеты остаются в `oldbuckets`, данные переносятся не сразу, а постепенно — это называется эвакуацией.

**Подробности:**
При чтении `v := m[key]` 
1. считается хеш, 
2. выбирается нужная область таблицы (или бакет), 
3. затем runtime проверяет кандидатов и сравнивает ключи. (сначала по короткому фрагменту хеша)

- На тип значений ограничений нет.
- Seed хеша задаётся на процесс (защита от hash-DoS; побочно — случайный порядок обхода)
- Мутация map во время `range` в той же горутине разрешена с оговорками; конкурентная запись из другой горутина без синхронизации — fatal error.
- В старой реализации `hmap` хранит, например,`count`,`B`(`log2` числа бакетов), seed хеша и указатели на бакеты.
- `new(map[K]V)` не используют потому что nil
- nil map:`m[k]` возвращает нулевое значение;`m[k] = v`— panic. Инициализированная map:`m := make(map[K]V)`.
- В func копируется заголовок, не указатель на map. Запись `m[k] = v` внутри func видна снаружи — общие данные, но это не передача *map.
- `v, ok := m[k]`— ok ложен, если ключа нет (даже когда нулевое значение был бы валидным значением)
- `delete(m, k)`,`clear(m)`(Go 1.21+),`clear(nil)`— no-op.`len(m)`— число пар.
- Сравнивать две map между собой нельзя — для равенства `maps.Equal` или ручной обход.
- map не может быть ключом другой map.
- Копия —` maps.Clone`
```go
var m map[string]int // nil
m = make(map[string]int)
v, ok := m[k]
delete(m, k)
clear(m) // Go 1.21+
```

## Процесс / поток / IPC
**Частота:** 6/84
**Темы:** #go/goroutine #go/scheduler
- [ ] Скорректировано
- [ ] последний повтор

- Программа - это файл в котором содержатся инструкции и данные. Процесс = исполняемый бинарь. При запуске программы ОС создаёт отдельный процесс — это сама программа и сопутствующие ресурсы. Экземпляр программы, выполняемой ОС.
- **Процесс - контейнер с памятью и ресурсам**и. Хранит код программы, но не может его выполнить. Среда выполнения, в которой содержатся инструкции, ресурсы полученные во время выполнения программы.
- Поток создается процессом, имеет собственный процесс управления и стек. **Поток=подмножество процесса.**
- **Поток - линия выполнения внутри процесса.** Каждый поток имеет доступ к родительскому процессу и содержит собственные ресурсы. По сути, поток — это единица выполнения кода на уровне ОС.
- В процессе может быть несколько потоков и множество горутин.
- ОС планирует потоки а процессы служат для изоляции потоков и управления ресурсами.
- Таким образом, имеется множество потоков и несколько ядер. Выполнением N потоков на M ядрах руководит планировщик операционной системы. Он берёт поток, загружает в память его **контекст** (ресурсы, дескрипторы, состояние регистров) и отправляет его на выполнение ядру. Через какой-то промежуток времени планировщик сохраняет контекст потока, прекращает его выполнение и загружает следующий поток.
- Так как потоков очень много, а ядер мало, то планировщик меняет потоки выполнения очень часто. Из-за этого создаётся впечатление, что сотня программ и сервисов работает параллельно. А на самом деле они выполняются по очереди.
- Переключение потоков - медленное потому что контекст потока не маленький.
**IPC:**
**Как формулируют на собесе:**
> Процессы и потоки могут друг с другом как-то общаться?
**Эталон на собесе:**
- Процессы **изолированы** по адресному пространству; для обмена данными нужен **IPC**: pipes/named pipes, сокеты (TCP, Unix domain), shared memory (`mmap`), message queues.
- Потоки **одного процесса** делят память; **горутины** — ещё легче: один процесс, координация через каналы/mutex внутри runtime.
- В Go типично: сокеты/`net`, `os/exec` + stdin/stdout, gRPC/HTTP между процессами; для локального IPC — Unix domain sockets.

## `sync.WaitGroup`
**Частота:** 5/84
**Темы:** #go/sync
- [x] Скорректировано ✅ 2026-06-30
- [x] последний повтор ✅ 2026-06-30

содержит счетчик который равен количеству еще не завершенных горутин


`wg.Add(n)` перед стартом goroutines; каждая горутина вызывает `Done`;`Wait` в main ждёт counter=0. Panic при отрицательном счётчике.
-`Add` до `go` или внутри горутина до `Wait`, но не после `Wait`.
-`defer wg.Done` в каждой горутина — типичный паттерн.
Не вызывать `Wait` из горутина, которая сама делает `Done`— deadlock.

Для работы с `WaitGroup` достаточно запомнить три метода
-`(*WaitGroup) Add(delta int) `— изменяет значение счётчика на указанную величину. Перед тем как создать горутину, достаточно вызвать `Add(1)`.
-`(*WaitGroup) Done() `— уменьшает значение счётчика на единицу. Этот метод вызывается в конце горутины.
-`(*WaitGroup) Wait() `— ожидает, когда значение счётчика будет равно нулю. Этот метод используется в основной функции, где нужно ожидать завершения горутин.
Увеличивать счётчик необходимо до вызова горутины, а не внутри или после неё. Представьте, что горутины ещё не успели начать работу, а цикл уже завершился. В таком случае `wg.Wait()` ждать просто нечего, так как счётчик не успел увеличиться.

## Сборщик мусора: что, зачем, отключение / Как работает GC
**Частота:** 5/84
**Темы:** #go/gc
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

**Эталон на собесе:**
GC освобождает **недостижимый** heap даже если память «ещё используется» другими объектами — циклы без ссылок снаружи тоже собираются. Tri-color, concurrent.`GOGC`,`GOMEMLIMIT`; полное off —`GOGC=off`(редко, риск OOM). Упростить жизнь GC: меньше аллокаций,`sync.Pool`, избегать лишних указателей.

- фase mark обходит граф от roots (stack, globals, registers).
- Concurrent GC снижает STW, но write barrier добавляет overhead на указатель writes.
- GOGC влияет на частоту циклов

Garbage Collection - это процесс освобождения места в памяти, которое больше не используется.

GC выполняется конкурентно, одновременно с потоками мутатора, в точном соответствии с типом (этот принцип также известен как чувствительность к типу), допускается параллельная выполнение нескольких потоков GC. Это конкурентная пометка и очистка (mark-sweep), при которой используется барьер записи (write barrier). При этом в процессе ничего не генерируется и не сжимается. Освобождение памяти выполняется на основе размера, выделенного для каждой программы Р, чтобы в общем случае минимизировать фрагментацию и избежать блокировок.

В основе работы GC Go лежит "трехцветный алгоритм". Официальное название "трехцветный алгоритм пометки и очистки". Использует барьер памяти. Главный принцип алгоритма трехцветной пометки и очистки состоит в разделении объектов, находящихся куче, на три набора, в соответствии с "цветом".  Условно разделяются на 3 цвета:
- черные объекты - гарантированно не имеют указателей на белые объекты;
- серые объекты - могут иметь указатели на белые объекты;
- белые объекты - на них могут ссылаться некоторые серые объекты и сами некоторые белые объекты могут ссылаться на некоторые черные.
Краткий алгоритм:
1. Все объекты сначала белые;
2. Идет перебор "корневых" объектов, помечаются как серые. Корневые - это объекты к которым можно обращаться напрямую, например глобальные переменные, элементы в стеке и т.д.
3. Идет перебор серых объектов, проверяются ссылки на другие объекты и помечаются на черные объекты. Если есть ссылка на белый объект, то белый становится серым.
4. Продолжается до тех пор, пока не будут перебраны все серые объекты.
5. Оставшиеся после перебора белые объекты считаются недостижимыми и занимаемая ими область памяти может быть освобождена.
Есть еще Мутатор - это приложение, работающее во время сборки мусора. Вызывает функцию барьера записи. Выполняется каждый раз, когда меняется указатель в куче. После изменения указателя объект считается достижимым и помечается как серый.

## Чем конкурентность отличается от параллелизма?
**Частота:** 5/84
**Темы:** #go/concurrency #go/scheduler
- [x] Скорректировано ✅ 2026-06-22
- [x] последний повтор ✅ 2026-07-03

Конкурентность — много задач конкурируют за один общий ресурс. Прогресс за счёт чередования (на одном или нескольких ядрах).

Параллелизм — много задач выполняются на многих ресурсах. Одновременное исполнение на CPU на нескольких ядрах; требует `GOMAXPROCS > 1` и независимую работу.

Будет или нет конкурентный код выполняться параллельно зависит от железа (несколько ядер). На одном ядре возможна конкурентность без параллелизма.

- При `GOMAXPROCS = 1` конкурентность есть, параллелизма на CPU — нет.
- I/O-нагрузка: много G ждут сеть/диск — высокая конкурентность при низкой загрузке CPU.
- CPU-нагрузка: параллелизм требует несколько P и достаточно независимых задач.
- Асинхронность (не блокировать вызывающий код) ≠ параллелизм (несколько ядер одновременно).

## Cooperative vs preemptive scheduling в Go?
**Частота:** 4/84
**Темы:** #go/scheduler
- [x] Скорректировано ✅ 2026-06-22
- [x] последний повтор ✅ 2026-06-29

кооперативная многозадачность - Горутина сама должна добровольно отдать управление.
вытесняющая многозадачность - Планировщик может принудительно остановить горутину и переключиться на другую.
Современный Go использует GMP-планировщик с поддержкой асинхронного вытеснения, поэтому одна "жадная" горутина обычно не мешает остальным работать.
Runtime вставляет специальные безопасные точки (safe points), где можно выполнить переключение без повреждения состояния программы.
sysmon вытесняет long CPU loops.

**Подробности:**
- До Go 1.14: yield только на blocking ops — канал, mutex, select, syscall, GC safepoint.
- Tight loop без вызовов функций мог indefinitely держать P до 1.14.
- С 1.14+: cooperative **и** preemptive — sysmon + async preemption (signal) на safepoints.
- Safepoint: prologue/epilogue функций, loop back-edges, runtime checks — не «любая инструкция».
- Не OS-style preemption: нет прерывания на каждой инструкции как у pthread.
-`runtime.Gosched()`— добровольная уступка: G попадает в run queue, другая G берёт тот же P.

## Work stealing и global queue
**Частота:** 4/84
**Темы:** #go/scheduler
- [x] Скорректировано ✅ 2026-06-29
- [x] последний повтор ✅ 2026-06-29

Воровство работы — балансировка планировщика: P (логический CPU) с пустой локальной очередью пытается забрать часть runnable горутин у другого процессора.

глобальная очередь нужна как общий резерв для новых или пробуждённых горутин и для балансировки, когда локальные очереди не дают работы. Это снижает простой процессора и уменьшает contention на одной общей очереди.


- Локальная очередь привязана к P → меньше lock contention, лучше cache locality.
- Work stealing: простаивающий P забирает ~половину не выполняющихся G у другого P (рандомная жертва).
- Global run queue — fallback для новых/woken G и fairness при неудачном steal.
- P периодически (~каждые 61 scheduler tick) проверяет global, чтобы local-heavy P не starvel других.
- Порядок поиска работы: local → steal → global → netpoll.
- Sysmon при дисбалансе может перемещать G в global.
- Stealing снижает idle time P при неравномерной нагрузке (burst HTTP handlers).
- Глобальная очередь участвует при wakeup/syscall return — runnable G не застревают у одного P.

## Передача и возврат: значение vs указатель? / Value vs pointer receiver
**Частота:** 4/84
**Темы:** #go/pointers #go/memory #go/performance #go/methods

- [x] Скорректировано ✅ 2026-06-27
- [x] последний повтор ✅ 2026-06-27

**Передача в функцию:**
**По значению** — копия аргумента. Дешево для `int`,`pointer`, маленьких struct (до ~few cache lines). Функция не может изменить оригинал (кроме полей-указателей внутри struct).

**По указателю** — общий объект: нужна **мутация**, struct **большой**, или тип **нельзя** копировать (`sync.Mutex`).

Go разрешает вызывать `*T `-метод на value и наоборот (авто `&`/ разыменование), но семантика копирования остаётся.

**Возврат из функции:**
- **По значению** — компилятор часто кладёт на stack или регистры; для маленьких struct это снижает аллокации на кучу и нагрузку на GC.
- **По указателю** — когда возвращаем большой объект, shared state, или явно «optional» через `nil`.
Escape analysis решает stack vs heap — не угадывать, а смотреть ` go build -gcflags="-m"`.

## errors.Is / errors.As / %w?
**Частота:** 3/84
**Темы:** #go/errors
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-30

`%w `в` fmt.Errorf ` сохраняет цепочку ошибок для unwrap.
`errors.Is` проверяет, есть ли в цепочке конкретная sentinel error, 
а `errors.As` достаёт ошибку нужного типа. Это позволяет добавлять контекст к ошибке и не ломать машинную проверку причины.

-`errors.Is(err, target)` проходит по цепочке `Unwrap` и учитывает пользовательский метод `Is`.
-`errors.As(err, &target)` требует указатель на переменную нужного типа и достаёт типизированную ошибку.

sentinel-ошибки удобны для стабильных причин; типизированные ошибки нужны, когда вызывающему коду важны поля.

**Подробности:**
- `net.Error`: `Timeout()` / `Temporary()` (deprecated в новых версиях) — **recoverable** vs fatal; в современном Go — typed errors + `errors.Is`/`As`, wrapping через `%w`.

## Атомарные операции
**Частота:** 3/84
**Темы:** #go/atomic
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27
- **Атомарная операция** — это операция, которая выполняется за один шаг относительно других горутин. Горутина не может прервать своё выполнение во время такой операции, а кроме этого, другие горутины не могут начать эту же самую операцию. Это похоже на транзакции из темы про базы данных, только у атомарной операции не может быть отката.
- sync/atomic - атомарные операции для целочисленных типов:`int32`,`int64`,`uint32`,` uint64`
- Во всех функциях передаются указатели на числовые значения в которых необходима атомарность
- atomic.AddInt64(&addr, 1) // прибавляем 1
- В пакете `sync/atomic` определены типы-обёртки:`atomic.Bool`,`atomic.Int32`,`atomic.Int64` и так далее. Для начала работы с такими «обёртками» достаточно описать переменную нужного типа, например,`var i atomic.Int64`. Эти типы вместо функций имеют соответствующие методы.

## Мапа потокобезопасная?
**Частота:** 3/84
**Темы:** #go/map #go/data-race
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

Обычная `map`**не потокобезопасна**.

| Сценарий                              | Можно?                                                  |
| ------------------------------------- | ------------------------------------------------------- |
| Несколько goroutine **только читают** | да                                                      |
| Хотя бы одна **пишет**                | **нет** — data race / `fatal error: concurrent map ...` |
| Read + write одновременно             | **нет**                                                 |
Защита:`sync.Mutex`/`RWMutex` вокруг map; 
**одна горутина-владелец** + канал; **`sync.Map`** для cache-like read-mostly .
`recover` от runtime fatal **не** спасает — map может быть уже повреждена.

-`go test -race` ловит гонки до production.
