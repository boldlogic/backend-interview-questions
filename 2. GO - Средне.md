## Что такое defer?
**Частота:** 8/84
**Темы:** #go/defer
- [x] Скорректировано ✅ 2026-06-29
- [x] последний повтор ✅ 2026-06-29
 
`defer` откладывает вызов функции до выхода из окружающей функции (return или panic). Несколько `defer` выполняются в порядке **LIFO**. 
`defer` выполняется **после** вычисления return values, но **до** выхода из функции. Записи defer — на куче (defer chain), не на стеке вызывающего.

Аргументы выражения в `defer` считаются в момент **регистрации**`defer`, не при выполнении.

Останавливает обычное исполнение текущей горутины, **раскручивает стек**, выполняет отложенные `defer` в обратном порядке, печатает stack trace и завершает процесс — если panic не погашен.

Типично:`close`,`Unlock`,`cancel()`, recover в middleware.

## `atomic` vs mutex
**Частота:** 14/84
**Темы:** #go/atomic #go/sync
- [x] Скорректировано ✅ 2026-06-27
- [x] последний повтор ✅ 2026-06-30

**`atomic.AddInt64(&v, 1)`** — одна атомарная RMW-операция без захвата mutex; 
подходит для счётчиков, флагов, указателей в lock-free структурах.

**Mutex** — защищает **несколько полей** и составные инварианты (map + len + cache).

| | atomic | mutex |
|---|--------|-------|
| Сценарий | один счётчик, CAS | map, slice, несколько полей |
| Скорость | быстрее mutex на hot counter | дороже, но универсальнее |
| Ограничение | только поддерживаемые типы | любые данные |

Когда счётчик/флаг — **`atomic`**, когда сложный инвариант — **mutex**.

(бонус) Atomic **быстрее mutex** для простого счётчика, но **медленнее** обычной локальной переменной.

## Work stealing и global queue
**Частота:** 3/84
**Темы:** #go/scheduler
- [x] Скорректировано ✅ 2026-06-29
- [x] последний повтор ✅ 2026-06-29

Воровство работы — балансировка планировщика: P (логический CPU) с пустой локальной очередью пытается забрать часть runnable горутин у другого процессора.

глобальная очередь нужна как общий резерв для новых или пробуждённых горутин и для балансировки, когда локальные очереди не дают работы. Это снижает простой процессора и уменьшает contention на одной общей очереди.


- Локальная очередь привязана к P → меньше lock contention, лучше cache locality.
- Work stealing: простаивающий P забирает ~половину не выполняющихся G у другого P (рандомная жертва).
- Global run queue — fallback для новых/woken G и fairness при неудачном steal.
- P периодически (~каждые 61 scheduler tick) проверяет global, чтобы local-heavy P не starvel других.
- Порядок поиска работы: local → steal → global → netpoll.
- Sysmon при дисбалансе может перемещать G в global.
- Stealing снижает idle time P при неравномерной нагрузке (burst HTTP handlers).
- Глобальная очередь участвует при wakeup/syscall return — runnable G не застревают у одного P.

## В чем разница между процессом и потоком
**Частота:** 5/84
**Темы:** #go/goroutine #go/scheduler
- [x] Скорректировано ✅ 2026-06-27
- [x] последний повтор ✅ 2026-06-30

- Программа - это файл в котором содержатся инструкции и данные. Процесс = исполняемый бинарь. При запуске программы ОС создаёт отдельный процесс — это сама программа и сопутствующие ресурсы. Экземпляр программы, выполняемой ОС.
- **Процесс - контейнер с памятью и ресурсам**и. Хранит код программы, но не может его выполнить. Среда выполнения, в которой содержатся инструкции, ресурсы полученные во время выполнения программы.
- Поток создается процессом, имеет собственный процесс управления и стек. **Поток=подмножество процесса.**
- **Поток - линия выполнения внутри процесса.** Каждый поток имеет доступ к родительскому процессу и содержит собственные ресурсы. По сути, поток — это единица выполнения кода на уровне ОС.
- В процессе может быть несколько потоков и множество горутин.
- ОС планирует потоки а процессы служат для изоляции потоков и управления ресурсами.
- Таким образом, имеется множество потоков и несколько ядер. Выполнением N потоков на M ядрах руководит планировщик операционной системы. Он берёт поток, загружает в память его **контекст** (ресурсы, дескрипторы, состояние регистров) и отправляет его на выполнение ядру. Через какой-то промежуток времени планировщик сохраняет контекст потока, прекращает его выполнение и загружает следующий поток.
- Так как потоков очень много, а ядер мало, то планировщик меняет потоки выполнения очень часто. Из-за этого создаётся впечатление, что сотня программ и сервисов работает параллельно. А на самом деле они выполняются по очереди.
- Переключение потоков - медленное потому что контекст потока не маленький.

## Сборщик мусора: что, зачем, отключение / Как работает GC
**Частота:** 6/84
**Темы:** #go/gc
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

**Эталон на собесе:**
GC освобождает **недостижимый** heap даже если память «ещё используется» другими объектами — циклы без ссылок снаружи тоже собираются. Tri-color, concurrent.`GOGC`,`GOMEMLIMIT`; полное off —`GOGC=off`(редко, риск OOM). Упростить жизнь GC: меньше аллокаций,`sync.Pool`, избегать лишних указателей.

- фase mark обходит граф от roots (stack, globals, registers).
- Concurrent GC снижает STW, но write barrier добавляет overhead на указатель writes.
- GOGC влияет на частоту циклов

Garbage Collection - это процесс освобождения места в памяти, которое больше не используется.

GC выполняется конкурентно, одновременно с потоками мутатора, в точном соответствии с типом (этот принцип также известен как чувствительность к типу), допускается параллельная выполнение нескольких потоков GC. Это конкурентная пометка и очистка (mark-sweep), при которой используется барьер записи (write barrier). При этом в процессе ничего не генерируется и не сжимается. Освобождение памяти выполняется на основе размера, выделенного для каждой программы Р, чтобы в общем случае минимизировать фрагментацию и избежать блокировок.

В основе работы GC Go лежит "трехцветный алгоритм". Официальное название "трехцветный алгоритм пометки и очистки". Использует барьер памяти. Главный принцип алгоритма трехцветной пометки и очистки состоит в разделении объектов, находящихся куче, на три набора, в соответствии с "цветом".  Условно разделяются на 3 цвета:
- черные объекты - гарантированно не имеют указателей на белые объекты;
- серые объекты - могут иметь указатели на белые объекты;
- белые объекты - на них могут ссылаться некоторые серые объекты и сами некоторые белые объекты могут ссылаться на некоторые черные.
Краткий алгоритм:
1. Все объекты сначала белые;
2. Идет перебор "корневых" объектов, помечаются как серые. Корневые - это объекты к которым можно обращаться напрямую, например глобальные переменные, элементы в стеке и т.д.
3. Идет перебор серых объектов, проверяются ссылки на другие объекты и помечаются на черные объекты. Если есть ссылка на белый объект, то белый становится серым.
4. Продолжается до тех пор, пока не будут перебраны все серые объекты.
5. Оставшиеся после перебора белые объекты считаются недостижимыми и занимаемая ими область памяти может быть освобождена.
Есть еще Мутатор - это приложение, работающее во время сборки мусора. Вызывает функцию барьера записи. Выполняется каждый раз, когда меняется указатель в куче. После изменения указателя объект считается достижимым и помечается как серый.

## Append внутри функции по значению — виден ли снаружи?
**Частота:** 2/84
**Темы:** #go/slice
- [x] Скорректировано ✅ 2026-06-18
- [x] последний повтор ✅ 2026-07-03

**Эталон на собесе:**
В функцию передается копия заголовка, базовый массив общий.
Append обновляет локальный заголовок внутри функции.
Функция меняет len у своей копии; у вызывающего len не меняется если не возвращать.
При этом если позволяет cap, то базовый массив обновляется и можно увидеть снаружи через расширение len (взятие слайса)
Аналогично при выделении нового базового массива - обновление указателя на базовый массив снаружи не виден.
существующие элементы могут измениться в общем массиве - мутация существующих элементов `s[i] = v` видна вызывающему
**Подробности:**
Фиксы
- Return `s = append(s, x)` или указатель `*[]T `.
- Всегда переприсваивать результат append.
- Без return/указателя len снаружи не меняется.
- При достаточном cap элементы мутируют общий базовый массив.

## errors.Is / errors.As / %w?
**Частота:** 3/84
**Темы:** #go/errors
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-30

`%w `в` fmt.Errorf ` сохраняет цепочку ошибок для unwrap.
`errors.Is` проверяет, есть ли в цепочке конкретная sentinel error, 
а `errors.As` достаёт ошибку нужного типа. Это позволяет добавлять контекст к ошибке и не ломать машинную проверку причины.

-`errors.Is(err, target)` проходит по цепочке `Unwrap` и учитывает пользовательский метод `Is`.
-`errors.As(err, &target)` требует указатель на переменную нужного типа и достаёт типизированную ошибку.

sentinel-ошибки удобны для стабильных причин; типизированные ошибки нужны, когда вызывающему коду важны поля.

## Бинарный поиск vs дерево поиска (оба O(log n))
**Темы:** #go/complexity #go/algorithms
**Частота:** 2/84
- [ ] Скорректировано
- [ ] последний повтор
**Как формулируют на собесе:**
> Бинпоиск и дерево — оба O(log n). Зачем оба? В чём разница по памяти?

**Эталон на собесе:**
Одинаковая **асимптотика**, разная **модель данных**
- **Бинарный поиск** — по **отсортированному массиву** in-place; доп. Память O(1), но вставка/удаление O(n).
- **Дерево поиска (BST/B-tree)** — структура с указателями/узлами; вставка/удаление/поиск O(log n) при балансировке; больше памяти на метаданные узлов, зато динамические обновления.
На собесе VK ждут: бинпоиск — когда массив уже есть и редко меняется; дерево — когда нужны частые вставки или индекс в БД (B-tree).
**Типичные ошибки:**
- «Разницы нет, оба логарифм» — игнорировать стоимость вставки и память.
- Путать бинпоиск в массиве с обходом дерева рекурсией (стек/alloc).

## Когда interface == nil?
**Частота:** 2/84
**Темы:** #go/interfaces #go/errors
- [x] Скорректировано ✅ 2026-06-30
- [x] последний повтор ✅ 2026-06-27

Interface равен nil только когда и динамический тип, и данные nil. 
Если в interface лежит типизированный nil указатель, сам interface уже не nil, потому type-компонента заполнена. Это часто ломает `if err != nil`, когда возвращают `(*MyError)(nil) `как` error `.

**Подробности:**
- Модель: interface значение =`(type, data) `.
-`var e *MyErr = nil; var err error = e` даёт `err != nil`.
- Проверять нужно место возврата: возвращать `nil`, а не типизированный nil.

## Можем ли взять указатель на элемент мапы
**Частота:** 3/84
**Темы:** #go/map #go/pointers
- [x] Скорректировано ✅ 2026-06-27
- [x] последний повтор ✅ 2026-06-27

- Нельзя взять адрес элемента map:`&m[k] ` не компилируется. Значение внутри map не addressable потому что такой адрес может потом оказаться недействительным.
- Причина: runtime может перемещать данные map при росте или внутренней перестройке, поэтому стабильный адрес элемента не гарантируется. Go запрещает указатель на значение, которое map может переложить в другое место.
- Адрес самой переменной map взять можно:`&m `. Нельзя именно брать адрес элемента по ключу.
- При этом если поместили структуру в мапу и нужно менять значение в поле, то можно сделать так
```go
type a struct{
b int
}
c:=make(map[key]*a,10)
c[key].b=1

```
- и менять через точку

> Что такое очередь с приоритетом? На какой структуре реализовать? Что такое heap?

**Эталон на собесе:**
**Priority queue** — элемент с наивысшим (или наименьшим) приоритетом извлекается первым. Наивно — отсортированный список O(n) на вставку; оптимально — **binary heap** (min-heap / max-heap): вставка и извлечение корня O(log n), peek O(1). В памяти heap часто хранится как **массив** с индексной арифметикой (родитель/дети).
**Типичные ошибки:**
- Путать heap (куча приоритетов) с heap памятью в Go.
- Предлагать только linked list без оценки сложности.

**Подробности:**
- В Python —`heapq`; в Go —`container/heap`.
- При коллизии приоритетов — FIFO внутри одного веса (зависит от реализации).

Чтение по ключу в среднем O(1) - константная. В худшем случае может деградировать до O(n), если много коллизий.
Запись и удаление тоже O(1) в среднем, но амортизированно: отдельная операция может быть дороже из-за роста таблицы и переноса данных.

## Утечка горутин
**Частота:** 3/84
**Темы:** #go/goroutine #go/channel #go/tooling
- [x] Скорректировано ✅ 2026-06-26
- [x] последний повтор ✅ 2026-06-27

Утечка горутин — это ситуация, когда горутина больше не нужна приложению, но не может завершиться и продолжает удерживать ресурсы. Чаще всего причиной являются зависание на канале, отсутствие отмены через context, незакрытые каналы или забытые ticker/timer. Предотвращается корректным управлением жизненным циклом через context и закрытие каналов.


- Переключение G: block (chan/mutex/WaitGroup), syscall, netpoll park,`runtime.Gosched`, preemption.
- Blocking syscall: handoff P, G в waiting; M может block в kernel, P продолжит другие G.
- Netpoller (epoll/kqueue/IOCP): readiness → G runnable → run queue.
- Safepoints нужны для GC stack scan, stack growth check и preemption.
- Long CPU loop: sysmon (~10 ms) может инициировать preemption post-1.14, но не на каждой инструкции.
- Утечка горутина: G заблокированы навсегда — send без recv, забытый ctx, worker без shutdown.
- Диагностика leak:` go tool pprof -http=:8080 'http://localhost/debug/pprof/goroutine?debug=2'`— stack trace покажет, на каком sync-примитиве висит G
- Fix leak: context cancel,`close(ch)`, WaitGroup, корректное завершение worker pool.

## Что такое планировщик
**Частота:** 2/84
**Темы:** #go/scheduler
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27
Планировщик Go — это компонент Go, отвечающий последовательность выполнения горутин, из которых состоит программа Go

планировщик Go оперирует горутинами только одной программы, он намного проще, дешевле и быстрее, чем планировщик ядра операционной системы.

В Go используется модель планировщика GMP.
**G (горутина)** — горутина, выполняемая задача.
**M (machine)** — поток операционной системы.
**P (processor)** — логический процессор runtime, через который горутины назначаются потокам.
У каждого процессора есть локальная очередь горутин. Если у одного процессора задач много, а у другого нет, используется механизм **воровства работы (work stealing)** — свободный процессора забирает часть задач себе.
При блокирующих системных вызовах runtime старается отвязать процессора от заблокированного потока и продолжить выполнение на другом потоке.
Для того чтобы одна горутина не могла бесконечно занимать процессор, используется **вытесняющая многозадачность (preemption)**.
Вытеснение и работа сборщика мусора выполняются через **безопасные точки (safepoints)** — места, где runtime может безопасно остановить горутину.

## Передача и возврат: значение vs указатель? / Value vs pointer receiver
**Частота:** 5/84
**Темы:** #go/pointers #go/memory #go/performance #go/methods

- [x] Скорректировано ✅ 2026-06-27
- [x] последний повтор ✅ 2026-06-27

**Передача в функцию:**
**По значению** — копия аргумента. Дешево для `int`,`pointer`, маленьких struct (до ~few cache lines). Функция не может изменить оригинал (кроме полей-указателей внутри struct).

**По указателю** — общий объект: нужна **мутация**, struct **большой**, или тип **нельзя** копировать (`sync.Mutex`).

Go разрешает вызывать `*T `-метод на value и наоборот (авто `&`/ разыменование), но семантика копирования остаётся.

**Возврат из функции:**
- **По значению** — компилятор часто кладёт на stack или регистры; для маленьких struct это снижает аллокации на кучу и нагрузку на GC.
- **По указателю** — когда возвращаем большой объект, shared state, или явно «optional» через `nil`.
Escape analysis решает stack vs heap — не угадывать, а смотреть ` go build -gcflags="-m"`.

## Inline: когда компилятор заинлайнирует функцию?
**Частота:** 0/84
**Темы:** #go/performance #go/compiler

- [x] Скорректировано ✅ 2026-06-27
- [x] последний повтор ✅ 2026-06-27

**Что ожидают на собесе:**
- **Inline** — тело маленькой функции **вставляется** в место вызова → нет call overhead, больше шансов оптимизаций.
- (бонус) Условия: маленькая **leaf**-функция, без `defer`, иногда `-gcflags="-m"` для проверки.
- (бонус+) ` go build -gcflags="all=-m"`/`-m=2 `— решение компилятора.
**Эталон на собесе:**
Компилятор Go **инлайнит** функцию, если ожидает выигрыш: обычно **короткая**, **leaf** (не вызывает другие функции или их мало), без **`defer`**, без сложного control flow. Бюджет инлайна ограничен — большие функции остаются вызовами.
**Что даёт:** убирает cost вызова, позволяет constant folding, dead code elimination, лучше register allocation.
**Как проверить:**
```bash
go build -gcflags="all=-m" ./pkg 2>&1 | grep inline
```
**Типичные ошибки:**
- Раздувать «helper» функции — перестают inline.
- Ставить `//go:noinline ` не зная зачем — только для бенчмарков/профиля.

## Массив vs связный список — производительность
**Частота:** 0/84
**Темы:** #go/slice #go/array #go/performance #go/memory

- [x] Скорректировано ✅ 2026-06-27
- [x] последний повтор ✅ 2026-06-27

- **Массив/slice быстрее** связного списка для последовательного доступа.
- Причина: **непрерывная память** → cache locality, prefetch, одна копия блока на stack/в регистры.
- (бонус) Связь с inline и escape analysis.

**Массив / slice** хранит элементы **подряд** в памяти
- O(1) при доступе по индексу
- отличная **CPU cache** locality
-`copy`/передача slice — один непрерывный блок (заголовок + указатель на data).
**Связный список** — узлы разбросаны по heap
- каждый `next`— **cache miss**
- больше allocations и pointer chasing
- в Go нет stdlib linked list для hot path (обычно `[]T `+ indices или slice).
Поэтому в Go почти всегда выбирают **slice** вместо hand-rolled linked list, если нет специфичной причины (stable iterators в C-style API).
