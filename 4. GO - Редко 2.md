## Канал vs мьютекс
**Частота:** 1/56
**Темы:** #go/channel #go/sync
- [x] Скорректировано ✅ 2026-06-26
- [x] последний повтор ✅ 2026-06-26

**Что ожидают на собесе:**


**Эталон на собесе:**
**Мьютекс** — примитив синхронизации, который позволяет только одной горутине находиться в части кода, где необходим эксклюзивный доступ. 

При этом, channel — передача работы/результатов между goroutines. 

**Подробности:**
- Counter/cache — mutex проще.
- Fan-in/fan-out — channel + select.
Когда первый поток входит в критическую секцию, мьютекс блокируется до тех пор, пока поток не покинет её. Пока мьютекс заблокирован, другие горутины ждут его разблокировки. Как только он разблокирован, одна из ожидающих горутин успевает заблокировать его и получить эксклюзивный доступ к критической секции кода.

## Конкурентная запись в мапу, почему нельзя?
**Частота:** 1/56
**Темы:** #go/map #go/data-race
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**
- Почему **read+write** или **write+write** без sync — fatal.
- (бонус) Параллельное **только чтение** — OK.

**Эталон на собесе:**
Обычная map **не потокобезопасна**. **Read-only** из нескольких goroutine допустим, если **никто не пишет**. Если **хотя бы одна** goroutine пишет — нужен **Mutex** / owner / `sync.Map`.

Запись — не атомарная операция: рантайм считает хеш, ищет место, меняет служебные структуры, иногда запускает рост или перенос данных.

**Подробности:**
- `concurrent map writes` и `concurrent map read and map write` приводят к fatal error runtime. `recover` от этого не спасает потому что мапа может быть испорчена
- Несколько параллельных чтений допустимы, если в это время никто не пишет.
- Проблема в том, что одна goroutine может менять структуру таблицы, а другая одновременно читать или писать по устаревшему состоянию.
- Одна goroutine владеет map — типичный паттерн через channel.
- В реализации есть внутренние флаги/проверки, которые помогают runtime обнаруживать часть таких ошибок, но это не замена race detector.

## Параллельные исходящие HTTP-запросы (fan-out)?
**Частота:** 1/56
**Темы:** #go/concurrency #go/context #go/stdlib
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
Типовая задача: один входящий HTTP-запрос → N независимых исходящих REST-вызовов → агрегировать JSON и отдать клиенту.

Паттерн: `errgroup.WithContext(parentCtx)` + по `g.Go` на каждый upstream; общий `ctx` с deadline/timeout; `g.Wait()` — сигнал «все завершились»; первая ошибка отменяет остальные через context.

Альтернатива: `sync.WaitGroup` + mutex под сбор результата; или одна goroutine-агрегатор и канал, но закрытие канала и «последняя goroutine» — хрупко без счётчика/`WaitGroup`.

**Типичные ошибки:**
- Счётчик/таймер вместо `WaitGroup`/`errgroup` — ненадёжное определение «все ответили».
- Нет timeout на весь fan-out — handler висит.
- Забыть передать `ctx` в `http.NewRequestWithContext`.

**Подробности:**
- См. [[3. GO - Редко 1#`errgroup`]] · [[3. GO - Редко 1#`sync.WaitGroup`]] · [[1. GO - Часто#context - что такое и зачем использовать?]].
- `errgroup.SetLimit(n)` — ограничить параллелизм к upstream.

## Системные вызовы (syscall) в Go?
**Частота:** 1/56
**Темы:** #go/scheduler #go/runtime
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


**Эталон на собесе:**
Системный вызов — переход из user mode в kernel mode: файловый I/O, часть сетевых операций, таймеры и т.д. Для потока ОС это дорогое переключение контекста.

В Go горутина на **блокирующем** syscall паркуется: связанный M может остаться в kernel, а P (логический CPU) передаётся другому M, чтобы другие G продолжали работу. После возврата из syscall G попадает в run queue (часто через global queue).

Сетевой I/O часто идёт через **netpoller** без долгой блокировки M на каждую операцию.

**Типичные ошибки:**
- «Горутина = поток ОС, syscall блокирует всё приложение» — неверно при нормальном GMP.
- Путают syscall с cooperative yield на channel/mutex.

**Подробности:**
- См. [[1. GO - Часто#Что такое модель GMP и GOMAXPROCS?]] · [[2. GO - Средне#Work stealing и global queue]].
- После syscall: [[5. GO - Редко 3#Memory arenas (runtime после syscall)]].
- События парковки G: channel, mutex, syscall, netpoll, GC safepoint, preemption.

## Указатель в цикле — один адрес
**Частота:** 1/56
**Темы:** #go/pointers #go/slice
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26

**Что ожидают на собесе:**


**Эталон на собесе:**
В `for range` до Go 1.22 переменная итерации переиспользовалась, поэтому взятие `&v` давало один и тот же адрес. При этом, правильнее брать адрес элемента через индекс: `&items[i]`, либо создавать копию переменной на итерации. В новых версиях ловушка смягчена для range, но привычка проверять адрес остаётся полезной.

**Типичные ошибки:**
- Не различать адрес копии значения и адрес элемента в slice.

**Подробности:**

```
for i := range items { 
ptrs = append(ptrs, &items[i]) 
}
```
берёт адрес элемента.
- Для map нельзя взять стабильный адрес значение напрямую: значения могут перемещаться.
- Та же идея важна для closures, которые захватывают переменную цикла.

## Что если GOMAXPROCS=1 и goroutine блокируется?
**Частота:** 1/56
**Темы:** #go/scheduler #go/data-race
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26

**Что ожидают на собесе:**


**Эталон на собесе:**
При `GOMAXPROCS=1` все горутины на одном процессоре — параллелизма нет, но конкурентность есть. При этом, блокирующий syscall/network может парковать горутину; netpoller и другие горутины продолжают работу.

**Типичные ошибки:**
- Думать, что GOMAXPROCS=1 убивает все goroutines.

**Подробности:**
- Один P — G исполняются по очереди на одном CPU, но тысячи G могут существовать одновременно.
- Block на channel/mutex: G паркуется, другая runnable G берёт P.
- Netpoller на одном P: сетевые G ждут readiness, CPU-G продолжают крутиться.
- Blocking syscall может отнять M; runtime создаст новый M для P, если нужно.
- `-race` ловит unsynchronized memory access даже при `GOMAXPROCS=1`.
- Логические гонки (lost update без data race) `-race` не найдёт.
- CPU-heavy G после 1.14 вытесняются sysmon, но не мгновенно — возможны короткие «монопольные» участки.

## Что такое массив?
**Частота:** 1/56
**Темы:** #go/array #go/types
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


> [!summary] Собес: как отвечать
> Массив - это последовательность элементов одного типа и постоянной длины. Размер массива - составная часть его типа и задается во время компиляции. 

- Размер после объявления не меняется.
- Многомерный `[M][N]T` — M элементов типа `[N]T`; пример: `[4][7]int`.
- Непрерывный блок N × sizeof(T), **доступ по индексу O(1)**; для `[M][N]T` — построчно. 
- Без инициализации каждый элемент — zero value своего типа. 
- value type: при присваивании и передаче в функцию копируются все элементы. Мутация параметра `[N]T` внутри функции снаружи не видна; чтобы менять исходное значение, параметр объявляют `*[N]T`.
- Два массива одного типа `[N]T` можно сравнивать оператором == , если сравним тип T — тогда же `[N]T` годится ключом map. Сравнение двух значений одного `[N]T` через  ==  поэлементное, слева направо
- Сравнимые типы: 
	- числа
	- string
	- pointer
	- array
	- struct с comparable-полями; 
- Значение `len(a)` подставляется компилятором как константа.
- Типы `[3]int` и `[5]int` несовместимы: ни присвоить одно другому, ни сравнить между собой нельзя. 
- Размер можно вывести из литерала (`[...]int{10, 20}`), задать явно или указать только нужные индексы (`[7]int{2: 3, 6: 11}`). 
- Пустой массив `[0]int` допустим. 
- Обращение по индексу-константе вне диапазона — ошибка компиляции; по переменному индексу вне `[0, N)` — паника.
- В `for range` по массиву переменная итерации — копия элемента, не ссылка на ячейку. Для изменения на месте обходят по индексу или берут указатель на элемент явно.
- Копирование struct с полем-массивом включает весь массив. 

```go
var a [5]int
b := [3]int{1, 2, 3}
c := [...]int{10, 20}
d := [7]int{6: 11, 2: 3}
```

## Эвакуация мапы
**Частота:** 1/56
**Темы:** #go/map #go/hash #go/runtime
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26

**Что ожидают на собесе:**


В старой реализации map эвакуация — это постепенный перенос данных из старых бакетов в новые после роста. Перенос идёт кусками во время последующих операций, поэтому какое-то время map живёт в промежуточном состоянии.

Рост запускался, при средней загрузке около 6.5 элементов на бакет или при слишком большом числе overflow buckets. Перенос выполнялся лениво, по мере операций с map.

Главный способ снизить вероятность роста — **давать capacity hint**: `make(map[K]V, n)`. Это ожидаемое количество элементов, а не количество бакетов и не размер памяти. Не защитит от коллизий.

В новой Swiss-map реализации детали роста другие: map разбита на группы/таблицы, при росте может происходить расширение или разделение таблиц. Поэтому объяснение через старую эвакуацию бакетов относится именно к старой реализации.

## 1000 горутин инкрементят int — получим 1000?
**Частота:** 0/56
**Темы:** #go/sync #go/data-race
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**
- Объяснить **data race**: read-modify-write без синхронизации → результат **< 1000** и недетерминирован.
- Назвать fix: `sync.Mutex` или `atomic.AddInt64(&globalVar, 1)`.

**Эталон на собесе:**
**Нет** — при `globalVar += 1` из 1000 goroutine без синхронизации будет **data race**: операция не атомарна (load → inc → store), interleaving теряет инкременты. Итог **< 1000**, каждый запуск разный.

**Fix:**
```go
// mutex
mu.Lock()
globalVar++
mu.Unlock()

// или atomic (предпочтительно для простого счётчика)
atomic.AddInt64(&globalVar, 1)
```

**Подробности:**
- `go test -race` покажет гонку.
- См. [[2. GO - Средне#`atomic` vs mutex]].
