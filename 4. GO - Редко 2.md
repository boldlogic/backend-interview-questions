## Что такое хеш-таблица / коллизии / эвакуация map
**Частота:** 3/84
**Темы:** #go/hash #go/map
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**
- Структура данных типа ключ-значение. Хранится в куче.
- В Go реализована в виде мапы.
- Можно использовать любой сравнимый тип данных в качестве ключа.
- Так же могут быть проблемы при использовании float
**Эталон на собесе:**
- Структура **ключ → значение**: ключ прогоняется через **hash-функцию**, по хешу выбирается ячейка/группа для поиска и вставки.
- Hash-функция должна давать **одинаковый хеш для одного ключа**; при коллизиях — probing или цепочки (в Go map — Swiss Table / open addressing).
- Поиск в среднем **O(1)**; в Go — тип `map[K]V`, ключ должен быть **comparable**.
- Проблемы с `float` как ключом: NaN ≠ NaN, нестабильное сравнение.
Ситуация когда два ключа получают один хеш и претендуют на одну ячейку памяти и они конфликтуют.
Есть разные способы разрешения коллизий
- отрытая адресация - перебираем ячейки и ищем свободную
- метод цепочек когда все коллизиии хранятся в одной ячейке связанным список
В го в старой мапе был метод цепочек с закрытой адресацией.
Коллизия — это ситуация, когда разные ключи имеют одинаковый хеш. При поиске Go сначала вычисляет хеш, затем проверяет кандидатов в соответствующей области таблицы и сравнивает сами ключи. Совпадение хеша еще не означает, что ключ найден — окончательное решение принимается сравнением ключей. Современная реализация `map` разрешает коллизии с помощью открытой адресации и пробирования, а не через связанные списки.
- В старой реализации map эвакуация — это постепенный перенос данных из старых бакетов в новые после роста. Перенос идёт кусками во время последующих операций, поэтому какое-то время map живёт в промежуточном состоянии.
- Рост запускался, при сред ней загрузке около 6.5 элементов на бакет или при слишком большом числе overflow buckets. Перенос выполнялся лениво, по мере операций с map.
- Главный способ снизить вероятность роста — **давать capacity hint**:`make(map[K]V, n)`. Это ожидаемое количество элементов, а не количество бакетов и не размер памяти. Не защитит от коллизий.
- В новой Swiss-map реализации детали роста другие: map разбита на группы/таблицы, при росте может происходить расширение или разделение таблиц. Поэтому объяс нение через старую эвакуацию бакетов относится именно к старой реализации.
С Go 1.24 runtime использует новую реализацию встроенной map на основе идей Swiss Table. Семантика для пользовательского кода та же:`map[K]V`,`range`,`delete`,`clear`, nil map и правила конкурентного доступа не изменились.
Главное отличие — другая внутренняя организация данных, которая улучшает locality и уменьшает накладные расходы старых overflow buckets.
**Подробности:**
Хеш-таблица основана на Swiss Table. Ключ хешируется, по хешу выбирается место, где может лежать ключ.
Данные организованы группами, рядом хранится служебная метадата — короткие отпечатки хеша. Сначала runtime быстро отбирает кандидатов по отпечаткам, затем сравнивает полные ключи.
Старой модели overflow buckets в прежнем виде нет: если место занято или произошла коллизия, поиск продолжается по правилам open addressing/Swiss Table. При росте используется другая логика расширения и разделения таблиц, поэтому старые детали про buckets и эвакуацию нельзя переносить один-в-один.

## Где в памяти размещается массив, а где слайс?
**Частота:** 1/84
**Темы:** #go/memory #go/slice #go/array
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

**Эталон на собесе:**
- **Массив**: размещение на стеке или в куче решает **escape analysis** — если массив не «убегает» из функции, часто на стеке.
- **Слайс**: заголовок (ptr, len, cap) может быть на стеке; **базовый массив** — на куче, если slice возвращается, сохраняется в heap-struct или capacity большой.
- До Go 1.25: маленький slice без escape иногда с буфером в кадре; при return — копия данных на кучу.

## Системные вызовы (syscall) в Go?
**Частота:** 1/84
**Темы:** #go/scheduler #go/runtime
- [ ] Скорректировано
- [ ] последний повтор

Системный вызов — переход из user mode в kernel mode: файловый I/O, часть сетевых операций, таймеры и т.д. Для потока ОС это дорогое переключение контекста.
В Go горутина на **блокирующем** syscall паркуется: связанный M может остаться в kernel, а P (логический CPU) передаётся другому M, чтобы другие G продолжали работу. После возврата из syscall G попадает в run queue (часто через global queue).
Сетевой I/O часто идёт через **netpoller** без долгой блокировки M на каждую операцию.


**Подробности:**
- После syscall: Memory arenas (runtime после syscall).
- События парковки G: канал, mutex, syscall, netpoll, GC safepoint, preemption.

## Структуры: порядок полей и выравнивание
**Частота:** 1/84
**Темы:** #go/types #go/memory
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

**Эталон на собесе:**
Struct — именованный набор полей. 
Размер и alignment зависят от порядка полей (padding). 
Оптимизация: от большего alignment к меньшему уменьшает размер struct.

Процессор быстрее работает с данными, расположенными по определенным границам памяти.
Компилятор выравнивает поля структуры по требованиям архитектуры, добавляя padding между полями при необходимости. Неправильный порядок полей может увеличить размер структуры. Поэтому обычно поля располагают от самых больших по размеру к самым маленьким, чтобы уменьшить количество padding и снизить потребление памяти.

## Чем хорош массив по сравнению со слайсом?
**Частота:** 1/84
**Темы:** #go/array #go/types
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26
**Что ожидают на собесе:**
> **Массив хорош тем, что имеет фиксированный размер, хранит данные непосредственно в себе, не перевыделяет память и не разделяет данные при копировании.**


- **Фиксированный размер.** Размер является частью типа и не может измениться.
- **Нет реаллокаций.** В отличие от `append` у слайса, массив никогда не перевыделяет память.
- **Полное копирование.** При присваивании копируются все элементы, поэтому два массива независимы.
- **Нет общей базовой памяти.** Изменение одной копии не влияет на другую.
- **Можно сравнивать оператором `==`**, если элементы сравнимы.
- **Часто размещается на стеке**, если небольшой и не "убегает" из области видимости, что позволяет избежать аллокаций в куче.


> **В прикладном коде преимущества массива редко перевешивают удобство слайсов. Поэтому почти все API стандартной библиотеки работают именно со слайсами. Массивы используют в основном тогда, когда размер фиксирован и известен заранее (например, `[16]byte` для UUID или `[32]byte` для SHA-256).**

## Что если GOMAXPROCS=1 и goroutine блокируется?
**Частота:** 1/84
**Темы:** #go/scheduler #go/data-race
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26
При `GOMAXPROCS=1` все горутины на одном процессоре — параллелизма нет, но конкурентность есть. Блокирующий syscall/network может парковать горутину; netpoller и другие горутины продолжают работу.

**Подробности:**
- Один P — G исполняются по очереди на одном CPU, но тысячи G могут существовать одновременно.
- Block на канал/mutex: G паркуется, другая runnable G берёт P.
- Netpoller на одном P: сетевые G ждут readiness, CPU-G продолжают крутиться.
- Blocking syscall может отнять M; runtime создаст новый M для P, если нужно.
-`-race `ловит unsynchronized memory access даже при` GOMAXPROCS=1 `.
- Логические гонки (lost update без гонка данных) `-race` не найдёт.
- CPU-heavy G после 1.14 вытесняются sysmon, но не мгновенно — возможны короткие «монопольные» участки.

## Что такое context switching и как горутины решают эту проблему
**Частота:** 1/84
**Темы:** #go/scheduler #go/goroutine
- [ ] Скорректировано
- [ ] последний повтор
**Что ожидают на собесе:**
- context switching это остановка выпол нения одного процесса и переключение на другой процесс
- с сохра нением стейта (стека, текущей инструкции) выгруженного процесса и загрузкой стейта нового процесса.
- Либо переход из user mode в kernel mode (syscall).
- Го рантайм работает в юзермоде и горутины не являются тредами
- поэтому переключение между горутинами не вызывает переключение контекста ОС-тредов.
- Но переключение между горутинами все равно имеет некий оверхед т.к нужно восстановить стек и последнюю выпол ненную инструкцию самой горутины.

## Что такое массив?
**Частота:** 1/84
**Темы:** #go/array #go/types
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-03
**Что ожидают на собесе:**
> [!summary] Собес: как отвечать
> Массив - это последовательность элементов одного типа и постоянной длины. Размер массива - составная часть его типа и задается во время компиляции.
- Многомерный `[M][N]T `— M элементов типа `[N]T `; пример:`[4][7]int `.
- Непрерывный блок N × sizeof(T), **доступ по индексу O(1)**; для `[M][N]T `— построчно. 
- доступ по индексу O(1), константная сложность потому что можно вычислить адрес 
- Без инициализации каждый элемент — нулевое значение своего типа.
- value type: при присваивании и передаче в функцию копируются все элементы. Мутация параметра `[N]T `внутри функции снаружи не видна; чтобы менять исходное значение, параметр объявляют`*[N]T `.
- Два массива одного типа `[N]T `можно сравнивать оператором == , если сравним тип T — тогда же`[N]T `годится ключом map. Срав нение двух значений одного`[N]T ` через == поэлементное, слева направо

- Значение `len(a)` подставляется компилятором как константа.
- Типы `[3]int `и`[5]int` несовместимы: ни присвоить одно другому, ни сравнить между собой нельзя.
- Размер можно вывести из литерала (`[...]int{10, 20}`), задать явно или указать только нужные индексы (`[7]int{2: 3, 6: 11}`).
- Пустой массив `[0]int ` допустим.
- Обращение по индексу-константе в не диапазона — ошибка компиляции; по переменному индексу в не `[0, N) `— паника.
- В `for range` по массиву переменная итерации — копия элемента, не ссылка на ячейку. Для изме нения на месте обходят по индексу или берут указатель на элемент явно.
- Копирование struct с полем-массивом включает весь массив.
```go
var a [5]int
b := [3]int{1, 2, 3}
c := [...]int{10, 20}
d := [7]int{6: 11, 2: 3}
```

## Операции и параметры канала
**Частота:** 1/84
**Темы:** #go/channel
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**
Основные операции с каналами:
- создание (`make`);
- отправка (`<-`);
- получение (`<-`);
- закрытие (`close`);
- чтение через `range`;
- ожидание нескольких каналов через `select`.
Дополнительно можно получить текущую длину буфера (`len`) и его емкость (`cap`) для буферизированных каналов.
**Эталон на собесе:**
- `make(chan T)` / `make(chan T, n)` — создание небуферизованного или буферизованного канала.
- Отправка `ch <- v`, получение `<-ch` или `v := <-ch`; `close(ch)` — закрытие (обычно отправителем).
- `for v := range ch` — чтение до закрытия; `select` — мультиплексирование нескольких каналов.
- `len(ch)`, `cap(ch)` — текущая заполненность и ёмкость буфера (для buffered).
У канала есть три основные характеристики:
- **тип элементов** (`chan int`, `chan User`);
- **направление** (`chan`, `<-chan`, `chan<-`);
- **емкость буфера** — небуферизированный (`cap == 0`) или буферизированный (`cap > 0`).

## 1000 горутин инкрементят int — получим 1000?
**Частота:** 0/84
**Темы:** #go/sync #go/data-race
- [ ] Скорректировано
- [ ] последний повтор
**Что ожидают на собесе:**
- Объяснить **гонка данных**: read-modify-write без синхронизации → результат **< 1000** и недетерминирован.
- Назвать fix:`sync.Mutex` или `atomic.AddInt64(&globalVar, 1)`.
**Эталон на собесе:**
**Нет** — при `globalVar += 1` из 1000 горутина без синхронизации будет **гонка данных**: операция не атомарна (load → inc → store), interleaving теряет инкременты. Итог **< 1000**, каждый запуск разный.
**Fix:**
```go
// mutex
mu.Lock()
globalVar++
mu.Unlock()
// или atomic (предпочтительно для простого счётчика)
atomic.AddInt64(&globalVar, 1)
```
**Подробности:**
-`go test -race` покажет гонку.

`context.WithValue` не предназначен для optional parameters или конфигурации. Его используют для на время запроса metadata, которое проходит через границы API: трассировка id, auth data, request id. Ключи лучше делать типизированными, чтобы избежать конфликтов.

- [ ] Скорректировано
- [ ] последний повтор

**Эталон на собесе:**
`make([]T, len, cap)`— готовый slice
`new(T)`→`*T ` с нулевое значение.
Основное различие между new и make состоит в том, что переменные, созданные с помощью make, правильно инициализируются, а не только обнуляется выделенная для них память. Кроме того, make можно применять только к хеш-таблицам, каналам и срезам, и эта функция не возвращает адрес памяти, то есть make не возвращает указатель

## ` sync.Cond`
**Частота:** 0/84
**Темы:** #go/sync
- [ ] Скорректировано
- [ ] последний повтор

**Эталон на собесе:**
Условная переменная:`Wait` освобождает mutex и спит до `Signal`/`Broadcast`.

**Подробности:**
- Cond + mutex: ждём изме нения общее состояние, не передачу владение.
- На практике часто канал; если Cond — цикл for против ложное пробуждение.
sync.Cond:
- работает только вместе с Locker (обычно Mutex);
- Wait() освобождает Mutex и засыпает;
- после пробуждения снова захватывает Mutex;
- Signal() будит одну горутину;
- Broadcast() будит все;
- Wait() всегда вызывают в цикле for, проверяя условие.
