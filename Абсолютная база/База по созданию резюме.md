## Красные флаги 2026

- Ссылки на GitHub — признак студента и «нет опыта»
- Указана желаемая зарплата
- У части HR триггерит перечисление стека и англоязычных терминов в скобках внутри достижений
- Коммерческий опыт параллельно обучению
- Стек в виде перечисления через запятую — лучше размазать по достижениям
- Деепричастия и формулировки типа «сократив», «снизив»
- Интересы и хобби в «О себе», если это не связано с работой
- Водительские права
- Город не Москва — ниже вилки или автоотказы; большинство вакансий в Москве
- Пройденные курсы — автоотказ
- Нестандартный (не hh-формат) — ATS не спарсят
- Достижения в % — признак нейронки
- Нет вышки — особенно когда она есть
- Писать, какие компании не рассматриваешь — ключевыми словами притягиваешь
- Одинаковые глаголы и канцеляриты
- Гладкие универсальные фразы без фактуры где не чувствуются руки

## Принципы описания опыта и «О себе» без повторов

Цель - писать резюме на русском так, чтобы оно читалось как живой профиль `Golang-разработчика`: уверенно, предметно, без самоуменьшения и без нейро-гладкости.

Главное правило: старые резюме, сборники формулировок, проектные файлы и топовые примеры можно использовать только как источник фактов, структуры и понимания рынка. Готовые формулировки из них не переносить.

### Правило неповторения

- Не копировать фразы из старых опубликованных резюме, сборников формулировок, проектных файлов и топовых примеров.
- Не оставлять совпадения длиннее 5-7 слов подряд, даже если фраза кажется удачной.
- Факты использовать можно: даты, роли, домены, технологии, числа, результаты.
- Язык переписывать заново: менять порядок мысли, синтаксис, глагол, объект и способ указания результата.
- Старые сильные фразы не улучшать точечно, а пересобирать с нуля вокруг того же факта.
- Если фраза узнаваемая даже без точного совпадения, заменять её на более простую и человеческую.

### Опыт

- Каждый опыт открывать коротким контекстом: домен, объект системы, что эта система делает.
- Буллет строить по STAR: действие + объект + технический способ + результат.
- Начинать буллет с глагола действия: `спроектировал`, `подготовил`, `разобрал`, `описал`, `согласовал`, `перевёл`, `добавил`, `написал`.
- Совершенный вид использовать только там, где вклад завершён и не искажает роль.
- Не приписывать себе чужую зону ответственности: если разбирал результаты нагрузочных проверок, не писать `провёл нагрузочные проверки`.
- Коммерческий опыт аналитика подавать через backend-факты: API, SQL, Kafka, Go-репозитории, OpenAPI, ClickHouse, Postgres, расследование дефектов, архитектурные артефакты.
- Личные проекты связывать одним доменом: инвестиционные данные, портфель, лимиты, котировки, справочники, служебные API.
- Технологии вплетать в задачу, а не перечислять ради ключевых слов.
- Числа оставлять только правдоподобные и защищаемые.

### «О себе»

- Не объяснять переход в Go.
- Не писать `бывший аналитик`, `без коммерческого опыта`, `хочу развиваться`, `не нулевой джун`.
- Держать 3-5 коротких предложений: что пишешь, с какими задачами силён, какой коммерческий фон усиливает позицию.
- Убирать LinkedIn-обобщения: `на стыке`, `связываю код, данные и контракты`, `нахожу точку изменения`.
- Писать через конкретные рабочие объекты: `API`, `SQL`, `Kafka`, `портфель`, `котировки`, `АБС`, `лимиты`, `ClickHouse`, `MS SQL`, `PostgreSQL`.
- Тон - спокойный инженерный, без просьбы о скидке.

### Язык и английские слова

- Русский язык должен быть естественным для российского HH: без кальки и без англоязычного мусора.
- Английские слова оставлять только как принятые технические названия: `Go`, `Golang`, `REST API`, `Kafka`, `PostgreSQL`, `Docker`, `OpenAPI`, `gRPC`, `ClickHouse`.
- Не использовать: `worker`, `handler`, `repository`, `hot path`, `flush`, `enqueue`, `tracking`, `background`, `structured logs`, `p99`, точные HTTP-коды, названия конфигов и портов.
- Не использовать длинное тире в тексте резюме.
- Не писать нейро-формулы: `полный цикл`, `под ключ`, `эффективно взаимодействовал`, `обеспечил стабильную работу`, `типовые задачи продуктовой разработки`.

### Проверка перед публикацией

- Должность: ровно `Golang-разработчик`.
- Старые формулировки не использованы дословно.
- Нет совпадений длиннее 5-7 слов со старыми резюме, сборниками, проектными файлами и топовыми примерами.
- Каждый буллет начинается с действия и содержит объект работы.
- STAR есть там, где это уместно и не искажает факты.
- Личные проекты читаются как связанный рабочий домен, а не набор учебных задач.
- Текст звучит по-русски, без самооправдания и без нейро-бреда.
