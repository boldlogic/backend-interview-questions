WSDL описывает, как взаимодействовать с веб-службой, включая:
- типы данных, которые используются в веб-службе;
- операции, которые можно выполнять с этими данными;
- форматы сообщений, которые используются для обмена данными между клиентом и сервером;
- расположение веб-службы (URL).
WSDL является основой для создания и использования веб-сервисов. Он позволяет разработчикам создавать приложения, которые могут взаимодействовать с другими приложениями через интернет. #### 1. Вот как расшифровывается акроним SOLID:
SOLID — это набор принципов, которые помогают разработчикам создавать понятный и поддерживаемый код.
1. **Принцип единственной ответственности (Single Responsibility Principle)**: у каждого класса или функции должна быть только одна ответственность. Это облегчает понимание и изменение кода.
2. **Принцип открытости/закрытости (Open-Closed Principle)**: классы должны быть открыты для расширения, но закрыты для изменения. Это позволяет добавлять новый функционал без изменения существующего кода.
3. **Принцип подстановки Барбары Лисков (Liskov Substitution Principle)**: объекты в программе должны заменяться их подтипами без изменения правильности программы.
4. **Принцип разделения интерфейса (Interface Segregation Principle)**: интерфейсы должны быть разделены на более мелкие, чтобы клиенты использовали только нужные им методы.
5. **Принцип инверсии зависимостей (Dependency Inversion Principle)**: зависимости должны идти от абстракций к конкретным реализациям, а не наоборот.

## 🔥 Часто задаваемые вопросы

### 1. **Что такое Хореография и Оркестрация?**

   - **Хореография** - паттерн, при котором сервисы независимо общаются и самостоятельно принимают решения как работать. Как танцоры на сцене - каждый знает свою партию и реагирует на других.

   - **Оркестрация** - паттерн при котором есть центральное звено, которое управляет сервисами. Как дирижёр в оркестре - говорит каждому что и когда делать.

---
### 2. **Достоинства и недостатки микросервисов**

   - **Достоинства:**
     - Распределение ответственности
     - Гибкость в изменении, каждый сервис может иметь свой стек
     - Отказоустойчивость

   - **Недостатки:**
     - Сложность поддержки
     - Необходимость документирования и тестирования
     - Сложность обновления
     - Повышенная нагрузка на сеть

### 3. Какие виды архитектур ПО знаешь?

 - Монолит - один большой сервис, который содержит в себе всё.
 - Микросервис - несколько сервисов, которые независимы и могут быть разработаны, развёрнуты и масштабированы независимо друг от друга.

  

### 4. В чем разница между монолитами и микросервисами? Какие плюсы и минусы той и другой архитектуры?

 - Плюсы монолитов: быстрая разработка на начальных этапах. Проще тестировать и отлаживать.

   - Минусы монолитов: сложности при масштабировании, высокая связанность.

 - Микросервисов

   - Плюсы микросервисов: можно использовать разный стек для разных сервисов, гибкость, масштабируемость, изоляция сбоев. Микросервисы позволяют использовать для каждого сервиса наиболее подходящие технологии, что может быть сложно или невозможно в монолитах. В микросервисах каждый сервис остается относительно простым, поскольку отвечает только за одну функциональную область.

   - Минусы микросервисов: сложность поддержки, необходимость большего количества сервисов. Нужно выстраиваться связи и интеграции между сервисами, как-то распределять транзакции, контролировать ошибки.

  

### 5. Что такое архитектурный стиль?

Архитектурный стиль - это способ организации системы, который определяет её структуру, компоненты и взаимодействие между ними.

  

### 6. Какие знаешь архитектурные стили?

• Event-Driven Architecture (EDA) - Событийно-ориентированная архитектура

Суть: Компоненты системы обмениваются событиями и реагируют на них. Хорошо подходит для систем, где важна асинхронная обработка и слабая связанность компонентов.

  

• Microservices Architecture (MSA) - Микросервисная архитектура

Суть: Приложение разбивается на небольшие независимые сервисы, каждый из которых отвечает за свою функцию. Позволяет легко масштабировать и обновлять отдельные части системы.

  

• Service-Oriented Architecture (SOA) - Сервисная ориентированная архитектура

Суть: Система строится из слабосвязанных сервисов, взаимодействующих через стандартизированные протоколы. Хорошо подходит для крупных корпоративных систем.

  

• Layered Architecture - Многослойная архитектура

Суть: Система разделяется на слои (уровни), где каждый слой выполняет определённую роль. Обеспечивает чёткое разделение ответственности между компонентами.

  

• Microkernel Architecture - Микроядровая архитектура

Суть: Базовая функциональность выносится в ядро, а остальные возможности реализуются через подключаемые компоненты. Позволяет легко расширять систему новыми возможностями.

  

• REST (Representational State Transfer) - Передача состояния представления

Суть: Архитектурный стиль для построения распределённых систем, основанный на протоколе HTTP и стандартных операциях над ресурсами. Каждый ресурс имеет уникальный идентификатор (URI), а взаимодействие происходит через стандартные HTTP-методы (GET, POST, PUT, DELETE). Обеспечивает простоту, масштабируемость и независимость от платформы.

  

### 7. Знаете ли вы CAP-теорему?

Теорема CAP утверждает, что в распределенной системе можно одновременно
обеспечить только два из трех свойств- согласованность, доступность и толерантность
к разделению. Третье свойство будет жертвоваться.

Согласованность: каждый узел видит одни и те же данные, даже если происходят одновременные обновления.

Доступность: все запросы получают ответы о том, был ли запрос успешным или нет.

Устойчивость к разделению на части: система продолжит работать, даже если связь между двумя разными узлами будет прервана.

### 8. Что означает устойчивость к отказам?

Устойчивость к отказам означает, что система может продолжать работать даже при наличии отказов в отдельных компонентах.

Это принцип, который подразумевает минимизацию зависимостей между различными частями системы.

 - Например, в монолите это можно реализовать через разбиение на модули, разделение кода на слои

 - В микросервисах: каждый микросервис должен иметь минимум зависимостей от других микросервисов. Это упрощает разработку, тестирование, развертывание каждого микросервиса отдельно

Пример слабой связанности - взаимодействие через брокеры или API
Пример высокой связанности - два сервиса смотрят в одну таблицу БД

### 1. В чем разница между  BPMN и UML?

• BPMN (Business Process Model and Notation) — это нотация и стандарт для моделирования бизнес-процессов. Она используется для создания диаграмм, которые показывают, как работает компания: кто что делает, в каком порядке и так далее. BPMN помогает понять, как улучшить процессы и сделать их более эффективными.

• UML (Unified Modeling Language) — это язык моделирования, который используется для создания различных видов диаграмм. Он применяется в разработке программного обеспечения и других областях. UML помогает визуализировать структуру системы, её компоненты и связи между ними.

  

### В чем разница между диаграммой классов и ER диаграммой?

Диаграммы классов (UML) и ER-диаграммы (Entity-Relationship) используются для моделирования структуры данных, но их цели и принципы различаются

  

ER-диаграмма: используется для проектирования базы данных (реляционной модели). Описывает сущности, их атрибуты и связи между ними.

  

Диаграмма классов (UML): применяется в разработке ПО. Описывает классы, их свойства (атрибуты), методы (операции) и связи в объектно-ориентированной системе.

### 1. Виды связей между таблицами
• Один к одному (1:1)
- Каждая запись в первой таблице соответствует ровно одной записи во второй таблице
- Используется, когда данные логически разделены на две части
- Пример: Таблица «Пользователи» и таблица «Профили пользователей»

• Один ко многим (1:N)
- Одна запись в первой таблице связана с несколькими записями во второй
- Самый распространённый тип связи
- Пример: Таблица «Авторы» и таблица «Книги»
 

• Многие ко многим (M:N)
- Записи из обеих таблиц могут быть связаны с несколькими записями друг друга
- Реализуется через промежуточную таблицу
- Пример: Таблица «Студенты» и таблица «Курсы» через таблицу «Регистрация»

### 2. Виды JOIN запросов

• INNER JOIN
- Возвращает только совпадающие записи из обеих таблиц

• OUTER JOIN
- LEFT JOIN: все записи из левой таблицы и совпадающие из правой
- RIGHT JOIN: все записи из правой таблицы и совпадающие из левой
- FULL JOIN: все записи из обеих таблиц

• CROSS JOIN
- Декартово произведение таблиц

• SELF JOIN
- Соединение таблицы с самой собой

### 3. Индексы в БД

- Оптимизация JOIN-операций

• Структура:
- Чаще всего B-дерево
- Содержит отсортированные значения и указатели на записи
- Автоматически поддерживается СУБД

• Недостатки:
- Занимают дополнительное место
- Замедляют операции вставки/обновления
- Требуют обслуживания

### 4. Транзакции и ACID

Транзакция - последовательность операций, которая должна быть либо выполнена целиком, либо не выполнена вовсе.


Свойства ACID:

• Атомарность (Atomicity)

- Транзакция выполняется целиком или не выполняется вообще

- Частичное выполнение невозможно

  

• Согласованность (Consistency)

- БД переходит из одного согласованного состояния в другое

- Все ограничения целостности сохраняются

  

• Изолированность (Isolation)

- Транзакции выполняются независимо друг от друга

- Промежуточные результаты недоступны другим транзакциям

  

• Долговечность (Durability)

- Результаты зафиксированной транзакции постоянны

- Изменения сохраняются даже при сбоях системы

  

### 5. Масштабирование БД

• Вертикальное масштабирование
- Увеличение мощности существующего сервера
- Добавление CPU, RAM, дисков
- Ограничено возможностями одного сервера

  
• Горизонтальное масштабирование

- Шардинг и репликация
- Теоретически не ограничено

### 7. Нормализация БД

Первые три нормальные формы (НФ):

• Первая НФ (1NF):
- Атомарность значений (неделимые на более мелкие части). Запрещены списки\массивы и так далее - только простые типы данных
- Уникальная идентификация строк. Все записи(строки) в таблице должны быть уникальными (то есть отличаться хотя бы по первичному ключу).
- Данные одного типа в столбце

• Вторая НФ (2NF):
- Соответствие 1NF
- Полная функциональная зависимость от первичного ключа. Все атрибуты должны зависеть от первичного ключа, а если он составной - то от всего составного первичного ключа, а не только от его части.
- Отсутствие частичных зависимостей
  

• Третья НФ (3NF):
- Соответствие 2NF
- Отсутствие транзитивных зависимостей
- Все неключевые атрибуты зависят только от ключа

Не должно быть транзитивных зависимостей, то есть не ключевые атрибуты не должны зависеть от других не ключевых атрибутов (должны зависеть только от первичного ключа).

### 1. Что такое БД?

База данных — это упорядоченный набор информации, хранящийся в компьютере. Она позволяет легко сохранять, находить, изменять и управлять данными.

  

### 2. Что такое СУБД?

СУБД (система управления базами данных) — это специальное программное обеспечение, которое позволяет создавать, хранить, управлять и извлекать данные из базы данных. Она обеспечивает:

• Структурированный доступ к информации. Данные организуются в таблицах или других структурах, что упрощает поиск и обработку.

• Контроль целостности и безопасности данных. СУБД следит, чтобы данные не были повреждены и имелись необходимые уровни защиты от несанкционированного доступа.

• Поддержку транзакций. Это позволяет выполнять несколько операций над данными так, чтобы в случае ошибки изменения можно было откатить.

• Многопользовательский доступ. СУБД обеспечивает одновременную работу многих пользователей с базой данных без конфликтов.

Таким образом, СУБД помогает не только хранить большие объёмы информации, но и управлять ими эффективно и безопасно, что особенно важно в современных информационных системах.

  

### 5. Что такое денормализация и когда ее использовать?

Денормализация — это процесс изменения структуры базы данных, который приводит к дублированию данных с целью ускорения запросов.

Когда использовать денормализацию:

• Если в базе данных есть запросы, которые выполняются медленно, и вы хотите ускорить их выполнение.

• Когда вам нужно уменьшить количество соединений между таблицами, чтобы упростить запросы.

• В случае, если ваша база данных работает на нескольких серверах, и вы хотите распределить данные более эффективно.

• Для повышения производительности при работе с большими объёмами данных.

• Однако денормализация может привести к увеличению размера базы данных и усложнению её обслуживания. Поэтому перед применением этого подхода необходимо тщательно проанализировать требования к системе и возможные последствия.

  

### 7. Виды Constraints?

Используются для обеспечения целостности и правильности данных.
• Primary Key — первичный ключ. Это уникальный идентификатор записи в таблице. Ни одна запись не может иметь такой же первичный ключ, как у другой записи.
• Foreign Key — внешний ключ. Он используется для связи двух таблиц и обеспечивает ссылочную целостность данных. Внешний ключ ссылается на первичный ключ другой таблицы.
• Unique — уникальное ограничение. Оно гарантирует, что все значения в столбце или наборе столбцов будут уникальными.
• Check — проверочное ограничение. Оно позволяет проверять данные на соответствие определённым условиям. Например, можно проверить, что значение столбца находится в определённом диапазоне.
• Not Null — ограничение «не null». Оно запрещает пустые значения в столбце.
• Default — значение по умолчанию. Если не указано другое значение, то будет использоваться значение, заданное по умолчанию.
• Index — индекс. Он ускоряет поиск и сортировку данных в базе данных. Индексы могут быть созданы для одного или нескольких столбцов таблицы.

  

### 11. Чем TRUNCATE отличается от DELETE?
• TRANCATE- транзакция, быстро очищать таблицу без журналирования. Не
откатывается, сбрасывает счётчик автоинкремента.
• DELETE- используется для удаления записей из таблицы с сохранением лога
транзакций для каждой удаленной записи

  

### 12. Отличия процедуры от триггера

Процедуру можно явно вызывать по имени процедуры и можно передавать параметры. Триггер не может быть вызван явно из другой процедуры БД, не принимает никаких параметров при вызове

  

### 13. Что такое триггер

Триггер - это блок кода на SQL, который автоматически запускается при возникновении определенных событий. Предназначена для проверки сложных ограничений целостности, автоматизации обработки данных, аудита действий пользователя, установки. Триггеры могут быть строчными или операторными.

  

Триггер состоит из:

* Время срабатывания (до или после)

* Имя таблицы

* Тип триггера (строчный или операторный)

* Предложение When (ограничительное условие срабатывания триггера)

* Тело триггера (блок SQL)

# REST API

## 🔥 Часто задаваемые вопросы

  

### 1. HTTP методы
- GET - получение данных
- POST - создание данных
- PUT - полное обновление
- PATCH - частичное обновление
- DELETE - удаление
- HEAD - получение метаданных
- OPTIONS - получение списка доступных методов

### 2. Чем POST отличается от GET?

• POST - передача данных на сервер для создания новой сущности, данные передаются в теле запроса
• GET - запрос данных с сервера, параметры передаются в URL

  

### 3. Чем PUT отличается от PATCH?
• PUT - полное обновление сущности (нужно передать все поля)
• PATCH - частичное изменение сущности (передаются только изменяемые поля)
  

### 4. Что такое идемпотентность? Какие методы HTTP идемпотентны?

Идемпотентность - свойство операции, при котором повторное выполнение с теми же входными данными даёт тот же результат.

  

Идемпотентные методы:
• GET - получение данных не меняет состояние
• PUT - повторное полное обновление даёт тот же результат
• DELETE - повторное удаление не меняет результат
• HEAD - получение метаданных не меняет состояние
• OPTIONS - получение списка методов не меняет состояние
  
Неидемпотентные методы:

• POST - каждый вызов создаёт новую сущность
• PATCH - может давать разные результаты при повторном применении


### 5. Какие методы безопасны?

Безапасный только Get. Остальные могут изменять состояние.
Так же можно отнести head, options.

  

### 5. Как сделать метод POST идемпотентным?

- Использовать идемпотентный ключ в запросе (уникальный идентификатор операции)

- Применять условное создание (создавать только если не существует)

- Использовать PUT вместо POST, если известен идентификатор

- Реализовать механизм проверки дубликатов

  

## Задают редко

### 1. Что такое RESTful принципы?

REST (Representational State Transfer) — архитектурный стиль для распределённых систем. Основные принципы:
• Клиент-серверная архитектура
- Разделение ответственности между клиентом и сервером
- Независимое развитие клиентской и серверной части

• Отсутствие состояния (Statelessness)
- Каждый запрос содержит всю необходимую информацию
- Сервер не хранит состояние между запросами
  

• Кэширование
- Ответы должны явно определять возможность кэширования
- Эффективное повторное использование данных

  

• Единообразие интерфейса
- Унифицированный способ взаимодействия с ресурсами
- Стандартные методы HTTP
- Самодокументируемые ответы


• Слоистая система
- Возможность добавления промежуточных слоёв (прокси, балансировщики)
- Клиент не должен знать о внутренней структуре системы

• Код по запросу (опционально)
- Возможность передачи исполняемого кода клиенту

### 2. Что такое stateless и stateful сервисы?
• Stateless сервисы (без состояния):
- Каждый запрос самодостаточен
- Не хранят информацию между запросами
- Легче масштабируются
- REST API является примером stateless архитектуры
  

• Stateful сервисы (с состоянием):
- Хранят информацию о сессии
- Помнят предыдущие запросы
- Сложнее в масштабировании
- Пример: WebSocket соединения

### 3. Коды ответов HTTP

Основные группы:
- 2xx: Успешное выполнение
  - 200 OK - запрос успешен
  - 201 Created - ресурс создан
  - 204 No Content - успешно, нет данных в ответе
- 4xx: Ошибка клиента
  - 400 Bad Request - неверный запрос
  - 401 Unauthorized - требуется аутентификация
  - 403 Forbidden - доступ запрещён
  - 404 Not Found - ресурс не найден
- 5xx: Ошибка сервера
  - 500 Internal Server Error - внутренняя ошибка
  - 503 Service Unavailable - сервис недоступен

### 4. Чем отличается код 200 от 201?
200- ок,
201 - ок- сущность создана

### 5. Что содержит HEADER в ответе REST?
HTTP-headers в REST - это метаданные, которые сервер или клиент отправляет вместе с HTTP-запросом или ответом.

### 2. **В чем разница между PUT и PATCH?**

- **PUT** - полная замена ресурса. Передаем весь объект целиком
- **PATCH** - частичное обновление ресурса. Передаем только изменяемые поля

### 3. **Что означает идемпотентность HTTP метода?**

Идемпотентность означает, что повторное выполнение одного и того же запроса с теми же параметрами даст тот же результат, что и первое выполнение.

**Идемпотентные методы**: GET, PUT, DELETE
**Не идемпотентные**: POST, PATCH (но можно сделать искусственно)

### 4. **Какие HTTP методы считаются безопасными?**

Безопасные методы не изменяют состояние сервера:
- **GET** - единственный безопасный метод

### 5. **Какие HTTP методы кешируются?**

Кешируемые методы:
- **GET** - всегда кешируется
- **POST** - в некоторых исключениях может кешироваться

### 6. **Когда использовать POST, а когда PUT для создания ресурса?**

- **POST** - когда ID ресурса генерируется сервером
- **PUT** - когда ID ресурса известен клиенту заранее

### 7. **Может ли DELETE запрос содержать тело?**

Да, DELETE может содержать тело запроса, хотя это не является стандартной практикой.

### 8. **В чем разница между GET и POST?**

- **GET**: 
  - Не имеет тела запроса
  - Параметры в URL
  - Безопасный и кешируемый
  - Идемпотентный
  
- **POST**:
  - Имеет тело запроса
  - Параметры в теле
  - Небезопасный и некешируемый
  - Не идемпотентный

### 9. **Почему PUT идемпотентный, а POST нет?**

- **PUT** - всегда заменяет ресурс полностью, поэтому повторные вызовы дают тот же результат
- **POST** - создает новый ресурс каждый раз, поэтому повторные вызовы создают разные ресурсы

### 10. **Можно ли использовать GET для передачи чувствительных данных?**

Нет, GET не должен использоваться для передачи чувствительных данных, так как:
- Параметры видны в URL
- URL может логироваться
- URL может передаваться в реферерах

## Задают редко

### 1. В чем разница между  BPMN и UML?
• BPMN (Business Process Model and Notation) — это нотация и стандарт для моделирования бизнес-процессов. Она используется для создания диаграмм, которые показывают, как работает компания: кто что делает, в каком порядке и так далее. BPMN помогает понять, как улучшить процессы и сделать их более эффективными.
• UML (Unified Modeling Language) — это язык моделирования, который используется для создания различных видов диаграмм. Он применяется в разработке программного обеспечения и других областях. UML помогает визуализировать структуру системы, её компоненты и связи между ними.

### В чем разница между диаграммой классов и ER диаграммой?
Диаграммы классов (UML) и ER-диаграммы (Entity-Relationship) используются для моделирования структуры данных, но их цели и принципы различаются

ER-диаграмма: используется для проектирования базы данных (реляционной модели). Описывает сущности, их атрибуты и связи между ними.

Диаграмма классов (UML): применяется в разработке ПО. Описывает классы, их свойства (атрибуты), методы (операции) и связи в объектно-ориентированной системе.

### 5. Что входит в нефункциональные требования?
Нефункциональные требования описывают характеристики системы, которые не связаны с её функциональностью. Например, это могут быть требования к безопасности, производительности, удобству использования, надёжности и масштабируемости.

### 6. В чем разница между User Story и Use Case?
 - User Story - это краткое описание функциональности, которую пользователь хочет получить.
 - Use Case - это более подробное описание функциональности, которая реализуется в системе.

# Файловая система Linux

## Системные каталоги
### Критические для работы системы
- **/boot** - файлы загрузчика ОС и образы ядра
- **/bin** - основные утилиты командной строки (в современных системах часто является символической ссылкой на /usr/bin)
- **/sbin** - системные утилиты для администрирования (в современных системах часто является символической ссылкой на /usr/sbin)
- **/lib** - системные библиотеки для /bin и /sbin (в современных системах часто является символической ссылкой на /usr/lib)
- **/etc** - конфигурационные файлы системы и сервисов

### Виртуальные файловые системы
- **/dev** - файлы устройств (hardware)
- **/proc** - информация о процессах и системе
  - `/proc/{pid}` - данные конкретного процесса
  - `/proc/uptime` - время работы системы
- **/sys** - информация об оборудовании

### Пользовательские данные
- **/home** - домашние каталоги пользователей
- **/root** - домашний каталог администратора
- **/usr** - программы и данные пользователей
  - `/usr/bin` - пользовательские программы
  - `/usr/sbin` - программы для администрирования
  - `/usr/lib` - библиотеки программ
  - `/usr/local` - программы, установленные из исходников
  - `/usr/src` - исходный код ядра и документация

### Временные и монтируемые каталоги
- **/tmp** - временные файлы (очищается при перезагрузке)
- **/media** - точка монтирования съемных носителей
- **/mnt** - точка монтирования файловых систем
- **/run** - временные файлы служб

### Специальные каталоги
- **/opt** - сторонние программные пакеты
- **/srv** - данные сервисов (например, веб-сервера)
- **/var** - логи и временные файлы баз данных

## Важно помнить
- Корневой каталог `/` доступен только root-пользователю для записи (но не только для чтения)
- Структура может незначительно отличаться в разных дистрибутивах
- Все в Linux является файлом (даже устройства и процессы)
