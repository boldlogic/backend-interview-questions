### 6.9 Graceful shutdown HTTP-сервера
**Частота:** 17/59

**Эталон на собесе:**
`http.Server.Shutdown(ctx)` — прекратить приём, дождаться активных соединений, затем close.

**Подробности:**
- Kubernetes `terminationGracePeriodSeconds`.
- Health-проверки перевести в not-ready до drain.
- Не убивать процесс до завершения in-flight запросов.
- Сигнал SIGTERM в K8s → preStop hook → Shutdown с timeout из context.

### 6.5 HTTP/1.1 vs HTTP/2 vs HTTP/3?
**Частота:** 8/59

**Эталон на собесе:**
HTTP — текстовый протокол request/response поверх TCP; HTTPS добавляет TLS. При этом, server должен задавать timeouts (Read, Write, Idle) и корректное завершение через Shutdown. На практике, middleware оборачивает http.Handler и даёт цепочку cross-cutting логики.

**Типичные ошибки:**
- Путают CORS и CSRF или считают, что CORS защищает сервер от всех cross-origin атак.

**Подробности:**
- HTTP/2 — multiplexing на одном TCP; HTTP/3 — QUIC/UDP с встроенным TLS 1.3.
- Context отмены прокидывают в Request.Context; клиентские timeouts — через context или Transport.


### 6.4 TCP vs UDP?
**Частота:** 9/59

**Эталон на собесе:**
TCP — надёжный, порядок байт, handshake, retransmit. При этом, uDP — datagram без гарантий, быстрее, подходит для realtime/metrics.

**Типичные ошибки:**
- «UDP всегда быстрее» без учёта потерь и application-level retry.
- Путают CORS и CSRF или считают, что CORS защищает сервер от всех cross-origin атак.

**Подробности:**
- TCP — HTTP, gRPC, PostgreSQL wire protocol.
- UDP — DNS, QUIC base, gaming, VoIP.
- Head-of-line blocking в TCP vs independent datagrams в UDP.

### 6.3 Зачем timeouts в HTTP?
**Частота:** 10/59

**Эталон на собесе:**
Timeout нужен, чтобы не держать соединения, goroutines и пул БД бесконечно. При этом, он задаёт границу SLA и через context отменяет downstream-работу.

**Типичные ошибки:**
- Не ставят timeouts — goroutine и соединения копятся при медленных клиентах.

**Подробности:**
- Разделяйте таймаут клиента, server timeout, deadline context и retry budget.
- Повторы делать с backoff и только там, где операция идемпотентна.
- Context отмены прокидывают в Request.Context; клиентские timeouts — через context или Transport.

### 6.2 HTTP vs HTTPS?
**Частота:** 9/59

**Эталон на собесе:**
HTTP передаёт данные открытым текстом. При этом, hTTPS добавляет TLS: шифрование, целостность и аутентификацию сервера сертификатом.

**Подробности:**
- TLS защищает транспорт, но не исправляет ошибки авторизации на уровне приложения.
- mTLS добавляет проверку клиента сертификатом.

### 6.1 Из чего состоит HTTP-запрос?
**Частота:** 3/59

**Эталон на собесе:**
HTTP-запрос состоит из стартовой строки (метод, URI, версия), заголовков, пустой строки и необязательного тела. При этом, для HTTP/1.1 важен заголовок Host.

**Подробности:**
- GET обычно без тела; POST/PUT/PATCH часто несут тело.
- Коды 4xx — ошибка клиента, 5xx — ошибка сервера.

### 6.1 HTTP методы
- GET - получение данных
- POST - создание данных
- PUT - полное обновление
- PATCH - частичное обновление
- DELETE - удаление
- HEAD - получение метаданных
- OPTIONS - получение списка доступных методов
**Частота:** часто


### 6.1 Чем POST отличается от GET?
• POST - передача данных на сервер для создания новой сущности, данные передаются в теле запроса
• GET - запрос данных с сервера, параметры передаются в URL
**Частота:** часто


### 6.1 Чем PUT отличается от PATCH?
• PUT - полное обновление сущности (нужно передать все поля)
• PATCH - частичное изменение сущности (передаются только изменяемые поля)
**Частота:** часто
### 6.1 Что такое идемпотентность? Какие методы HTTP идемпотентны?
Идемпотентность - повторное выполнение с теми же входными данными даёт тот же результат.

Идемпотентные методы: 
• GET - получение данных не меняет состояние
• PUT - повторное полное обновление даёт тот же результат
• DELETE - повторное удаление не меняет результат
• HEAD - получение метаданных не меняет состояние
• OPTIONS - получение списка методов не меняет состояние

Неидемпотентные методы:
• POST - каждый вызов создаёт новую сущность
• PATCH - может давать разные результаты при повторном применении
**Частота:** часто


### 6.1 Какие методы безопасны?
Безапасный только Get. Остальные могут изменять состояние.
Так же можно отнести head, options.
**Частота:** часто


### 6.1 Как сделать метод POST идемпотентным?
- Использовать идемпотентный ключ в запросе (уникальный идентификатор операции)
- Применять условное создание (создавать только если не существует)
- Использовать PUT вместо POST, если известен идентификатор
- Реализовать механизм проверки дубликатов
**Частота:** часто


### 6.1 Что такое RESTful принципы?
REST (Representational State Transfer) — архитектурный стиль для распределённых систем. Основные принципы:

• Клиент-серверная архитектура
- Разделение ответственности между клиентом и сервером
- Независимое развитие клиентской и серверной части

• Отсутствие состояния (Statelessness)
- Каждый запрос содержит всю необходимую информацию
- Сервер не хранит состояние между запросами

• Кэширование
- Ответы должны явно определять возможность кэширования
- Эффективное повторное использование данных

• Единообразие интерфейса
- Унифицированный способ взаимодействия с ресурсами
- Стандартные методы HTTP
- Самодокументируемые ответы

• Слоистая система
- Возможность добавления промежуточных слоёв (прокси, балансировщики)
- Клиент не должен знать о внутренней структуре системы

• Код по запросу (опционально)
- Возможность передачи исполняемого кода клиенту

**Частота:** средне


### 6.1 Что такое stateless и stateful сервисы?
• Stateless сервисы (без состояния):
- Каждый запрос самодостаточен
- Не хранят информацию между запросами
- Легче масштабируются
- REST API является примером stateless архитектуры

• Stateful сервисы (с состоянием):
- Хранят информацию о сессии
- Помнят предыдущие запросы
- Сложнее в масштабировании
- Пример: WebSocket соединения
**Частота:** редко


### 6.1 Коды ответов HTTP
Основные группы:
- 2xx: Успешное выполнение
  - 200 OK - запрос успешен
  - 201 Created - ресурс создан
  - 204 No Content - успешно, нет данных в ответе
- 4xx: Ошибка клиента
  - 400 Bad Request - неверный запрос
  - 401 Unauthorized - требуется аутентификация
  - 403 Forbidden - доступ запрещён
  - 404 Not Found - ресурс не найден
- 5xx: Ошибка сервера
  - 500 Internal Server Error - внутренняя ошибка
  - 503 Service Unavailable - сервис недоступен
**Частота:** редко

**Частота:** редко

### 6.1 Что такое XSD?

**Частота:** редко


XSD — это шаблон для формирования или проверки XML.
XSD-схемы позволяют определить:
• типы данных;
• структуру элементов и их вложенность;
• атрибуты элементов и их значения;
• ограничения и правила для данных.
