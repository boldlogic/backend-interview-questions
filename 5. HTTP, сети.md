## 4. Что такое идемпотентность? Какие методы HTTP идемпотентны?
**Частота:** часто
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21

Идемпотентность - повторное выполнение с теми же входными данными даёт тот же результат.

Идемпотентные методы: 
• GET - получение данных не меняет состояние
• PUT - повторное полное обновление даёт тот же результат
• DELETE - повторное удаление не меняет результат
• HEAD - получение метаданных не меняет состояние
• OPTIONS - получение списка методов не меняет состояние

Неидемпотентные методы:
• POST - каждый вызов создаёт новую сущность
• PATCH - может давать разные результаты при повторном применении

## 8. Что такое RESTful принципы?
**Частота:** средне
- [ ] Скорректировано
- [ ] последний повтор

REST (Representational State Transfer) — архитектурный стиль для распределённых систем. Основные принципы:

• Клиент-серверная архитектура
- Разделение ответственности между клиентом и сервером
- Независимое развитие клиентской и серверной части

• Отсутствие состояния (Statelessness)
- Каждый запрос содержит всю необходимую информацию
- Сервер не хранит состояние между запросами

• Кэширование
- Ответы должны явно определять возможность кэширования
- Эффективное повторное использование данных

• Единообразие интерфейса
- Унифицированный способ взаимодействия с ресурсами
- Стандартные методы HTTP
- Самодокументируемые ответы

• Слоистая система
- Возможность добавления промежуточных слоёв (прокси, балансировщики)
- Клиент не должен знать о внутренней структуре системы

• Код по запросу (опционально)
- Возможность передачи исполняемого кода клиенту

## 9. Зачем timeouts в HTTP?
**Частота:** 10/59
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21

**Эталон на собесе:**
Timeout нужен, чтобы не держать соединения, горутины и пул БД бесконечно. При этом, он задаёт границу SLA и через context отменяет downstream-работу.

**Подробности:**

- Повторы делать с backoff и только там, где операция идемпотентна.
- Context отмены прокидывают в Request.Context; клиентские timeouts — через context или Transport.

## 10. HTTP vs HTTPS?
**Частота:** 9/59
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21

**Эталон на собесе:**
HTTP передаёт данные открытым текстом. При этом, hTTPS добавляет TLS: шифрование, целостность и аутентификацию сервера сертификатом.

**Подробности:**
- TLS защищает транспорт, но не исправляет ошибки авторизации на уровне приложения.
- mTLS добавляет проверку клиента сертификатом.

## 11. TCP vs UDP?
**Частота:** 9/59
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21

**Эталон на собесе:**
TCP — надёжный, порядок байт, handshake, retransmit. При этом, uDP — datagram без гарантий, быстрее, подходит для realtime/metrics.

**Типичные ошибки:**
- «UDP всегда быстрее» без учёта потерь и application-level retry.

**Подробности:**
- TCP — HTTP, gRPC, PostgreSQL wire protocol.
- UDP — DNS, QUIC base, gaming, VoIP.

## 14. Коды ответов HTTP
**Частота:** редко
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21

Основные группы:
- 2xx: Успешное выполнение
  - 200 OK - запрос успешен
  - 201 Created - ресурс создан
  - 204 No Content - успешно, нет данных в ответе
- 4xx: Ошибка клиента
  - 400 Bad Request - неверный запрос
  - 401 Unauthorized - требуется аутентификация
  - 403 Forbidden - доступ запрещён
  - 404 Not Found - ресурс не найден
  - 409 Conflict
  - 429 Too many requests
- 5xx: Ошибка сервера
  - 500 Internal Server Error - внутренняя ошибка
  - 503 Service Unavailable - сервис недоступен

## 17. Что такое stateless и stateful сервисы?
**Частота:** редко
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21

• Stateless сервисы (без состояния):
- Каждый запрос самодостаточен
- Не хранят информацию между запросами
- Легче масштабируются
- REST API является примером stateless архитектуры

• Stateful сервисы (с состоянием):
- Хранят информацию о сессии
- Помнят предыдущие запросы
- Сложнее в масштабировании
- Пример: WebSocket соединения
