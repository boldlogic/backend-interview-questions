# 5. HTTP, сети

## 1. HTTP методы
**Частота:** часто
- [ ] Скорректировано
- [ ] последний повтор

- GET - получение данных. Дополнительные параметры (`?ключ=значение`) могут быть переданы прямо в URL
- POST - позволяет отправлять данные на сервер, это могут быть файлы и содержимое различных форм;
- PUT - полное обновление
- PATCH - частичное обновление
- DELETE - удаление
- HEAD - подобен GET, но возвращает только заголовки ответа, без тела. Может, например, использоваться для предварительного получения размера ответа.
- OPTIONS - получение списка доступных методов

## 4. Что такое идемпотентность? Какие методы HTTP идемпотентны?
**Частота:** часто
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21

Идемпотентность - повторное выполнение с теми же входными данными даёт тот же результат.

Идемпотентные методы: 
• GET - получение данных не меняет состояние
• PUT - повторное полное обновление даёт тот же результат
• DELETE - повторное удаление не меняет результат
• HEAD - получение метаданных не меняет состояние
• OPTIONS - получение списка методов не меняет состояние

Неидемпотентные методы:
• POST - каждый вызов создаёт новую сущность
• PATCH - может давать разные результаты при повторном применении

## 8. Что такое RESTful принципы?
**Частота:** средне
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-22

REST (Representational State Transfer) — архитектурный стиль для распределённых систем. Основные принципы:

• Клиент-серверная архитектура
- Разделение ответственности между клиентом и сервером
- Независимое развитие клиентской и серверной части

• Отсутствие состояния (Statelessness)
- Каждый запрос содержит всю необходимую информацию
- Сервер не хранит состояние между запросами

• Кэширование
- Ответы должны явно определять возможность кэширования

• Единообразие интерфейса
- Унифицированный способ взаимодействия с ресурсами
- Стандартные методы HTTP
- Самодокументируемые ответы

• Слоистая система
- Возможность добавления промежуточных слоёв (прокси, балансировщики)
- Клиент не должен знать о внутренней структуре системы

• Код по запросу (опционально)
- Возможность передачи исполняемого кода клиенту

## 13. Из чего состоит HTTP-запрос?
**Частота:** 3/59
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21

**Эталон на собесе:**

**Подробности:**
- GET обычно без тела; POST/PUT/PATCH часто несут тело.

## 14. Коды ответов HTTP
**Частота:** редко
- [x] Скорректировано ✅ 2026-06-22
- [x] последний повтор ✅ 2026-06-22

Код состояния или статус указывает на то, успешно обработался запрос или произошла какая-то ошибка. Код состояния — трёхзначное число и первая цифра указывает на его тип. Пояснение в краткой форме описывает код состояния.

Основные группы:
- 1xx: информационный характер
	- 102 Processing
- 2xx: Успешное выполнение
  - 200 OK - запрос успешен
  - 201 Created - ресурс создан
  - 204 No Content - успешно, нет данных в ответе. Как 200 но без тела ответа
- 3xx: редиректы
	- 301 Moved Permanently
- 4xx: Ошибка клиента
  - 400 Bad Request - неверный запрос
  - 401 Unauthorized - требуется аутентификация
  - 403 Forbidden - доступ запрещён
  - 404 Not Found - ресурс не найден
  - 409 Conflict
  - 415 Unsupported media type. Ожидаем Json, прислали XML
  - 413 Request entity too large. Ожидаем 1кб, прислали 1МБ
  - 429 Too many requests. Не более 10RPS - 11RPS
- 5xx: Ошибка сервера
  - 500 Internal Server Error - внутренняя ошибка
  - 503 Service Unavailable - сервис недоступен

## 17. Что такое stateless и stateful сервисы?
**Частота:** редко
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21

• Stateless сервисы (без состояния):
- Каждый запрос самодостаточен
- Не хранят информацию между запросами
- Легче масштабируются
- REST API является примером stateless архитектуры

• Stateful сервисы (с состоянием):
- Хранят информацию о сессии
- Помнят предыдущие запросы
- Сложнее в масштабировании
- Пример: WebSocket соединения

## 18. Что такое URL?
**Частота:** редко
- [x] Скорректировано ✅ 2026-06-22
- [x] последний повтор ✅ 2026-06-21
```
<схема>:[//[<логин>[:<пароль>]@]<хост>[:<порт>]][/<URL‐путь>][?<параметры>][#<якорь>]
```

- **схема** — как правило, указывается сетевой протокол `https` или `http`;
- **логин** — логин пользователя для доступа к ресурсу;
- **пароль** — пароль пользователя. Логин и пароль в URL практически не используются из соображений безопасности;
- **хост** — IP-адрес или доменное имя;
- **порт** — порт;
- **URL-путь** — путь к запрашиваемой странице или ресурсу;
- **параметры** — параметры `ключ=значение` передаваемые на сервер методом GET. В качестве разделителя используется знак `&`. Например: `?page=1&search=john`;
- **якорь** — при указанном якоре браузер при открытии страницы перейдёт к заголовку или элементу c таким атрибутом `id`.
В URL-адресах, не считая служебных символов (например, `: & = /`), можно использовать только латинские буквы, цифры, минус, знак подчёркивания, точку и тильду. Все остальные символы нужно перекодировать, предварительно преобразовав их в кодировку UTF-8. Из кодировки UTF-8 каждый байт преобразуется в 16-ричное представление с добавлением знака `%`. Так пробел будет преобразован в `%20`


#### 3. Чем идентификация отличается от авторизации и аутентификации?
• Идентификация — это когда система узнаёт пользователя по имени, адресу или другому уникальному идентификатору.
• Авторизация — это процесс, в котором система решает, что пользователю можно делать в системе.
• Аутентификация — это проверка подлинности пользователя, например, с помощью пароля или отпечатка пальца.

### 6.6 REST principles / gRPC vs HTTP?
**Частота:** 1/59

**Эталон на собесе:**
REST — stateless API, ресурсы по URL, семантика HTTP-методов, JSON. При этом, gRPC — HTTP/2, protobuf, генерация кода, streaming; для internal low-latency RPC.

**Типичные ошибки:**
- Путают CORS и CSRF или считают, что CORS защищает сервер от всех cross-origin атак.

**Подробности:**
- grpc-gateway — REST поверх gRPC.
- Версионирование proto через optional fields.
- REST — API без состояния, ресурсы по URL, семантика HTTP-методов, JSON.
- gRPC — HTTP/2, protobuf, генерация кода, streaming.

### 6.8 WebSocket vs REST
**Частота:** 2/59

**Эталон на собесе:**
WebSocket — долгоживущее двунаправленное соединение поверх HTTP upgrade; REST — request/response. При этом, wS для push/streaming, REST для CRUD и кэшируемых API.

**Типичные ошибки:**
- Использовать WS вместо REST там, где достаточно polling.
- Не делать heartbeat/ping — мёртвые соединения не обнаруживаются.

**Подробности:**
- Противодавление, повторное подключение, аутентификация при upgrade.
- WS — push/streaming; REST — polling и CDN cache.
- Heartbeat/ping для обнаружения мёртвых соединений.


### 6.11 CORS и cross-origin (браузер)
**Частота:** 2/59

**Эталон на собесе:**
CORS — заголовки `Access-Control-*`; браузер блокирует cross-origin без разрешения сервера. При этом, preflight `OPTIONS` — для «непростых» запросов.

**Типичные ошибки:**
- Путают CORS и CSRF или считают, что CORS защищает сервер от всех cross-origin атак.

**Подробности:**
- CORS — контролируется браузером; сервер отвечает заголовками `Access-Control-*`.
- Preflight OPTIONS для сложных запросов (non-simple).
- Credentials требуют явного `Allow-Credentials` и конкретного Origin.
