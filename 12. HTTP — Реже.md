## Идемпотентность HTTP / Как сделать POST идемпотентным?
**Частота:** 13/105
**Темы:** #http #network
- [x] Скорректировано ✅ 2026-06-27
- [x] последний повтор ✅ 2026-07-09

Идемпотентность — повторное выполнение с теми же входными данными даёт тот же результат.

**Идемпотентные:** GET, PUT, DELETE, HEAD, OPTIONS.
**Неидемпотентные:** POST (каждый вызов создаёт новую сущность), PATCH (может давать разные результаты).

**Как сделать POST идемпотентным:** идемпотентный ключ в запросе (уникальный идентификатор операции), условное создание (только если не существует), PUT вместо POST если ID известен, проверка дубликатов.

## HTTP методы
**Частота:** 12/105
**Темы:** #http #network
- [x] Скорректировано ✅ 2026-06-27
- [x] последний повтор ✅ 2026-07-09

**GET** — чтение, параметры в URL, безопасный, кэшируемый, идемпотентный.
**POST** — создание (ID генерирует сервер), данные в теле, не идемпотентный.
**PUT** — полное обновление / создание (ID известен клиенту), идемпотентный.
**PATCH** — частичное обновление (только изменяемые поля), не идемпотентный.
**DELETE** — удаление, идемпотентный.
**HEAD** — как GET но без тела (только заголовки).
**OPTIONS** — список доступных методов.

**Тело в GET:** HTTP формально не запрещает, на практике **не используют** (прокси/кэш ломают). Фильтры — query или `POST /search`.

**204 vs 404:** **204** — успех без тела; **404** — ресурс не найден.

**Безопасные:** GET, HEAD, OPTIONS (не меняют состояние). **POST vs GET:** POST — данные в теле, не кэшируется; GET — параметры в URL, не для чувствительных данных (видны в логах/referrer).

## HTTP/1.1 vs HTTP/2 vs HTTP/3?
**Частота:** 6/105
**Темы:** #http #network
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-09

**HTTP/1.1** — текстовый, одно TCP-соединение для последовательных request/response. Keep-alive переиспользует, но HoL-блокировка на уровне соединения. Параллелизм — несколько TCP (браузеры: ~6 на домен).

**HTTP/2** — бинарный, мультиплексирование потоков на одном TCP. Сжатие заголовков (HPACK), приоритизация, server push. Обязателен TLS. HoL-блокировка на уровне TCP (потеря пакета задерживает все потоки).

**HTTP/3** — QUIC (UDP + встроенный TLS 1.3). Устраняет TCP HoL. 0-RTT для повторных соединений. Миграция между сетями без разрыва.

## Из чего состоит HTTP-запрос? / Как разделяются заголовки и тело?
**Частота:** 6/105
**Темы:** #http #network
- [x] Скорректировано ✅ 2026-06-21
- [x] последний повтор ✅ 2026-07-09

HTTP-запрос: стартовая строка (метод, URI, версия) → заголовки → **пустая строка** (`\r\n\r\n`) → тело. Для HTTP/1.1 обязателен `Host`.

GET обычно без тела; POST/PUT/PATCH — с телом. После последнего заголовка идёт пустая строка (CRLF CRLF), дальше тело как сырые байты.

## DNS — как работает резолвинг?
**Частота:** 4/105
**Темы:** #http #network
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-09

DNS — распределённая система: hostname → IP. Порядок: `/etc/hosts` → кэш ОС/браузера → recursive resolver (провайдер, 8.8.8.8) → authoritative DNS (A/AAAA для IP, CNAME — алиас). Запросы — UDP :53, большой ответ — TCP. Кэширование по TTL.

**«google.com в адресной строке»:** DNS → TCP/TLS (или QUIC) → HTTP GET → HTML/ресурсы.

## От чего защищает HTTPS (TLS)? / Что не шифруется в HTTPS?
**Частота:** 2/105
**Темы:** #http #network
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-09

TLS даёт **конфиденциальность** (перехватчик не читает payload), **целостность** (подмена трафика заметна) и **аутентификацию сервера** (сертификат). Не заменяет авторизацию приложения.

**Не шифруется:** IP-адреса, порты, SNI (имя хоста в ClientHello), размер и тайминги пакетов. После handshake заголовки и тело — внутри TLS. ECH/SNI-encryption — отдельная тема.

## Что такое stateless и stateful сервисы?
**Частота:** 2/105
**Темы:** #http #network
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-09

**Stateless:** каждый запрос самодостаточен, сервер не хранит состояние между запросами. Легче масштабируются. REST API — пример stateless.

**Темы:** #http #network
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-09

## WebSocket vs gRPC
**Частота:** 0/105
**Темы:** #http #network
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-09

WebSocket — двунаправленный канал поверх HTTP-upgrade, текстовый/бинарный, подходит для браузеров и простой интеграции. gRPC — бинарный протокол поверх HTTP/2 (Protobuf), строгая типизация, streaming (unary/server/client/bidi), подходит для межсервисного взаимодействия. gRPC для высокопроизводительного service-to-service; WS для real-time клиентам.
