### Хэш-таблица (map / dict)
**Частота:** 55/155
**Темы:** #theory #data-structures #hashmap

Хэш-таблица: ключ → хэш → бакет/слот. Средний доступ **O(1)**, при плохих коллизиях деградация до O(n).

Общее:
- ключ должен быть хэшируемым и сравнимым на равенство;
- коллизии решают цепочками или открытой адресацией;
- при росте — rehash / эвакуация (средняя стоимость амортизируется);
- **не потокобезопасна** без внешней синхронизации.

**Go:** `map` — бакеты/Swiss map, load factor, нельзя брать `&m[k]`, concurrent map write = fatal.  
**Python:** `dict` — хэш-таблица; ключи — hashable (immutable по смыслу); порядок вставки сохраняется (CPython 3.7+).

### Массив и динамический список (array / slice / list)
**Частота:** 40/155
**Темы:** #theory #data-structures #arrays

**Массив** — фиксированная длина, непрерывная память, доступ по индексу O(1).  
**Динамический список** — растущая коллекция поверх массива (amortized append), хранит длину/ёмкость.

Общее:
- индексируемость vs множество/хэш-таблица;
- копирование «всего буфера» vs копирование заголовка/ссылки;
- выход за границы — ошибка runtime.

**Go:** массив `[n]T` vs слайс `[]T` (ptr+len+cap).  
**Python:** `list` — динамический массив ссылок; `tuple` — фиксированная неизменяемая последовательность.

### Гонки данных, дедлоки и синхронизация
**Частота:** 35/155
**Темы:** #theory #concurrency #sync

**Race (гонка данных)** — несколько потоков/горутин пишут/читают общую память без синхронизации; результат зависит от порядка.

**Deadlock** — взаимное ожидание блокировок (A ждёт B, B ждёт A). Профилактика: единый порядок захвата lock, таймауты, избегать nested lock без нужды.

**Livelock** — формально не «стоят на lock», но прогресса нет (взаимные уступки/retry без backoff).

Общие примитивы: mutex / RW-lock, атомики, каналы/очереди как способ убрать shared mutable state.

**Go:** `-race`, `sync.Mutex`/`RWMutex`, каналы.  
**Python:** `threading.Lock`, GIL не отменяет логические гонки на уровне данных приложения.

### Конкурентность vs параллелизм
**Частота:** 23/155
**Темы:** #theory #concurrency

**Конкурентность** — много задач в одном интервале времени (чередование / ожидание I/O).  
**Параллелизм** — одновременное исполнение на нескольких ядрах CPU.

На одном ядре возможна конкурентность без параллелизма. Асинхронность (не блокировать вызывающего) ≠ параллелизм.

**Go:** горутины + scheduler; `GOMAXPROCS`.  
**Python:** `threading` (часто I/O; GIL на CPU bytecode), `multiprocessing` (процессы), `asyncio` (кооперативная конкурентность в одном потоке).

### Итераторы и ленивые последовательности
**Частота:** 23/155
**Темы:** #theory #iterators

**Итератор** — объект обхода: «следующий элемент» / Stop.  
**Итерируемое** — то, из чего получают итератор.

**Ленивая последовательность / генератор** — значения по запросу, без полной материализации в памяти.

**Python:** `__iter__` / `__next__`, generator functions (`yield`).  
**Go:** обычно `for range`; ленивость — через каналы/кастомный API, не как синтаксис генераторов.

### Изменяемость и семантика копирования
**Частота:** 23/155
**Темы:** #theory #types #memory

**Immutable** — значение нельзя изменить на месте; «изменение» = новое значение.  
**Mutable** — объект меняется in-place; алиасы видят одну и ту же мутацию.

Связано с: передача по значению vs по ссылке; безопасность как ключ хэш-таблицы; гонки при shared mutable state.

**Python:** `str`/`tuple`/`frozenset` immutable; `list`/`dict`/`set` mutable; `==` vs `is`.  
**Go:** передача копирует значение; slice/map/channel — заголовок со ссылкой на общую структуру; value vs pointer receiver.

### Память: стек, куча и GC
**Частота:** 20/155
**Темы:** #theory #memory #gc

**Стек** — кадры вызовов, быстро выделяется/освобождается, ограничен.  
**Куча** — объекты с временем жизни дольше кадра / «убежавшие» из scope; обслуживает **GC**.

Утечки: достижимые, но ненужные объекты (кэш без TTL, «забытые» задачи/горутины/потоки).

**Go:** escape analysis (stack vs heap), GC, pprof heap.  
**Python (CPython):** reference counting + цикл-детектор; `gc` модуль; циклы ссылок.

---

### Асимптотическая сложность (Big-O)
**Частота:** 20/155
**Темы:** #theory #complexity #algorithms

Big-O — рост числа операций/памяти от размера входа n (обычно worst case). Константы отбрасывают.

Классы: O(1), O(log n), O(n), O(n log n), O(n²), O(2ⁿ)…

Примеры: доступ по индексу/ключу хэш-таблицы ≈ O(1); полный обход ≈ O(n); эффективная сортировка ≈ O(n log n).

### Множество (set)
**Частота:** 14/155
**Темы:** #theory #data-structures #set

Множество — уникальные элементы, без (гарантированного) порядка индексов; проверка принадлежности в среднем O(1) на хэш-реализации.

Операции: add / remove / contains; union / intersection / difference.

**Go:** отдельного set нет → `map[T]struct{}`.  
**Python:** встроенный `set` / `frozenset` (immutable, hashable).

### Интерфейсы и полиморфизм
**Частота:** 13/155
**Темы:** #theory #oop #interfaces

**Интерфейс (контракт)** — набор операций, которые можно выполнить над сущностью, без привязки к конкретной реализации/структуре данных. Полиморфизм: один контракт — много реализаций; код работает с интерфейсом, не зная внутреннего устройства объекта.

Зачем: слабая связанность, подмены в тестах, DI, расширение без правки вызывающего кода.

**Виды полиморфного поведения (общая теория):**
- **subtype / inclusion** — потомок/реализация подставляется там, где ждут базовый контракт (классика ООП);
- **ad hoc** — разное поведение для разных типов аргументов (перегрузки, отдельные ветки по типу);
- **параметрический** — одна логика для разных типов (generics / type parameters).

**Go:** неявная реализация интерфейса; маленькие интерфейсы; value interface = (тип, данные).  
**Python:** duck typing / `Protocol` (typing); ABC при явных контрактах.

### Равенство значений vs идентичность
**Частота:** 8/155
**Темы:** #theory #types

**Равенство** — одинаковое содержимое / семантика `==`.  
**Идентичность** — один и тот же объект в памяти.

**Python:** `==` vs `is` (и interning мелких int/str — ловушка).  
**Go:** `==` для comparable типов; для reference-like структур сравнивают содержимое/`reflect`/указатели осознанно; map/slice не comparable целиком.

### Что такое ООП
**Частота:** 0/155
**Темы:** #theory #oop

**ООП** — методология, где программа — совокупность **объектов** (экземпляров **классов**), а классы связаны иерархиями (часто через наследование / подтипы). Объекты взаимодействуют, обмениваясь **сообщениями** (вызовами методов).

Классические критерии «настоящего» ООП: объекты как основные строительные блоки; экземпляры классов; иерархии. Без наследования/подтипов чаще говорят о программировании с абстрактными типами данных, а не о полном ООП.

Состояние объекта меняют через его публичный контракт (сообщения), а не через прямой доступ к внутренностям — это стыкуется с инкапсуляцией.

---

### Принципы ООП
**Частота:** 0/155
**Темы:** #theory #oop

Базовый набор на собесе:
- **Инкапсуляция** — объединить данные и поведение, скрыть реализацию, открыть контракт.
- **Наследование** — описать новую сущность на базе существующей (is-a / переиспользование структуры и поведения).
- **Полиморфизм** — работать через общий контракт с разными реализациями.
- **Абстракция** — выделить существенные характеристики, отбросить несущественные детали.

Часто добавляют: **обмен сообщениями** (единственный способ «попросить» объект что-то сделать) и **переиспользование** как следствие принципов выше.

Порядок «строго от инкапсуляции к полиморфизму» полезен для объяснения зависимостей, но это учебная схема, а не закон природы.

---

### Инкапсуляция
**Частота:** 0/155
**Темы:** #theory #oop

**Инкапсуляция** — объединение данных и операций над ними в одной сущности и **сокрытие** деталей реализации: снаружи виден контракт (публичные операции), внутри — поля и вспомогательная логика.

Цель: внешний код не зависит от внутренней реализации; можно менять внутренности, не ломая клиентов, пока контракт стабилен.

Не путать с «просто private везде»: открытый API — тоже часть инкапсуляции; полностью закрытый объект бесполезен.

---

### Наследование
**Частота:** 0/155
**Темы:** #theory #oop

**Наследование** — описание нового типа на основе существующего с частичным/полным заимствованием поведения и структуры. Базовый тип — предок; новый — потомок.

Зачем: переиспользовать общее, специализировать частное (override), моделировать is-a.

Риски: глубокие хрупкие иерархии, «наследование реализации» вместо композиции, нарушение LSP. Во многих языках (в т.ч. Go) классического class-наследования нет — роль берут интерфейсы + композиция/embedding.

---

### Абстракция
**Частота:** 0/155
**Темы:** #theory #oop

**Абстрагирование** — выделить существенные характеристики сущности и отбросить несущественные для текущей задачи. **Абстракция** — результат: модель «что важно», без лишних деталей реализации.

На практике: интерфейсы/протоколы, абстрактные типы, доменные модели. Связана с инкапсуляцией (прячем «как»), но акцент на «что моделируем».

---

### Обмен сообщениями в ООП
**Частота:** 0/155
**Темы:** #theory #oop

Объекты взаимодействуют, **посылая сообщения** (запрос выполнить действие + аргументы). В ООП это обычно вызов метода: единственный штатный способ передать управление объекту.

Если объект «понимает» сообщение — у него есть соответствующий метод. Ответ может менять состояние и/или слать сообщения дальше. В сочетании с динамическим связыванием выбор реализации часто откладывается до runtime.

### Класс, объект, интерфейс (контракт)
**Частота:** 0/155
**Темы:** #theory #oop

- **Класс** — описание сущности: состояние (поля), поведение (методы), правила взаимодействия. С точки зрения языка — сложный тип / чертёж.
- **Объект (экземпляр)** — конкретный представитель класса со своим состоянием; поведение задаётся классом.
- **Интерфейс** здесь — **контракт использования**: публичные операции (и при необходимости публичные атрибуты), через которые с сущностью работают снаружи. Не обязательно языковой keyword `interface`.

См. также карточку **Интерфейсы и полиморфизм** (поведение vs реализация, Go/Python).

### Плюсы и минусы ООП
**Частота:** 0/155
**Темы:** #theory #oop

**Плюсы:** модель близка к «сущностям предметной области»; локализация данных и операций; модульность через инкапсуляцию; расширяемость через полиморфизм/подтипы; переиспользование проверенных компонентов; проще подменять реализации (в т.ч. в тестах).

**Минусы:** сложные иерархии трудно читать («где живёт метод?»); поведение «размазано» по override-цепочке; документировать контракты сложнее (метод могут переопределить); накладные расходы динамического связывания; избыточная универсальность базовых классов (мёртвый код в наследниках).

На собесе ждут баланс: не «ООП всегда хорошо», а когда уместно vs процедурное / data-oriented / композиция без глубокого наследования.

### «Является» и «имеет» (is-a / has-a)
**Частота:** 0/155
**Темы:** #theory #oop

- **«Является» (is-a)** — отношение **наследования / подтипа**: Smartphone является Phone.
- **«Имеет» (has-a)** — **ассоциация** (в т.ч. агрегация или композиция): Car имеет Engine / Driver.

Ошибка уровня junior: моделировать has-a через наследование («машина наследует двигатель»).

### Композиция vs агрегация
**Частота:** 0/155
**Темы:** #theory #oop

Обе — варианты ассоциации «часть–целое».

- **Композиция** — часть **не существует** без целого: владелец создаёт и уничтожает часть (жизненный цикл связан). Пример: двигатель, созданный внутри автомобиля.
- **Агрегация** — часть **может жить отдельно**, передаётся/назначается снаружи. Пример: водитель и машина.

Практический ориентир: создание зависимости «внутри» владельца ≈ композиция; dependency injection снаружи ≈ агрегация. Часто предпочтительнее агрегация + DI (тестируемость, DIP); композицию — когда часть концептуально неотделима.

### Статическое и динамическое связывание
**Частота:** 0/155
**Темы:** #theory #oop

**Связывание** — сопоставление вызова метода с конкретным телом метода.

- **Статическое (early)** — решение до выполнения (компилятор/линкер): известен точный target.
- **Динамическое (late / runtime)** — выбор реализации **во время выполнения** по фактическому типу объекта (vtable / диспетчеризация / duck typing).

Динамическое связывание — основа subtype-полиморфизма. Цена: косвенность вызова и нужна runtime-информация о типе. Детали «когда язык всегда late, а когда early» — в языке (для Java — в `oop.md` java-пакета).

### Модульное тестирование (unit)
**Частота:** 0/155
**Темы:** #theory #testing

**Unit / компонентное тестирование** — проверка **отдельного** модуля (функции, класса, пакета) на корректность в изоляции. Цель: быстро ловить регрессии после изменений, локализовать дефект.

Условно:
- **state-based** — после вызова смотрим состояние объекта / возвращаемое значение;
- **interaction** — проверяем, что с зависимостями общались правильно (часто через mock/spy).

Зависимости обычно подменяют test doubles, чтобы не тянуть сеть/БД.

---

### Интеграционное тестирование
**Частота:** 0/155
**Темы:** #theory #testing

**Интеграционное тестирование** — проверка **нескольких модулей вместе** как одного блока: реальные (или почти реальные) стыки, контракты, протокол, транзакции, сериализация.

Ищет дефекты на границах: несовместимые ожидания, конфиг, таймауты, схема данных — то, что unit с моками часто не видит.

---

### Unit vs integration
**Частота:** 0/155
**Темы:** #theory #testing

Общее: оба опираются на интерфейсы модулей и тестовое окружение. Разница — **цель и тип дефектов**, а значит стратегия данных и анализа.

| | Unit | Integration |
| --- | --- | --- |
| Фокус | один модуль в изоляции | стык 2+ модулей / с внешней системой |
| Зависимости | чаще doubles | чаще реальные или testcontainers |
| Скорость / стабильность | быстрее, детерминированнее | медленнее, flaky-риск выше |
| Что ловит | логика модуля | контракты, wiring, I/O |

Пример: класс дергает web-сервис через зависимость. Реальный клиент + сеть → integration; stub с фиксированным ответом → unit (state); spy/mock с проверкой вызова → unit (interaction).

### Test doubles: dummy, fake, stub, spy, mock
**Частота:** 0/155
**Темы:** #theory #testing

Подмены зависимостей в тестах (классификация xUnit):

- **dummy** — передали «для формы», методы почти не вызывают (`null`, пустой объект);
- **fake** — облегчённая рабочая реализация (in-memory DB, fake HTTP), чтобы ускорить/упростить;
- **stub** — отдаёт **заранее заданные** ответы на запросы из SUT, входящие вызовы по сути игнорирует;
- **spy** — как stub + **журнал вызовов** (сколько раз, с какими аргументами);
- **mock** — объект с **ожиданиями** по взаимодействию: что вызовут, в каком порядке; проверяет interaction, не только состояние.

На собесе часто путают stub и mock: stub кормит данными; mock проверяет «как звали».

### stub vs mock
**Частота:** 0/155
**Темы:** #theory #testing

- **stub** — заглушка с запрограммированным ответом; фокус на **состоянии** / результате SUT.
- **mock** — подмена с контролем **взаимодействия** (факт вызова, аргументы, порядок); фокус на protocol между объектами.

Оба — test doubles. Spy ближе к mock по фиксации вызовов, но без жёсткого «сценария ожиданий» заранее.

### Фикстуры (test fixtures)
**Частота:** 0/155
**Темы:** #theory #testing

**Фикстура** — заранее известное **состояние окружения**, нужное тесту: данные, объекты, временные каталоги, поднятый контейнер. Задача — **повторяемость**: каждый прогон стартует из одного и того же setup.

Типичный lifecycle: setup перед тестом / suite → teardown после. Конкретные аннотации/API — в фреймворке (JUnit, pytest, testing в Go).
