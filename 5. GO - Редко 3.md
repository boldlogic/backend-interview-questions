## Что делает runtime Go при нехватке памяти?
**Частота:** редко
**Темы:** #go/gc #go/runtime
- [ ] Скорректировано
- [ ] последний повтор

**Как формулируют на собесе:**
> Выделили память, ОС отказала / памяти нет совсем — что сделает Go runtime?

**Эталон на собесе:**
При давлении на память runtime сначала пытается освободить heap через GC (в том числе фоновый). Если выделить память всё равно не удаётся — процесс падает с `fatal error: runtime: out of memory`. Go не подменяет swap/OOM killer ОС.

**Типичные ошибки:**
- Ожидать, что GC всегда спасёт от OOM при неограниченном росте heap.
- Путать с настройкой GOGC — она влияет на частоту GC, но не отменяет лимит памяти процесса.

**Подробности:**
- `GOMEMLIMIT` (Go 1.19+) — soft limit, runtime раньше ужесточает GC.
- См. §17 GOGC, [[3. GO - Редко#25. Как работает GC (tri-color)?]].

## Что такое дедлок и рейс кондишион
**Темы:** #go/deadlock #go/data-race
- [x] Скорректировано ✅ 2026-06-26
- [ ] последний повтор

**Что ожидают на собесе:**


Дедлок - состояние когда две или несколько горутин пытаются захватить блокировку друг у друга и не могут продолжить работу. 

**Deadlock** — это ситуация, когда горутины взаимно заблокированы и бесконечно ждут друг друга, поэтому выполнение не может продолжиться.

1 горутина пытается захватить блокировку у второй а
а вторая пытаются захватить блокировку у первой. 
И они встают в дедлок и не могут продолжить работу

Race condition — ситуация, когда несколько горутин одновременно работают с общими данными, и результат зависит от порядка выполнения.

**Race condition** — это одновременный небезопасный доступ нескольких горутин к общим данным, когда хотя бы одна из них изменяет данные, и итог зависит от порядка выполнения операций.

Результат непредсказуем

два потока увеличивают счетчик без синхронизации

## Что такое массив?
**Частота:** редко
**Темы:** #go/array #go/types
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**


> [!summary] Собес: как отвечать
> Массив - это последовательность элементов одного типа и постоянной длины. Размер массива - составная часть его типа и задается во время компиляции. 

- Размер после объявления не меняется.
- Многомерный `[M][N]T` — M элементов типа `[N]T`; пример: `[4][7]int`.
- Непрерывный блок N × sizeof(T), **доступ по индексу O(1)**; для `[M][N]T` — построчно. 
- Без инициализации каждый элемент — zero value своего типа. 
- value type: при присваивании и передаче в функцию копируются все элементы. Мутация параметра `[N]T` внутри функции снаружи не видна; чтобы менять исходное значение, параметр объявляют `*[N]T`.
- Два массива одного типа `[N]T` можно сравнивать оператором == , если сравним тип T — тогда же `[N]T` годится ключом map. Сравнение двух значений одного `[N]T` через  ==  поэлементное, слева направо
- Сравнимые типы: 
	- числа
	- string
	- pointer
	- array
	- struct с comparable-полями; 
- Значение `len(a)` подставляется компилятором как константа.
- Типы `[3]int` и `[5]int` несовместимы: ни присвоить одно другому, ни сравнить между собой нельзя. 
- Размер можно вывести из литерала (`[...]int{10, 20}`), задать явно или указать только нужные индексы (`[7]int{2: 3, 6: 11}`). 
- Пустой массив `[0]int` допустим. 
- Обращение по индексу-константе вне диапазона — ошибка компиляции; по переменному индексу вне `[0, N)` — паника.
- В `for range` по массиву переменная итерации — копия элемента, не ссылка на ячейку. Для изменения на месте обходят по индексу или берут указатель на элемент явно.
- Копирование struct с полем-массивом включает весь массив. 

```go
var a [5]int
b := [3]int{1, 2, 3}
c := [...]int{10, 20}
d := [7]int{6: 11, 2: 3}
```

## Эвакуация мапы
**Темы:** #go/map #go/hash #go/runtime
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26

**Что ожидают на собесе:**


В старой реализации map эвакуация — это постепенный перенос данных из старых бакетов в новые после роста. Перенос идёт кусками во время последующих операций, поэтому какое-то время map живёт в промежуточном состоянии.

Рост запускался, при средней загрузке около 6.5 элементов на бакет или при слишком большом числе overflow buckets. Перенос выполнялся лениво, по мере операций с map.

Главный способ снизить вероятность роста — **давать capacity hint**: `make(map[K]V, n)`. Это ожидаемое количество элементов, а не количество бакетов и не размер памяти. Не защитит от коллизий.

В новой Swiss-map реализации детали роста другие: map разбита на группы/таблицы, при росте может происходить расширение или разделение таблиц. Поэтому объяснение через старую эвакуацию бакетов относится именно к старой реализации.
