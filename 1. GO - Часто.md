**Эталон на собесе:**
Есть буферизированный и не буферизированный.
**Небуферизированный** канал — синхронный: отправитель встречается с получателем, данные передаются из стека одной горутины в стек другой горутины. Работают по аналогии с эстафетной палочкой: нельзя отправить, пока некому прочитать.
- Создание без ёмкости
```go
ch := make(chan [тип данных])
```
- Ёмкость и длина равны 0.
**Буферизированный** - канал у которого есть определенный буфер, не блокирует запись, пока len < cap. Буферы помогают избежать лишних простоев. Буфер это кольцевая очередь. По аналогии с почтовым ящиком: пока есть место в ящике, отправитель может положить значение и уйти.
- Создание с ёмкостью
```go
ch := make(chan [тип данных], 1)
```
- Ёмкость фиксирована (проверяется через `cap()`), текущее количество элементов — через `len()`.
- **Буферизация влияет только на поведение блокировки.**
- буферизированный с буфером 1 != небуферизированному

## Как устроен слайс?
**Частота:** 17/56
**Темы:** #go/slice
- [x] Скорректировано ✅ 2026-06-18
- [ ] последний повтор
**Что ожидают на собесе:**
- Назвать три поля заголовка: **указатель на базовый массив**, **len**, **cap**.
- Объяснить, что slice — view на непрерывную область памяти, а не «сам массив».
**Эталон на собесе:**
Слайс — **структура-заголовок** (SliceHeader): указатель на первый элемент базового массива + **len** (сколько элементов видно) + **cap** (сколько элементов помещается в текущий базовый массив без перевыделения). `cap ≥ len` всегда.
Инициализируется через make или литерал. Иначе nil - слайс.
Адрес слайса (&slice) — это адрес структуры с метаданными (SliceHeader), которая содержит информацию о Data, Len, Cap.
Длина меняется через append.
- Append без превышения cap — тот же базовый массив.
- Рост cap при append: до 256 элементов ~×2, далее плавный переход к ~×1.25 через хитрые формулы с выравниваниями.
Передача slice в функцию копирует заголовок, базовый массив общий но не элементы — мутации существующих элементов видны снаружи.
Сложность append O(1), при создании нового базового массива О(n)
copy(dst, src) копирует min(len(dst), len(src)) элементов, не cap.
**Nil vs пустой:** `var s []int` — nil (`len=0`, `cap=0`); `s := []int{}` или `make([]int, 0)` — non-nil, тоже `len=0`. Оба принимают `append`.
**Синтаксис среза:** `s[low:high]` — `[low, high)`; опущенный low = 0, high = len. Full slice: `s[low:high:max]` — cap нового view = `max - low`.
```go
var nilSlice []int // nil
nonNil := make([]int, 0) // [] non-nil
s := make([]int, 3, 10)
t := []int{1, 2, 3}
```
### Строка и `[]byte`
- Строка **неизменяемая**, UTF-8; `s[i]` — **байт**, не символ.
- `for range` по строке — **руны**.
- Изменить текст: `[]rune`, `strings.Builder` или `[]byte` + копия.

**Эталон на собесе:**
Запись в закрытый channel — panic. При этом, чтение — сначала буфер, потом zero значение, `ok=false`.
повторное закрытие — panic.
| Состояние | Запись (`ch <- v`) | Чтение (`<-ch`, `v, ok := <-ch`) | Закрытие (`close(ch)`) |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| **nil** | Блокировка навсегда | Блокировка навсегда | Паника |
| **Не nil и не закрыт** | Небуферизованный: без готового получателя — блокировка. Буферизированный: при месте в буфере — без блокировки, иначе блок до чтения | Блокируется до получения значения; в буфере — сразу, если есть данные | Закрывает канал; не влияет на уже находящиеся данные |
| **Закрыт** (`close(ch)`) | **Паника** | Возвращает нулевое значение типа канала (например, 0 для `chan int`); `ok = false` при форме `v, ok := <-ch` | **Паника** (повторное закрытие) |
**Подробности:**
- `for range ch` завершается после close+вычитывания.

## Как устроена map под капотом?
**Частота:** 15/56
**Темы:** #go/map #go/hash #go/runtime
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-22
**Что ожидают на собесе:**
- Сказать «хеш-таблица»: массив бакетов + hash-функция.
- (бонус) Как обрабатываются коллизии (overflow buckets / open addressing в Swiss map).
**Эталон на собесе:**
Map — хеш-таблица: **массив бакетов** + **hash-функция** по ключу.
1. Ключ хешируется
2. по хешу выбирается бакет
3. внутри бакета ищется точное совпадение ключа (часто сначала по короткому фрагменту хеша).
**Коллизии:** несколько ключей попали в один бакет → в старой реализации **overflow buckets** (цепочка дополнительных бакетов); в Go 1.24+ (Swiss map) — **open addressing** внутри групп. Много коллизий = хуже locality и больше сравнений ключей.
До Go 1.24 основа реализации — массив бакетов. В одном бакете до 8 пар ключ/значение + служебные данные. Если в бакете несколько кандидатов, сначала проверяется короткий фрагмент хеша, потом сравнивается полный ключ.
Если в один бакет попало слишком много ключей, появляются **overflow buckets** — дополнительные бакеты-цепочки. Это хуже для производительности, потому что приходится ходить дальше по связанному списку.
При росте создаётся новая область бакетов. Обычно число бакетов увеличивается, но возможен и same-size grow, когда проблема в большом числе overflow buckets. Старые бакеты остаются в `oldbuckets`, данные переносятся не сразу, а постепенно — это называется эвакуацией.
**Подробности:**
При чтении `v := m[key]` считается хеш, выбирается нужная область таблицы, затем runtime проверяет кандидатов и сравнивает ключи.
- На тип значений ограничений нет.
- Seed хеша задаётся на процесс (защита от hash-DoS; побочно — случайный порядок обхода)
- Мутация map во время `range` в той же goroutine разрешена с оговорками; конкурентная запись из другой goroutine без синхронизации — fatal error.
- В старой реализации `hmap` хранит, например, `count`, `B` (`log2` числа бакетов), seed хеша и указатели на бакеты.
- `new(map[K]V)` не используют потому что nil
- nil map: `m[k]` возвращает zero value; `m[k] = v` — panic. Инициализированная map: `m := make(map[K]V)`.
- В func копируется заголовок, не указатель на map. Запись `m[k] = v` внутри func видна снаружи — общие данные, но это не передача *map.
- `v, ok := m[k]` — ok ложен, если ключа нет (даже когда zero value был бы валидным значением)
- `delete(m, k)`, `clear(m)` (Go 1.21+), `clear(nil)` — no-op. `len(m)` — число пар.
- Сравнивать две map между собой нельзя — для равенства `maps.Equal` или ручной обход.
- С nil допустимо только m == nil (не пустая make-map).
- map не может быть ключом другой map.
- Копия — `maps.Clone`
```go
var m map[string]int // nil
m = make(map[string]int)
v, ok := m[k]
delete(m, k)
clear(m) // Go 1.21+
```

## Mutex и RWMutex
**Частота:** 14/56
**Темы:** #go/sync
- [x] Скорректировано ✅ 2026-06-21
- [x] последний повтор ✅ 2026-06-26
**Что ожидают на собесе:**
- Зачем Mutex: исключить **data race** — только одна goroutine в критической секции.
- (бонус) Отличие `RWMutex`; (бонус+) FIFO-очередь ожидания, starvation, приоритет writer в `RWMutex`.
**Эталон на собесе:**
**Mutex** — эксклюзивная блокировка: в один момент времени **только одна** goroutine выполняет защищённый код. Это убирает гонку при read-modify-write и составных инвариантах на нескольких полях.
**RWMutex** — много параллельных **читателей** (`RLock`/`RUnlock`) **или** один **писатель** (`Lock`/`Unlock`). Писатель блокирует всех читателей; новые читатели не проходят, пока ждёт писатель.
**Подробности:**
- RWMutex не магия при частых записях — читатели могут **голодать**, писатели тоже при постоянном потоке readers.
- В `sync.RWMutex` при ожидании writer новые readers **не** захватывают lock (приоритет записи над новым чтением) — иначе writer мог бы ждать бесконечно.
- Ожидающие goroutine ставятся в **FIFO**-очередь семафора; при длинных критических секциях возможен **starvation** — нужны короткие секции и иногда fair lock / отдельная архитектура.
- Для map под нагрузкой — shard+mutex или `sync.Map` .
RWMutex имеет те же методы `Lock()` и `Unlock()`, но использовать их нужно только для критической секции, изменяющей данные. Для кода, который читает данные, нужно использовать методы `RLock()` и `RUnlock()`. `RLock()` не даст выполниться `Lock()` и начать изменение данных, пока не будут завершены все операции чтения.
| Состояние | Метод `RLock()` | Метод `Lock()` |
| --- | --- | --- |
| Мьютекс свободен | Возьмёт мьютекс в режиме чтения | Возьмёт мьютекс в режиме записи |
| Одна горутина уже взяла мьютекс через `RLock()` | Возьмёт мьютекс в режиме чтения. Блокировки не будет | Будет блокировать горутину до тех пор, пока другие горутины не отпустят мьютекс |
| Одна горутина уже взяла мьютекс через `RLock()`. Вторая ждёт `Lock()` | Будет блокировать горутину до тех пор, пока другая горутина не дождётся метода `Lock()` и не отпустит его | Будет блокировать горутину до тех пор, пока не будут отпущены все остальные блокировки |
| Одна горутина взяла мьютекс через `Lock()` | Будет блокировать горутину до тех пор, пока не будут отпущены все блокировки на запись | Будет блокировать горутину до тех пор, пока не будут отпущены все остальные блокировки |
При использовании мьютексов нужно обязательно придерживаться трёх основных правил
1. После блокировки мьютекса его всегда нужно разблокировать. Если этого не сделать, другие горутины так и будут ожидать своей очереди на выполнение критической секции.
2. Если вы применяете мьютексы для синхронизации доступа к общим данным, следите за тем, чтобы не было горутин, работающих с этими данными без мьютекса. Например, если значение общей переменной меняется горутинами в двух местах, а мьютекс применяется только в одном, то смысла в этом нет, так как ошибки всё равно будут.
3. В общем случае нужно стремиться сокращать продолжительность выполняемого кода внутри критической секции.

## Рост capacity слайса / Как работает append?
**Частота:** 11/56
**Темы:** #go/slice
- [x] Скорректировано ✅ 2026-06-26
- [x] последний повтор ✅ 2026-06-23
**Что ожидают на собесе:**
**Эталон на собесе:**
При превышении cap — выделяется новый массив, копирование элементов, новый указатель в заголовке слайса.
Рост cap при append
- до 256 элементов ~×2
- далее плавный переход к ~×1.25 через хитрые формулы с выравниваниями.
**Подробности:**
Runtime `nextslicecap` (Go 1.18+)
- `oldCap < 256` — **×2**
- `oldCap ≥ 256` — плавный рост к **~×1.25** (`newcap += (newcap + 3×256) / 4`)
- `newLen > 2×oldCap` — `newcap = newLen`
- cap округляется до **size class** аллокатора — реальный cap может быть чуть больше формулы. Выравнивание памяти с округлением до 1 байта вверх, если размер элемента меньше 8 бит
**Сложность:** один `append` — O(1)
realloc — O(n)
серия append по одному — O(1) амортизированно.
**Append в func** до realloc меняются **элементы** в общем базовый массив, **`len` caller** — нет; после realloc новый ptr только внутри func.

## Чем горутина отличается от потока?
**Частота:** 10/56
**Темы:** #go/goroutine #go/scheduler
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26
**Что ожидают на собесе:**
**Эталон на собесе:**
Goroutine — легковесный поток
- ~2–8 KB стека, растёт и сжимается . Это делает горутины более эффективными в плане использования памяти.
- у потока стек обычно фиксированный ~1–8 MiB.
- Создание горутины занимает меньше времени, чем создание потока, поскольку при этом не создается системный ресурс
- Переключение между горутинами занимает меньше времени, чем переключение между потоками, поскольку осуществляется полностью внутри процесса, что исключает необходимость выполнения сравнительно медленных системных вызовов
При этом, поток ОС — поток ядра. Планировщик Go (GMP) мультиплексирует G на M.
**Подробности:**
- Переключение G — в user space: сохраняются стек G и PC, без обязательного kernel context switch на каждую goroutine.
- M:N модель: тысячи горутин мультиплексируются на десятки потоков; число потоков не равно числу горутин.
- `GOMAXPROCS` по умолчанию = `runtime.NumCPU()` — сколько G одновременно исполняются на CPU (число P).
- Netpoller: при сетевом I/O горутина паркуется, поток продолжает выполнять другие горутины — процесс не блокируется целиком.
- Создание горутины дешевле потока ОС: нет syscall на каждую goroutine, runtime сам управляет пулом потоков.

## Чем слайс отличается от массива?
**Частота:** 10/56
**Темы:** #go/slice #go/array #go/types
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26
**Что ожидают на собесе:**
**Эталон на собесе:**
Массив - это структура с фиксированной длиной, размер - часть типа.
А слайс это надстройка над массивом которая позволяет иметь динамическую длину. Слайс не хранит данные сам, а является ссылкой на часть базового массива = ссылка+метаданные.
Массив обычно сравнимый, если элементы сравнимые, слайс не сравнимый.
Массив после объявления заполняется нулевыми значениями, а слайс nil - нужно мейкать.
Массив в функцию обычно копируется целиком - мутации снаружи не видны, а у слайса копируется только заголовок - мутации существующих элементов в общем базовом массиве видны.
- `[N]T` — размер часть типа, value копируется целиком при присваивании.
- `[]T` — view на базовый массив; копируется только заголовок, **данные общие** у subslicе.
- `[N]T` **comparable** (если `T` comparable) и **может быть ключом map**; **slice — нет**.

## Stack vs heap — зачем и производительность?
**Частота:** 9/56
**Темы:** #go/memory
- [ ] Скорректировано
- [ ] последний повтор
**Что ожидают на собесе:**
**Эталон на собесе:**
Stack — frame функции, дешёвый. При этом, heap — когда анализ escape не может доказать, что указатель не уйдёт наружу. На практике, профилировать, не гадать.
**Типичные ошибки:**
- «Всё на heap» без анализ escape.

## Чем конкурентность  отличается от параллелизма?
**Частота:** 6/56
**Темы:** #go/concurrency #go/scheduler
- [x] Скорректировано ✅ 2026-06-22
- [x] последний повтор ✅ 2026-06-26
**Как формулируют на собесе:**
> Concurrency vs parallelism — в чём разница?
**Эталон на собесе:**
Конкурентность — много задач конкурируют за один общий ресурс.
Параллелизм — много задач выполняются на многих ресурсах.
Будет или нет конкурентный код выполняться параллельно зависит от железа (несколько ядер). На одном ядре возможна конкурентность без параллелизма.
Параллелизм — это одновременное выполнение нескольких сущностей определенного вида, тогда как конкурентность — способ структурирования компонентов, позволяющий им выполняться независимо, когда это возможно.
**Типичные ошибки:**
- Путать «async» и «parallel» без уточнения ядер.
- Считать, что goroutines всегда параллельны.

**Подробности:**
- Concurrency — структура программы: много задач, progress через interleaving (на одном или многих ядрах).
- Parallelism — одновременное CPU-исполнение на нескольких ядрах; требует `GOMAXPROCS>1` и независимую работу.
- При `GOMAXPROCS=1` concurrency есть, parallelism на CPU — нет.
- I/O-bound: много G ждут сеть/диск — высокая concurrency при низкой CPU-загрузке.
- CPU-bound: parallelism требует несколько P и достаточно параллельной нагрузки.
- Async (не блокировать caller) ≠ parallel (несколько ядер одновременно).

## defer, panic, recover
**Частота:** 5/56
**Темы:** #go/errors
- [ ] Скорректировано
- [ ] последний повтор
**Что ожидают на собесе:**
**Эталон на собесе:**
`defer` — отложенный вызов при выходе из функции (LIFO).
Аргументы выражения в `defer` считаются в момент **регистрации** `defer`, не при выполнении.
Останавливает обычное исполнение текущей goroutine, **раскручивает стек**, выполняет отложенные `defer` (LIFO), печатает stack trace и завершает процесс — если panic не погашен.
`panic(v)` — `v` любого типа; `recover()` возвращает этот аргумент.
При этом, `recover` ловит panic только в той же goroutine, где `defer recover`.
**Подробности:**
- defer с recover — типичный паттерн в HTTP middleware. Handler без recover — одна паника роняет весь процесс.
- `recover` только в `defer` **той же goroutine**. Panic в одной goroutine не ловится `recover` в другой.
- Не всё recoverable: OOM, concurrent map write, deadlock.
- `recover()` вне deferred func — no-op, возвращает nil.
- Runtime сам вызывает panic: nil pointer deref, index out of range, send on closed channel, failed type assertion без `ok`.
```go
defer func() {
if r := recover(); r != nil {
log.Printf("panic: %v\n%s", r, debug.Stack())
}
}()
```
| | `return error` | `panic` |
| ------------ | ------------------------------------- | ------------------------------- |
| Когда | сеть, файлы, validation, «нет данных» | невозможно продолжать безопасно |
| Стоимость | обычный return | раскрутка стека |
| В библиотеке | основной путь | только документированные случаи |

## Что такое модель GMP и GOMAXPROCS?
**Частота:** 5/56
**Темы:** #go/scheduler
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26
**Что ожидают на собесе:**
**Эталон на собесе:**
GMP
- **G** (goroutine). Содержит стек горутины, состояние выполнения, информацию для планировщика.
- **M** (Machine). Реальный поток ОС. На них запускаются горутины
- **P** (Processor) логический CPU (контекст планировщика). связывает горутины и потоки. У каждого P есть локальная очередь горутин, кэш аллокаций и данные для планировщика
**Подробности:**
- M должен быть привязан к P, чтобы выполнять G; без P M idle или в syscall.
- Local run queue (~256 G): новые G от `go` кладутся в local P текущей G (load spreading).
- Пустая локальная очередь → кража половины горутин у случайного P → global run queue → netpoll.
- `GOMAXPROCS(n)` ограничивает число P (на скольких ядрах будет выполняться код), не число G и не число M (M может быть больше при блокирующих syscall).
- Sysmon — фоновый поток (M): следит за long-running G, retake P, будит netpoller.
- Blocking syscall: G отсоединяется, M может остаться в kernel; P передаётся другому M.
- Netpoller пробуждает G, когда файловый дескриптор готов к read/write.
```
M1 -> syscall (заблокирован)
P1 отвязывается от M1
P1 прикрепляется к M2
другие G продолжают работать
```

## `sync.Map`
**Частота:** 4/56
**Темы:** #go/sync #go/map
- [ ] Скорректировано
- [ ] последний повтор
**Что ожидают на собесе:**
- Когда `sync.Map` вместо `map+mutex`.
- **Решает ли** проблему конкурентного map — да для **Load/Store**; **нет** для мутаций **значений** внутри без отдельного lock.
**Эталон на собесе:**
`sync.Map` — потокобезопасная специализированная map из стандартной библиотеки.
Она работает не как обычная мапа, а через методы
Она нужна не просто «когда есть несколько goroutine», а когда подходит её модель нагрузки.
Официальные хорошие сценарии
- ключ один раз записали и потом много раз читают, например cache, который в основном только растёт
- разные goroutine часто работают с разными, почти независимыми наборами ключей.
В обычном коде часто лучше `map[K]V` + `sync.Mutex`/`sync.RWMutex`: это типобезопаснее и проще для инвариантов.
`sync.Map` не типобезопасна: ключи и значения имеют тип `any`.
**Подробности:**
- Основные методы: `Load`, `Store`, `LoadOrStore`, `LoadAndDelete`, `Delete`, `Range`.
- - `(m *Map) Delete(key any)` — удаляет значение указанного ключа
- - `(m *Map) Load(key any) (value any, ok bool)` — возвращает значение ключа или `nil`, если оно отсутствует. В первом случае `ok` равно `true`, во втором — `false`
- - `(m *Map) LoadOrStore(key, value any) (actual any, loaded bool)` — функция возвращает значение ключа, если оно существует. В противном случае, сохраняется и возвращается значение `value`. Возвращаемый параметр `loaded` равен `true`, если значение существует, и `false`, если оно было добавлено
- - `(m *Map) Range(f func(key, value any) bool)` — перебирает все элементы мапы и для каждого вызывает функцию `f`. Если нужно прекратить перебор, то функция должна возвратить `false`
- - `(m *Map) Store(key, value any)` — присваивает значение ключу.
- В новых версиях Go есть также `Swap`, `CompareAndSwap`, `CompareAndDelete`, `Clear`.
- Под капотом используется read-only часть и dirty-часть под mutex, но это implementation detail.
- Составная операция на нескольких ключах не становится атомарной: нужен внешний mutex, owner goroutine или транзакция на уровне хранилища.
- что для начала работы достаточно создать переменную типа `sync.Map`, вызов `make()` не нужен
Потокобезопасность типа `sync.Map` относится только к обращению с элементами мапы. Если мапа содержит какие-то объекты, например, слайсы, работа непосредственно с этими объектами требует отдельной синхронизации.

## Cooperative vs preemptive scheduling в Go?
**Частота:** 4/56
**Темы:** #go/scheduler

**Что ожидают на собесе:**
**Эталон на собесе:**
кооперативная многозадачность - Горутина сама должна добровольно отдать управление.
вытесняющая многозадачность - Планировщик может принудительно остановить горутину и переключиться на другую.
Современный Go использует GMP-планировщик с поддержкой асинхронного вытеснения, поэтому одна "жадная" горутина обычно не мешает остальным работать.
Runtime вставляет специальные безопасные точки (safe points), где можно выполнить переключение без повреждения состояния программы.
sysmon вытесняет long CPU loops.
**Подробности:**
- До Go 1.14: yield только на blocking ops — channel, mutex, select, syscall, GC safepoint.
- Tight loop без вызовов функций мог indefinitely держать P до 1.14.
- С 1.14+: cooperative **и** preemptive — sysmon + async preemption (signal) на safepoints.
- Safepoint: prologue/epilogue функций, loop back-edges, runtime checks — не «любая инструкция».
- Не OS-style preemption: нет прерывания на каждой инструкции как у pthread.
- `runtime.Gosched()` — добровольная уступка: G попадает в run queue, другая G берёт тот же P.
- С Go 1.21+ preemption улучшен для части паттернов (async preemption без остановки на каждом safepoint).

## Data race и `-race`
**Частота:** 4/56
**Темы:** #go/data-race #go/sync
- [ ] Скорректировано
- [ ] последний повтор
**Что ожидают на собесе:**
**Эталон на собесе:**
Data race возникает, когда несколько goroutines обращаются к одной переменной без синхронизации и хотя бы одно обращение — запись.
При этом, исправляют через mutex, channel владение, atomic или неизменяемый data.
`-race` инструментирует программу и находит реальные гонки на выполненных путях, но не доказывает их отсутствие.
**Подробности:**
- Happens-before задают `Mutex.Unlock` → `Lock`, channel send → receive, `sync.Once`, atomic Load/Store.
- `-race` обычно запускают в CI на тестах и интеграционных сценариях; он замедляет выполнение и увеличивает память.
- Гонка возможна и при `GOMAXPROCS=1`: модель памяти Go требует синхронизацию, а не только отсутствие параллельных ядер.

## Embedding struct
**Частота:** 4/56
**Темы:** #go/methods #go/interfaces
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26
**Что ожидают на собесе:**
**Эталон на собесе:**
ООП в Go строится через композицию и интерфейсы, а не через наследование классов. При этом, embedding встраивает поле и продвигает его методы, но это не subclass: состояние и инварианты всё равно принадлежат конкретной struct. Полиморфизм обычно выражают маленькими интерфейсы.
**Подробности:**
- Embedding продвигает методы вложенного типа, но не создаёт виртуальную таблицу наследования.
- Инкапсуляция в Go задаётся экспортируемыми и неэкспортируемыми именами.
- Интерфейсы реализуются неявно, поэтому зависимость можно держать на стороне потребителя.

## Какие ключи могут быть у мапы?
**Частота:** 4/56
**Темы:** #go/map #go/types
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-26
**Что ожидают на собесе:**
Ключом может быть только сравнимый тип
| Можно | Нельзя |
| ------------------------------------------ | ------------------------------------------------------- |
| числа, `bool`, `string` | **slice** `[]T` |
| указатель, channel, interface | **map**, **func** |
| **array** `[N]T`, если элементы comparable | struct/array с полем slice/map/func |
| struct, если **все** поля comparable | `[]byte` как ключ — только через `string` или `[N]byte` |
Примеры ключей: int, "user:42", [16]byte (UUID), [2]int.
