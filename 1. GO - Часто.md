## Что при записи/чтении из закрытого канала? / Что произойдет с читателями/писателями если закрыть канал?
**Частота:** 25/84
**Темы:** #go/channel

- [x] последний повтор ✅ 2026-07-05
### Писатель
Запись в закрытый канал — **panic**; 
### Читатель
чтение — сначала буфер, потом нулевое значение и `ok=false`. Закрытие не выбрасывает данные
```go
for v := range ch {
fmt.Println(v)
}
```
Цикл автоматически завершится после чтения всех данных из закрытого канала.

Если были заблокированные читатели - После закрытия канала читатель **разблокируется**.


### Повторное закрытие — panic.
`for range ch` завершается после close+вычитывания.

| Состояние                | Запись (`ch <- v`)                                                                                                                  | Чтение (`<-ch`, `v, ok := <-ch`)                                                                             | Закрытие (`close(ch)`)                               |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| **nil**                  | Блокировка навсегда                                                                                                                 | Блокировка навсегда                                                                                          | Паника                                               |
| **Не nil и не закрыт**   | Небуферизованный: без готового получателя — блокировка. Буферизированный: при месте в буфере — без блокировки, иначе блок до чтения | Блокируется до получения значения; в буфере — сразу, если есть данные                                        | Закрывает канал; не влияет на уже находящиеся данные |
| **Закрыт** (`close(ch)`) | **Паника**                                                                                                                          | Возвращает нулевое значение типа канала (например, 0 для `chan int`); `ok = false` при форме `v, ok := <-ch` | **Паника** (повторное закрытие)                      |

Закрытие определяют только при чтении через конструкцию `v, ok := <-ch`, где `ok == false` означает, что канал закрыт и буфер пуст.

## Что такое планировщик / GMP и GOMAXPROCS?
**Частота:** 22/84
**Темы:** #go/scheduler
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-05
Планировщик Go — это компонент Go, отвечающий последовательность выполнения горутин, из которых состоит программа Go

планировщик Go оперирует горутинами только одной программы, он намного проще, дешевле и быстрее, чем планировщик ядра операционной системы.

- **G** (горутина). Содержит стек горутины, состояние выполнения, информацию для планировщика.
- **M** (Machine). Реальный поток ОС. На них запускаются горутины
- **P** (Processor) логический CPU (контекст планировщика). Связывает горутины и потоки. У каждого P есть локальная очередь горутин, кэш аллокаций и данные для планировщика

У каждого процессора есть локальная очередь горутин  (~256 G): новые G от `go` кладутся в локальную очередь процессора текущей G. 

Если у одного процессора задач много, а у другого нет, используется механизм **воровства работы (work stealing)** — свободный процессора забирает часть задач себе.

При блокирующих системных вызовах runtime старается отвязать процессора от заблокированного потока и продолжить выполнение на другом потоке.

Для того чтобы одна горутина не могла бесконечно занимать процессор, используется **вытесняющая многозадачность**.

Вытеснение и работа сборщика мусора выполняются через **безопасные точки (safepoints)** — места, где runtime может безопасно остановить горутину.

- M должен быть привязан к P, чтобы выполнять G; без P M idle или в syscall.

- Пустая локальная очередь → кража половины горутин у случайного P → global run queue → netpoll.
- `GOMAXPROCS(n)` ограничивает число P (на скольких ядрах будет выполняться код), не число G и не число M (M может быть больше при блокирующих syscall).
- Sysmon — фоновый поток (M): следит за long-running G, retake P, будит netpoller.
- Blocking syscall: G отсоединяется, M может остаться в kernel; P передаётся другому M.
- Netpoller пробуждает G, когда файловый дескриптор готов к read/write.
```
M1 -> syscall (заблокирован)
P1 отвязывается от M1
P1 прикрепляется к M2
другие G продолжают работать
```

## Что такое дедлок и рейс кондишион, и `-race`
**Частота:** 18/84
**Темы:** #go/data-race #go/sync #go/deadlock
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-05

**Дедлок** - состояние когда две или несколько горутин пытаются захватить блокировку друг у друга, и не могут продолжить работу.

1 горутина пытается захватить блокировку у второй а
а вторая пытаются захватить блокировку у первой.
И они встают в дедлок и не могут продолжить работу

**Livelock** — горутины формально не ждут lock навсегда, но из‑за взаимных уступок и повторных попыток **нет прогресса** (часто высокий CPU).

В Go: busy-loop с `TryLock` без backoff; бесконечные retry без изменения общего состояния.
Профилактика: backoff/jitter, единый порядок захвата lock (как при deadlock), не крутить spin на примитивах.

**Race condition** — ситуация, когда несколько горутин одновременно работают с общими данными, и результат зависит от порядка выполнения.
Результат непредсказуем
два потока увеличивают счетчик без синхронизации

| | Deadlock | Livelock |
|---|----------|----------|
| Состояние | заблокированы, ждут ресурс | «активны», но не продвигаются |
| CPU | обычно низкий | часто высокий |
| Пример | A ждёт lock B, B ждёт lock A | оба постоянно `TryLock` / `Gosched` и снова retry |

**Профилактика**: мьютексы, каналы, атомики, 
единый порядок lock, backoff; 
гонки —`-race `, mutex/atomic.

`-race ` инструментирует программу и находит реальные гонки на выполненных путях, но не доказывает их отсутствие. обычно запускают в CI на тестах и интеграционных сценариях; он замедляет выполнение и увеличивает память.

Гонка возможна и при `GOMAXPROCS=1`: модель памяти Go требует синхронизацию, а не только отсутствие параллельных ядер.

## Как устроен слайс?
**Частота:** 17/84
**Темы:** #go/slice
- [x] Скорректировано ✅ 2026-06-28
- [x] последний повтор ✅ 2026-07-02

Слайс — **структура-заголовок** (SliceHeader): 
указатель на первый элемент базового массива
len (сколько элементов видно)
**cap** (сколько элементов помещается в текущий базовый массив без перевыделения).
`cap ≥ len` всегда.

Не потокобезопасен. Параллельный `append` к одному слайсу без синхронизации — **гонка** (и на slice header, и на backing array). 

Передача slice в функцию копирует заголовок, базовый массив общий но не элементы — мутации существующих элементов видны снаружи.

copy(dst, src) копирует min(len(dst), len(src)) элементов, не cap.

**Nil vs пустой:**`var s []int`— nil (`len=0`,`cap=0`);
`s := []int{}`или` make([]int, 0) `— non-nil, тоже `len=0`. 
Оба принимают `append`.

Адрес слайса (&slice) — это адрес структуры с метаданными (SliceHeader)

**Синтаксис среза:**`s[low:high]`—`[low, high) `; опущенный low = 0, high = len. Full slice:`s[low:high:max]`— cap нового представление =`max - low`.
```go
var nilSlice []int // nil
nonNil := make([]int, 0) // [] non-nil
s := make([]int, 3, 10)
t := []int{1, 2, 3}
```
### Строка и `[]byte`
- Строка **неизменяемая**, UTF-8;`s[i]`— **байт**, не символ.
- `for range` по строке — **руны**.
- Изменить текст:`[]rune `,`strings.Builder` или `[]byte `+ копия.

## `atomic` vs mutex
**Частота:** 15/84
**Темы:** #go/atomic #go/sync
- [x] Скорректировано ✅ 2026-06-27
- [x] последний повтор ✅ 2026-06-30

**`atomic.AddInt64(&v, 1)`** — одна атомарная RMW-операция без захвата mutex; 
подходит для счётчиков, флагов, указателей в lock-free структурах.

**Mutex** — защищает **несколько полей** и составные инварианты (map + len + cache).

| | atomic | mutex |
|---|--------|-------|
| Сценарий | один счётчик, CAS | map, slice, несколько полей |
| Скорость | быстрее mutex на hot counter | дороже, но универсальнее |
| Ограничение | только поддерживаемые типы | любые данные |

Когда счётчик/флаг — **`atomic`**, когда сложный инвариант — **mutex**.

Atomic **быстрее mutex** для простого счётчика, но **медленнее** обычной локальной переменной.

**Подробности:**
- **Lock-free** (неформально): операция завершается за конечное число шагов без внешнего lock; `sync/atomic` — примитивы, не «готовый lock-free контейнер» из коробки.

## context - что такое, как устроен и зачем использовать?
**Частота:** 15/84
**Темы:** #go/context
- [x] Скорректировано ✅ 2026-06-26
- [x] последний повтор ✅ 2026-06-29

В основном нужен для отмены, чтобы завершить горутины. Но так же можно передавать какие-то данные.

это инструмент управления временем жизни операции и через него передаются сигналы.
Используется при graceful shutdown - отлавливаем системные сигналы, контекст закрываем.
А во всех горутинах слушаем закрытие контекста и это позволяет нам отреагировать и корректно завершить все процессы

Дерево контекстов:`Background`/`TODO`→`WithCancel`/`WithTimeout`/`WithDeadline`/`WithValue`.
Отмена родителя отменяет детей.
`Done()`— канал закрытия;
`Err()`— причина.

Разные виды контекстов.
В них можно содержать сессионные данные, и метаданные.
нежелательно использовать для бизнес данных.
- бекграунд - корневой
-`WithCancel()`— дочерний контекст можно отменить вызовом специальной функции; Тип `CancelFunc` определяет функцию без параметров и возвращаемых значений. Такой тип контекста используется, когда необходима отмена действий по какому-то сигналу.
-`WithTimeout()`— дочерний контекст отменяется после указанного периода времени
-`WithDeadline()`— дочерний контекст отменяется в определённое время
-`WithValue()`— дочерний контекст не отменяется, но содержит пару «ключ-значение».
в context done приходит значение
Например если горутина зависает и контекст имеет таймаут
и слушаем контекст дан и когда таймаут наступает - завершаем
Первый аргумент —`ctx context.Context`. Пробрасывать cancel по дереву вызовов.


**Подробности:**
-`ctx.Done` нужно слушать в долгом I/O и worker loops.
- Значения в context — только на время запроса metadata: трассировка id, auth claims.
- Cancel/deadline распространяются вниз по дереву вызовов.
- Тип `Context`— интерфейсный, но обычно не требует определять свою структуру и соответствующие методы
- Для создания пустого контекста можно использовать две функции:`context.Background()` и `context.TODO()`. Обе они возвращают пустой контекст, который не может быть отменён и не содержит никаких свойств. Это, так называемый, **корневой**, или родительский контекст самого верхнего уровня. Он необходим для создания дочерних контекстов с условием.
- Дочерние контексты создаются навешиванием новых условий на родительский контекст.
- Вызывайте функцию `cancel()`, чтобы избежать утечек памяти. Для этого лучше использовать `defer cancel()`. В противном случае сборщик мусора не удалит созданный контекст
- Кроме прослушивания канала `ctx.Done()` есть ещё один способ узнать об отмене контекста — вызвать метод `Err()`, который возвратит ошибку, если контекст отменён. При этом возможны следующие значения ошибки
-`context.Canceled`— контекст отменён вызовом функции ` cancel()`
-`context.DeadlineExceeded`— контекст отменён по истечению времени

## Рост capacity слайса / Как работает append?
**Частота:** 12/84
**Темы:** #go/slice
- [x] Скорректировано ✅ 2026-06-28
- [x] последний повтор ✅ 2026-07-03

При превышении cap — выделяется новый массив, происходит копирование элементов, новый указатель записывается в заголовок слайса.

Рост cap
- Append без превышения cap — тот же базовый массив.
- до 256 элементов ~×2
- далее плавный переход к ~×1.25 через хитрые формулы с выравниваниями.

Runtime `nextslicecap`(Go 1.18+)
 `oldCap < 256`— **×2**
`oldCap ≥ 256`— плавный рост к **~×1.25** (`newcap += (newcap + 3×256) / 4`)
`newLen > 2×oldCap`—` newcap = newLen`
cap округляется до **size class** аллокатора — реальный cap может быть чуть больше формулы. Выравнивание памяти с округлением до 1 байта вверх, если размер элемента меньше 8 бит

**Сложность:** один `append`— O(1)
при создании нового базового массива О(n)
серия append по одному — O(1) амортизированно.

**Append в func** до realloc меняются **элементы** в общем базовый массив, **`len` caller** — нет; после realloc новый ptr только внутри func.

## Чем слайс отличается от массива? / Чем хорош массив по сравнению со слайсом?
**Частота:** 13/84
**Темы:** #go/slice #go/array #go/types
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-03

Массив - это структура с фиксированной длиной, размер - часть типа. Определяется в момент компиляции. 
А слайс это надстройка над массивом которая позволяет иметь динамическую длину. 
Слайс не хранит данные сам, а является ссылкой на часть базового массива = ссылка+метаданные.

Массив обычно сравнимый, если элементы сравнимые, слайс не сравнимый.

Массив после объявления заполняется нулевыми значениями, а слайс nil - нужно мейкать.
Массив в функцию обычно копируется целиком - мутации снаружи не видны, а у слайса копируется только заголовок - мутации существующих элементов в общем базовом массиве видны.

Массив хорош тем, что имеет фиксированный размер, хранит данные непосредственно в себе, не перевыделяет память и не разделяет данные при копировании.**

 **В прикладном коде преимущества массива редко перевешивают удобство слайсов. Поэтому почти все API стандартной библиотеки работают именно со слайсами. Массивы используют в основном тогда, когда размер фиксирован и известен заранее (например, `[16]byte` для UUID или `[32]byte` для SHA-256).**

Канал - примитив синхронизации который предназначен для обмена данными между горутинами. либо сообщать горутине что нужно завершить работу
- Потокобезопасный за счет мьютекса внутри, 
- Ссылочный тип. Когда передаете канал в функции, на самом деле передается указатель на канал.
- **какие бывают** есть деление по направлению - на каналы только для чтения или только для записи, делаются через приведение типа.
- Каждое записанное в канал значение может быть считано только один раз, обработка в порядке ФИФО. 
- Хранится в куче.

Структура ` hchan`
- mutex
- размера буфера
- указателя на буфер
- **кол-ва элементов буфера**
- **кольцевой буфер до ёмкости**
- **очередь читающих горутин**
- **очередь пишущих горутин**
- флаг closed.

Есть буферизированный и небуферизированный.
**Небуферизированный канал — синхронный: отправитель встречается с получателем напрямую, иначе одна из сторон блокируется.**  
Данные передаются из стека одной горутины в стек другой горутины. 
Работают по аналогии с эстафетной палочкой: нельзя отправить, пока некому прочитать.
- Создание без ёмкости
```go
ch := make(chan [тип данных])
```
- Ёмкость и длина равны 0.

**Буферизированный - канал у которого есть определенный буфер,** 
**не блокирует запись, пока len < cap.** 
**чтение не блокируется, пока в буфере есть данные.** 
После заполнения буфера запись начинает блокироваться, а после его опустошения — чтение.

Буфер это кольцевая очередь. По аналогии с почтовым ящиком: пока есть место в ящике, отправитель может положить значение и уйти.
- Создание с ёмкостью
```go
ch := make(chan [тип данных], 1)
```
- Ёмкость фиксирована (проверяется через `cap()`), текущее количество элементов — через `len()`.
- Буферизация влияет только на поведение блокировки.
- буферизированный с буфером 1 != небуферизированному
- Читатель может будить заблокированного писателя, а писатель может будить читателя

## Stack vs heap — зачем и производительность? / утечка памяти
**Частота:** 10/84
**Темы:** #go/memory
- [x] Скорректировано ✅ 2026-07-03
- [x] последний повтор ✅ 2026-07-03

**Эталон на собесе:**
- **Стек** — LIFO кадр функции, рост/освобождение за O(1), быстрый, но **ограничен по размеру** (растёт при необходимости, но не бесконечен).
- **Куча** — когда escape analysis не может доказать, что значение не «убежит» из scope: указатель наружу, return slice/map, замыкание, interface, большой объект.
- На куче аллокации дороже: GC, heap allocator; на практике **профилировать**, не гадать (`go build -gcflags=-m` для escape). - компилятор проверяет, «убегает» ли значение из scope на heap.
- Идея Go: всё, что может жить на стеке, компилятор оставляет на стеке; остальное — на куче автоматически.

**Утечка памяти** — объекты на куче достижимы, но не нужны (горутина leak, global cache). 
Глубокая **рекурсия** → stack overflow. 
Бесконечный **append** без освобождения → OOM. 
Большая struct по значению vs указатель — копирование vs один объект на heap (escape analysis).

## Способы синхронизации горутин / Какие примитивы синхронизации / как горутины общаются
**Частота:** 10/84
**Темы:** #go/sync #go/channel #go/scheduler 
- [x] Скорректировано ✅ 2026-07-03
- [x] последний повтор ✅ 2026-06-29

В Go основные примитивы синхронизации находятся в пакетах `sync` и `sync/atomic`, также для синхронизации широко используются каналы.

- **`sync.Mutex`** — взаимоисключение. Гарантирует, что только одна горутина одновременно работает с критической секцией. **защита общего состояния.**
- **`sync.RWMutex`** — разделяет доступ на множество читателей или одного писателя. **когда чтений значительно больше, чем записей.**
- **`sync.WaitGroup`** — позволяет дождаться завершения группы горутин.
- **`sync.Once`** — гарантирует, что функция будет выполнена только один раз. **ленивая инициализация.**
- **`sync.Cond`** — позволяет горутинам ждать наступления определенного условия и пробуждать одну (`Signal`) или все (`Broadcast`) ожидающие.  ожидание изменения общего состояния.
- **`sync.Map`** — потокобезопасная реализация map для некоторых сценариев конкурентного доступа.
- **Каналы (`chan`)** — используются для синхронизации и обмена данными между горутинами.
- **Пакет `sync/atomic`** — простые атомарные операции над отдельными переменными, когда mutex избыточен.

Указатель - переменная которая хранит адрес другой переменной
на 64 занимает 8 байт, на 32 битных - 4 байта.

мы с переменными можем работать через их адрес
При работе с указателями, если вы хотите получить значение указателя, необходимо использовать операцию `*`, которая называется разыменованием указателя, и оператор &, чтобы получить адрес памяти переменной.


Тип `*T `хранит адрес значения типа` T `.
`&x `— взять адрес,
`*p `— разыменовать. 
Нулевой указатель `nil`— нет объекта.

Есть две основные причины использовать указатели в ваших программах: 
- указатели позволяют обмениваться данными по ссылке, а не по значению, особенно между функциями Go; 
- указатели бывают чрезвычайно полезны, если вы хотите отличить нулевое значение от неприсвоенного.


Указатель — адрес значения; передача по значению копирует struct. 
Указатель нужен для мутации снаружи, больших struct, optional (`nil`). 

В Go нет C-ссылок; «по ссылке» для параметров — только pointer.

## `sync.Map`
**Частота:** 8/84
**Темы:** #go/sync #go/map
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

`sync.Map`— потокобезопасная специализированная map из стандартной библиотеки.
Она работает не как обычная мапа, а через методы

Официальные хорошие сценарии
- ключ один раз записали и потом много раз читают, например cache, который в основном только растёт
- разные горутина часто работают с разными, почти независимыми наборами ключей.
В обычном коде часто лучше `map[K]V`+`sync.Mutex`/`sync.RWMutex`: это типобезопаснее и проще для инвариантов.
`sync.Map` не типобезопасна: ключи и значения имеют тип `any`.

**Подробности:**
- Основные методы:`Load`,`Store`,`LoadOrStore`,`LoadAndDelete`,`Delete`,`Range`.
- -`(m *Map) Delete(key any) `— удаляет значение указанного ключа
- -`(m *Map) Load(key any) (value any, ok bool) `— возвращает значение ключа или `nil`, если оно отсутствует. В первом случае `ok` равно `true`, во втором —` false`
- -`(m *Map) LoadOrStore(key, value any) (actual any, loaded bool) `— функция возвращает значение ключа, если оно существует. В противном случае, сохраняется и возвращается значение `value`. Возвращаемый параметр `loaded` равен `true`, если значение существует, и `false`, если оно было добавлено
- -`(m *Map) Range(f func(key, value any) bool) `— перебирает все элементы мапы и для каждого вызывает функцию `f`. Если нужно прекратить перебор, то функция должна возвратить ` false`
- -`(m *Map) Store(key, value any) `— присваивает значение ключу.
- В новых версиях Go есть также `Swap`,`CompareAndSwap`,`CompareAndDelete`,`Clear`.
- Под капотом используется read-only часть и dirty-часть под mutex, но это implementation detail.
- Составная операция на нескольких ключах не становится атомарной: нужен внешний mutex, владелец горутина или транзакция на уровне хранилища.
- что для начала работы достаточно создать переменную типа `sync.Map`, вызов `make()` не нужен
Потокобезопасность типа `sync.Map` относится только к обращению с элементами мапы. Если мапа содержит какие-то объекты, например, слайсы, работа непосредственно с этими объектами требует отдельной синхронизации.

## Для чего используется интерфейс? / что такое / как устроен интерфейс?

Интерфейс описывает **поведение**, не структуру данных. Набор методов. 
Тип реализует интерфейс неявно, если его набор методов содержит все методы интерфейса 

Абстракция поведения, 
dependency injection, 
тестируемость (моки), 
полиморфизм без наследования. 

Идиома: **принимай интерфейсы, возвращай конкретные типы**; маленькие интерфейсы

Значение interface хранит динамический тип и данные.

Указательный и value receiver влияют на то, какие методы попадают в set.

`any`— алиас ` interface{}` без методов.

Интерфейс хранить в пакете **потребителя**. Маленький iface (1–2 метода) при необходимости **скопировать** в consumer-пакет дешевле лишней зависимости (`io.Reader` pattern).
