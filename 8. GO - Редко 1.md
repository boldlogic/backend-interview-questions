## Какие ключевые особенности Golang / недостатки
**Частота:** 9/86
**Темы:** #go/general
- [x] Скорректировано ✅ 2026-06-26
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Go — компилируемый, статически типизированный язык со сборщиком мусора. Ключевые особенности:

- **Простота:** минималистичный синтаксис, низкий порог входа, код читается одинаково у разных разработчиков.
- **Конкурентность:** goroutines (легковесные, ~2 КБ стека) + каналы для коммуникации. Модель CSP — «не разделяй память, общайся».
- **Компиляция:** быстрая, кроссплатформенная, в один нативный бинарник без внешних зависимостей. Статические ошибки на этапе компиляции.
- **Композиция вместо наследования:** embedding структур, неявная реализация интерфейсов (satisfies implicitly) — нет классов и иерархий.
- **Производительность:** близко к C, GC с низкими паузами — Green Tea GC (1.26, по умолчанию) снижает overhead на 10–40%.

**Недостатки:**
- Многословная обработка ошибок: `if err != nil` после каждого вызова, нет try/catch, ошибки легко пропустить.
- Ограниченная stdlib: нет тернарного оператора, нет map/filter/reduce, нет enum (iota — компромисс).
- GC — паузы есть (хоть и низкие), latency-sensitive приложения могут страдать.
- Нет классического ООП: нет наследования, нет перегрузки методов, нет классов.
- До 1.18 не было дженериков — legacy-код без них; текущие дженерики ограничены (нет method generics, нет операторного overloading).

**Подробности:**
- **Неявные интерфейсы** — ключевое отличие от Java/C#: тип реализует интерфейс самим фактом наличия методов, без `implements`. Позволяет писать мок-реализации и оборачивать чужие типы без изменения их кода.
- **Goroutines vs потоки ОС:** горутина стартует с ~2 КБ стека (растёт динамически), поток ОС — ~1 МБ фиксированно. Go runtime мультиплексирует M горутин на N потоков ОС (модель GMP). Каналы — типобезопасная альтернатива shared memory + мьютексам.
- **Компиляция в бинарник:** нет JVM/CLR, нет холодного старта JIT. Для контейнеров — образ FROM scratch с одним бинарником. Кросскомпиляция: `GOOS=linux GOARCH=arm64 go build`.
- **Обработка ошибок:** Go 1.13+ — `%w` для wrapping, `errors.Is`/`errors.As` для unwrapping, `errors.Join` (1.20) для нескольких ошибок, `errors.AsType` (1.26) — типобезопасный дженерик-вариант `As`. Базовая модель (возврат error последним значением) — по-прежнему многословна.
- **iota:** генерирует последовательные целые в `const`-блоке. Не полноценный enum — нет типобезопасности (iota — это просто int), нет итерации по значениям, нет строкового представления.

## Что такое context switching и как горутины решают эту проблему
**Частота:** 7/86
**Темы:** #go/scheduler #go/goroutine
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Context switch — сохранение состояния текущего потока (регистры, stack pointer, program counter) и загрузка состояния следующего. Для потоков ОС это **дорого**: переход в kernel mode, сохранение/восстановление всех регистров, смена page tables, сброс TLB. ~1–10 мкс на операцию.

Горутины решают проблему тем, что переключение происходит **в user-space**, без участия ядра ОС:
- Сохраняется только ~3 регистра (SP, PC, G-указатель), а не полный набор.
- Стек горутины — ~2 КБ (растёт динамически) против ~1 МБ фиксированного у потока ОС. Меньше памяти для сохранения/восстановления.
- Планировщик Go (GMP) переключает горутины на одном потоке ОС — поток продолжает работать, не тратя время на kernel transition.
- Результат: переключение горутины ~десятки наносекунд, на 2–3 порядка быстрее thread switch.

**Подробности:**
- Thread switch требует: syscall → kernel stack → save regs → pick next thread → restore regs → iret. При смене процесса — ещё смена адресного пространства (CR3, сброс TLB).
- Goroutine switch: `gopark` (сохранить SP/PC в G) → выбрать следующую G из runq → `goready` (загрузить SP/PC из G). Всё в user-space, ни одного syscall.
- Переключение происходит в кооперативных точках (вызов функции, канал, syscall) или принудительно через preemption (sysmon, >10 мс на P с Go 1.14+).
- **CPU-bound:** горутины сверх числа ядер дают только оверхед на переключение — параллелизм ограничен железом. **I/O-bound:** тысячи горутин сверх ядер — норма, потому что заблокированные (канал, сеть, диск) горутины не потребляют CPU и не участвуют в переключении.

## Как горутина понимает что пора проснуться
**Частота:** 6/86
**Темы:** #go/scheduler #go/channel
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Горутина блокируется через `gopark` — runtime снимает её с P, переводит в состояние **waiting** и помещает в очередь ожидания. Пробуждение — парная операция переводит горутину обратно в **runnable** (`goready`) и ставит в run-очередь P. Основные механизмы пробуждения:

- **Каналы:** горутина-читатель попадает в `recvq` (очередь получателей), писатель — в `sendq` (очередь отправителей). При появлении парной операции: для небуферизованного — прямая передача значения со стека на стек, для буферизованного — копирование через буфер, затем горутина будится.
- **Сетевой ввод/вывод:** не блокирует поток ОС — горутина регистрируется в **netpoller** (epoll/kqueue), поток возвращается к другим горутинам. Когда сокет готов, netpoller будит горутину.
- **sysmon** — фоновый системный поток: обнаруживает горутины, работающие >10 мс, и вытесняет их. Также проверяет netpoller и таймеры.
- **Таймеры:** горутина, ожидающая `time.Sleep` / `time.After`, помещается в кучу таймеров; sysmon или dedicated timer-поток будят по истечении.

**Подробности:**
- **Канал — пошагово:** читатель вызывает `<-ch` на пустом канале → создаётся `sudog` (структура с указателем на горутину + буфер для значения) → `sudog` помещается в `recvq` → `gopark` переводит G в waiting. Когда писатель делает `ch <- v`: копирует значение в `sudog.elem` (или напрямую на стек читателя для небуферизованного), удаляет `sudog` из `recvq`, вызывает `goready` → G в runnable → ставится в локальную runq P.
- **Netpoll:** Go runtime интегрирован с epoll (Linux) / kqueue (macOS) / IOCP (Windows). Сетевые вызовы (`net.Conn.Read`) не блокируют OS-поток — файловый дескриптор регистрируется в epoll, горутина паркуется, поток ОС освобождается. Когда данные приходят, netpoller будит связанную горутину. Дисковый I/O, напротив, блокирует поток — runtime может создать дополнительный M.
- **sysmon:** работает без привязки к P, просыпается каждые ~20 мкс. Задачи: вытеснение долго-работающих горутин (>10 мс на P), проверка netpoller (нет ли готовых сетевых горутин), проверка таймеров, освобождение простаивающих потоков ОС.

## Сборщик мусора: что, зачем, как работает, отключение
**Частота:** 6/86
**Темы:** #go/gc
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

Garbage Collection - это процесс освобождения места в памяти, которое больше не используется.

GC освобождает **недостижимый** heap даже если память «ещё используется» другими объектами — циклы без ссылок снаружи тоже собираются. Tri-color, concurrent.`GOGC`,`GOMEMLIMIT`; полное off —`GOGC=off`(редко, риск OOM). Упростить жизнь GC: меньше аллокаций,`sync.Pool`, избегать лишних указателей.

- фase mark обходит граф от roots (stack, globals, registers).
- Concurrent GC снижает STW, но write barrier добавляет overhead на указатель writes.
- GOGC влияет на частоту циклов

GC выполняется конкурентно, одновременно с потоками мутатора, в точном соответствии с типом (этот принцип также известен как чувствительность к типу), допускается параллельная выполнение нескольких потоков GC. Это конкурентная пометка и очистка (mark-sweep), при которой используется барьер записи (write barrier). При этом в процессе ничего не генерируется и не сжимается. Освобождение памяти выполняется на основе размера, выделенного для каждой программы Р, чтобы в общем случае минимизировать фрагментацию и избежать блокировок.

В основе работы GC Go лежит "трехцветный алгоритм". Использует барьер памяти. Главный принцип алгоритма трехцветной пометки и очистки состоит в разделении объектов, находящихся куче, на три набора, в соответствии с "цветом".  Условно разделяются на 3 цвета:
- черные объекты - гарантированно не имеют указателей на белые объекты;
- серые объекты - могут иметь указатели на белые объекты;
- белые объекты - на них могут ссылаться некоторые серые объекты и сами некоторые белые объекты могут ссылаться на некоторые черные.
Краткий алгоритм:
1. Все объекты сначала белые;
2. Идет перебор "корневых" объектов, помечаются как серые. Корневые - это объекты к которым можно обращаться напрямую, например глобальные переменные, элементы в стеке и т.д.
3. Идет перебор серых объектов, проверяются ссылки на другие объекты и помечаются на черные объекты. Если есть ссылка на белый объект, то белый становится серым.
4. Продолжается до тех пор, пока не будут перебраны все серые объекты.
5. Оставшиеся после перебора белые объекты считаются недостижимыми и занимаемая ими область памяти может быть освобождена.
Есть еще Мутатор - это приложение, работающее во время сборки мусора. Вызывает функцию барьера записи. Выполняется каждый раз, когда меняется указатель в куче. После изменения указателя объект считается достижимым и помечается как серый.

Настройка GOGC задаёт целевой рост heap относительно live objects после GC (100 = heap ~2× live). Выше GOGC — реже GC, больше память; ниже — чаще GC, меньше RSS. Настраивают через env GODEBUG/gogc или runtime debug.SetGCPercent.

- по умолчанию GOGC=100.
- GOMEMLIMIT (Go 1.19+) — soft limit памяти, взаимодействует с GC pacing.
- Смотреть GODEBUG=gctrace=1 для диагностики пауз.

## Мапа потокобезопасная? / конкурентность и типичные сценарии / почему нельзя
**Частота:** 5/86
**Темы:** #go/map #go/data-race
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

Обычная `map`**не потокобезопасна**. **Read-only** из нескольких горутин допустим, если **никто не пишет**. Если **хотя бы одна** горутина пишет — нужен **Mutex** / одна горутина - владелец /`sync.Map`.

| Сценарий                              | Можно?                                                  |
| ------------------------------------- | ------------------------------------------------------- |
| Несколько goroutine **только читают** | да                                                      |
| Хотя бы одна **пишет**                | **нет** — data race / `fatal error: concurrent map ...` |
| Read + write одновременно             | **нет**                                                 |
`concurrent map writes` и `concurrent map read and map write` приводят к fatal error runtime.`recover` от этого не спасает потому что мапа может быть испорчена

-`go test -race` ловит гонки до production.

Почему:  Запись — не атомарная операция: рантайм считает хеш, ищет место, меняет служебные структуры, иногда запускает рост или перенос данных. Проблема в том, что одна горутина может менять структуру таблицы, а другая одновременно читать или писать по устаревшему состоянию.

В реализации есть внутренние флаги/проверки, которые помогают runtime обнаруживать часть таких ошибок, но это не замена race detector.

## Чем конкурентность отличается от параллелизма?
**Частота:** 6/86
**Темы:** #go/concurrency #go/scheduler
- [x] Скорректировано ✅ 2026-06-22
- [x] последний повтор ✅ 2026-07-03

Конкурентность — много задач конкурируют за один общий ресурс. Прогресс за счёт чередования (на одном или нескольких ядрах).

Параллелизм — много задач выполняются на многих ресурсах. Одновременное исполнение на CPU на нескольких ядрах; требует `GOMAXPROCS > 1` и независимую работу.

Будет или нет конкурентный код выполняться параллельно зависит от железа (несколько ядер). На одном ядре возможна конкурентность без параллелизма.

- При `GOMAXPROCS = 1` конкурентность есть, параллелизма на CPU — нет.
- I/O-нагрузка: много G ждут сеть/диск — высокая конкурентность при низкой загрузке CPU.
- CPU-нагрузка: параллелизм требует несколько P и достаточно независимых задач.
- Асинхронность (не блокировать вызывающий код) ≠ параллелизм (несколько ядер одновременно).

## Что делает runtime Go при нехватке памяти?
**Частота:** 5/86
**Темы:** #go/gc #go/runtime
- [x] Скорректировано ✅ 2026-06-27
- [x] последний повтор ✅ 2026-07-08

При давлении на память runtime принудительно запускает GC. Если после GC выделить память всё равно не удаётся — `fatal error: runtime: out of memory`, процесс падает. Go не подменяет swap/OOM killer ОС.

**Подробности:**
- `GOMEMLIMIT` (Go 1.19+, `debug.SetMemoryLimit`) — soft limit: runtime учащает GC, а при быстрых аллокациях троттлит аллоцирующую горутину. Target heap = `min(GOGC-расчёт, GOMEMLIMIT)`.
- Go 1.26: **Green Tea GC** по умолчанию — новый GC (10–40% меньше overhead), улучшает локальность и CPU scalability при scanning'е мелких объектов, использует векторные инструкции на новых amd64.

## Generics vs interfaces?
**Частота:** 4/86
**Темы:** #go/generics #go/interfaces
- [x] Скорректировано ✅ 2026-06-29
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Интерфейсы — runtime-полиморфизм: описывают поведение через method set, позволяют подменять реализацию (`io.Reader`). Generics — compile-time-полиморфизм: type parameters + constraints, позволяют писать типобезопасные контейнеры и алгоритмы без boxing в `any`.

Ключевое отличие: интерфейсы решают «что объект умеет делать» (поведение), дженерики — «с какими типами он работает» (типобезопасная универсальность).

Пример: `Sort[T any]` — нужен дженерик, чтобы слайс остался `[]int`, а не `[]any` с приведением типов. `io.Reader` — нужен интерфейс, чтобы подменять файл на сокет без изменения кода.

**Когда что использовать:**
- **Generics:** контейнеры (стек, кеш, tree), алгоритмы над типами (sort, filter), type-safe API без `any` и reflection.
- **Interfaces:** подмена реализации (БД/mock, файл/сеть), dependency inversion, несколько типов с общим поведением.

**Подробности:**
- Компилятор мономорфизирует generics (stenciling/GC-shape) — нет боксинга, нет виртуального вызова. Интерфейсы — itable + allocation на heap для non-pointer типов.
- `any` (бывший `interface{}`) + type switch — не замена дженерикам: теряется типобезопасность, паника при неверном cast, аллокации.
- Generics в Go 1.18+ — ограничены: нет method generics (нельзя `func (s Stack[V])` где V — type param), нет операторного overloading, constraint только через interface.

## Передача и возврат: значение vs указатель? / Value vs pointer receiver
**Частота:** 4/86
**Темы:** #go/pointers #go/memory #go/performance #go/methods

- [x] Скорректировано ✅ 2026-06-27
- [x] последний повтор ✅ 2026-06-27

**Передача в функцию:**
**По значению** — копия аргумента. Дешево для `int`,`pointer`, маленьких struct (до ~few cache lines). Функция не может изменить оригинал (кроме полей-указателей внутри struct).

**По указателю** — общий объект: нужна **мутация**, struct **большой**, или тип **нельзя** копировать (`sync.Mutex`).

Go разрешает вызывать `*T `-метод на value и наоборот (авто `&`/ разыменование), но семантика копирования остаётся.

**Возврат из функции:**
- **По значению** — компилятор часто кладёт на stack или регистры; для маленьких struct это снижает аллокации на кучу и нагрузку на GC.
- **По указателю** — когда возвращаем большой объект, shared state, или явно «optional» через `nil`.
Escape analysis решает stack vs heap — не угадывать, а смотреть ` go build -gcflags="-m"`.

## errors.Is / errors.As / %w?
**Частота:** 3/86
**Темы:** #go/errors
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-30

`%w `в` fmt.Errorf ` сохраняет цепочку ошибок для unwrap.
`errors.Is` проверяет, есть ли в цепочке конкретная sentinel error, 
а `errors.As` достаёт ошибку нужного типа. Это позволяет добавлять контекст к ошибке и не ломать машинную проверку причины.

-`errors.Is(err, target)` проходит по цепочке `Unwrap` и учитывает пользовательский метод `Is`.
-`errors.As(err, &target)` требует указатель на переменную нужного типа и достаёт типизированную ошибку.

sentinel-ошибки удобны для стабильных причин; типизированные ошибки нужны, когда вызывающему коду важны поля.

**Подробности:**
- `net.Error`: `Timeout()` / `Temporary()` (deprecated в новых версиях) — **recoverable** vs fatal; в современном Go — typed errors + `errors.Is`/`As`, wrapping через `%w`.

## Memory arenas (runtime после syscall)
**Частота:** 4/86
**Темы:** #go/memory #go/gc
- [ ] Скорректировано
- [ ] последний повтор

**Эталон на собесе:**
Memory arena — единица управления heap в Go runtime: регион виртуальной памяти ~64 МБ (на 64-бит), получаемый от ОС через `mmap`/`VirtualAlloc`. Внутри arena: spans → pages → bitmap для GC. Когда heap исчерпывает свободные страницы, runtime делает сисколл для выделения нового arena-региона. Не путать с экспериментальным пакетом `arena` (Go 1.20, удалён).

**Подробности:**
- **Структура `heapArena`:** каждая arena содержит `bitmap` (разметка указателей для GC), `spans` (привязка страниц к mspan), `pageInUse`/`pageMarks` (учёт аллокаций и mark). Разрешённая адресация через `mheap_.arenas` даёт O(1)-доступ к метаданным любой страницы.
- **Сисколл:** при нехватке свободных страниц runtime вызывает `sysAlloc` → `mmap` (Linux) или `VirtualAlloc` (Windows) для нового arena-региона. Сами arenas и есть результат сисколла.
- **Аллокатор внутри arena:** `mcache` (per-P, без блокировок) → `mcentral` (per-size-class, лёгкий lock) → `mheap.pageAlloc` (глобальный). Для объектов <32 КБ; крупные — напрямую через mheap.
- **Go 1.26:** рандомизация базового адреса arenas при старте (защита от предсказания адресов при cgo-уязвимостях). WebAssembly: уменьшенный размер arena-чанков для low-memory окружений.
- **Не `arena`-пакет:** в Go 1.20 был эксперимент `GOEXPERIMENT=arena` — user-facing API для ручного управления памятью (аллокация вне GC, освобождение разом). Удалён в последующих версиях. Runtime arenas — внутренний механизм, пользователь с ними напрямую не работает.

## Атомарные операции
**Частота:** 3/86
**Темы:** #go/atomic
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27
- **Атомарная операция** — это операция, которая выполняется за один шаг относительно других горутин. Горутина не может прервать своё выполнение во время такой операции, а кроме этого, другие горутины не могут начать эту же самую операцию. Это похоже на транзакции из темы про базы данных, только у атомарной операции не может быть отката.
- sync/atomic - атомарные операции для целочисленных типов:`int32`,`int64`,`uint32`,` uint64`
- Во всех функциях передаются указатели на числовые значения в которых необходима атомарность
- atomic.AddInt64(&addr, 1) // прибавляем 1
- В пакете `sync/atomic` определены типы-обёртки:`atomic.Bool`,`atomic.Int32`,`atomic.Int64` и так далее. Для начала работы с такими «обёртками» достаточно описать переменную нужного типа, например,`var i atomic.Int64`. Эти типы вместо функций имеют соответствующие методы.

## Когда interface == nil / `any` / struct{}
**Частота:** 3/86
**Темы:** #go/interfaces #go/errors
- [ ] Скорректировано
- [ ] последний повтор

Interface равен nil только когда и динамический тип, и данные nil. 
Если в interface лежит типизированный nil указатель, сам interface уже не nil, потому type-компонента заполнена. Это часто ломает `if err != nil`, когда возвращают `(*MyError)(nil) `как` error `.
**Подробности:**
- Модель: interface значение =`(type, data) `.
-`var e *MyErr = nil; var err error = e` даёт `err != nil`.
- Проверять нужно место возврата: возвращать `nil`, а не типизированный nil.
**Эталон на собесе:**
` interface{}`/`any`— любой тип (нет методов в method set). 
Пустая ` struct{}`— тип нулевого размера, часто значение в set-map.
`any` хранит (type, value);
`struct{}`— конкретный тип, не «всё подряд».

## Можем ли взять указатель на элемент мапы
**Частота:** 3/86
**Темы:** #go/map #go/pointers
- [x] Скорректировано ✅ 2026-06-27
- [x] последний повтор ✅ 2026-06-27

- Нельзя взять адрес элемента map:`&m[k] ` не компилируется. Значение внутри map не addressable потому что такой адрес может потом оказаться недействительным.
- Причина: runtime может перемещать данные map при росте или внутренней перестройке, поэтому стабильный адрес элемента не гарантируется. Go запрещает указатель на значение, которое map может переложить в другое место.
- Адрес самой переменной map взять можно:`&m `. Нельзя именно брать адрес элемента по ключу.
- При этом если поместили структуру в мапу и нужно менять значение в поле, то можно сделать так
```go
type a struct{
b int
}
c:=make(map[key]*a,10)
c[key].b=1

```
- и менять через точку

## Структуры: порядок полей и выравнивание
**Частота:** 3/86
**Темы:** #go/types #go/memory
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Процессор быстрее читает данные, выровненные по границам размера типа (int64 — по 8 байт). Компилятор добавляет **padding** (пустые байты) между полями struct, чтобы каждое поле начиналось с правильного выравнивания. Разный порядок полей → разный размер struct.

**Оптимизация:** располагать поля от большего alignment к меньшему. Например:
- `bool(1) + int64(8) + bool(1) + int32(4)` = 32 байта (7 padding между первым bool и int64)
- `int64(8) + int32(4) + bool(1) + bool(1)` = 24 байта (padding минимален)

**Подробности:**
- `unsafe.Sizeof` показывает реальный размер struct с учётом padding, `unsafe.Alignof` — требуемое выравнивание.
- На 64-бит: указатели/`int64` = 8, `int32` = 4, `int16` = 2, `bool`/`byte` = 1. Самый большой alignment поля определяет alignment всей struct.
- В Go нет прямого контроля над выравниванием (в отличие от C с `__attribute__((packed))`) — компилятор решает сам.
- Оптимизация порядка полей значима только для горячих структур (миллионы экземпляров) — для единичных struct разница в несколько байт несущественна.

## Утечка горутин
**Частота:** 3/86
**Темы:** #go/goroutine #go/channel #go/tooling
- [x] Скорректировано ✅ 2026-06-26
- [x] последний повтор ✅ 2026-06-27

Утечка горутин — это ситуация, когда горутина больше не нужна приложению, но не может завершиться и продолжает удерживать ресурсы. Чаще всего причиной являются зависание на канале, отсутствие отмены через context, незакрытые каналы или забытые ticker/timer. Предотвращается корректным управлением жизненным циклом через context и закрытие каналов.


- Переключение G: block (chan/mutex/WaitGroup), syscall, netpoll park,`runtime.Gosched`, preemption.
- Blocking syscall: handoff P, G в waiting; M может block в kernel, P продолжит другие G.
- Netpoller (epoll/kqueue/IOCP): readiness → G runnable → run queue.
- Safepoints нужны для GC stack scan, stack growth check и preemption.
- Long CPU loop: sysmon (~10 ms) может инициировать preemption post-1.14, но не на каждой инструкции.
- Утечка горутина: G заблокированы навсегда — send без recv, забытый ctx, worker без shutdown.
- Диагностика leak:` go tool pprof -http=:8080 'http://localhost/debug/pprof/goroutine?debug=2'`— stack trace покажет, на каком sync-примитиве висит G
- Fix leak: context cancel,`close(ch)`, WaitGroup, корректное завершение worker pool.

## `errgroup`
**Частота:** 2/86
**Темы:** #go/sync #go/context #go/errors
- [x] Скорректировано ✅ 2026-06-30
- [x] последний повтор ✅ 2026-06-30

`errgroup` — это удобная обертка над ожиданием группы горутин. Она позволяет запускать параллельные задачи, дождаться их завершения, получить первую ошибку и, при использовании `WithContext`, отменить остальные задачи через `Context`, если одна из них завершилась с ошибкой.
```go
g, ctx := errgroup.WithContext(ctx)

g.Go(func() error {
    return loadUsers(ctx)
})

g.Go(func() error {
    return loadOrders(ctx)
})

if err := g.Wait(); err != nil {
    return err
}
```
