### 9.1 Rate limit при нескольких репликах?
**Частота:** 15/59

**Эталон на собесе:**
Per-replica limiter → N × limit. При этом, решение: Redis sliding window / token bucket, или gateway-level limit.

**Типичные ошибки:**
- «Поставим ограничение частоты в middleware» без общее состояние.
- Декларируют CAP без привязки к конкретному сценарию partition.

**Подробности:**
- Учитывать burst и fair per-tenant keys.
- Saga — последовательность локальных транзакций с compensating actions; 2PC — координатор + prepare.
- Negative cache хранит «ключ не найден», чтобы не бить БД повторно.

### 9.2 Saga / 2PC для двух БД?
**Частота:** 2/59

**Эталон на собесе:**
Saga — цепочка локальных транзакций с компенсационными действиями при сбое. При этом, 2PC — prepare/commit через координатора; даёт более жёсткую согласованность, но блокируется и плохо переносит отказы координатора.

**Типичные ошибки:**
- Путает Saga с распределённой транзакцией и не называет компенсации.
- Предлагают 2PC между двумя БД без учёта availability и operational complexity.

**Подробности:**
- Saga бывает через центрального оркестратора или через события между сервисами.
- Outbox помогает надёжно публиковать событие вместе с локальной транзакцией.

### 9.3 CAP theorem?
**Частота:** 11/59

**Эталон на собесе:**
CAP — при network partition: Consistency или Availability (не оба в строгом смысле). При этом, практика: eventual consistency + reconciliation.

**Типичные ошибки:**
- «Можно всё три» — упрощение.
- Декларируют CAP без привязки к конкретному сценарию partition.

**Подробности:**
- CP: etcd, strong consensus.
- AP: Cassandra, Dynamo-style.
- Saga — последовательность локальных транзакций с compensating actions; 2PC — координатор + prepare.

### 9.4 Clean / hexagonal architecture?
**Частота:** 2/59

**Эталон на собесе:**
Слои: handler → service → repository; интерфейсы на границах; domain не зависит от infra.

**Типичные ошибки:**
- Путает слои приложения или не знает, где граница domain/infra.
- Декларируют CAP без привязки к конкретному сценарию partition.

**Подробности:**
- Dependency inversion via интерфейсы injected in main.
- Layers: handler → service → repository;
- domain не depends on infra.

### 9.5 SD: latency растёт неделями, restart помогает
**Частота:** 1/59

**Эталон на собесе:**
Если latency растёт неделями и restart помогает, сначала проверяйте утечки goroutines/heap, рост очередей, исчерпание пула БД и деградацию cache. При этом, нужны метрики, логи и pprof, а не гипотеза «надо больше железа».

**Типичные ошибки:**
- Может, там недостаточно подробно, ты вроде нормально объяснялся. Что, короче, поставить надо?
- Декларируют CAP без привязки к конкретному сценарию partition.

**Подробности:**
- Смотреть RPS, ошибки, latency percentiles, RSS/heap, goroutine count, DB pool и slow queries.
- pprof CPU/heap/goroutine включать контролируемо, с учётом overhead.

### 9.6 Монолит vs микросервисы
**Частота:** 11/59

**Эталон на собесе:**
Монолит — OK для малой команды/MVP. При этом, микросервисы — когда нужны независимый deploy, масштаб по доменам, но растут latency и операционная сложность.

**Типичные ошибки:**
- «Микросервисы всегда лучше».
- Декларируют CAP без привязки к конкретному сценарию partition.

**Подробности:**
- Strangler fig migration.
- Observability, contracts, idempotency критичны.
- Saga — последовательность локальных транзакций с compensating actions; 2PC — координатор + prepare.

### 9.7 Strangler fig pattern
**Частота:** 1/59

**Эталон на собесе:**
Strangler fig — постепенная замена legacy: новый код идёт через фасад, старая система оборачивается и отключается по частям. При этом, снижает big-bang риск миграции.

**Типичные ошибки:**
- Пытаются полный cutover без параллельного периода.
- Не планируют rollback при частичной миграции.

**Подробности:**
- Strangler fig при выносе из legacy: параллельный read old/new, постепенный cutover.
- Saga — последовательность локальных транзакций с compensating actions; 2PC — координатор + prepare.

### 9.9 Negative cache
**Частота:** 4/59

**Эталон на собесе:**
Кэшируем факт отсутствия (404 / empty) с TTL — защита от cache stampede и лишних I/O.

**Типичные ошибки:**
- Декларируют CAP без привязки к конкретному сценарию partition.

**Подробности:**
- Осторожно с инвалидацией при появлении данных; короткий TTL для negative entries.
- Negative cache хранит «ключ не найден», чтобы не бить БД повторно.

### 9.12 Что класть в кэш (и что не класть)
**Частота:** редко

**Как формулируют на собесе:**
> Что стоит класть в кэш? Что не стоит?

**Эталон на собесе:**
**Класть:** данные с высоким read ratio, предсказуемый размер, допустимая устарелость (TTL), дорогой источник (БД, внешний API) — профиль, справочники, hot keys.

**Не класть:** редко читаемое, очень большие объекты, секреты без нужды, данные без стратегии инвалидации.

**Типичные ошибки:**
- Кэшировать без TTL и без плана инвалидации при записи.
- Класть тяжёлые blob в Redis вместо CDN/object storage.

**Подробности:**
- См. [[9. Архитектура#9.9 Negative cache]].
- Cache-aside: кэш → промах → БД → положить в кэш.

### 9.11 Partitioning vs sharding
**Частота:** 6/59

**Эталон на собесе:**
Partitioning делит данные по ключу внутри одной логической системы (шарды таблиц, range/hash). При этом, sharding — распределение по независимым узлам/БД с routing. На практике, sharding сложнее в ops, partitioning — в одном кластере.

**Типичные ошибки:**
- Используют термины как синонимы без уточнения topology.
- Шардируют без стратегии rebalance и cross-shard queries.

**Подробности:**
- Postgres partitioning vs application-level sharding; cross-shard query дороже.
- Saga — последовательность локальных транзакций с compensating actions; 2PC — координатор + prepare.

### 9.11 **Что такое Хореография и Оркестрация?**
   - **Хореография** - паттерн, при котором сервисы независимо общаются и самостоятельно принимают решения как работать. Как танцоры на сцене - каждый знает свою партию и реагирует на других.
   - **Оркестрация** - паттерн при котором есть центральное звено, которое управляет сервисами. Как дирижёр в оркестре - говорит каждому что и когда делать.

### 3. Какие виды архитектур ПО знаешь? 
 - Монолит - один большой сервис, который содержит в себе всё.
 - Микросервис - несколько сервисов, которые независимы и могут быть разработаны, развёрнуты и масштабированы независимо друг от друга. 

### 4. В чем разница между монолитами и микросервисами? Какие плюсы и минусы той и другой архитектуры? 
 - Плюсы монолитов: быстрая разработка на начальных этапах. Проще тестировать и отлаживать.
   - Минусы монолитов: сложности при масштабировании, высокая связанность.
 - Микросервисов 
   - Плюсы микросервисов: можно использовать разный стек для разных сервисов, гибкость, масштабируемость, изоляция сбоев. Микросервисы позволяют использовать для каждого сервиса наиболее подходящие технологии, что может быть сложно или невозможно в монолитах. В микросервисах каждый сервис остается относительно простым, поскольку отвечает только за одну функциональную область.
   - Минусы микросервисов: сложность поддержки, необходимость большего количества сервисов. Нужно выстраиваться связи и интеграции между сервисами, как-то распределять транзакции, контролировать ошибки.

### 5. Что такое архитектурный стиль? 
Архитектурный стиль - это способ организации системы, который определяет её структуру, компоненты и взаимодействие между ними.

### 6. Какие знаешь архитектурные стили? 
• Event-Driven Architecture (EDA) - Событийно-ориентированная архитектура
Суть: Компоненты системы обмениваются событиями и реагируют на них. Хорошо подходит для систем, где важна асинхронная обработка и слабая связанность компонентов.

• Microservices Architecture (MSA) - Микросервисная архитектура
Суть: Приложение разбивается на небольшие независимые сервисы, каждый из которых отвечает за свою функцию. Позволяет легко масштабировать и обновлять отдельные части системы.

• Service-Oriented Architecture (SOA) - Сервисная ориентированная архитектура
Суть: Система строится из слабосвязанных сервисов, взаимодействующих через стандартизированные протоколы. Хорошо подходит для крупных корпоративных систем.

• Layered Architecture - Многослойная архитектура
Суть: Система разделяется на слои (уровни), где каждый слой выполняет определённую роль. Обеспечивает чёткое разделение ответственности между компонентами.

• Microkernel Architecture - Микроядровая архитектура
Суть: Базовая функциональность выносится в ядро, а остальные возможности реализуются через подключаемые компоненты. Позволяет легко расширять систему новыми возможностями.

• REST (Representational State Transfer) - Передача состояния представления
Суть: Архитектурный стиль для построения распределённых систем, основанный на протоколе HTTP и стандартных операциях над ресурсами. Каждый ресурс имеет уникальный идентификатор (URI), а взаимодействие происходит через стандартные HTTP-методы (GET, POST, PUT, DELETE). Обеспечивает простоту, масштабируемость и независимость от платформы.

### 7. Знаете ли вы CAP-теорему?
Теорема CAP утверждает, что в распределенной системе можно одновременно
обеспечить только два из трех свойств- согласованность, доступность и толерантность
к разделению. Третье свойство будет жертвоваться.

Согласованность: каждый узел видит одни и те же данные, даже если происходят одновременные обновления.

Доступность: все запросы получают ответы о том, был ли запрос успешным или нет.

Устойчивость к разделению на части: система продолжит работать, даже если связь между двумя разными узлами будет прервана.


### 8. Что означает устойчивость к отказам?
Устойчивость к отказам означает, что система может продолжать работать даже при наличии отказов в отдельных компонентах.


### Что такое архитектура?
Архитектура ПО – это каркас, на котором создаётся весь программный продукт. Это – план, который указывает, где и какие куски должны быть, и как они связаны друг с другом

### Низкая связанность что это? 
Это принцип, который подразумевает минимизацию зависимостей между различными частями системы. 
 - Например, в монолите это можно реализовать через разбиение на модули, разделение кода на слои
 - В микросервисах: каждый микросервис должен иметь минимум зависимостей от других микросервисов. Это упрощает разработку, тестирование, развертывание каждого микросервиса отдельно

Пример слабой связанности - взаимодействие через брокеры или API
Пример высокой связанности - два сервиса смотрят в одну таблицу БД
