# 7. HTTP, сети

## 1. HTTP методы
**Частота:** часто
- [ ] Скорректировано
- [ ] последний повтор

- GET - получение данных. Дополнительные параметры (`?ключ=значение`) могут быть переданы прямо в URL
- POST - позволяет отправлять данные на сервер, это могут быть файлы и содержимое различных форм;
- PUT - полное обновление
- PATCH - частичное обновление
- DELETE - удаление
- HEAD - подобен GET, но возвращает только заголовки ответа, без тела. Может, например, использоваться для предварительного получения размера ответа.
- OPTIONS - получение списка доступных методов

## 5. Что такое идемпотентность? Какие методы HTTP идемпотентны?
**Частота:** часто
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21

Идемпотентность - повторное выполнение с теми же входными данными даёт тот же результат.

Идемпотентные методы: 
• GET - получение данных не меняет состояние
• PUT - повторное полное обновление даёт тот же результат
• DELETE - повторное удаление не меняет результат
• HEAD - получение метаданных не меняет состояние
• OPTIONS - получение списка методов не меняет состояние

Неидемпотентные методы:
• POST - каждый вызов создаёт новую сущность
• PATCH - может давать разные результаты при повторном применении

## 8. Что такое RESTful принципы?
**Частота:** средне
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-22

REST (Representational State Transfer) — архитектурный стиль для распределённых систем. Основные принципы:

• Клиент-серверная архитектура
- Разделение ответственности между клиентом и сервером
- Независимое развитие клиентской и серверной части

• Отсутствие состояния (Statelessness)
- Каждый запрос содержит всю необходимую информацию
- Сервер не хранит состояние между запросами

• Кэширование
- Ответы должны явно определять возможность кэширования

• Единообразие интерфейса
- Унифицированный способ взаимодействия с ресурсами
- Стандартные методы HTTP
- Самодокументируемые ответы

• Слоистая система
- Возможность добавления промежуточных слоёв (прокси, балансировщики)
- Клиент не должен знать о внутренней структуре системы

• Код по запросу (опционально)
- Возможность передачи исполняемого кода клиенту

## 10. Чем идентификация отличается от авторизации и аутентификации?
- [ ] Скорректировано
- [ ] последний повтор

## 15. Из чего состоит HTTP-запрос?
**Частота:** 3/59
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21

**Эталон на собесе:**

**Подробности:**
- GET обычно без тела; POST/PUT/PATCH часто несут тело.
- Граница заголовков и тела — см. §28.

## 22. Коды ответов HTTP
**Частота:** редко
- [x] Скорректировано ✅ 2026-06-22
- [x] последний повтор ✅ 2026-06-22

Код состояния или статус указывает на то, успешно обработался запрос или произошла какая-то ошибка. Код состояния — трёхзначное число и первая цифра указывает на его тип. Пояснение в краткой форме описывает код состояния.

Основные группы:
- 1xx: информационный характер
	- 102 Processing
- 2xx: Успешное выполнение
  - 200 OK - запрос успешен
  - 201 Created - ресурс создан
  - 204 No Content - успешно, нет данных в ответе. Как 200 но без тела ответа
- 3xx: редиректы
	- 301 Moved Permanently
- 4xx: Ошибка клиента
  - 400 Bad Request - неверный запрос
  - 401 Unauthorized - требуется аутентификация
  - 403 Forbidden - доступ запрещён
  - 404 Not Found - ресурс не найден
  - 409 Conflict
  - 415 Unsupported media type. Ожидаем Json, прислали XML
  - 413 Request entity too large. Ожидаем 1кб, прислали 1МБ
  - 429 Too many requests. Не более 10RPS - 11RPS
- 5xx: Ошибка сервера
  - 500 Internal Server Error - внутренняя ошибка
  - 503 Service Unavailable - сервис недоступен

## 23. Что такое stateless и stateful сервисы?
**Частота:** редко
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21

• Stateless сервисы (без состояния):
- Каждый запрос самодостаточен
- Не хранят информацию между запросами
- Легче масштабируются
- REST API является примером stateless архитектуры

• Stateful сервисы (с состоянием):
- Хранят информацию о сессии
- Помнят предыдущие запросы
- Сложнее в масштабировании
- Пример: WebSocket соединения

## 25. Что такое URL?
**Частота:** редко
- [x] Скорректировано ✅ 2026-06-22
- [x] последний повтор ✅ 2026-06-21

```
<схема>:[//[<логин>[:<пароль>]@]<хост>[:<порт>]][/<URL‐путь>][?<параметры>][#<якорь>]
```

- **схема** — как правило, указывается сетевой протокол `https` или `http`;
- **логин** — логин пользователя для доступа к ресурсу;
- **пароль** — пароль пользователя. Логин и пароль в URL практически не используются из соображений безопасности;
- **хост** — IP-адрес или доменное имя;
- **порт** — порт;
- **URL-путь** — путь к запрашиваемой странице или ресурсу;
- **параметры** — параметры `ключ=значение` передаваемые на сервер методом GET. В качестве разделителя используется знак `&`. Например: `?page=1&search=john`;
- **якорь** — при указанном якоре браузер при открытии страницы перейдёт к заголовку или элементу c таким атрибутом `id`.
В URL-адресах, не считая служебных символов (например, `: & = /`), можно использовать только латинские буквы, цифры, минус, знак подчёркивания, точку и тильду. Все остальные символы нужно перекодировать, предварительно преобразовав их в кодировку UTF-8. Из кодировки UTF-8 каждый байт преобразуется в 16-ричное представление с добавлением знака `%`. Так пробел будет преобразован в `%20`

## 26. Что не шифруется в HTTPS?
**Частота:** редко
- [ ] Скорректировано
- [ ] последний повтор

**Как формулируют на собесе:**
> Что в HTTP-запросе остаётся незашифрованным при HTTPS?

**Эталон на собесе:**
Тело запроса и ответа **шифруются** в TLS (application data). Видимы метаданные **до** или **вне** зашифрованного канала: IP-адреса, порты, SNI (имя хоста в ClientHello), размер и время трафика. После handshake HTTP-заголовки и тело идут внутри TLS — снаружи их не прочитать.

**Типичные ошибки:**
- «Тело не шифруется» — наоборот, основная нагрузка защищена TLS.
- Путать видимость SNI/DNS с отсутствием шифрования payload.

**Подробности:**
- См. §12 HTTP vs HTTPS.
- Что даёт TLS (конфиденциальность, целостность) — §29.
- ECH/SNI encryption — отдельная тема; классически SNI виден.

## 27. Как подобрать timeout (p99)?
**Частота:** редко
- [ ] Скорректировано
- [ ] последний повтор

**Как формулируют на собесе:**
> Зачем таймауты и как выбрать значение?

**Эталон на собесе:**
Таймаут ограничивает ожидание и освобождает ресурсы (соединения, горутины). Подбор: смотреть latency-метрики (p95/p99), взять p99 + запас (10–30%) под джиттер и ретраи. Учитывать цепочку: client timeout ≥ сумма downstream + margin.

**Типичные ошибки:**
- Один глобальный timeout на всё без разделения connect/read/deadline.
- Таймаут меньше p99 — ложные ошибки под нагрузкой.

**Подробности:**
- См. §11 (зачем timeouts), context deadline в Go.

## 28. Как разделяются заголовки и тело HTTP-запроса?
**Частота:** редко
- [ ] Скорректировано
- [ ] последний повтор

**Как формулируют на собесе:**
> Чем в HTTP/1.1 отделяется block заголовков от body?

**Эталон на собесе:**
После последнего заголовка идёт **пустая строка** — в wire format это `\r\n\r\n` (CRLF CRLF). Дальше — тело как сырые байты (JSON, XML, form-data и т.д.), без вложенной «структуры HTTP».

**Типичные ошибки:**
- Искать разделитель внутри JSON-тела.
- Путать с `Content-Length` / chunked — это уже как читать body, не где граница заголовков.

**Подробности:**
- См. §15 (состав HTTP-запроса).

> Что даёт шифрование? От чего защищает HTTPS?

**Эталон на собесе:**
TLS даёт **конфиденциальность** (перехватчик не читает payload), **целостность** (подмена/инъекция в трафик заметна) и **аутентификацию сервера** (сертификат). Не заменяет авторизацию приложения и не скрывает все метаданные канала.

**Типичные ошибки:**
- Считать, что TLS защищает от XSS/SQLi на сервере.
- Путать с вопросом «что **не** шифруется» (SNI, IP) — см. §26.

**Подробности:**
- См. §12 HTTP vs HTTPS, §26 (видимые метаданные).

## 30. /etc/hosts — локальный редирект домена
**Частота:** редко
- [ ] Скорректировано
- [ ] последний повтор

**Как формулируют на собесе:**
> Как сделать, чтобы `vk.com` открывался на `localhost`?

**Эталон на собесе:**
Добавить запись в **`/etc/hosts`** (Windows: `C:\Windows\System32\drivers\etc\hosts`): `127.0.0.1 vk.com`. Резолвинг имени произойдёт **до** DNS; браузер пойдёт на локальный IP. Альтернативы: локальный DNS (dnsmasq), proxy с подменой, правила в dev-окружении — но на собесе чаще ждут hosts.

**Типичные ошибки:**
- Путать с HTTP redirect (301/302) — это уже уровень приложения после резолва.
- Забыть про HTTPS: сертификат для `vk.com` не подойдёт к локальному серверу без своего cert/SNI.

**Подробности:**
- См. [[7. HTTP, сети#25. Что такое URL?]] (hostname → IP).
- Нужны права администратора для правки файла.

## 31. XSS (Cross-Site Scripting)
**Частота:** редко
- [ ] Скорректировано
- [ ] последний повтор

**Как формулируют на собесе:**
> Что такое XSS? Как защищаться?

**Эталон на собесе:**
**XSS** — внедрение исполняемого JS в страницу, которую видит жертва (stored/reflected/DOM). Браузер жертвы выполняет чужой скрипт в контексте доверенного сайта → кража cookie/session, подмена UI, действия от имени пользователя.

**Защита:** экранирование вывода (context-aware), CSP, HttpOnly/SameSite cookies, валидация входа; не хранить секреты в localStorage без нужды.

**Типичные ошибки:**
- Считать, что HTTPS от XSS защищает (TLS шифрует канал, не санитизирует HTML).
- Путать XSS и CSRF.

**Подробности:**
- См. [[7. HTTP, сети#29. От чего защищает HTTPS (TLS)?]] — TLS не заменяет санитизацию.

## 32. CSRF (Cross-Site Request Forgery)
**Частота:** редко
- [ ] Скорректировано
- [ ] последний повтор

**Как формулируют на собесе:**
> Что такое CSRF? Как понять, что запрос не подделан?

**Эталон на собесе:**
**CSRF** — браузер жертвы **сам** отправляет авторизованный запрос на сайт, куда пользователь уже залогинен (куки подставляются автоматически), пока жертва открыла вредную страницу.

**Защита:** CSRF-токен (double-submit / synchronizer token), проверка `Origin`/`Referer`, SameSite cookies, re-auth для чувствительных операций.

**Типичные ошибки:**
- Путать CSRF и CORS (CORS — политика браузера на чтение ответа, не защита сервера от подделки запроса с куками).
- Путать CSRF-токен с TLS-сертификатом.

**Подробности:**
- См. [[7. HTTP, сети#17. CORS и cross-origin (браузер)]] — отличие от CSRF.

## 33. DNS — как работает резолвинг?
**Частота:** редко
- [ ] Скорректировано
- [ ] последний повтор

**Как формулируют на собесе:**
> Что такое DNS? Как браузер узнаёт IP по домену?

**Эталон на собесе:**
**DNS** — распределённая система имён: hostname → IP (и другие записи). Браузер/ОС вызывает **резолвер**. Типичный порядок: **`/etc/hosts`** → кэш ОС/браузера → recursive resolver (провайдер, `8.8.8.8`, `1.1.1.1`) → authoritative DNS (A/AAAA для IP, CNAME — алиас).

Запросы чаще **UDP :53**; при большом ответе — TCP. Ответ кэшируется по **TTL**.

**Типичные ошибки:**
- Путать DNS с HTTP redirect.
- Считать, что hosts и DNS — одно и то же (hosts проверяется **раньше** DNS).
- Путать URL и hostname (DNS резолвит имя, не полный path).

**Подробности:**
- См. [[7. HTTP, сети#25. Что такое URL?]], [[7. HTTP, сети#30. /etc/hosts — локальный редирект домена]].
- DNS часто упоминают рядом с [[7. HTTP, сети#13. TCP vs UDP?]] (UDP для коротких DNS-запросов).

## 34. Man-in-the-middle (MITM)
**Частота:** редко
- [ ] Скорректировано
- [ ] последний повтор

**Как формулируют на собесе:**
> Что такое man-in-the-middle? Как бороться?

**Эталон на собесе:**
**MITM** — злоумышленник **между** клиентом и сервером: перехватывает, читает или подменяет трафик (типично публичный Wi‑Fi, скомпрометированный прокси, rogue AP).

**Защита:** **HTTPS/TLS** с проверкой сертификата, HSTS, не доверять самоподписанным cert без причины, VPN в недоверенных сетях, certificate pinning (мобильные приложения).

**Типичные ошибки:**
- Считать, что HTTP + «секретный заголовок» заменяет TLS.
- Путать MITM с CSRF или XSS.

**Подробности:**
- См. [[7. HTTP, сети#12. HTTP vs HTTPS?]], [[7. HTTP, сети#29. От чего защищает HTTPS (TLS)?]].
