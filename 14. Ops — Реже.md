## Load average в Linux
**Частота:** 3/86
**Темы:** #ops #linux #devops
- [ ] Скорректировано
- [ ] последний повтор
**Эталон на собесе:**
Среднее **число задач в очереди на CPU** (runnable + часто uninterruptible sleep) за 1, 5 и 15 минут. Это не процент загрузки CPU и не загрузка RAM. Сравнивать с числом логических ядер: load ≈ число ядер — нормальная загрузка; сильно выше — очередь на CPU растёт.
**Типичные ошибки:**
- «Средняя загрузка памяти» или «% CPU».
- Не учитывать количество ядер при интерпретации.

**Подробности:**
-`uptime`, первая строка `top`— те же три числа.
- Высокий load при низком CPU% бывает при I/O wait (D-state).

### Docker layers
**Частота:** 2/86
**Темы:** #ops #linux #devops
**Эталон на собесе:**
Docker образ — слои (layers) из Dockerfile instructions; каждый RUN/COPY добавляет layer. Общие слои кэшируются между образами; меньше слоёв и правильный порядок COPY → быстрее build и меньше размер.
**Типичные ошибки:**
- Не используют multi-stage build — тащат toolchain в runtime образ.
- Меняют часто меняющийся файл до редко меняющихся — ломают cache.

**Подробности:**
- Liveness probe перезапускает pod; readiness — убирает из Service endpoints.
- Redis — cache, ограничение частоты, pub/sub, distributed lock; не primary database.

## Нет памяти: swap, OOM killer
**Частота:** 2/86
**Темы:** #ops #linux #devops #go/memory
- [ ] Скорректировано
- [ ] последний повтор
**Как формулируют на собесе:**
> Аллокатор отказал, swap нет — что будет?
**Эталон на собесе:**
Ядро может сначала вытеснять страницы в swap (если включён). Если физической памяти и swap не хватает — **OOM killer** убивает процесс(ы) по heuristics (oom_score). Процесс получает SIGKILL; данные несохранённые теряются. Overcommit (`vm.overcommit_memory`) влияет на то, когда отказ случится — при commit или при touch.


-`dmesg`,`/var/log `— кто убит OOM.

## Что такое fork?
**Частота:** 1/86
**Темы:** #ops #linux #devops
- [ ] Скорректировано
- [ ] последний повтор
**Эталон на собесе:**
`fork()`— системный вызов POSIX: создаёт **дочерний процесс** — копию родителя (память часто copy-on-write). У дочернего свой PID; оба продолжают после точки вызова. Типичный паттерн:`fork()`+`exec()`— запуск другой программы в дочернем процессе. В Go напрямую не используют; важно отличать **процесс** от **потока** и от **горутины**.


- Prefork-модели (nginx, старые PostgreSQL) — пул процессов до нагрузки.

## Blue-green deployment
**Частота:** 0/86
**Темы:** #ops #devops #deploy
- [ ] Скорректировано
- [ ] последний повтор
**Эталон на собесе:**
Две идентичные prod-среды (blue/green). Активная обслуживает трафик; новая версия деплоится в inactive → smoke/load → переключение маршрутизации → при проблемах мгновенный rollback на старую среду.
**Подробности:**
- Минимальный downtime; дороже — две полные среды.
- Переключение на уровне LB/Ingress/DNS.

## Canary deployment
**Частота:** 0/86
**Темы:** #ops #devops #deploy
- [ ] Скорректировано
- [ ] последний повтор
**Эталон на собесе:**
Новая версия получает **долю** трафика (1–5% → постепенно больше). Мониторинг ошибок/latency; при деградации — откат, при успехе — расширение до 100%. Меньше риск, чем big-bang deploy.
**Подробности:**
- K8s: rolling update + maxSurge/maxUnavailable; service mesh — weighted routing.
- Отличие от blue-green: одна инфраструктура, две версии одновременно.

## Система контроля версий (Git) — основы
**Частота:** 2/86
**Темы:** #ops #git

**Эталон на собесе:**
- **VCS** хранит историю изменений кода и позволяет откатиться к любой версии.
- **Git** — распределённая VCS: каждый разработчик имеет полную копию репозитория.

## SLA / SLO / SLI
**Частота:** 0/86
**Темы:** #ops #devops #sre
- [ ] Скорректировано
- [ ] последний повтор
**Эталон на собесе:**
**SLI** — измеряемая метрика (availability, p99 latency, error rate). 
**SLO** — внутренняя цель по SLI (99.9% uptime / месяц). 
**SLA** — контракт с клиентом: SLO + последствия нарушения (штраф, credits).
**Подробности:**
- Error budget = 1 − SLO; тратится на релизы и инцidents.
- Пример SLI: `(successful_requests / total_requests)` за окно.

## Системные каталоги
**Частота:** 0/86
### Критические для работы системы
- **/boot** - файлы загрузчика ОС и образы ядра
- **/bin** - основные утилиты командной строки (в современных системах часто является символической ссылкой на /usr/bin)
- **/sbin** - системные утилиты для администрирования (в современных системах часто является символической ссылкой на /usr/sbin)
- **/lib** - системные библиотеки для /bin и /sbin (в современных системах часто является символической ссылкой на /usr/lib)
- **/etc** - конфигурационные файлы системы и сервисов

### Виртуальные файловые системы
- **/dev** - файлы устройств (hardware)
- **/proc** - информация о процессах и системе
  - `/proc/{pid}` - данные конкретного процесса
  - `/proc/uptime` - время работы системы
- **/sys** - информация об оборудовании

### Пользовательские данные
- **/home** - домашние каталоги пользователей
- **/root** - домашний каталог администратора
- **/usr** - программы и данные пользователей
  - `/usr/bin` - пользовательские программы
  - `/usr/sbin` - программы для администрирования
  - `/usr/lib` - библиотеки программ
  - `/usr/local` - программы, установленные из исходников
  - `/usr/src` - исходный код ядра и документация

### Временные и монтируемые каталоги
- **/tmp** - временные файлы (очищается при перезагрузке)
- **/media** - точка монтирования съемных носителей
- **/mnt** - точка монтирования файловых систем
- **/run** - временные файлы служб

### Специальные каталоги
- **/opt** - сторонние программные пакеты
- **/srv** - данные сервисов (например, веб-сервера)
- **/var** - логи и временные файлы баз данных
