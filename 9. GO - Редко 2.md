## Как в го можно создать собственный тип
**Частота:** 2/84
**Темы:** #go/types #go/methods
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
В Go три способа создать собственный тип:

- **`type Name int`** — type definition: новый тип на основе существующего. Name и int — разные типы, несовместимы без явного приведения. Можно добавлять методы.
- **`type Name = int`** — type alias (Go 1.9): синоним, Name и int — один и тот же тип, взаимозаменяемы без приведения. Методы исходного типа доступны.
- **Struct** — `type User struct { ... }`. Ключевое отличие от ООП — **композиция вместо наследования**: embedding struct добавляет поля и методы встроенного типа, но не создаёт иерархию «родитель-потомок». Методы встроенной struct «промоутятся» и доступны как у внешней.

**Подробности:**
- Type definition (`type A B`) создаёт **новый тип** с тем же underlying type. Явное приведение обязательно: `A(b)`. Методы не наследуются — их надо определять заново.
- Type alias (`type A = B`) — **тот же тип**. Используется для рефакторинга (переезд типа между пакетами без ломания API) и для совместимости.
- Embedding struct — не наследование: нет виртуальных методов, нет переопределения, нет полиморфизма через базовый класс. Вместо этого — интерфейсы + композиция.

## Операции и параметры канала
**Частота:** 1/84
**Темы:** #go/channel
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**
Основные операции с каналами:
- создание (`make`);
- отправка (`<-`);
- получение (`<-`);
- закрытие (`close`);
- чтение через `range`;
- ожидание нескольких каналов через `select`.
Дополнительно можно получить текущую длину буфера (`len`) и его емкость (`cap`) для буферизированных каналов.
**Эталон на собесе:**
- `make(chan T)` / `make(chan T, n)` — создание небуферизованного или буферизованного канала.
- Отправка `ch <- v`, получение `<-ch` или `v := <-ch`; `close(ch)` — закрытие (обычно отправителем).
- `for v := range ch` — чтение до закрытия; `select` — мультиплексирование нескольких каналов.
- `len(ch)`, `cap(ch)` — текущая заполненность и ёмкость буфера (для buffered).
У канала есть три основные характеристики:
- **тип элементов** (`chan int`, `chan User`);
- **направление** (`chan`, `<-chan`, `chan<-`);
- **емкость буфера** — небуферизированный (`cap == 0`) или буферизированный (`cap > 0`).

## Системные вызовы (syscall) в Go?
**Частота:** 10/84
**Темы:** #go/scheduler #go/runtime
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Системный вызов — переход из user mode в kernel mode: файловый I/O, часть сетевых операций, таймеры. Для Go критично не само определение, а **как runtime обрабатывает блокирующий syscall без остановки всех горутин**.

При блокирующем syscall горутина паркуется (`entersyscall`), её M (поток ОС) остаётся в kernel, а P (логический процессор) **передаётся другому M** (handoff) — остальные горутины продолжают работу. После возврата из syscall (`exitsyscall`) горутина попадает в очередь (обычно global runq) и позже подхватывается планировщиком.

**Ключевое различие:** сетевой I/O vs дисковый I/O:
- **Сеть:** не блокирует поток — горутина регистрируется в **netpoller** (epoll/kqueue), M освобождается для других горутин.
- **Диск/файлы:** блокирует поток ОС — runtime создаёт дополнительный M (если есть свободный или новый), чтобы P не простаивал. Причина: ОС не предоставляет неблокирующий API для файловых операций (в отличие от сокетов).

**Подробности:**
- **entersyscall / exitsyscall:** runtime-функции, обрамляющие syscall. `entersyscall` открепляет P от M; `exitsyscall` пытается вернуть P обратно, а если P уже занят новым M — G уходит в global runq.
- **Handoff:** когда P освобождается от M, уходящего в блокирующий syscall, планировщик ищет свободный M (из idle-пула) или создаёт новый (`newm`). Максимум потоков — 10 000 по умолчанию (`runtime/debug.SetMaxThreads`).
- **Кооперативная точка:** до Go 1.14 syscall был одной из немногих точек переключения контекста. Сейчас добавлена асинхронная preemption (сигналы ОС), но syscall остаётся важным механизмом.
- **CGO:** вызов C-функции через cgo — тоже блокирующий с точки зрения Go runtime. Похожая механика — M блокируется на C-стеке, P передаётся другому M.

## Структуры: порядок полей и выравнивание
**Частота:** 3/84
**Темы:** #go/types #go/memory
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Процессор быстрее читает данные, выровненные по границам размера типа (int64 — по 8 байт). Компилятор добавляет **padding** (пустые байты) между полями struct, чтобы каждое поле начиналось с правильного выравнивания. Разный порядок полей → разный размер struct.

**Оптимизация:** располагать поля от большего alignment к меньшему. Например:
- `bool(1) + int64(8) + bool(1) + int32(4)` = 32 байта (7 padding между первым bool и int64)
- `int64(8) + int32(4) + bool(1) + bool(1)` = 24 байта (padding минимален)

**Подробности:**
- `unsafe.Sizeof` показывает реальный размер struct с учётом padding, `unsafe.Alignof` — требуемое выравнивание.
- На 64-бит: указатели/`int64` = 8, `int32` = 4, `int16` = 2, `bool`/`byte` = 1. Самый большой alignment поля определяет alignment всей struct.
- В Go нет прямого контроля над выравниванием (в отличие от C с `__attribute__((packed))`) — компилятор решает сам.
- Оптимизация порядка полей значима только для горячих структур (миллионы экземпляров) — для единичных struct разница в несколько байт несущественна.

`rune` — псевдоним `int32`, кодовая точка Unicode. `byte` — псевдоним `uint8`.

Enum в Go нет. Реализуется через `const` + `iota`: `const ( A = iota; B; C )`. Не типобезопасен (iota — это `int`), нет итерации по значениям, нет строкового представления.

Переполнение: для констант — ошибка компиляции. Для переменных — wraparound по модулю 2ⁿ (`uint8(255) + 1 = 0`).

## Что если GOMAXPROCS=1 и goroutine блокируется?
**Частота:** 1/84
**Темы:** #go/scheduler
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-08

При `GOMAXPROCS=1` один P, все горутины исполняются на одном CPU — параллелизма нет, конкурентность есть. При блокировке:

- **Канал/mutex:** G паркуется, P берёт следующую runnable G. Поток ОС не блокируется.
- **Сетевой I/O:** G уходит в netpoller (epoll), P свободен для других G.
- **Блокирующий syscall (диск):** M остаётся в kernel, runtime создаёт **новый M** для P — без этого единственный P простаивал бы.

## Что такое context switching и как горутины решают эту проблему
**Частота:** 7/84
**Темы:** #go/scheduler #go/goroutine
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
Context switch — сохранение состояния текущего потока (регистры, stack pointer, program counter) и загрузка состояния следующего. Для потоков ОС это **дорого**: переход в kernel mode, сохранение/восстановление всех регистров, смена page tables, сброс TLB. ~1–10 мкс на операцию.

Горутины решают проблему тем, что переключение происходит **в user-space**, без участия ядра ОС:
- Сохраняется только ~3 регистра (SP, PC, G-указатель), а не полный набор.
- Стек горутины — ~2 КБ (растёт динамически) против ~1 МБ фиксированного у потока ОС. Меньше памяти для сохранения/восстановления.
- Планировщик Go (GMP) переключает горутины на одном потоке ОС — поток продолжает работать, не тратя время на kernel transition.
- Результат: переключение горутины ~десятки наносекунд, на 2–3 порядка быстрее thread switch.

**Подробности:**
- Thread switch требует: syscall → kernel stack → save regs → pick next thread → restore regs → iret. При смене процесса — ещё смена адресного пространства (CR3, сброс TLB).
- Goroutine switch: `gopark` (сохранить SP/PC в G) → выбрать следующую G из runq → `goready` (загрузить SP/PC из G). Всё в user-space, ни одного syscall.
- Переключение происходит в кооперативных точках (вызов функции, канал, syscall) или принудительно через preemption (sysmon, >10 мс на P с Go 1.14+).
- **CPU-bound:** горутины сверх числа ядер дают только оверхед на переключение — параллелизм ограничен железом. **I/O-bound:** тысячи горутин сверх ядер — норма, потому что заблокированные (канал, сеть, диск) горутины не потребляют CPU и не участвуют в переключении.

## Что такое массив? / Для чего можно использовать массивы в Golang?
**Частота:** 2/84
**Темы:** #go/array #go/types
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-03
**Что ожидают на собесе:**
> [!summary] Собес: как отвечать
> Массив - это последовательность элементов одного типа и постоянной длины. Размер массива - составная часть его типа и задается во время компиляции.
- Многомерный `[M][N]T `— M элементов типа `[N]T `; пример:`[4][7]int `.
- Непрерывный блок N × sizeof(T), **доступ по индексу O(1)**; для `[M][N]T `— построчно. 
- доступ по индексу O(1), константная сложность потому что можно вычислить адрес 
- Без инициализации каждый элемент — нулевое значение своего типа.
- value type: при присваивании и передаче в функцию копируются все элементы. Мутация параметра `[N]T `внутри функции снаружи не видна; чтобы менять исходное значение, параметр объявляют`*[N]T `.
- Два массива одного типа `[N]T `можно сравнивать оператором == , если сравним тип T — тогда же`[N]T `годится ключом map. Срав нение двух значений одного`[N]T ` через == поэлементное, слева направо

- Значение `len(a)` подставляется компилятором как константа.
- Типы `[3]int `и`[5]int` несовместимы: ни присвоить одно другому, ни сравнить между собой нельзя.
- Размер можно вывести из литерала (`[...]int{10, 20}`), задать явно или указать только нужные индексы (`[7]int{2: 3, 6: 11}`).
- Пустой массив `[0]int ` допустим.
- Обращение по индексу-константе в не диапазона — ошибка компиляции; по переменному индексу в не `[0, N) `— паника.
- В `for range` по массиву переменная итерации — копия элемента, не ссылка на ячейку. Для изме нения на месте обходят по индексу или берут указатель на элемент явно.
- Копирование struct с полем-массивом включает весь массив.
```go
var a [5]int
b := [3]int{1, 2, 3}
c := [...]int{10, 20}
d := [7]int{6: 11, 2: 3}
```

использовать когда
- Когда **заранее известна фиксированная длина** и не планируется resize — массив на стеке/в struct без лишних аллокаций.
- Пример: фиксированный буфер, `[N]byte` под hash/crypto, embed в struct, stack-friendly hot path.

## ` context.WithValue` — антипаттерны

- Wait() освобождает Mutex и засыпает;
- после пробуждения снова захватывает Mutex;
- Signal() будит одну горутину;
- Broadcast() будит все;
- Wait() всегда вызывают в цикле for, проверяя условие.
