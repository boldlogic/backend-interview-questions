- **Table-driven tests**: кейсы в слайсе `[]struct{ name, input, want ... }`, один `TestXxx` с циклом и `t.Run(tc.name, ...)`.

## `sync.Pool`
**Частота:** 2/92
**Темы:** #go/sync #go/gc
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

**Эталон на собесе:**
- `sync.Pool` — кэш **временных** объектов per-P (локально для процессора), снижает аллокации и нагрузку на GC.
- `Get`/`Put`: взяли объект, вернули в пул после использования; между вызовами GC **может очистить** пул — полной гарантии хранения нет.
- Не хранить в Pool долгоживущее состояние; после `Put` не держать ссылки на объект снаружи.
- Типичное применение: буферы `[]byte`, временные struct под hot path (переиспользуем вместо постоянных `new`/alloc).

## Append внутри функции по значению — виден ли снаружи?
**Частота:** 2/92
**Темы:** #go/slice
- [x] Скорректировано ✅ 2026-06-18
- [x] последний повтор ✅ 2026-07-03

**Эталон на собесе:**
В функцию передается копия заголовка, базовый массив общий.
Append обновляет локальный заголовок внутри функции.
Функция меняет len у своей копии; у вызывающего len не меняется если не возвращать.
При этом если позволяет cap, то базовый массив обновляется и можно увидеть снаружи через расширение len (взятие слайса)
Аналогично при выделении нового базового массива - обновление указателя на базовый массив снаружи не виден.
существующие элементы могут измениться в общем массиве - мутация существующих элементов `s[i] = v` видна вызывающему
**Подробности:**
Фиксы
- Return `s = append(s, x)` или указатель `*[]T `.
- Всегда переприсваивать результат append.
- Без return/указателя len снаружи не меняется.
- При достаточном cap элементы мутируют общий базовый массив.

## Бинарный поиск vs дерево поиска (оба O(log n))
**Темы:** #go/complexity #go/algorithms
**Частота:** 2/92
- [ ] Скорректировано
- [ ] последний повтор
**Как формулируют на собесе:**
> Бинпоиск и дерево — оба O(log n). Зачем оба? В чём разница по памяти?

**Эталон на собесе:**
Одинаковая **асимптотика**, разная **модель данных**
- **Бинарный поиск** — по **отсортированному массиву** in-place; доп. Память O(1), но вставка/удаление O(n).
- **Дерево поиска (BST/B-tree)** — структура с указателями/узлами; вставка/удаление/поиск O(log n) при балансировке; больше памяти на метаданные узлов, зато динамические обновления.
На собесе VK ждут: бинпоиск — когда массив уже есть и редко меняется; дерево — когда нужны частые вставки или индекс в БД (B-tree).
**Типичные ошибки:**
- «Разницы нет, оба логарифм» — игнорировать стоимость вставки и память.
- Путать бинпоиск в массиве с обходом дерева рекурсией (стек/alloc).

## Как в го можно создать собственный тип
**Частота:** 2/92
**Темы:** #go/types #go/methods
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-08

**Эталон на собесе:**
В Go три способа создать собственный тип:

- **`type Name int`** — type definition: новый тип на основе существующего. Name и int — разные типы, несовместимы без явного приведения. Можно добавлять методы.
- **`type Name = int`** — type alias (Go 1.9): синоним, Name и int — один и тот же тип, взаимозаменяемы без приведения. Методы исходного типа доступны.
- **Struct** — `type User struct { ... }`. Ключевое отличие от ООП — **композиция вместо наследования**: embedding struct добавляет поля и методы встроенного типа, но не создаёт иерархию «родитель-потомок». Методы встроенной struct «промоутятся» и доступны как у внешней.

**Подробности:**
- Type definition (`type A B`) создаёт **новый тип** с тем же underlying type. Явное приведение обязательно: `A(b)`. Методы не наследуются — их надо определять заново.
- Type alias (`type A = B`) — **тот же тип**. Используется для рефакторинга (переезд типа между пакетами без ломания API) и для совместимости.
- Embedding struct — не наследование: нет виртуальных методов, нет переопределения, нет полиморфизма через базовый класс. Вместо этого — интерфейсы + композиция.

## Канал vs мьютекс
**Частота:** 2/92
**Темы:** #go/channel #go/sync
- [x] Скорректировано ✅ 2026-06-26
- [x] последний повтор ✅ 2026-06-27

- **Мьютекс** — эксклюзивный доступ к общему состоянию (counter, cache, map под lock); одна goroutine в критической секции, остальные ждут разблокировки.
- **Канал** — передача **владения** данными/работой между goroutines; естественен для pipeline, fan-in/fan-out, сигналов «готово».
- Counter/cache — mutex проще; orchestration и поток задач — канал + `select`.
- Канал не заменяет mutex для произвольного shared state: без отдельной goroutine-владельца map всё равно нужен mutex.

## Очередь с приоритетом и binary heap
**Темы:** #go/algorithms #go/complexity
**Частота:** 2/92
- [ ] Скорректировано
- [ ] последний повтор
**Как формулируют на собесе:**
> Что такое очередь с приоритетом? На какой структуре реализовать? Что такое heap?

**Эталон на собесе:**
**Priority queue** — элемент с наивысшим (или наименьшим) приоритетом извлекается первым. Наивно — отсортированный список O(n) на вставку; оптимально — **binary heap** (min-heap / max-heap): вставка и извлечение корня O(log n), peek O(1). В памяти heap часто хранится как **массив** с индексной арифметикой (родитель/дети).
**Типичные ошибки:**
- Путать heap (куча приоритетов) с heap памятью в Go.
- Предлагать только linked list без оценки сложности.

**Подробности:**
- В Python —`heapq`; в Go —`container/heap`.
- При коллизии приоритетов — FIFO внутри одного веса (зависит от реализации).

## Параллельные исходящие HTTP-запросы (fan-out)?
**Частота:** 2/92
**Темы:** #go/concurrency #go/context #go/stdlib
- [ ] Скорректировано

**Что ожидают на собесе:**
- Типовая задача: один входящий HTTP-запрос → N независимых исходящих REST-вызовов → агрегировать JSON и отдать клиенту

**Эталон на собесе:**
Типовая задача: один входящий HTTP-запрос → N независимых исходящих REST-вызовов → агрегировать JSON и отдать клиенту.
Паттерн:`errgroup.WithContext(parentCtx)`+ по `g.Go` на каждый выше по цепочке; общий `ctx` с deadline/timeout;`g.Wait()`— сигнал «все завершились»; первая ошибка отменяет остальные через context.

**Типичные ошибки:**
- Счётчик/таймер вместо `WaitGroup`/`errgroup`— ненадёжное определение «все ответили».
- Нет timeout на весь fan-out — handler висит.
- Забыть передать `ctx` в `http.NewRequestWithContext`.

## Типы: руна, enum, переполнение
**Частота:** 2/92
**Темы:** #go/types #go/string
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-08

`rune` — псевдоним `int32`, кодовая точка Unicode. `byte` — псевдоним `uint8`.

Enum в Go нет. Реализуется через `const` + `iota`: `const ( A = iota; B; C )`. Не типобезопасен (iota — это `int`), нет итерации по значениям, нет строкового представления.

Переполнение: для констант — ошибка компиляции. Для переменных — wraparound по модулю 2ⁿ (`uint8(255) + 1 = 0`).

## Указатель в цикле — один адрес
**Частота:** 2/92
**Темы:** #go/pointers #go/slice
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

В `for range` до Go 1.22 переменная итерации переиспользовалась, поэтому взятие `&v ` давало один и тот же адрес. Правильнее брать адрес элемента через индекс:`&items[i] `, либо создавать копию переменной на итерации. В новых версиях ловушка смягчена для range, но привычка проверять адрес остаётся полезной.

**Подробности:**
```
for i := range items {
ptrs = append(ptrs, &items[i])
}
```
берёт адрес элемента.
- Для map нельзя взять стабильный адрес значение напрямую: значения могут перемещаться.
- Та же идея важна для closures, которые захватывают переменную цикла.

## Что такое массив? / Для чего можно использовать массивы в Golang?
**Частота:** 2/92
**Темы:** #go/array #go/types
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-03
**Что ожидают на собесе:**
> [!summary] Собес: как отвечать
> Массив - это последовательность элементов одного типа и постоянной длины. Размер массива - составная часть его типа и задается во время компиляции.
- Многомерный `[M][N]T `— M элементов типа `[N]T `; пример:`[4][7]int `.
- Непрерывный блок N × sizeof(T), **доступ по индексу O(1)**; для `[M][N]T `— построчно. 
- доступ по индексу O(1), константная сложность потому что можно вычислить адрес 
- Без инициализации каждый элемент — нулевое значение своего типа.
- value type: при присваивании и передаче в функцию копируются все элементы. Мутация параметра `[N]T `внутри функции снаружи не видна; чтобы менять исходное значение, параметр объявляют`*[N]T `.
- Два массива одного типа `[N]T `можно сравнивать оператором == , если сравним тип T — тогда же`[N]T `годится ключом map. Срав нение двух значений одного`[N]T ` через == поэлементное, слева направо

- Значение `len(a)` подставляется компилятором как константа.
- Типы `[3]int `и`[5]int` несовместимы: ни присвоить одно другому, ни сравнить между собой нельзя.
- Размер можно вывести из литерала (`[...]int{10, 20}`), задать явно или указать только нужные индексы (`[7]int{2: 3, 6: 11}`).
- Пустой массив `[0]int ` допустим.
- Обращение по индексу-константе в не диапазона — ошибка компиляции; по переменному индексу в не `[0, N) `— паника.
- В `for range` по массиву переменная итерации — копия элемента, не ссылка на ячейку. Для изме нения на месте обходят по индексу или берут указатель на элемент явно.
- Копирование struct с полем-массивом включает весь массив.
```go
var a [5]int
b := [3]int{1, 2, 3}
c := [...]int{10, 20}
d := [7]int{6: 11, 2: 3}
```

использовать когда
- Когда **заранее известна фиксированная длина** и не планируется resize — массив на стеке/в struct без лишних аллокаций.
- Пример: фиксированный буфер, `[N]byte` под hash/crypto, embed в struct, stack-friendly hot path.

## Write barrier?
**Частота:** 1/92
**Темы:** #go/gc
- [ ] Скорректировано
- [ ] последний повтор

**Эталон на собесе:**
Write barrier — механизм, сохраняющий трёхцветный инвариант при конкурентной разметке. Когда мутатор пишет указатель `*slot = ptr` в heap во время mark-фазы, барьер затеняет ptr — помечает серым. Без барьера чёрный объект мог бы получить ссылку на белый в обход GC → живой объект оказался бы ложно освобождён. Срабатывает только на pointer-записи в heap; value-типы не затрагивает.

**Подробности:**
- **Dijkstra insertion barrier:** `затенить(ptr); *slot = ptr` — затеняет цель любой pointer-записи. Консервативен (затеняет даже если ptr уже чёрный), зато прост и предсказуем.
- **Альтернативы:** Steele (snapshot: затеняет старый + новый), Yuasa (deletion: затеняет старый). Go выбрал Dijkstra.
- **Стек:** write barrier на запись в стек НЕ ставится — слишком дорого для горячего пути. Вместо этого в конце mark-фазы все стеки горутин ресканируются (STW-пауза ~10–100 µs на горутину).
- **Когда активен:** только во время конкурентной разметки (`gcphase == _GCmark`); в остальное — проверка флага `gcWriteBarrier` мгновенно выходит.
- **Массовые операции:** `copy`, `append` слайсов указателей, `typedmemmove` идут через оптимизированный путь с учётом барьера (не поэлементный вызов).
- **Цена:** ~5–10 инструкций на pointer-write в heap. В pprof видно как `gcWriteBarrier` + mark assist при профилировании GC-нагрузки.

## Где в памяти размещается массив, а где слайс?
**Частота:** 1/92
**Темы:** #go/memory #go/slice #go/array
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

**Эталон на собесе:**
- **Массив**: размещение на стеке или в куче решает **escape analysis** — если массив не «убегает» из функции, часто на стеке.
- **Слайс**: заголовок (ptr, len, cap) может быть на стеке; **базовый массив** — на куче, если slice возвращается, сохраняется в heap-struct или capacity большой.

## Операции и параметры канала
**Частота:** 1/92
**Темы:** #go/channel
- [ ] Скорректировано
- [ ] последний повтор

**Что ожидают на собесе:**
Основные операции с каналами:
- создание (`make`);
- отправка (`<-`);
- получение (`<-`);
- закрытие (`close`);
- чтение через `range`;
- ожидание нескольких каналов через `select`.
Дополнительно можно получить текущую длину буфера (`len`) и его емкость (`cap`) для буферизированных каналов.
**Эталон на собесе:**
- `make(chan T)` / `make(chan T, n)` — создание небуферизованного или буферизованного канала.
- Отправка `ch <- v`, получение `<-ch` или `v := <-ch`; `close(ch)` — закрытие (обычно отправителем).
- `for v := range ch` — чтение до закрытия; `select` — мультиплексирование нескольких каналов.
- `len(ch)`, `cap(ch)` — текущая заполненность и ёмкость буфера (для buffered).
У канала есть три основные характеристики:
- **тип элементов** (`chan int`, `chan User`);
- **направление** (`chan`, `<-chan`, `chan<-`);
- **емкость буфера** — небуферизированный (`cap == 0`) или буферизированный (`cap > 0`).

## Что если GOMAXPROCS=1 и goroutine блокируется?
**Частота:** 1/92
**Темы:** #go/scheduler
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-07-08

При `GOMAXPROCS=1` один P, все горутины исполняются на одном CPU — параллелизма нет, конкурентность есть. При блокировке:

- **Канал/mutex:** G паркуется, P берёт следующую runnable G. Поток ОС не блокируется.
- **Сетевой I/O:** G уходит в netpoller (epoll), P свободен для других G.
- **Блокирующий syscall (диск):** M остаётся в kernel, runtime создаёт **новый M** для P — без этого единственный P простаивал бы.

## Что используется для неблокирующего чтения из канала?
**Частота:** 1/92
**Темы:** #go/select #go/channel
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-27

` select { case v := <-ch: ...; default: ... При этом, }` не блокируется, если канал не готов. На практике для «только свежих» метрик часто используют канал cap=1 и drain старого значения.
**Подробности:**
- Для ring-buffer поведения: попробовать прочитать старое значение, затем отправить новое.
-`default` делает операцию неблокирующей, но busy-loop без backoff грузит CPU.
- select с default даёт non-blocking операции; без default горутина блокируется.
