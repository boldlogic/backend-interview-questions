## 2. Чем слайс отличается от массива?
**Частота:** 36/59
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21
**Эталон на собесе:**
Массив - это структура с фиксированной длиной, размер - часть типа. 
А слайс это надстройка над массивом которая позволяет иметь динамическую длину. Слайс не хранит данные сам, а является ссылкой на часть базового массива = ссылка+метаданные. 

Массив обычно сравнимый, если элементы сравнимые, слайс не сравнимый. 

Массив после объявления заполняется нулевыми значениями, а слайс nil - нужно мейкать.

Массив в функцию обычно копируется целиком - мутации снаружи не видны, а у слайса копируется только заголовок - мутации существующих элементов в общем базовом массиве видны.

## 3. Рост capacity слайса / Как работает append?
**Частота:** 10/59
- [x] Скорректировано ✅ 2026-06-18
- [x] последний повтор ✅ 2026-06-21

**Эталон на собесе:**
При `len == cap` — выделяется новый массив, копирование элементов, новый указатель в заголовке слайса.

Рост cap при append: 
- до 256 элементов ~×2, 
- далее плавный переход к ~×1.25 через хитрые формулы с выравниваниями.
- cap округляется до **size class** аллокатора — реальный cap может быть чуть больше формулы

**Подробности:**
Runtime `nextslicecap` (Go 1.18+):
- `oldCap < 256` — **×2**
- `oldCap ≥ 256` — плавный рост к **~×1.25** (`newcap += (newcap + 3×256) / 4`)
- `newLen > 2×oldCap` — `newcap = newLen`
- cap округляется до **size class** аллокатора — реальный cap может быть чуть больше формулы. Выравнивание памяти с округлением до 1 байта вверх, если размер элемента меньше 8 бит

**Сложность:** один `append` — O(1); 
realloc — O(n); 
серия append по одному — O(1) амортизированно.

**Append в func** до realloc меняются **элементы** в общем базовый массив, **`len` caller** — нет; после realloc новый ptr только внутри func.

## 4. Как устроена map под капотом?
**Частота:** 23/59
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21
**Эталон на собесе:**
Map — хеш-таблица. Ключ хешируется, по хешу выбирается область таблицы, дальше рантайм ищет конкретный ключ внутри бакета/группы.

До Go 1.24 основа реализации — массив бакетов. В одном бакете до 8 пар ключ/значение + служебные данные. Если в бакете несколько кандидатов, сначала проверяется короткий фрагмент хеша, потом сравнивается полный ключ.
Если в один бакет попало слишком много ключей, появляются **overflow buckets** — дополнительные бакеты-цепочки. Это хуже для производительности, потому что приходится ходить дальше по связанному списку.

При росте создаётся новая область бакетов. Обычно число бакетов увеличивается, но возможен и same-size grow, когда проблема в большом числе overflow buckets. Старые бакеты остаются в `oldbuckets`, данные переносятся не сразу, а постепенно — это называется эвакуацией.

**Подробности:**
При чтении `v := m[key]` считается хеш, выбирается нужная область таблицы, затем runtime проверяет кандидатов и сравнивает ключи.

- Мутация map во время `range` в той же goroutine разрешена с оговорками; конкурентная запись из другой goroutine без синхронизации — fatal error.
- В старой реализации `hmap` хранит, например, `count`, `B` (`log2` числа бакетов), seed хеша и указатели на бакеты.

## 5. Порядок итерации map
**Частота:** 24/59
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21
**Эталон на собесе:**
Итерация `for k, v := range m` идёт в неопределённом порядке. Нельзя полагаться ни на порядок вставки, ни на стабильность между разными обходами. Для детерминированного порядка нужно собрать ключи и отсортировать.

**Подробности:**
- Runtime намеренно не даёт стабильного порядка, чтобы код не начинал зависеть от детали реализации.
- Порядок может отличаться между запусками программы и между двумя обходами одной и той же map.
- С Go 1.23 `maps.Keys(m)` возвращает iterator, а не slice. Для сортировки удобно: `keys := slices.Sorted(maps.Keys(m))`.
- Если во время обхода удалить ключ, который ещё не был посещён, он уже не будет выдан. Если добавить новый ключ, он может попасть в текущий обход, а может не попасть.

## 6. Какие виды каналов бывают?
**Частота:** 36/59
- [x] Скорректировано ✅ 2026-06-17
- [x] последний повтор ✅ 2026-06-21
**Эталон на собесе:**
Есть буферизированный и не буферизированный. 

**Небуферизированный** канал — синхронный: отправитель встречается с получателем, данные передаются из стека одной горутины в стек другой горутины. Работают по аналогии с эстафетной палочкой: нельзя отправить, пока некому прочитать. 
- Создание без ёмкости:
  ```go
  ch := make(chan [тип данных])
  ```
- Ёмкость и длина равны 0.

**Буферизированный** - канал у которого есть определенный буфер, не блокирует запись, пока len < cap. Буферы помогают избежать лишних простоев. Буфер это кольцевая очередь. По аналогии с почтовым ящиком: пока есть место в ящике, отправитель может положить значение и уйти. 
- Создание с ёмкостью:
  ```go
  ch := make(chan [тип данных], 1)
  ```
- Ёмкость фиксирована (проверяется через `cap()`), текущее количество элементов — через `len()`.
- **Буферизация влияет только на поведение блокировки.**

## 8. Указатель в цикле — один адрес
**Частота:** 31/59
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21

**Эталон на собесе:**
В `for range` до Go 1.22 переменная итерации переиспользовалась, поэтому взятие `&v` давало один и тот же адрес. При этом, правильнее брать адрес элемента через индекс: `&items[i]`, либо создавать копию переменной на итерации. В новых версиях ловушка смягчена для range, но привычка проверять адрес остаётся полезной.

**Типичные ошибки:**
- Не различать адрес копии значения и адрес элемента в slice.

**Подробности:**
- `for i := range items { ptrs = append(ptrs, &items[i]) }` берёт адрес элемента.
- Для map нельзя взять стабильный адрес значение напрямую: значения могут перемещаться.
- Та же идея важна для closures, которые захватывают переменную цикла.

## 10. Select: псевдослучайный выбор case
**Частота:** 13/59
- [x] Скорректировано ✅ 2026-06-21
- [x] последний повтор ✅ 2026-06-21
**Эталон на собесе:**
Если несколько ветвей готовы — runtime выбирает случайный. Порядок ветвей игнорируется. 

- Позволяет работать с несколькими каналами одновременно.
- Перебирает условия `case`; выполняется случайный сработавший блок. Это сделано для предотвращения зависаний и взаимоблокировок. 

- нужно учитывать что при закрытии канала может возвращать нулевые значения
- case с чтением nil канала игнорируется

default
- Выполняется, если ни один `case` не может быть выполнен.
- Если отсутствует, `select` будет ожидать выполнения одного из `case`.

**Подробности:**
- Не путать с `switch` по порядку.
- - Проверка вариантов идёт в **случайном порядке!**
- Starvation не гарантируется равномерной.
- select с default даёт non-blocking операции; без default goroutine блокируется.
- select в цикле

Если нужно постоянно проводить проверки условий `case`, то `select` помещают в цикл. Важно не забыть про `default`, он может привести к росту утилизации ресурсов — может срабатывать на каждой итерации.

 Для прерывания цикла с select
- `return` для выхода из функции.
- Изменение условия цикла.
- `break` с меткой цикла.

## 13. Канал vs мьютекс
**Частота:** 11/59
- [x] Скорректировано ✅ 2026-06-21
- [x] последний повтор ✅ 2026-06-21
**Эталон на собесе:**
**Мьютекс** (англ. mutual exclusion — «взаимное исключение») — примитив синхронизации, который позволяет только одной горутине находиться в части кода, где необходим эксклюзивный доступ. Когда первый поток входит в критическую секцию, мьютекс блокируется до тех пор, пока поток не покинет её. Пока мьютекс заблокирован, другие горутины ждут его разблокировки. Как только он разблокирован, одна из ожидающих горутин успевает заблокировать его и получить эксклюзивный доступ к критической секции кода.


При этом, channel — передача работы/результатов между goroutines. 


**Подробности:**
- Counter/cache — mutex проще.
- Fan-in/fan-out — channel + select.

## 16. Чем concurrency отличается от parallelism?
**Частота:** 29/59
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21
**Как формулируют на собесе:**
> Concurrency vs parallelism — в чём разница?

**Эталон на собесе:**
Конкурентность — много задач выполняются одновременно (структура программы). 
Разбиение одного процесса на несколько неза

При этом, параллелизм — физически на нескольких ядрах. Будет или нет конкурентный код выполняться параллельно зависит от железа (несколько ядер)

На одном ядре возможна конкурентность без параллелизма.



**Типичные ошибки:**
- Путать «async» и «parallel» без уточнения ядер.
- Считать, что goroutines всегда параллельны.

**Подробности:**
- Concurrency — структура программы: много задач, progress через interleaving (на одном или многих ядрах).
- Parallelism — одновременное CPU-исполнение на нескольких ядрах; требует `GOMAXPROCS>1` и независимую работу.
- При `GOMAXPROCS=1` concurrency есть, parallelism на CPU — нет.
- I/O-bound: много G ждут сеть/диск — высокая concurrency при низкой CPU-загрузке.
- CPU-bound: parallelism требует несколько P и достаточно параллельной нагрузки.
- Async (не блокировать caller) ≠ parallel (несколько ядер одновременно).
- Rob Pike: concurrency — организация работы (gopher с маркерами), parallelism — масштаб на железе.

## 17. Чем горутина отличается от потока?
**Частота:** 26/59
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21
**Эталон на собесе:**
Goroutine — зелёная нить runtime (~2–8 KB стека, растёт). 
- Создание горутины занимает меньше времени, чем создание потока, поскольку при этом не создается системный ресурс
- Исходный размер стека горутин меньше размера стека потоков и может быть увеличен по мере необходимости. Это делает горутины более эффективными в плане использования памяти.
- Переключение между горутинами занимает меньше времени, чем переключение между потоками, поскольку осуществляется полностью внутри процесса, что исключает необходимость выполнения сравнительно медленных системных вызовов

При этом, поток ОС — поток ядра. Планировщик Go (GMP) мультиплексирует G на M.


**Подробности:**
- Стартовый стек goroutine ~2 KiB, растёт и сжимается динамически; у OS thread стек обычно фиксированный ~1–8 MiB.
- Переключение G — в user space: сохраняются стек G и PC, без обязательного kernel context switch на каждую goroutine.
- M:N модель: тысячи G мультиплексируются на десятки M; число M не равно числу G.
- `GOMAXPROCS` по умолчанию = `runtime.NumCPU()` — сколько G одновременно исполняются на CPU (число P).
- Netpoller: при сетевом I/O G паркуется, M продолжает выполнять другие G — процесс не блокируется целиком.
- С Go 1.14+ — async/signal preemption на safepoint; до 1.14 tight CPU loop мог monopolize P.
- Создание G дешевле thread: нет syscall на каждую goroutine, runtime сам управляет пулом M.

## 18. В чем разница между процессом и потоком
- [ ] Скорректировано
- [x] последний повтор ✅ 2026-06-21
При запуске программы ОС создаёт отдельный процесс — это сама программа и сопутствующие ресурсы. 

Процесс - контейнер с памятью и ресурсами. Хранит код программы, но не может его выполнить. Процесс - экземпляр программы, выполняемой ОС. 

Поток - линия выполнения внутри процесса. Каждый поток имеет доступ к родительскому процессу и содержит собственные ресурсы. По сути, поток — это единица выполнения кода на уровне ОС. 

Процесс состоит из одного или нескольких потоков. 


ОС планирует потоки а процессы служат для изоляции потоков и управления ресурсами. 

Таким образом, имеется множество потоков и несколько ядер. Выполнением N потоков на M ядрах руководит планировщик операционной системы. Он берёт поток, загружает в память его **контекст** (ресурсы, дескрипторы, состояние регистров) и отправляет его на выполнение ядру. Через какой-то промежуток времени планировщик сохраняет контекст потока, прекращает его выполнение и загружает следующий поток.

Так как потоков очень много, а ядер мало, то планировщик меняет потоки выполнения очень часто. Из-за этого создаётся впечатление, что сотня программ и сервисов работает параллельно. А на самом деле они выполняются по очереди — как если бы каменщик бегал от стены к стене и клал в каждую понемногу камней

Переключение потоков - медленное потому что контекст потока не маленький.

## 21. Mutex и RWMutex
**Частота:** 22/59
- [x] Скорректировано ✅ 2026-06-21
- [x] последний повтор ✅ 2026-06-21

**Эталон на собесе:**
Mutex — эксклюзивный lock. 
При этом, rWMutex — несколько `RLock` для read или один `Lock` для write.


**Подробности:**
- RWMutex не magic при частых write — reader starvation.
- Для map под нагрузкой — shard+mutex или `sync.Map`.
- RWMutex блокирует writers при любых readers и наоборот для writer.


`sync.RWMutex`.Этот мьютекс позволяет выполнять либо любое количество операций чтения, либо одну операцию записи. При этом на время выполнения записи, операции чтения блокируются.

Мьютекс имеет те же методы `Lock()` и `Unlock()`, но использовать их нужно только для критической секции, изменяющей данные. Для кода, который читает данные, нужно использовать методы `RLock()` и `RUnlock()`. `RLock()` не даст выполниться `Lock()` и начать изменение данных, пока не будут завершены все операции чтения.

| Состояние | Метод `RLock()` | Метод `Lock()` |
| --- | --- | --- |
| Мьютекс свободен | Возьмёт мьютекс в режиме чтения | Возьмёт мьютекс в режиме записи |
| Одна горутина уже взяла мьютекс через `RLock()` | Возьмёт мьютекс в режиме чтения. Блокировки не будет | Будет блокировать горутину до тех пор, пока другие горутины не отпустят мьютекс |
| Одна горутина уже взяла мьютекс через `RLock()`. Вторая ждёт `Lock()` | Будет блокировать горутину до тех пор, пока другая горутина не дождётся метода `Lock()` и не отпустит его | Будет блокировать горутину до тех пор, пока не будут отпущены все остальные блокировки |
| Одна горутина взяла мьютекс через `Lock()` | Будет блокировать горутину до тех пор, пока не будут отпущены все блокировки на запись | Будет блокировать горутину до тех пор, пока не будут отпущены все остальные блокировки |
При использовании мьютексов нужно обязательно придерживаться трёх основных правил:

1. После блокировки мьютекса его всегда нужно разблокировать. Если этого не сделать, другие горутины так и будут ожидать своей очереди на выполнение критической секции.
2. Если вы применяете мьютексы для синхронизации доступа к общим данным, следите за тем, чтобы не было горутин, работающих с этими данными без мьютекса. Например, если значение общей переменной меняется горутинами в двух местах, а мьютекс применяется только в одном, то смысла в этом нет, так как ошибки всё равно будут.
3. В общем случае нужно стремиться сокращать продолжительность выполняемого кода внутри критической секции.
