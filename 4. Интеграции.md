### Kafka / RabbitMQ?
**Частота:** 39/177
**Темы:** #integration #messaging

**Kafka** — распределённый **append-only log** (event streaming): высокая пропускная способность, персистентность на диске, replay по offset, независимые пайплайны через consumer groups. Масштабирование — партициями.

**Когда Kafka:** поток событий / CDC / аналитика / много producer+consumer; нужен replay и кратное масштабирование чтения.  
**Когда не Kafka «из коробки»:** классическая очередь задач с TTL, приоритетами, delayed messages, AMQP/MQTT; DLQ — обычно **в приложении/Connect**, не как у Rabbit dead-letter exchange. (Оговорка «Kafka — не брокер» на собесе лучше формулировать как: **не AMQP-брокер очередей**, а distributed commit log.)

**RabbitMQ** — брокер сообщений: exchange → routing key → queue; удобен для job queue, RPC-over-mq, сложной маршрутизации, TTL/DLQ из коробки.

| | Kafka | RabbitMQ |
| --- | --- | --- |
| Модель | log / stream (topic + partition) | очередь задач + exchanges |
| Хранение | журнал, retention / compact | обычно удаление после ack |
| Replay | да, по offset | обычно нет |
| Throughput | очень высокий (batch, zero-copy) | высокий, другой профиль |
| Routing | partition key / custom Partitioner | direct / topic / fanout / headers |
| Доставка | **Pull** (consumer `poll`) | чаще **Push** |
| Порядок | строго внутри partition | зависит от queue/prefetch |
| Когда | event streaming, CDC, analytics | job queue, сложный routing, RPC |

### Kafka: topic, partition, offset, consumer group
**Частота:** 19/177
**Темы:** #integration #messaging #kafka

**Компоненты (кратко):** Producer пишет → Broker хранит → Consumer читает. **Topic** — логический канал. **Partition** — упорядоченный append-only log на диске (параллелизм и масштаб). **Offset** — позиция сообщения в партиции; consumer коммитит progress (обычно в `__consumer_offsets`) и может **перечитывать**. **Consumer group** — партиции делятся между членами; **одну партицию** в момент времени читает **один** consumer группы.

**Устройство топика:**
- партиции режутся на **segment**-файлы; запись идёт в **active** segment;
- удаление старых данных — **посегментно** по retention (policy `delete`) или **compaction** (`cleanup.policy=compact` — последнее значение на ключ);
- поиск по offset быстрый (индекс сегмента).

**Topic configs (часто спрашивают):**

| property | смысл | пример |
| --- | --- | --- |
| `num.partitions` | число партиций | `3` |
| `replication.factor` | число реплик партиции | `3` |
| `min.insync.replicas` | минимум ISR для `acks=all` | `2` |
| `retention.ms` | хранить по времени | `604800000` (7d) |
| `retention.bytes` | хранить по объёму партиции | `10737418240` (10GB) |
| `segment.bytes` | размер сегмента | `1073741824` (1GB) |
| `cleanup.policy` | `delete` или `compact` (или оба) | `delete` |

Типичный topic profile:

```properties
num.partitions=6
replication.factor=3
min.insync.replicas=2
retention.ms=604800000
retention.bytes=-1
segment.bytes=1073741824
cleanup.policy=delete
```

**Репликация:** у каждой партиции **leader** (produce/fetch) и followers; падение leader → новый из ISR. `unclean.leader.election.enable=true` — можно выбрать отставшую реплику → риск потери данных (в проде обычно `false`).

**Сколько партиций:** throughput, желаемый параллелизм consumers (верхняя граница = число партиций), ключ для локальности/порядка. Увеличить можно; уменьшить — только новый topic.

**Consumers vs partitions:** consumers > partitions → idle; partitions > consumers → один consumer тянет несколько партиций.  
**Несколько groups** на один topic — независимые offset; lag одной группы не бьёт по другой.  
**Порядок / dedup-by-offset** — только внутри partition.

**Две семантики поверх одних топиков:** внутри одной group — как «очередь» (каждое сообщение одному члену); разные groups — pub/sub (все группы видят весь поток).

### Семантики доставки: at-most-once / at-least-once / exactly-once
**Частота:** 14/177
**Темы:** #integration #messaging

- **At-most-once** — не больше одного раза: возможна **потеря**, дубликатов нет (например commit offset до обработки / acks=0).
- **At-least-once** — минимум один раз: **дубликаты** возможны, потерь нет при нормальных retry (обработал → потом commit; producer retries).
- **Exactly-once** — ровно один раз end-to-end. В Kafka это не «магия галочки», а связка:
  - **idempotent producer** (PID + seq) — без дублей при retry produce в рамках сессии;
  - **transactions** (Transactions API) — атомарно «прочитал из A → записал в B» (типично Streams / EOS pipeline);
  - на стороне consumer часто всё равно нужна **идемпотентность обработчика** (бизнес-ключ), если пишете во внешнюю БД вне транзакций Kafka.

На практике чаще: **at-least-once + идемпотентный handler** (и при необходимости idempotent producer / EOS внутри Kafka).

### Что такое синхронные и асинхронные вызовы?
**Частота:** 12/177
**Темы:** #integration #messaging

**Эталон на собесе:**
- **Синхронный** — клиент **ждёт ответа**; нужен результат «здесь и сейчас», простая трассировка, жёсткая связность и SLA по latency.
- **Асинхронный** — клиент **не блокируется**; подходит для долгих операций, fan-out, сглаживания пиков, слабой связности.

**Когда sync:** онлайн UI (статус заказа в CRM), платёж «до экрана успеха», read-after-write с консистентностью.

**Когда async:** ночные выгрузки, уведомления, интеграция 5000 филиалов, тяжёлая обработка, eventual consistency допустима.

**Реализация async:** брокер, **HTTP 202** + job id + polling/webhook, callback, outbox.

**Особенности sync:** проще отладка, каскадные таймауты, нужен circuit breaker.

**Особенности async:** буферизация, at-least-once, идempotency, сложнее end-to-end trace.

### Dead Letter Queue (DLQ)
**Частота:** 4/177
**Темы:** #integration #messaging

**Эталон на собесе:**
**DLQ** — отдельный **topic/queue** для сообщений, которые consumer **не смог обработать** после N retry (poison message).

**Паттерны:** retry с backoff → DLQ; ручной replay из DLQ после фикса; в Rabbit — dead-letter exchange; в Kafka — отдельный topic + routing в коде/connector.

Не путать с at-least-once duplicate — DLQ про **бизнес/parse failure**, не про сеть.

### Выбор транспорта межсервисного взаимодействия: HTTP vs gRPC vs брокер
**Частота:** 4/177
**Темы:** #integration #architecture

- **HTTP/REST** — простота, JSON, широкая поддержка; sync request-response; OpenAPI.
- **gRPC** — **Protocol Buffers**, HTTP/2, **строгий контракт**, codegen; эффективнее JSON; streaming; лучше internal microservices.
- **Брокер** — decoupling, async, буфер пиков.

**REST vs gRPC:** REST — ресурсы + HTTP verbs, human-readable; gRPC — RPC-методы, бинарный протокол, типобезопасность, не для браузера напрямую (нужен grpc-web/gateway).

**REST «асинхронным»:** `POST` создаёт job → **202 Accepted** + `Location: /jobs/{id}`; клиент **poll** `GET /jobs/{id}` или **webhook** callback; тяжёлая работа в worker/очереди. Альтернатива — сразу брокер вместо sync HTTP.

### Kafka producer: acks и idempotent producer
**Частота:** 2/177
**Темы:** #integration #messaging #kafka

Путь записи: record (key/value/headers) → **выбор партиции** → batch в буфере → (опционально сжатие) → отправка leader-у партиции → ack по политике.

**Партиционирование:** есть key → hash(key) → одна и та же партиция (порядок по ключу). Нет key → round-robin / sticky. Custom **Partitioner** (`partitioner.class`) — своя логика; sticky уменьшает число мелких батчей.

**acks (гарантия записи на брокер):**
- **acks=0** — fire-and-forget: не ждём подтверждения; максимум скорости, возможны потери.
- **acks=1** — leader записал в свой log.
- **acks=all (-1)** — подтвердили все **in-sync replicas** (с учётом `min.insync.replicas`); выше durability, выше latency.

**Idempotent producer** (`enable.idempotence=true`): PID + sequence numbers; брокер отбрасывает дубликаты при retry в рамках сессии producer'а. Часто вместе с `acks=all`. Это **не** полный EOS во внешнюю БД.

**Ключевые producer configs:**

| property | смысл |
| --- | --- |
| `bootstrap.servers` | точки входа в кластер (метаданные топиков/лидеров) |
| `key.serializer` / `value.serializer` | ключ/значение → bytes (String, ByteArray, Long, Avro/Protobuf…) |
| `batch.size` | макс. размер батча в байтах (напр. 16384); больше → throughput↑, latency может↑ |
| `linger.ms` | сколько ждать накопления батча (напр. 5); 0 = почти сразу |
| `buffer.memory` | память на буфер исходящих (напр. 32MB); переполнение → блокировка send |
| `compression.type` | `none` / `gzip` / `snappy` / `lz4` / `zstd` — меньше сеть/диск, CPU↑ |
| `acks` | `0` / `1` / `all` |
| `retries` / `delivery.timeout.ms` | повторы при временных сбоях; общий дедлайн доставки |
| `enable.idempotence` | `true` — дедуп retry на брокере |
| `max.request.size` | макс. размер produce-запроса (согласовать с `message.max.bytes` на брокере) |
| `request.timeout.ms` | таймаут ожидания ответа брокера |

Типичный «надёжный» профиль:

```properties
bootstrap.servers=kafka1:9092,kafka2:9092
acks=all
enable.idempotence=true
retries=2147483647
delivery.timeout.ms=120000
compression.type=lz4
linger.ms=5
batch.size=32768
```

### Очередь vs топик
**Частота:** 2/177
**Темы:** #integration #messaging

**По литературе:**
Сводка по брокерам в банке + «Проектирование событийно-ориентированных систем…» (Kafka):

- **Очередь** (классика): сообщение забирает **один** consumer (competing consumers) — модель задач.
- **Топик** (pub/sub): публикация многим подписчикам.

В **Kafka**: хранение — **topic + partition** (журнал); семантика «очереди задач» появляется через **consumer group** (партиции делятся между членами группы); **несколько групп** на один topic читают независимо (разные offset). Чеклист Habr Top-150.

### Kafka: consumer group, coordinator и rebalance
**Частота:** 1/177
**Темы:** #integration #messaging #kafka

Модель чтения — **pull**: consumer сам запрашивает данные (`poll`), контролирует скорость. Типичный цикл: `subscribe(topics)` (членство в group) → цикл `poll()` → обработка → commit offset.

**Group coordinator** — брокер, который ведёт membership, назначает партиции и принимает commit offset. Это **не** «лидер среди consumer-приложений».

**Rebalance** — переназначение партиций при join/leave / смене subscription / изменении числа партиций; на время обычно stop-the-world (cooperative sticky смягчает).

**Heartbeat:** фоновый поток; молчание дольше `session.timeout.ms` → выкидывают из group → rebalance.

**Commit offset:**
- **commitSync** — ждёт успеха; надёжнее, медленнее;
- **commitAsync** — быстрее; при сбое при at-least-once возможны дубли.

**At-least-once на практике:** `enable.auto.commit=false` и commit **после** успешной обработки (или идемпотентный handler при auto-commit).

**Ключевые consumer configs:**

| property | смысл |
| --- | --- |
| `bootstrap.servers` | брокеры для метаданных/fetch |
| `group.id` | id consumer group (обязателен для subscribe) |
| `key.deserializer` / `value.deserializer` | bytes → типы |
| `auto.offset.reset` | нет committed offset: `earliest` с начала log, `latest` с конца |
| `enable.auto.commit` | `true` — автоcommit по таймеру; для ручного контроля — `false` |
| `auto.commit.interval.ms` | интервал автоcommit (если включён) |
| `max.poll.records` | макс. записей за один `poll()` |
| `max.poll.interval.ms` | макс. пауза между poll при обработке; иначе rebalance |
| `session.timeout.ms` | без heartbeat → consumer «мёртв» |
| `heartbeat.interval.ms` | период heartbeat (обычно ≪ session.timeout) |
| `fetch.min.bytes` / `fetch.max.wait.ms` | батчинг на стороне fetch |
| `client.rack` | предпочтение ближайшего replica/брокера при rack-aware (рядом с `broker.rack`) |

Типичный профиль «ручной commit, читаем историю»:

```properties
bootstrap.servers=kafka1:9092,kafka2:9092
group.id=orders-workers
enable.auto.commit=false
auto.offset.reset=earliest
max.poll.records=500
session.timeout.ms=45000
heartbeat.interval.ms=3000
```

**Lag** Kafka не чинит сама — мониторинг → масштаб consumers / быстрее handler (см. Ops).

Ловушка: **group coordinator** ≠ **partition leader**.

### ZooKeeper vs KRaft
**Частота:** 1/177
**Темы:** #integration #messaging #kafka

**ZooKeeper (legacy)** — внешний consensus для metadata кластера: brokers, topics/partitions, election **controller**.

**KRaft (Kafka Raft)** — metadata quorum **внутри** Kafka (controller voters); отдельный ZK-кластер не нужен; проще ops на 3.x+.

На собесе: «кто хранит metadata и выбирает controller»; миграция ZK→KRaft — отдельный ops-проект. Клиентские понятия topic/partition/group от этого не меняются.

### Очередь в БД vs message broker
**Частота:** 1/177
**Темы:** #integration #messaging #database

**Эталон на собесе:**
**Таблица-очередь** в БД (status + polling) — просто стартовать, но **плохо масштабируется**: блокировки, hot rows, рост latency, сложный fan-out.

**Broker (Kafka/Rabbit)** — decoupling, буфер пиков, параллельные consumers, replay (Kafka), mature delivery semantics.

**Когда БД:** мало сообщений, один consumer, уже есть транзакция с доменными данными (см. **outbox**). **Когда broker:** event-driven, высокий RPS, many subscribers.

### Schema Registry (Kafka)
**Частота:** 0/177
**Темы:** #integration #messaging #kafka

**Schema Registry** — сервис схем (часто Avro/Protobuf/JSON Schema) для сообщений Kafka: producers/consumers регистрируют и читают schema id, проверяют **совместимость** при эволюции (backward/forward/full).

### Kafka Connect, Streams, MirrorMaker
**Частота:** 0/177
**Темы:** #integration #messaging #kafka

**Connect API** — фреймворк коннекторов source/sink (БД, S3, Elasticsearch…) без ручного consumer/producer-кода; масштабируется workers/tasks.

**Streams API** — библиотека в процессе приложения: читать топик(и) → transform/aggregate/join → писать обратно в Kafka. DSL (filter/map/aggregate/join) + exactly-once при правильной настройке. Это не отдельный «кластер Flink», а код рядом с сервисом.

**MirrorMaker (MM2)** — репликация топиков **между кластерами** (DR, multi-DC, миграция).

**AdminClient** — программное управление: create/delete topics, ACL, описать кластер. **Quota API** — лимиты produce/consume на клиента, чтобы один клиент не забил брокер.

**Consumer vs Streams:** Consumer — «прочитал и обработал» (часто во внешнюю систему). Streams — непрерывный topology graph с состоянием и записью обратно в Kafka.

### Kafka Streams vs Apache Flink
**Частота:** 0/177
**Темы:** #integration #messaging #kafka

| | **Kafka Streams** | **Apache Flink** |
| --- | --- | --- |
| Что это | библиотека внутри JVM-приложения | отдельный distributed runtime / кластер |
| Источники | заточен под Kafka | Kafka, файлы, БД и др. |
| Ops | деплой как обычный сервис | нужен кластер JobManager/TaskManagers |
| Сложность | проще для event processing «вокруг Kafka» | сильнее в сложном state, windowing, batch+stream |
| Масштаб | часто от числа партиций / инстансов приложения | task parallelism, свой ресурсный менеджер |

**Streams**, если уже Kafka и нужна лёгкая обработка в сервисе. **Flink**, если тяжёлая аналитика/сложный state/не только Kafka как источник.

### WSDL — описание веб-сервиса

**WSDL** — XML-язык описания веб-сервиса (обычно SOAP): какие есть **операции**, какие **типы/сообщения**, как упакованы запрос/ответ, где **endpoint** (URL). По WSDL tooling генерирует клиент и серверный скелет.

Типы внутри часто описаны через **XSD**. Для REST ту же роль контракта играет **OpenAPI** (не WSDL).

### XML vs JSON в интеграциях
**Частота:** 0/177
**Темы:** #integration #contracts

| | **XML** | **JSON** |
| --- | --- | --- |
| Форма | иерархическая разметка, теги | объекты/массивы |
| Схема | XSD / DTD, namespaces | JSON Schema / OpenAPI |
| Типичные кейсы | SOAP, WSDL, отраслевые/госформаты | публичные REST API |
| Парсинг | тяжелее, больше verbosity | компактнее, проще в вебе |

Выбор по **экосистеме контракта и потребителей**, не по моде: enterprise SOAP → XML; browser/mobile REST → JSON.
