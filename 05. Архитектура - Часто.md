### Монолит vs микросервисы, главные компромиссы?
**Частота:** 43/202
**Темы:** #architecture #system-design

**Монолит** — подходит для малой команды, MVP, когда домен ещё не стабилен и нет потребности в независимом масштабе. Дешевле операционно, быстрее скорость выхода на рынок, проще консистентность.
**Микросервисы** — когда нужны **независимый deploy**, масштаб **по доменам**, разные команды-владельцы, но растут **latency**, **сложность ops** и стоимость поддержки. Требуют observability, CI/CD, контрактов, стратегии данных.

| | Монолит | Микросервисы |
|---|---------|--------------|
| Задержка | внутри процесса | сетевые вызовы |
| Деплой | целиком | по сервису |
| Консистентность | одна БД / TX | Saga, eventual |
| Команда | 1–2 небольшие автономные команды | platform + domain teams |

### Что класть в кэш (и что не класть)
**Частота:** 17/202
**Темы:** #architecture #system-design #architecture/cache

**Класть:** данные с высокой долей чтений, предсказуемый размер, допустимый TTL, дорогой источник (БД, внешний API) — профили, справочники, горячие ключи.

### Saga / 2PC для двух БД?
**Частота:** 15/202
**Темы:** #architecture #system-design

Saga — цепочка локальных транзакций с компенсационными действиями при сбое. 2PC — prepare/commit через координатора; даёт более жёсткую согласованность, но блокируется и плохо переносит отказы координатора.

**Подробности:**
- Saga бывает через центрального оркестратора или через события между сервисами.
- Outbox помогает надёжно публиковать событие вместе с локальной транзакцией.

### Clean / hexagonal architecture?
**Частота:** 12/202
**Темы:** #architecture #system-design
**Что ожидают на собесе:**
- Domain в центре; инфраструктура — адаптеры снаружи.
- Слои: transport (HTTP/gRPC) → use case/service → repository; зависимости направлены внутрь.

**Эталон на собесе:**
Чистая (hexagonal) архитектура: бизнес-логика не зависит от БД, HTTP и фреймворков. 
**Domain/application** объявляет интерфейсы (ports), **infrastructure** их реализует (adapters).
Типичные слои: handler → service → repository. 
Интерфейсы на границах; в `main` — wiring зависимостей.

**Подробности:**
- Инверсия зависимостей: интерфейс объявляет потребитель (domain), реализация — infra.
- Domain не импортирует драйвер БД, клиентов HTTP и ORM.

### Transactional outbox
**Частота:** 9/202
**Темы:** #architecture #system-design #messaging

**Transactional outbox** — паттерн надёжной публикации событий: в одной БД-транзакции сохраняются изменение агрегата и строка в таблице outbox. Фоновый процесс читает outbox и отправляет сообщение в Kafka/RabbitMQ; после успешной доставки помечает запись отправленной.
Гарантия: либо и данные, и запись outbox закоммичены, либо откат — нет сценария «записали в БД, но событие потеряли». Дубликаты возможны → consumer должен быть идемпотентным.

**Подробности:**
- Часто в паре с Saga при распределённых транзакциях.
- Альтернатива — dual write (запись в БД и брокер отдельно) без outbox: риск рассинхрона.

### Какие знаешь архитектурные стили?
**Частота:** 4/202
**Темы:** #architecture #system-design
**Что ожидают на собесе:**

• Event-Driven Architecture (EDA) - Событийно-ориентированная архитектура
Суть: Компоненты системы обмениваются событиями и реагируют на них. Хорошо подходит для систем, где важна асинхронная обработка и слабая связанность компонентов.
• Microservices Architecture (MSA) - Микросервисная архитектура
Суть: Приложение разбивается на небольшие независимые сервисы, каждый из которых отвечает за свою функцию. Позволяет легко масштабировать и обновлять отдельные части системы.
• Service-Oriented Architecture (SOA) - Сервисная ориентированная архитектура
Суть: Система строится из слабосвязанных сервисов, взаимодействующих через стандартизированные протоколы. Хорошо подходит для крупных корпоративных систем.
• Layered Architecture - Многослойная архитектура
Суть: Система разделяется на слои (уровни), где каждый слой выполняет определённую роль. Обеспечивает чёткое разделение ответственности между компонентами.
• Microkernel Architecture - Микроядровая архитектура
Суть: Базовая функциональность выносится в ядро, а остальные возможности реализуются через подключаемые компоненты. Позволяет легко расширять систему новыми возможностями.
• REST (Representational State Transfer) - Передача состояния представления
Суть: Архитектурный стиль для построения распределённых систем, основанный на протоколе HTTP и стандартных операциях над ресурсами. Каждый ресурс имеет уникальный идентификатор (URI), а взаимодействие происходит через стандартные HTTP-методы (GET, POST, PUT, DELETE). Обеспечивает простоту, масштабируемость и независимость от платформы.

### KISS / DRY
**Частота:** 1/202
**Темы:** #architecture

- **DRY (Don't Repeat Yourself)** — одна точка правды для знания/логики; дубли ломаются порознь.
- **KISS (Keep It Simple)** — не усложняй без необходимости; проще читать и сопровождать.
- **Бритва Оккама** — не плодить сущности «на вырост», пока нет реальной потребности.
- **EPO / «premature optimization»** — сначала Make it Work → Make it Right → Make it Fast; ранняя микрооптимизация часто вреднее.

На собесе связывают с SOLID: принципы — ориентир, а не догма; простота и отсутствие дублей важнее «идеальной» иерархии классов.

### Event Sourcing
**Частота:** 0/202
**Темы:** #architecture #events

**По литературе:**
«Проектирование событийно-ориентированных систем в Apache Kafka» (гл. 7): **источники событий (event sourcing)** — события (изменения состояния) хранятся **неизменно и по порядку**; журнал = аудит; текущее состояние = **replay** событий. В отличие от CRUD «update in place» новое состояние — **новое событие**, не перезапись.

Часто рядом **CQRS**: запись событий (напр. в Kafka) и отдельная read-модель (БД). Плюсы: версионирование данных, восстановление после порчи; цена — сложность проекций и эволюции схем. Чеклист Habr Top-150.

### Клиент-серверная архитектура
**Частота:** 0/202
**Темы:** #architecture

**По литературе:**
«Проектирование веб-API» (ограничения REST): **модель клиент–сервер** — чёткое разделение проблем: клиент (мобильное/веб) и API-сервер обмениваются данными, ответственности разделены. Клиент–сервер = разделение ответственностей между потребителем и поставщиком.

База для веб/API; не синоним микросервисов. Чеклист Habr Top-150.

### Нейминг методов: глагол + объект
**Частота:** 0/202
**Темы:** #architecture #code-quality

Читаемые имена: **глагол + объект + уточнения** (`By` / `With` / `And`).

- Чтение: `find…`, `get…`, `list…`
- Запись: `save…`, `update…`, `clear…`
- Уточнения: `findUsersByStatus`, `clearCacheForUser`, `calculateReportAndSave`

Опционально отразить результат: `saveOrderAndReturnStatus`.  
CQRS-вкус: **query** не меняет состояние; **command** меняет (и может вернуть статус). Имя должно самодокументироваться без комментария.
