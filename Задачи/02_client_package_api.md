## Важно

Подобные задачи не имеют однозначного/правильного решения. Нужно быть очень аккуратным, не навязывать свою точку зрения и постараться понять варианты, которые предлагает кандидат.


## Задача

У нас есть сетевое key-value хранилище (что-то вроде memcached), нужно создать API пакета go-клиента.
Т.е. нужно набросать экспортируемые типы, переменные, сигнатуры ф-ций и методов (без имплементации).

Возможно стоит отметить, что пакет предполагается выложить на github. 
Т.е. на надо использовать какой-нибудь DI framework компании, в которой работал кандидат (хотя можно обсудить и такой вариант)  


## Примерный ход обсуждения

### Обсуждение инициализации client

Тут главное то, что есть обязательные и опциональные парамтеры. 
Выясняем какой подход/подходы использует/знает кандидат

Частые проблемы дизайна инициализации:
- "двухэтапный" конструктор  (Create + init или Init + Connect)
- конструкторы для каждой комбинации опциональных параметров

Если предлагается вариант New с параметром Config/Params/Settings, нужно обсудить варианты опций - указатель или просто дефолтные значения, плюсы-минусы.
Если кандидат знает про паттерн [Functional Options](https://dave.cheney.net/2014/10/17/functional-options-for-friendly-apis) (иногда его называют просто Options), можно обсудить плюсы/минусы.


### Обсуждение методов Write/Read client

Тут важно, чтобы в параметрах был контекст. Если нет, попробовать задать вопросы-подсказки - "что, если нужно задавать разные таймаут времени выполнения метода", "часто используется трассировка, как передавать трассировочную инф-цию к серверу" (если кандидат знает про распред трассировку)

Обычно метод Read выглядит как-то так:

```go
func (*Client) Read(ctx context.Context, key string) (value []byte, err error)
```

По такому методу нужно сделать уточнение - как трактовать результат _nil, nil_? Значит ли это что ключа нет или что по ключу лежит nil (иногда это важно, напр. когда хранилище используется как set)? Как изменить API, чтобы различать два этих кейса? Варианты: спец. ошибка, три возвращаемых рез-та, etc.
