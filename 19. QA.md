### Модульное тестирование (unit)
**Частота:** 0/6
**Темы:** #qa #unit-testing #test-types

**Unit / компонентное тестирование** — проверка **отдельного** модуля (функции, класса, пакета) на корректность в изоляции. Цель: быстро ловить регрессии после изменений, локализовать дефект.

Условно:
- **state-based** — после вызова смотрим состояние объекта / возвращаемое значение;
- **interaction** — проверяем, что с зависимостями общались правильно (часто через mock/spy).

Зависимости обычно подменяют test doubles, чтобы не тянуть сеть/БД.

Связано с **Тестовая пирамида** (низ пирамиды) и карточками doubles ниже.

---

### Интеграционное тестирование
**Частота:** 0/6
**Темы:** #qa #integration-testing #test-types

**Интеграционное тестирование** — проверка **нескольких модулей вместе** как одного блока: реальные (или почти реальные) стыки, контракты, протокол, транзакции, сериализация.

Ищет дефекты на границах: несовместимые ожидания, конфиг, таймауты, схема данных — то, что unit с моками часто не видит.

---

### Unit vs integration
**Частота:** 0/6
**Темы:** #qa #unit-testing #integration-testing #test-types

Общее: оба опираются на интерфейсы модулей и тестовое окружение. Разница — **цель и тип дефектов**, а значит стратегия данных и анализа.

| | Unit | Integration |
| --- | --- | --- |
| Фокус | один модуль в изоляции | стык 2+ модулей / с внешней системой |
| Зависимости | чаще doubles | чаще реальные или testcontainers |
| Скорость / стабильность | быстрее, детерминированнее | медленнее, flaky-риск выше |
| Что ловит | логика модуля | контракты, wiring, I/O |

Пример: класс дергает web-сервис через зависимость. Реальный клиент + сеть → integration; stub с фиксированным ответом → unit (state); spy/mock с проверкой вызова → unit (interaction).

### Test doubles: dummy, fake, stub, spy, mock
**Частота:** 0/6
**Темы:** #qa #aqa #mocks #test-doubles

Подмены зависимостей в тестах (классификация xUnit):

- **dummy** — передали «для формы», методы почти не вызывают (`null`, пустой объект);
- **fake** — облегчённая рабочая реализация (in-memory DB, fake HTTP), чтобы ускорить/упростить;
- **stub** — отдаёт **заранее заданные** ответы на запросы из SUT, входящие вызовы по сути игнорирует;
- **spy** — как stub + **журнал вызовов** (сколько раз, с какими аргументами);
- **mock** — объект с **ожиданиями** по взаимодействию: что вызовут, в каком порядке; проверяет interaction, не только состояние.

На собесе часто путают stub и mock: stub кормит данными; mock проверяет «как звали».

---

### stub vs mock
**Частота:** 0/6
**Темы:** #qa #aqa #mocks #test-doubles

- **stub** — заглушка с запрограммированным ответом; фокус на **состоянии** / результате SUT.
- **mock** — подмена с контролем **взаимодействия** (факт вызова, аргументы, порядок); фокус на protocol между объектами.

Оба — test doubles. Spy ближе к mock по фиксации вызовов, но без жёсткого «сценария ожиданий» заранее.

### Фикстуры (test fixtures)
**Частота:** 0/6
**Темы:** #qa #aqa #fixtures

**Фикстура** — заранее известное **состояние окружения**, нужное тесту: данные, объекты, временные каталоги, поднятый контейнер. Задача — **повторяемость**: каждый прогон стартует из одного и того же setup.

Типичный lifecycle: setup перед тестом / suite → teardown после. Конкретные API — в фреймворке (см. **Фикстуры Pytest**; в Java — JUnit `@Before*` / `@After*`).
