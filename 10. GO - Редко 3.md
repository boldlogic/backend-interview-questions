## Чем mutex отличается от семафора?
**Частота:** 1/94
**Темы:** #go/sync

**Эталон на собесе:**
`Mutex`— бинарный lock: один владелец, эксклюзивный доступ. Семафор (в Go —` chan struct{}`с буфером N или` golang.org/x/sync/semaphore `) считает «слоты»: до N горутин одновременно, остальные ждут. 

Mutex — «только одна», семафор — «не больше N».
**Подробности:**
- Для rate limiting и пула воркеров чаще семафор; для защиты структуры данных — mutex.

## ` context.WithValue` — антипаттерны
**Частота:** 0/94
**Темы:** #go/context

`context.WithValue` не предназначен для optional parameters или конфигурации. Его используют для на время запроса metadata, которое проходит через границы API: трассировка id, auth data, request id. Ключи лучше делать типизированными, чтобы избежать конфликтов.

- Основная роль context — cancel/deadline, values вторичны.
- WithValue усложняет явность зависимостей, поэтому данные должны быть небольшими и на время запроса.
- Типизированный private key снижает риск коллизий ключей

## ` make`vs` new`
**Частота:** 0/94
**Темы:** #go/types #go/memory

**Эталон на собесе:**
`make([]T, len, cap)`— готовый slice
`new(T)`→`*T ` с нулевое значение.
Основное различие между new и make состоит в том, что переменные, созданные с помощью make, правильно инициализируются, а не только обнуляется выделенная для них память. Кроме того, make можно применять только к хеш-таблицам, каналам и срезам, и эта функция не возвращает адрес памяти, то есть make не возвращает указатель

## ` sync.Cond`
**Частота:** 0/94
**Темы:** #go/sync

**Эталон на собесе:**
Условная переменная:`Wait` освобождает mutex и спит до `Signal`/`Broadcast`.

**Подробности:**
- Cond + mutex: ждём изме нения общее состояние, не передачу владение.
- На практике часто канал; если Cond — цикл for против ложное пробуждение.
sync.Cond:
- работает только вместе с Locker (обычно Mutex);
- Wait() освобождает Mutex и засыпает;
- после пробуждения снова захватывает Mutex;
- Signal() будит одну горутину;
- Broadcast() будит все;
- Wait() всегда вызывают в цикле for, проверяя условие.

## Buffer overflow — возможен ли в Go?
**Частота:** 0/94
**Темы:** #go/memory #go/unsafe #go/security

**Buffer overflow** — выход записи/чтения за пределы выделенного буфера с затиранием чужих данных. Классическая уязвимость C/C++.
Go — **memory-safe** для обычного кода
- Индексация `s[i]` проверяет `0 ≤ i < len(s)`— **panic** вместо silent corruption.
- Slice не даёт взять указатель «мимо» без `unsafe`.
Обход (не для production без веской причины): пакет **`unsafe`**, **`unsafe.Slice`**, cgo-вызовы нативных библиотек — там ответственность на программисте.

## go.mod / go.sum в git?
**Частота:** 0/94
**Темы:** #go/tooling #go/modules

`go.mod`— манифест Go-модуля: путь модуля (`module`), версия Go (`go`), прямые зависимости (`require`), при необходимости `replace`/`exclude`/`retract`.
Фиксирует **какие** модули и **какие версии** нужны проекту. Это не checksum-файл: целостность и воспроизводимость обеспечивает `go.sum`.

Go.sum фиксирует checksum модулей для reproducible builds — коммитят в git вместе с go.mod. Без go.sum `go build` может подтянуть другие версии зависимостей при сбое proxy. 

-`go mod init`,`go mod tidy` синхронизируют зависимости с импортами в коде.
-`replace`— локальная подмена модуля (форк, monorepo).
- Коммитят в git вместе с `go.sum`.

## Inline: когда компилятор заинлайнирует функцию?
**Частота:** 0/94
**Темы:** #go/performance #go/compiler


**Что ожидают на собесе:**
- **Inline** — тело маленькой функции **вставляется** в место вызова → нет call overhead, больше шансов оптимизаций.
- (бонус) Условия: маленькая **leaf**-функция, без `defer`, иногда `-gcflags="-m"` для проверки.
- (бонус+) ` go build -gcflags="all=-m"`/`-m=2 `— решение компилятора.
**Эталон на собесе:**
Компилятор Go **инлайнит** функцию, если ожидает выигрыш: обычно **короткая**, **leaf** (не вызывает другие функции или их мало), без **`defer`**, без сложного control flow. Бюджет инлайна ограничен — большие функции остаются вызовами.
**Что даёт:** убирает cost вызова, позволяет constant folding, dead code elimination, лучше register allocation.
**Как проверить:**
```bash
go build -gcflags="all=-m" ./pkg 2>&1 | grep inline
```
**Типичные ошибки:**
- Раздувать «helper» функции — перестают inline.
- Ставить `//go:noinline ` не зная зачем — только для бенчмарков/профиля.

## ORM vs `database/sql`
**Частота:** 0/94
**Темы:** #go/db #go/tooling
**Эталон на собесе:**
**`database/sql`** — stdlib: явный SQL, контроль запросов, меньше магии. **ORM** (GORM, sqlx+helpers) — маппинг struct↔таблица, миграции, CRUD быстрее; риск N+1, тяжёлых неявных JOIN, сложного дебага SQL. На highload часто sql + codegen (`sqlc`) или ORM только для простого CRUD.
**Подробности:**
- ORM удобен для прототипов; для hot path — явный SQL и EXPLAIN.

## Safepoints / вытеснение / G на разных P
**Частота:** 0/94
**Темы:** #go/scheduler #go/gc

**Эталон на собесе:**
Safepoint (безопасная точка) — место в коде, где runtime гарантированно понимает состояние горутины и может безопасно сделать что-то служебное
- остановить горутину для GC
- выполнить preemption
- просканировать стек
- переместить стек при его росте
- собрать диагностическую информацию.
Идея
1. Runtime помечает горутину как кандидата на остановку.
2. Потоку отправляется сигнал.
3. Когда поток достигает безопасного места выполнения, происходит прерывание.
**Подробности:**
```
GMP
↓
Work stealing распределяет задачи
Preemption не дает одной G захватить CPU
Safepoints позволяют безопасно выполнить это preemption
и работу GC
Go — **вытесняющий** M:N (GMP) с preemption (с 1.14+ асинхронно). G может стартовать на одном P и продолжить на другом. 
При `go f()` runtime создаёт G и кладёт в очередь P/global. 
Ручное уступление —`runtime.Gosched()`. 
```

## Код ревью слайс
**Частота:** 0/94
**Темы:** #go/slice
**Что ожидают на собесе:**

| # | Вопрос на review | Красный флаг | Fix |
| --- | -------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 1 | Результат `append` сохранён? | `_ = append(...)`, append в func без return | `s = append(s, x)`; `return s` или `*sl = append(*sl, x)` |
| 2 | Func должна удлинить slice? | `func f(s []T) { s = append(s, x) }` | return нового slice или `*[]T` |
| 3 | Возвращается subslice большого буфера? | `return big[:5]` из `[ ]byte` на MB | `copy`/`append([]T(nil), s...)`/`slices.Clone` |
| 4 | Subslice + append с запасом cap? | короткий `s[1:3]` + append перезаписывает хвост родителя | `s[low:high:max]` или изоляция |
| 5 | Нужна независимая копия? | мутация shared backing нежелательна | `copy(dst, src)` или `append([]T(nil), s...)`; `copy` — `min(len(dst), len(src))` элементов |
| 6 | `for range` + `&v` / сбор `[]*T`? | все указатели на один адрес (до Go 1.22) | `&s[i]`, `v := v`; с 1.22 — своя переменная на итерацию |
| 7 | Delete / укорочение `[]*T`? | «мёртвый» хвост держит объекты (до 1.22) | `slices.Delete`; явный `clear` хвоста на старых версиях |
| 8 | Контракт API: nil vs `[]T{}`? | смешение «нет данных=null» и «пустой массив» | зафиксировать в типе/JSON: nil или non-nil empty |
| 9 | Размер известен заранее? | серия `append` без cap | `make([]T, 0, n)` |
| 10 | Trace в цепочке вызовов? | непонятно, общий ли backing после op | для каждого slice записать `{len, cap}` после subslice/append |
- **`s = append(s, x)`** — всегда присваивать результат; иначе неясно, realloc был или нет.
- **Reuse буфера:**`s = s[:0]`— сброс len при сохранении cap (pool/batch).
- **Склейка:**`append(s1, s2...)`; Go 1.22+ —`slices.Concat(s1, s2)`.
- **Первые N / хвост:**`s[:n]`,`s[n:]`,`s[low:high:max]` для ограничения cap.
- **Изоляция:**`append([]T(nil), s...)` или `slices.Clone(s)`.
- **Prealloc:**`res := make([]T, 0, n)`+ один проход append.
- **Обнуление элементов:**`clear(s)`(Go 1.21+) вместо ручного цикла.

## Массив vs связный список — производительность
**Частота:** 0/94
**Темы:** #go/slice #go/array #go/performance #go/memory


- **Массив/slice быстрее** связного списка для последовательного доступа.
- Причина: **непрерывная память** → cache locality, prefetch, одна копия блока на stack/в регистры.
- (бонус) Связь с inline и escape analysis.

**Массив / slice** хранит элементы **подряд** в памяти
- O(1) при доступе по индексу
- отличная **CPU cache** locality
-`copy`/передача slice — один непрерывный блок (заголовок + указатель на data).
**Связный список** — узлы разбросаны по heap
- каждый `next`— **cache miss**
- больше allocations и pointer chasing
- в Go нет stdlib linked list для hot path (обычно `[]T `+ indices или slice).
Поэтому в Go почти всегда выбирают **slice** вместо hand-rolled linked list, если нет специфичной причины (stable iterators в C-style API).

## Слайс: ограничения, make/copy/append, типичные ошибки
**Частота:** 0/94
**Темы:** #go/slice

**Что ожидают на собесе:**
- Слайс — это дескриптор (pointer, len, cap), а не массив.
- Копируется дескриптор, поэтому данные могут быть общими.
- append может выделить новый массив.
- Всегда присваивать результат append.
- Если известен размер — заранее задавать capacity.
- Не удерживать большой массив маленьким слайсом.
- Не изменять один слайс одновременно из нескольких горутин.
Основные ограничения слайсов:
- не потокобезопасны;
- `append` может перевыделить память;
- несколько слайсов могут разделять один базовый массив;
- нельзя выходить за границы;
- маленький слайс может удерживать большой массив в памяти;
- нельзя сравнивать между собой оператором `==` (кроме сравнения с `nil`);
- `make([]T, len)` — создать слайс заданной длины.
- `make([]T, len, cap)` — создать слайс с заданными длиной и емкостью.
- `[]T{...}` — создать слайс с начальными элементами (длина равна числу элементов).
**Подробности:**
При использовании функции copy() для срезов следует быть очень осторожным, поскольку количество элементов, копируемых встроенной функцией copy(dst, src), составляет минимум из len(dst) и len(src).

## Сценарии блокировки каналов (без читателя)
**Частота:** 0/94
**Темы:** #go/channel #go/deadlock

**Что ожидают на собесе:**
Если одна горутина читает, а другая пишет, то независимо от того, кто пришел первым, тот, кто пришел раньше, блокируется до тех пор, пока не появится вторая сторона. После этого значение передается напрямую от отправителя к получателю.
Запись в небуферизованный канал сразу блокируется без читателя. Запись в буферизованный канал выполняется, пока есть свободное место в буфере; после заполнения буфера следующие записи также блокируются до появления читателя.
