## Как убить процесс в Linux?
**Частота:** 7/141
**Темы:** #ops #linux #devops
- [ ] Скорректировано
- [ ] последний повтор
kill `<pid>` — послать сигнал (по умолчанию SIGTERM, 15): процесс может корректно завершиться. 
kill -9 `<pid>/kill -KILL`— SIGKILL: немедленное убийство без обработки. Сначала пробуют TERM, -9 — когда процесс не реагирует.

**Подробности:**
- `kill -l` — список сигналов.
- Ctrl+C → **SIGINT**; Ctrl+Z → **SIGTSTP** (stop).
- **SIGKILL** и **SIGSTOP** нельзя перехватить, заблокировать или игнорировать — только принудительное действие ядра.
- Сначала **SIGTERM**, `-9` — когда процесс не реагирует.
- В контейнере/K8s — `kubectl delete pod`, stop grace period; `killall`/`pkill` — по имени.

### Docker layers
**Частота:** 3/141
**Темы:** #ops #linux #devops
**Эталон на собесе:**
Docker образ — слои (layers) из Dockerfile instructions; каждый RUN/COPY добавляет layer. Общие слои кэшируются между образами; меньше слоёв и правильный порядок COPY → быстрее build и меньше размер.
**Типичные ошибки:**
- Не используют multi-stage build — тащат toolchain в runtime образ.
- Меняют часто меняющийся файл до редко меняющихся — ломают cache.

**Подробности:**
- Copy-on-write overlay FS (overlay2) — writable layer только у контейнера.
- Сначала COPY редко меняющихся зависимостей, потом исходников — лучше cache при rebuild.
- `docker history` / `docker inspect` — какие инструкции создали слой.

## IPC между процессами в Linux
**Частота:** 1/141
**Темы:** #ops #linux

**Эталон на собесе:**
Процессы **изолированы** (своё адресное пространство) — для общения нужен **IPC**:
- **Pipes / named pipes (FIFO)** — поток байт; pipe: stdout одного → stdin другого (`cmd1 | cmd2`).
- **Unix domain / TCP sockets** — сетевой стиль между процессами (локально или по сети).
- **Shared memory** (`shm`, `mmap`) — общий сегмент; нужна синхронизация (mutex/semaphore).
- **Message queues** (POSIX SysV/mqueue).
- **Signals** — асинхронные уведомления (не транспорт данных).
- Практика backend: HTTP/gRPC, очереди (Kafka/RabbitMQ), файлы, БД.

## du vs df — занятое место на диске
**Частота:** 0/141
**Темы:** #ops #linux

**Эталон на собесе:**
**df** — занятость **файловой системы/раздела** целиком (сколько занято/свободно на mount point).

**du** — суммарный размер **дерева каталогов** (рекурсивно по файлам); ищут, **кто съел место** (`du -sh /*`, `du -h --max-depth=1`).

`df` показывает «диск полон», `du` помогает найти **какой каталог** раздуился.

**Сценарии рассинхрона:** `df` «полон», `du` мало — **deleted but open** (см. карточку про deleted file) или **зарезервировано root** (`tune2fs -m`, ext reserved blocks). `du` мало, `df` ок — смотреть **inode** (`df -i`).

## epoll / select / poll — multiplexing I/O
**Частота:** 0/141
**Темы:** #ops #linux #go/concurrency

**Эталон в контексте Go/Linux:**
**select/poll/epoll** — механизмы ядра Linux, чтобы **один поток ждал множество FD** (сокеты, pipes) без busy-wait.

**select** — старый, лимит FD, O(n) при срабатывании. **poll** — без лимита 1024, но всё ещё linear scan. **epoll** — масштабируется лучше (edge/level triggered); основа **netpoller** в Go runtime.

С **epoll** сетевые read/write через netpoller **не блокируют OS-thread** на каждое соединение — горутина паркуется, thread освобождается. Без multiplexer блокирующий `read` на сокете = поток занят.

## Hard link vs symbolic link (symlink)
**Частота:** 0/141
**Темы:** #ops #linux

**Эталон на собесе:**
**Hard link** — ещё одно **имя того же inode** (тот же файл на диске); удаление одного имени не удаляет данные, пока счётчик ссылок > 0. Нельзя на каталоги (обычно) и между разными ФС.

**Symlink (мягкая ссылка)** — отдельный файл, хранящий **путь** к цели; может указывать на несуществующий файл, на другой раздел, на каталог. При удалении **цели** symlink «битый»; удаление **symlink** не трогает цель.

**Hard link:** удаление одного имени уменьшает счётчик ссылок на inode; данные живут, пока есть хотя бы одна hard link. Удаление symlink — только запись-путь.

Отличие от **относительного пути** в shell: путь — строка в команде; link — объект ФС.

### Kubernetes Service
**Частота:** 0/141
**Темы:** #ops #linux #devops
**Эталон на собесе:**
Service — **стабильная точка доступа** к набору Pod'ов с ephemeral IP. **Selector** связывает Service с Pod'ами; **Endpoints** — актуальный список ready Pod'ов; **kube-proxy** (или CNI/eBPF) балансирует трафик. Типы: **ClusterIP** (внутри кластера), **NodePort**, **LoadBalancer**, **ExternalName**.

**Типичные ошибки:**
- Путают Service с Ingress (L4 endpoint vs L7 маршрутизация).
- Думают, что Service создаёт Pod'ы — это Deployment/ReplicaSet/StatefulSet.

**Подробности:**
- DNS: `<service>.<namespace>.svc.cluster.local` — stable имя поверх сменяющихся Pod IP.
- Readiness probe убирает Pod из Endpoints, пока не готов принимать трафик.
- Доступ снаружи кластера — LoadBalancer или Ingress, не только ClusterIP.

## Linux namespaces и cgroups
**Частота:** 0/141
**Темы:** #ops #linux #devops

**Эталон на собесе:**
Основа **контейнеризации** на Linux (Docker, K8s runtime).

**Namespaces** — изоляция **видимости**: PID (дерево процессов), network (интерфейсы, routing), mount (ФС), UTS (hostname), IPC, user (UID/GID). Процесс в namespace «не видит» чужие ресурсы.

**Cgroups** — лимиты и учёт **потребления**: CPU, память, I/O, pids. В Kubernetes `resources.requests/limits` мапятся на cgroups контейнера.

Вместе: namespaces «что видит процесс», cgroups «сколько может потреблять». Основа Docker/K8s runtime (namespaces + cgroups; исторически ещё LXC, OpenVZ).

**Типы namespaces:** PID, Network, Mount, UTS (hostname), IPC, User. Смотреть: `/proc/<pid>/ns/`.

**Cgroup v1 подсистемы (пример):** cpu, cpuacct, memory, blkio, devices, freezer, pids, net_cls, netprio, hugetlb. Список: `ls /sys/fs/cgroup/`. В K8s `resources.requests/limits` → cgroups контейнера.

## Load average в Linux
**Частота:** 0/141
**Темы:** #ops #linux #devops
- [ ] Скорректировано
- [ ] последний повтор
**Эталон на собесе:**
Среднее **число задач в очереди на CPU** (runnable + часто uninterruptible sleep) за 1, 5 и 15 минут. Это не процент загрузки CPU и не загрузка RAM. Сравнивать с числом логических ядер: load ≈ число ядер — нормальная загрузка; сильно выше — очередь на CPU растёт.

**Если LA высокий и «тупит сервер»:** на хосте смотреть `uptime`, `top`/`htop` (кто грузит CPU), `vmstat` (очередь, память, swap), `iostat` (диск и **iowait**), `dmesg` (OOM, ошибки диска), `ss`/`netstat` (сеть). Prometheus снаружи полезен, но на собесе часто ждут именно консольные утилиты.
**Типичные ошибки:**
- «Средняя загрузка памяти» или «% CPU».
- Не учитывать количество ядер при интерпретации.

**Подробности:**
- `uptime`, первая строка `top` — те же три числа за 1/5/15 мин.
- LA 1 мин **выше** 5/15 — нагрузка **растёт**; ниже — **падает**.
- LA **> числа CPU** — очередь на CPU; 0.0 — idle.
- Высокий load при низком CPU% бывает при **I/O wait** (D-state).

## RAID — уровни 0 и 1
**Частота:** 0/141
**Темы:** #ops #linux

**Эталон на собесе:**
**RAID 0** — striping: данные на несколько дисков параллельно; **ёмкость суммируется** (2×100 GB → 200 GB), выше скорость записи; **отказ одного диска = потеря всего массива**.

**RAID 1** — mirroring: полная **копия** на второй диск; ёмкость ≈ одного диска; выше отказоустойчивость; чтение может быть быстрее за счёт параллельного чтения с зеркал.

## stdin, stdout, stderr и перенаправление
**Частота:** 0/141
**Темы:** #ops #linux

**Эталон на собесе:**
Стандартные потоки процесса: **0 stdin**, **1 stdout**, **2 stderr** (FD в `/proc/<pid>/fd/`).

**Перенаправление:** `cmd > file` (stdout в файл), `cmd 2> file` (stderr), `cmd &> file` (оба), `cmd < file` (stdin из файла), `cmd >> file` (append).

**Pipe:** `cmd1 | cmd2` — stdout первого → stdin второго; `tee file` — дублирует stdout в файл и на экран (`cmd | tee out.log`).

**Объединение потоков:** `cmd &> file` или `cmd > file 2>&1` — stdout + stderr в один файл.

**Фон и detach:** `cmd &` — фон; `disown` — убрать из job table; **`nohup cmd &`** — игнор SIGHUP при выходе из shell; **screen/tmux** — persistent session.

**`/dev/null`** — «чёрная дыра»: `> /dev/null 2>&1` глушит вывод.

## VIRT и RES в top; физическая vs виртуальная память
**Частота:** 0/141
**Темы:** #ops #linux #go/memory

**Эталон на собесе:**
**VIRT** — размер **виртуального адресного пространства** процесса (код, heap, stack, mmap, shared libs, иногда зарезервированные, но не тронутые страницы). Может быть **намного больше** физической RAM.

**RES** (resident) — сколько страниц **сейчас в RAM** (resident set). Часть VIRT может быть в swap или ещё не подставлена (lazy allocation).

**Физическая память** — реальные RAM-страницы. **Виртуальная** — адреса процесса; MMU/page tables **мапят** виртуальные адреса на физические (или swap) при обращении. Процессы **изолированы** разными таблицами страниц.

## Нет памяти: swap, OOM killer
**Частота:** 0/141
**Темы:** #ops #linux #devops #go/memory
- [ ] Скорректировано
- [ ] последний повтор
**Как формулируют на собесе:**
> Аллокатор отказал, swap нет — что будет?
**Эталон на собесе:**
Ядро может сначала вытеснять страницы в swap (если включён). Если физической памяти и swap не хватает — **OOM killer** убивает процесс(ы) по heuristics (oom_score). Процесс получает SIGKILL; данные несохранённые теряются. Overcommit (`vm.overcommit_memory`) влияет на то, когда отказ случится — при commit или при touch.


- `dmesg`, `/var/log` — кто убит OOM.

**Создание swap-файла:** `fallocate -l 1G /swapfile` (или `dd`), `chmod 600`, `mkswap`, `swapon`; постоянно — строка в `/etc/fstab`. **`swappiness`** — `/proc/sys/vm/swappiness` (0–100, агрессивность swap vs reclaim cache).

## Удалил файл — df всё ещё показывает 100%
**Частота:** 0/141
**Темы:** #ops #linux #devops

**Эталон на собесе:**
Файл **удалён из каталога**, но **процесс держит открытый файловый дескриптор** — место не освобождается, пока дескриптор не закроют.

**Диагностика:** `lsof +L1` или `lsof | grep deleted` — какой PID держит файл.

**Действия:** если можно — **перезапуск/rollout** процесса; если нельзя — **обнулить** файл без закрытия FD: `truncate -s 0 /proc/<pid>/fd/<n>` (или `: > /proc/.../fd/n`). Просто `rm` после этого не поможет, если процесс уже держит inode.
